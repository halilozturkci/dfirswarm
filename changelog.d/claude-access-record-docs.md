### Changed: a sensitive output is used by agents, and the documentation says so

A new decision (`docs/adr/0018`) states what the sensitivity mark is for: it protects what flows out of the run (the board, the ledger, the report, the package, the trace's command lines, the network and the model provider), not the secret from the agents of the run, which need a cracked password or a recovered key to do their work. A sensitive output stays readable in the store by every seat and job; derived jobs stay visible and sensitive; a job with no declared scope that names a sensitive path runs, with the dependency declared for it and recorded; the harness does no echo detection and holds no standard output back; every read it can see is to be recorded, with the report naming each reading seat's model and host and saying the record is a lower bound; a package made with `--redact` is to replace the trace lines that record marks with hashes, and without it `HYGIENE.json` is to count them. This change is documentation only and changes no behaviour: the record itself follows.

`docs/packs.md` no longer gives "the agent cannot open the file" as the reason for a tool's values-to-file contract and its measures against a hint of a value in an answer; the reason is that a value belongs in a marked file and not in an answer. Those measures stay as built and are not extended. `docs/protocol.md` gains a paragraph on who may read a sensitive output, and the worker prompt tells an agent that a sensitive output is not hidden from it, that its reads are recorded and that the value goes to another job as an input. The kickoff goldens are refreshed for the prompt.
