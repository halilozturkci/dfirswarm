### Changed: computer-forensics-base `check_inputs` answers `complete`, `partial` or `failed`, and its lists are bounded

- **`status` follows the tool contract; the verdict is in `ok`.** The answer used to say `OK` or `FAIL`, and a run that only ran out of time gave the same `FAIL` as a modified file. Now `status` is `complete` when every file was checked and the walk over `inputs/` finished, whatever it showed (a modified, missing or added file is `complete` with `ok: false`); `partial` when a file is `not_checked` or `unreadable`, or a manifest entry is `malformed` or has no digest (it was not verified); `failed` when the tool refused and checked nothing (no manifest, a bad parameter, a manifest it cannot read). `status_basis` says which. The exit code is unchanged: 0 only when every check agreed.
- **The answer lists at most 200 modified, missing and added paths**, with `modified_total`, `missing_total` and `added_total`, as it already did for the five other lists. 100,000 added files used to make an answer of about 2.4 MB; it is now under 6 KB. The receipts file holds a row for every one of them, and now also for each added file, each malformed or duplicate manifest entry and the place a walk stopped, so what the answer cuts is on disk and named (`receipts_file`).
- **The walk over `inputs/` for added files is on the clock.** It reads the clock for every entry and, when its time runs out, adds a `not_checked` entry that says where it stopped. The budget `max_seconds` is for the manifest and the hashing; the walk has a fifth of it more, at most 60 seconds, so a run ends within 1,760 seconds of its start, inside the manifest's 1,800.
- **A file swapped for a pipe cannot hold the run.** A file is opened without blocking, without following a link, and checked to be a regular file on the descriptor before it is read. A manifest path that holds a NUL or a lone surrogate is a missing file, and an unforeseen error is a `failed` answer with the error's class, not a traceback.
