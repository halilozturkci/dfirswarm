### Fixed: computer-forensics-base `timeline_super` counts on a byte clock and says an empty timeline; `disk-timeline` names the log bytes it did not read

- **`timeline_super` reads the clock by bytes as well as by lines.** Counting psort's output read the clock every 20,000 lines, so a file of a few enormous lines (up to the 8 MiB line limit, and the tail of a longer line skipped in blocks) could outrun the tool's limit. It now reads the clock at least every MiB read and before each block of a skipped tail, opens the output without blocking and checks that it is a regular file, and a count the clock stops is `summary_complete: false` and a `partial` status with the line it stopped at.
- **A run that parsed no event is not a plain `complete`.** When psort exits 0 and writes no event, the status is `partial` and `status_basis` says the programs ran and wrote no event, so nothing is shown about the source: an empty timeline is not evidence that nothing happened, and a parser may have failed (read pinfo). `coverage_note` is unchanged and still true.
- **`timeline_super` installs its stop handlers at module level** right after the PROCESS block, with a minimal last word (`failed`, `interrupted`, exit 128 plus the signal) until `main()` has its own; arguments nested past the parser are refused as JSON, refusals carry `status: failed`, and what the PROCESS block could not do (`process_notes`) is in the answer when there is any. The start of the interpreter is not claimed.
- **`disk-timeline` says which logs it read only the first 32 MiB of.** Its scan of Plaso's logs for error and no-event lines read a file to 32 MiB and said nothing of the rest. `coverage.json` now has `plaso_signals_not_read` (the file and the bytes not read; for a gzip stream, that more follows) and an error line per such log, so the run is `partial` and not `complete` over lines it did not look at.
