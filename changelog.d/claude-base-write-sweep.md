### Fixed: computer-forensics-base answers `complete` only when every file it names was written whole, under a file-size limit

- **`disk-volumes` and `memory-windows`** (shell recipes) check the writes that carry the answer. A step output, `index.tsv`, `partitions.txt` or `coverage.json` that could not be written whole (a file-size limit, `ulimit -f`, makes the write fail while `fls` and `mactime` still exit 0) makes the answer `partial` and names the file, and a file at or past the limit is named in the notes. `coverage.json` is written beside and renamed over, so it is whole or absent, and the final answer is built from the values the recipe holds instead of re-reading the file (the re-read raised `JSONDecodeError` and left an empty stdout).
- **`ad1-items`, `archive-members` and `disk-timeline`** write `coverage.json` (and `image.json`) whole or not at all (a temporary file renamed over the name).
- **`ad1_extract`** says a failure of the manifest's flush or close as a manifest error and answers `partial`, where it used to end with a traceback; `coverage.json` is written whole or not at all, and a failed write makes a `complete` answer `partial`.
- **`sqlite_query`** opens the database once (a FIFO put in its place is refused, not waited on) and points SQLite at that open descriptor through `/proc/self/fd`, so a swap between the check and SQLite's own open cannot reach it.
- `tests/test_write_sweep.py` runs both shell recipes (with stand-in `mmls`, `fsstat`, `fls`, `mactime` and `vol`), `archive-members` and ten tools under `ulimit -f` at fifteen sizes from 1 up to the largest file the run makes plus one, and holds each answer to: JSON on stdout, no traceback, no death by signal, every new `*.json` parses, and a `complete` answer leaves no non-JSON file at the limit. A test in `tests/ad1-pack.test.ts` does the same for `ad1_extract` with a 300-item image. `ad1-items` and `disk-timeline` are not in these test files (they need an AD1 reader and plaso fixtures); they were swept by hand in verification with no finding, and their writes use the same whole-or-nothing helper.
- **A full disk, not only a size limit.** `file_carver` closed its output file before it removed its temporary file, so a close that failed with "no space left" left a hidden `.file_carver-*` file behind; the temporary file is now removed whatever the close does. `feature_scan` answered `complete` when a full disk cut bulk_extractor's files and the program still exited 0; it now reads bulk_extractor's stderr for a full disk or quota and writes a 64 KiB probe beside its files, and answers `partial` (basis says why) when either shows the disk refused a write. A probe cannot tell which file was cut, and says so. `disk-volumes` and `memory-windows` write a 4 KiB probe beside their outputs before the answer and answer `partial` (naming the cause) when the disk refuses it, because a step cut by a full disk can still exit 0; they also replace a coverage file they cannot rewrite by a short one that says `partial` (or remove it), so an earlier one that says `complete` never stands over a cut `index.tsv`. `archive_extract` no longer changes the mode of an `out_dir` or `extracted/` directory that already existed.
- `tests/test_enospc_sweep.py` runs the scenarios of `tests/test_write_sweep.py` (and `feature_scan`) inside `unshare -rm` on a tmpfs mounted over the working directory, sized from the room the inputs take plus 8 KiB up to 1.6 times what the run writes and the page boundaries around that, and holds each answer to the same checks plus: no hidden or `.tmp` file that a complete run does not leave, and a `complete` answer has every file of a complete run at its size. `tests/ad1-pack.test.ts` does the same for `ad1_extract`. They skip with a reason where `unshare -rm` is not allowed. On the earlier head the `file_carver` case fails at tmpfs 1,200,128 (a 600 KB output) and the `feature_scan` case fails at every size that cuts its files.
- `test_disk_volumes`' shared-clock test uses a 6-second clock over 4-second steps (it was 3 over 2, which a loaded machine could tip).
- `tests/shared-blocks.json` declares the PROCESS and STOP carriers as the census counts them (24 and 58), and `tests/tool-contract-allowed.json` no longer lists `catalog_search`, `check_inputs` and `sqlite_query`, which meet the status contract.
- **A hostile `out_dir` with the program present.** `timeline_super` looked at `out_dir` (exists, is a directory, list it) outside any handler, so a name of 256 or more characters or a parent that cannot be searched ended in a traceback with no JSON; it now answers `failed` with the reason. `feature_scan` found that an existing `out_dir` it could not write in, or one on another file system, only after bulk_extractor had run, and then died on the `os.replace` of its two hidden `.feature_scan-*` files, leaving them behind; it now refuses an `out_dir` that is not a writable directory before the run, and moves the files in under a handler and removes the hidden files when it refuses and when it fails to move them (an error nobody foresaw is covered by the last-resort handler below). Twelve tools that had no last-resort handler (`ad1_extract`, `archive_extract`, `feature_scan`, `file_carver`, `file_type`, `image_layout`, `ioc_scan`, `sig_carve`, `sqlite_query`, `sqlite_snapshot`, `timeline_super`, `timestamp_decode`) now answer an error nobody foresaw as JSON (class and, for a file-system error, its reason) with exit 1, after removing the hidden temporaries (see the round 9 note below), as a stop signal does; a stop signal that arrives while the handler runs is answered by its document and exit 1, not 128 + the signal. `archive_extract` contains an error in one member as that member's row and goes on (partial, exit 0, by design); only an error outside a member ends in the handler.
- **A disk that fills during a step, and has room again at the end.** `disk-volumes` and `memory-windows` ran each step with its output straight to the file, so a cut `bodyfile.txt` showed only in a look at the disk when the run ended. Each step now runs under a small perl wrapper that copies the program's output to the file with every write checked: the step exits 74 at the moment a write is refused (a full disk or a file-size limit), the file is named in the notes and the run is partial, whatever the disk looks like afterwards. `feature_scan` cannot do this (bulk_extractor writes its own files), so a `complete` answer now says what was checked (its stderr names no full disk or quota, a 64 KiB write beside its files worked at the end) and what was not (that each file is whole).
- `tests/test_hostile_out_matrix.py` runs `timeline_super`, `feature_scan`, `icat_extract`, `archive_extract`, `file_carver`, `sqlite_snapshot` and the recipes `disk-volumes`, `memory-windows`, `disk-timeline` and `archive-members` with a stand-in for each external program on PATH (Plaso, bulk_extractor, icat, the Sleuth Kit, Volatility) so the code after the program is reached, against an `out` of 255 and 300 characters, under a mode-0 parent, an existing directory of mode 555, a file in place of a directory, a symlink to nowhere, a parent that is a symlink to nowhere, a read-only file system (`unshare -rm`, tmpfs `ro`) and parents that do not exist, as a non-root user (as nobody by `setpriv` when the test is root). Each answer is JSON, has no traceback, leaves nothing hidden or `.tmp` anywhere under the working directory and is not `complete` where nothing can be written. A test in `tests/ad1-pack.test.ts` does the same for `ad1_extract`. The real external programs were never run by any test, only stand-ins; `archive_extract` was run with zip input only, so its `7z` and `tar` paths are not in the matrix.
- `tests/test_enospc_sweep.py` has two new cases, `disk_volumes_freed` and `memory_windows_freed`, where each stand-in program frees a 16 KiB ballast file as it ends (another job freeing space); `disk_volumes_freed` fails on the previous head at tmpfs 237,568 to 278,528.
- **The last-resort handler cleans up (round 8).** The handler of the twelve tools printed its document and ended without removing the tool's hidden temporaries; with a fault injected at the Nth call of `time.monotonic`, `os.fstat`, `os.stat` or `os.lstat`, `file_type`, `feature_scan`, `file_carver` and `sig_carve` left `.file_type-*`, `.feature_scan-*.stdout/.stderr`, `.file_carver-*` and `.sig_carve-*` behind. The handler (one text, identical in the twelve) now runs the cleanup a stop signal runs first. `tests/test_fault_injection.py` injects the fault with a `sitecustomize.py` at the first eight values of N and four more up to the last call, for each of eleven tools (a test in `tests/ad1-pack.test.ts` does it for `ad1_extract`), and holds each run to one JSON document, no death by signal and no dot-file left; on the previous head it fails for `feature_scan`, `file_carver` and `file_type`.
- **The step wrapper of `disk-volumes` and `memory-windows` (round 8).** It now keeps its clock itself and puts the step in a process group of its own: when the program has exited it takes what is readable and ends the step (a `sleep 90 &` left behind no longer holds the recipe, and is ended with the step), and at the deadline it sends SIGTERM to the group and SIGKILL two seconds later (a step that ignores SIGTERM and SIGALRM no longer keeps the recipe past its clock). That a write was refused is now said in a marker file of the wrapper's own, not by exit code 74, so a program that exits 74 itself is an ordinary failed step; a refused write during detection or at the end of a run is `partial` (`applies: unknown` for `detect`) and says so, where it used to be reported as `unsupported` or `applies: false` for a valid image. Without perl the recipe answers that perl is missing and says nothing about the image. `tests/test_step_wrapper.py` has a test for each; all fail on the previous head.
- **One temporary-file lifecycle (round 9).** The hidden temporaries of the tools were made, named and removed in a dozen places, and the fault sweep kept finding another one that a fault between its creation and its registration left behind (`.file_type-*`, `.ioc_scan-*`, `.sqlite_query-*`, `receipt.json.tmp.<pid>`, `snapshot.json.tmp.<pid>`, `ad1_extract.coverage.json.tmp`, `.feature_scan-*`, `.feature_scan.probe`). There is now one block (`# BEGIN SHARED TEMPS`, byte-identical in the sixteen tools and the three Python recipes): `temp_create` makes the file and registers it before anything else is done with it, `temp_hold` registers a name that is about to be made, `temp_done` and `temp_replace` unregister a file that was renamed into place, `temp_drop` removes one, and what is still registered is removed on every way out: at the end of the process (`atexit`, so a normal end, `sys.exit` and any exception), by the last-resort handler (which lists in `temporaries_left` a file it could not remove), and by the stop signal's own cleanup. Every `mkstemp`, `NamedTemporaryFile` and `.tmp` name in the tools and recipes, and `write_json_atomic` of `archive_extract` and `sqlite_snapshot` (which caught only `OSError`), and the recipes' write probe of `--out`, now go through it. The one exception is the lossless pager class that `sig_carve` shares byte for byte with the tool library: it registers its file by `_tmp` before `os.fdopen`, as it did. The shell recipes' `.fsstat.tmp`, `.disk_probe.tmp` and `mktemp` files are removed by an `EXIT` trap on any way out of the script.
- `tests/test_fault_injection.py` is the verifier's matrix: a `RuntimeError`, an `OSError(ENOSPC)` or a `KeyboardInterrupt` at the Nth call of `os.write`, `os.close`, `os.replace`, `os.rename`, `os.fsync`, `os.open`, `os.unlink`, `os.fdopen`, `os.link`, `os.stat`, `os.fstat`, `os.lstat`, `builtins.open` or `time.monotonic`, for each of thirteen tools and the recipes `archive-members` and `disk-timeline` (and `ad1_extract` in `tests/ad1-pack.test.ts`), at a sample of N by default and at every N up to 40 plus a spread with `FAULT_FULL=1`. Each run must give one JSON document (or a stop's exit code) and leave no dot-file and no `*.tmp*` file; a fault in `os.unlink` is the cleanup failing itself and is held to the JSON only. On the previous head it fails for ten of the tools.
- **The step wrapper's marker (round 9).** The file that carries the wrapper's word that a write was refused is now armed by the caller before the step and unlinked by the wrapper (an unlink needs no room, where creating a file did not), the wrapper takes `STEP_MARK` out of the program's environment, and a marker that cannot be armed (no inodes, no room) makes the step "not known" (partial; `applies: unknown` for `detect`), never "no partition table". The `EXIT` trap is set before the directory is made.
