### Changed: triage-collection names the offline route it adopted for Velociraptor

The `unreferenced_ok` reason in `pack.json` and the `why` of the Velociraptor entry in `requires/host.json` no longer call the program "a candidate offline reader of its own containers (unverified)". Both now say what the pack does: the Velociraptor program is declared for operator preparation only, it is never run and it is not in the analysis image; the pack reads Velociraptor collection containers and collection zips offline with its own adapters (`velociraptor_container/2` in the record tools, `collection_id` for a container directory, and the `collection-intake` recipe for a zip).

### Added: triage-collection names an encrypted Velociraptor collection instead of reading it as a plain archive

Velociraptor 0.77.2 writes an encrypted collection when a password is set: an outer zip of `data.zip`, a stored member encrypted with the zip password (WinZip AES), and `metadata.json` (present when the collector was given metadata, with the keys `Scheme`, `EncryptedPass` and `PublicKey`). The four record tools, `collection_id` and the `collection-intake` recipe now name that form: the source is `unsupported` (new adapter `velociraptor_encrypted/1`, `supported: false`), the answer or run is `partial`, the failure counts are `null`, and `collection_id`'s `delivery.not_observed` says the collector's records were not read. The recipe applies to such a zip, names the payload as the collection's encrypted payload (not an archive to extract and not a member that failed to read) and lists it under `encrypted_collections` in `coverage.json`. The form is recognised by the documented member names and metadata keys (and, in a zip, the encrypted flag of `data.zip`), never by entropy. Nothing is decrypted. The metadata values (an encrypted password, a key) are withheld: the answer gives presence and length only, and the strings go only to the values file of a `secret_output` job. A plain container is read as before. The manifests of `collection_id` and `collection_manifest_parse` say so under their containers and "Not measured".

### Fixed: triage-collection's four record tools stop their census at the memory bound, and join names NFC-normalised

The census of `collection_manifest_parse`, `collection_manifest_verify`, `collection_path_map` and `collection_coverage` used to grow to its cap of 2,000,000 entries whatever the memory: a worker VM with 2 GiB could be OOM-killed with no JSON (measured with 768 MB: the base was killed with no answer; the fixed tool ended `partial` with the reason after 1,326,080 entries and a peak of 571 MB). The census now stops, `partial`, when the process holds 60% of the memory it may hold, as the recipe's pass already did; the bound is `COLLECTION_MEMORY_BYTES` when set (a positive whole number; the recipe's `COLLECTION_INTAKE_MEMORY_BYTES` is still read), else the cgroup or address-space limit. No record is called missing from a census that stopped. The join key is NFC-normalised before it is case-folded in every carrier, so a name a macOS host wrote in decomposed form matches its precomposed record (it was `missing` plus `unexpected`). `collection_manifest_verify` lists the links and special files below a per-file record in a table of their own (`links_and_special_files`), with their kind, never following them, and counts them in its denominators; they are not counted among the unexpected files.

### Fixed: triage-collection's collection_coverage says when it did not read its whole verification table

`collection_coverage` stopped reading the `verification` table at 5,000,000 rows (or at the time limit) without a word, so a question could be `complete` without the mismatches in the rows it never read, and it read a line of any length whole. The table is now read in binary with a bound of 1 MiB to a line (a longer line is skipped to its end and counted in `verification.rows_not_used` and `verification.lines_over_the_bound`), and a table cut by the row cap, the time limit or the memory bound makes the answer `partial`, with the cut in `status_basis`, `verification.truncated`, `truncated_because` and `rows_not_read` (a lower bound where the count itself was cut), and the state `verification_table_cut` on each question. `COLLECTION_COVERAGE_MAX_VERIFICATION_ROWS` lowers the cap for a test and never raises it.

### Fixed: triage-collection's collection_path_map no longer says "no record names it" below a record it did not read whole

A delivered file below the directory of a per-file record (a KAPE copy log, a Velociraptor `uploads.json`) that was not read whole was labelled `hypothesis_only`, though an unread row of that record may name it; `collection_manifest_verify` and `collection_coverage` already counted that case apart. The row now has its own status, `undecided_record_not_read_whole`, counted in `by_status`, said in `by_status_basis` and listed in the manifest.

### Fixed: triage-collection's collection-intake recipe finds nested archives by their bytes, and says what its tar end check accepts

A member was named as an archive inside the archive only by its suffix, so a `.dat` member, or one with no suffix, that held zip, tar, gzip, bzip2, xz, 7z, rar or cab magic left the run `complete`. The pass, which already reads every member, now looks at its first bytes: such a member is named (`found_by` says suffix, bytes or both; `format` names the format; its row in `inventory.tsv` carries a note) and the run is `partial` where it may hold records. A collected file below a recognised layout, or one a record names as delivered, still does not make the run partial, and a zip-based document or package named like one (`.docx`, `.xlsx`, `.pptx`, `.odt`, `.jar`, `.apk` and the like) is listed with `document_or_package` and does not by itself make it so. The archives kept for the verdict are bounded (50,000; the rest are counted, the run is partial, and every member is in `inventory.tsv`). A tar that ends with one zero block was always accepted, as GNU tar does; it is now noted in `coverage.json` (`notes`), and the message and the docstring say that two is the standard. The README and the docstring say that the tar end check reads tarfile internals, that CI runs the suites on Python 3.12 (Linux) and 3.14 (macOS) and not on the analysis image's 3.11, and that on a Python without those internals the end is `unknown` and the run is partial.

### Fixed: triage-collection's recipe no longer hangs on a pipe, the tools' post-walk loops obey the clock, and the runs are a table

- The `collection-intake` recipe opened its target with a plain `open`, so a FIFO as the target hung `detect` and `run`. Every open of the target (the sniff, the zip, the tar, the layout check) now goes through one function that opens without blocking and without following a link and requires a regular file; a pipe, a device or a link ends in JSON (`failed` for `run`, `applies: false` for `detect`) with the reason.
- The loops that run after the walk (the search for the collectors' records and for encrypted collections in the shared block, the search for delivered files no record names in `collection_manifest_verify`, the match of delivered files to the questions in `collection_coverage`, the collision checks of `collection_path_map`) did not ask the clock, so a delivery of 2,000,000 files could run far past `time_limit_seconds`. They now ask the clock and the memory bound every 256 entries; where one ends early the census is marked stopped and not complete and the answer is `partial`. The recipe also says when its census stopped.
- `collection_manifest_parse` returned its runs as a list that grows with the delivery; they are now a table (a page inline, the whole in the file `tables.runs` names). The recipe's `coverage.json` carries the first 200 problems with their count; every source that is not parsed is in `units.json`.
- A zip named like a document (`.docx`, `.jar`, `.apk` and the like) is treated as a document or package only when its first member is the one such a file starts with (`[Content_Types].xml`, `mimetype`, `META-INF/` or `AndroidManifest.xml`); a zip that holds collector records under such a name is named and the run is partial.
- A row of the verification table whose status is not a string no longer fails `collection_coverage`; it is counted in `rows_not_used`. The memory message no longer says "0 MB" for a small bound.
