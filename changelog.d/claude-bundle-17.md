### Added: CI runs the pack-tool suites on the images' Python 3.11

The pack tools run in the VM images on Debian 12's Python 3.11, and no CI job met that interpreter: the Linux jobs run Ubuntu 24.04's 3.12 and the macOS jobs 3.14. A new job, `python-311`, runs the `tests/pack-*.test.ts` suites in two shards inside the base image's own `node:24-bookworm-slim` (the digest `images/base.Dockerfile` pins; a test compares the two), with Debian's `python3` installed from the images' apt snapshot, as the image's unprivileged user, and fails when the interpreter is not 3.11. `scripts/test-select.ts` reports `py311` for a change to a pack, the tool library, an image file or a pack-tool suite, and every run that runs everything (the nightly run, a run by hand, the `full-ci` label, a change to the workflow) runs the job; `CI green` needs it. The container runs with `--init` (the runner's own first process reaps nothing, and a program a suite kills would stay a zombie that a stop-signal case still sees as a pid), and the job leaves out one case by its name, lnk_jumplist's walk of `/` with a one-second clock, which needs a file system too big to walk in a second and ends `complete` on the image's small root; the Linux and macOS jobs run it, and a test holds the job to that one name. The job adds runner time to every pull request that changes a pack.

### Fixed: the named flaky tests no longer depend on the host's clock or load

The model gateway's refusal log takes its clock from an option (default `Date.now`), and its test drives a fake clock across a minute boundary instead of counting six calls inside whatever minute the host was in. The 19 test files and one fixture that read `ru_maxrss` read the tool's own peak through one helper (`tests/fixtures/peak_rss.py`, `tests/peak-rss.ts`): on Linux `ru_maxrss` keeps the size of the process image that exec replaced, so a child forked from a large parent read as that large; the helper reads VmHWM of the image the process runs now, and `tests/peak-rss.test.ts` fails if a suite reads `ru_maxrss` itself again. The heartbeat test of `tests/table-lock.test.ts` no longer fails when a heartbeat tick is between its read and its write while the test replaces the lock directory (ENOTEMPTY on the macOS runner, run 40645078378). The stop-signal tests of the network pack (pcap_extract, suricata_run) and the re-parenting case of the linux pack wait for a state with a deadline (a minute; twenty seconds for the linux case) instead of a fixed number of polls and a fixed sleep afterwards, and the mobile-forensics slow-reader test counts the pauses it made instead of the wall time the host took.

The `python-311` workflow has not run on GitHub: it was checked by parsing the YAML and by running its `run:` blocks in the repository's base image (same `node:24-bookworm-slim` digest, Python 3.11.2) under Docker, without the apt step and `npm ci`, which are downloads. Only the workspace is handed to the `node` user; `$RUNNER_TEMP` stays the runner's, which writes each later step's files there, and a test holds the job to that. A run that runs everything fails when it finds no pack-tool suite.

### Changed: bounds of the stop-signal and slow-reader cases that moved with the clock-free rewrites

The pcap_extract case of a slow `ps` (a stub that sleeps 30 s) now bounds the tree walk at 20 s, not 8 s; the "child is gone" checks of the pcap_extract and suricata_run stop cases wait up to 30 s for the pid to go instead of 0.3 s; the mobile-forensics slow-reader case uses a 4 s stall clock (it was 1 s) with a 250 ms pause per chunk and a 180 s guard (it was 60 s). That case is slow by design and fails under `taskset -c 0` (one CPU for the test process and the tool) on the old test and the new alike. The peak-memory helper samples only the direct child, so a grandchild's memory is not counted, and `tests/peak-rss.test.ts` holds those 19 files and the fixture to it.
