### Added: memory-forensics `mem_fs` export names the zero-filled and unread ranges of each file

`mem_fs` in `mode: export` writes a ranges file for each file it copies, JSON Lines under `$OUT/mem_fs/%ranges/`, named `<output name>%.json` (a directory no export can have, and a file name that is never the directory of another ranges file), found while the file is copied: the range read, the ranges the mount did not give (the read that failed, listed whole because the failing page within it is not known; a file that ends before the size the mount reports), the ranges the copy did not reach (a stop, a bound, a write that failed, the rest of a file after its first read error) and the zero-filled pages, whole aligned 4096-byte pages in which every copied byte is 0. The answer names each ranges file in `items[].ranges` with its size, sha256 and a count of each class, and carries a total in `ranges`; the manifest row of the export names it too. Zero-filled means the bytes are zeros: MemProcFS fills a page it cannot read with zeros, and a file can hold real zeros, so it is not proof that data is missing; the answer and the `preserve-regions` skill say so, and the skill now tells the agent to read the ranges file instead of noting such pages by hand. A ranges file that cannot be written whole (a full disk) is named as a problem of that file and makes the answer not complete; it is never reported as a fact about the memory.

### Fixed: memory-forensics `mem_fs` no longer calls a file that ended short of, or ran past, the size the mount reports exported whole, and a stop waits for the copy to end

A file whose read ended before the size the mount reported, or that gave more bytes than it reported, was counted as exported and the answer was `complete`. It is now `partial`, its item says how many bytes the file had and how many the mount reports, and a missing range is an unavailable range in its ranges file. A stop (SIGTERM, SIGINT, SIGHUP) in the middle of a large copy answered before the copy had ended, with no items and a ranges file still empty: on CPython 3.12 a `join()` cut by the exception of a signal handler marks the thread as stopped, so the wait for the worker returned at once. The tool now waits for an event the worker sets as its last act; the copy ends at its next chunk, the file is listed with its manifest row, its ranges file ends in a summary row, and a worker that does not end in its grace period is named in `unfinished` and the answer no longer says the file is kept and named. When every ranges file is cut the basis says the files were copied whole and the ranges files were not. The source of an export is read unbuffered, so a read error is placed at the offset where it failed. Volatility's `dumpfiles` is run only by agents; no pack tool or recipe calls it, so there is no adapter that needed the same change.
