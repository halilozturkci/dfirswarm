### Added: memory-forensics `mem_fs` export names the zero-filled and unread ranges of each file

`mem_fs` in `mode: export` writes a ranges file for each file it copies, JSON Lines under `$OUT/mem_fs/%ranges/` (a name no export can have), found while the file is copied: the range read, the ranges the mount did not give (a read error at an offset; a file that ends before the size the mount reports), the ranges the copy did not reach (a stop, a bound, a write that failed) and the zero-filled pages, whole aligned 4096-byte pages in which every copied byte is 0. The answer names each ranges file in `items[].ranges` with its size, sha256 and a count of each class, and carries a total in `ranges`; the manifest row of the export names it too. Zero-filled means the bytes are zeros: MemProcFS fills a page it cannot read with zeros, and a file can hold real zeros, so it is not proof that data is missing; the answer and the `preserve-regions` skill say so, and the skill now tells the agent to read the ranges file instead of noting such pages by hand. A ranges file that cannot be written whole (a full disk) is named as a problem of that file and makes the answer not complete; it is never reported as a fact about the memory.

### Fixed: memory-forensics `mem_fs` no longer calls a file that ended short of the size the mount reports exported whole

A file whose read ended before the size the mount reported was counted as exported and the answer was `complete`. It is now `partial`, its item says how many bytes the file had and how many the mount reports, and the missing range is an unavailable range in its ranges file. The source of an export is read unbuffered, so a read error is placed at the offset where it failed. Volatility's `dumpfiles` is run only by agents; no pack tool or recipe calls it, so there is no adapter that needed the same change.
