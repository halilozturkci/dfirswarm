### Added: custody holds the access record to the trace and to the scope manifests

Custody now runs the access record's verifier (`verifyAccess`, `scripts/sensitive-access.ts`) within its own deadline and reports it as the check `sensitive access`. A recorded `sensitive_access` line with no trace row behind it, or that the rules do not read as naming its job, is a FAIL. A recorded `because` or `auto_declared` of the journal that disagrees with the scope manifest its job's `job_started` names (`scope.manifest_sha256`) is a FAIL: a way that names an object of the scope needs a manifest that holds the object, `named_in_text` is for a job with no scope, and a manifest that is missing, not a regular file, larger than 64 MiB or not hashing to its recorded hash is told as unverified. A seat row the rules read as an access that no line records, and a row recorded twice, are a WARN (a passed check whose reason begins `WARN:`), with none at the burst limit; lines written under other rules are a note, never a FAIL. A run with no sensitive output is not applicable. The summary of a run with a sensitive output ends with the sentence that a seat whose rows never reach the hub trace leaves the record missing and counting does not catch it, and the fixed lower-bound sentence. No chained register is added; `custody.json` gains `access_record` (counts and a few examples).

The command line `sensitive-access.ts --verify` tells the same disagreement. `tests/sensitive-access-fixture.ts` now gives the jobs that declared a scope their scope manifest, as the job service writes it.

### Added: the report, the run summary, HYGIENE.json and `swarm.sh access` say who used a sensitive output

The access record (`scripts/sensitive-access.ts`) now reaches the reader of a run's results. The report has a section "Sensitive outputs and who used them", after the sensitive material of the entries: per sensitive job, who asked for it and under which lead, where its sensitivity comes from, each seat the harness observed reading it with that seat's model and host, the count, the first and last time, the way and the certainty, the jobs made from it, the ledger entries that cite it, and the operator's console views; a link the harness verified, a read it observed and an agent's claim are kept apart, and "opened" is said only of an agent's claim. It ends with the two fixed sentences; a run with no sensitive output says so in one line. The report's ledger entries and its jobs appendix say where each sensitivity is derived from. `summary.md` has one line, "Sensitive outputs". `HYGIENE.json` has `access: {roots, readers, edges, maybe}`, whole counts and no name. `swarm.sh access <id> [--job jN] [--seat NAME] [--json]` calls the reader and nothing else; it writes nothing, in the run or in the operator's audit. `renderReportBody` takes the record as `access` (read from the sandbox when not given). No record of its own is added.

### Added: a seat is told once, in one sentence, that it read a sensitive output

When a seat's tool call reads a sensitive output, the result ends with one sentence, once per seat and job: the output is sensitive, the run records reads of it, its value does not belong in a post, the ledger or a command line, and it goes to another job as an input. It informs and never blocks, like the evidence-code note, and a failed read is not a read. The seat asks the hub, which classifies the call with the access record's one classifier (a possible reach is not a read; the question is bounded to five seconds); a host run, with no hub, runs the same classifier with the index it can read in the run's directory, without the copies the hub kept. The sentence is one constant (`SENSITIVE_READ_NOTE`) that the worker prompt quotes word for word and a test holds equal; the prompt's two wordings of it are now one, and the kickoff goldens are refreshed for it. The hub answers a new call, `sensitiveRead`; an older hub that does not is no note.
