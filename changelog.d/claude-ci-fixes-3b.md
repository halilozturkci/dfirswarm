### Fixed: a second stop signal no longer takes the answer of pe_directories, elf_directories and macho_directories away, and a stopped mem_fs copy no longer waits for a flush

`pe_directories`, `elf_directories` and `macho_directories` (reverse-engineering 1.16.6, tool versions 8, 4 and 4) marked the answer to a stop as begun before it had written it. Two stop signals sent one after the other (both usually pending when the first is handled) entered the handler a second time between two of its bytecodes, found the answer marked, wrote nothing and ended the call with the exit code and no document. The handler now ignores a stop signal that arrives while the first is being answered.

`mem_fs` (memory-forensics 1.15.8, tool version 18) flushed the bytes of a copy that had been stopped, which on a slow disk took longer than the worker's grace period of 5 seconds, so the answer named the file as unfinished. A copy that was stopped is no longer flushed; its bytes are written, the file is kept and named, and its ranges file ends in its summary as before.

In the tests, the stop of a copy of a large sparse file comes when the copy has begun (8 MiB on disk) and with a flush that takes 20 seconds; the second-signal case is a test of its own, sent from inside the first handler; the time limits of `persistence_normalise` (services) and of the skip of a record over `max_record_bytes` are counted in looks at a clock, not in seconds of a host; the stand-in reader of the `unified_log` storm case waits for the file of the sleepers' pids instead of ending at once; the SIGTERM case of `macho_directories` counts from the signal handler; and the mem_fs stop case asserts the clean-up's documented bound (100 s) and names its timings.
