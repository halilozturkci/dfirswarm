### Fixed: on macOS a program's leftover that the tool had seen was never ended; disk-volumes and memory-windows no longer say a good disk refused a write; the step wrapper ends the group where there is no /proc

- **The shared process block (all 62 carriers, general and windows text).** Without `/proc` a process was seen below a program through libproc (its start time as `("libproc", (sec, usec))`) and looked for again, when its parent had gone, in a table read through `ps` (`("ps", "<lstart>")`). The two texts never compare equal, so `reap_orphans` and the no-subreaper look in `settle()` took every process the tool had seen for another process that had since taken its pid, and ended none: a plain leftover that held a program's pipes, or sat in the tool's group, was still running when the answer was printed. A new `_same_ident(pid, before, listed)` compares the two when they are the same kind of identity and otherwise reads the pid again the way it was first read; `_exempt` does the same. New: `tests/pack-shared-process-identity.test.ts` runs both texts on a host made to look like that (no `/proc/self`, libproc answered from `/proc`, `ps` as it is); it fails on the old text. The pinned texts in `tests/pack-shared-process.test.ts` and `tests/pack-re-process.test.ts` are the new ones. Every carrier's tool version is raised by one, and its pack's patch version.
- **`disk-volumes` and `memory-windows`.** The probe write that asks whether the disk still takes a write compared the output of `wc -c` with `4096`; the BSD `wc` pads its count with spaces, so on macOS every run was `partial` with "the disk under the output directory refused a probe write". The count is trimmed. The wrapper that runs each step found the members of its group only through `/proc`, so on macOS a descendant of a step (`sleep 90 &`) outlived the recipe's clock; it now asks `ps` where there is no `/proc`, and `alive` reads the state through `ps` there. `disk-volumes` also answers `failed` with "a write was refused ... or python3 could not be run" when its own helper could not start (the macOS bash keeps a here document over 512 bytes in a temporary file, which a file-size limit refuses), where it said the target was not a regular file.
- **`check_inputs`** (base pack, tool version 14, and its library copy) closes the receipts file where a refused write is caught, so a buffer the file object still held is not flushed, and refused again, when it is collected (a traceback on stderr under `ulimit -f`, seen on macOS).
- **Tests.** The pack-tool harnesses start the real interpreter (`PYTHON3` of `tests/host-gates.ts`), not whatever `python3` a narrowed PATH finds (macOS has Xcode's 3.9 in `/usr/bin`); `host-gates.ts` has `CLEAN`, what a clean run answers on the host. The cases that hold only where a tool adopts orphans (a clean run is `complete`, a setsid leftover is found) are skipped elsewhere with the one named reason. The base pack's Python tests make their directories under `/tmp` on macOS (its per-user temporary directory is token-shaped, and the tools withhold such a part of a path from their answers), expect `partial` and exit 1 for a clean run of a tool that runs a program, and skip the two cases that need `F_SETPIPE_SZ` or a file name that is not UTF-8. The shell suites no longer compare the padded `wc -l` of BSD or call `stat -c` without the `stat -f` form.
