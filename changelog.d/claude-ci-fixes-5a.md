### Fixed: `clr_inspect` no longer fails a call when another call writes to the same tool-output directory at the same time; the tests state more exactly what they wait for and what a host holds

- **`clr_inspect`** (reverse-engineering 1.16.7, tool version 6; the mobile pack 1.10.6 carries its own test only). The reconstruction and its log were given their final names in three steps: an empty file of the name was made (O_EXCL), unlinked, and the real file linked in its place. In the moment between the unlink and the link a call running at the same time took the free name, and the link of the first failed: `failed`, "the reconstruction could not be linked under its final name". The two files are now given their names by one `link(2)` each, which fails when the name exists (the next name, `-2`, `-3`, is tried), so no name is ever free and no empty placeholder is left behind by a stop signal. The case of four calls at once (`tests/pack-re-clr-inspect.test.ts`) fails on a loaded host without it; its failure message now prints the answer.
- **`journal_export`, process-apply suites (not the tools).** The two cases that failed on the pack-tool job's container (`errflood` of `export`, `stdin` of `verify`: `complete` where `partial` is expected, after 80 to 140 ms) could not be made to fail in the same image on a local host, 40 runs and a full shard under load. The stand-in now waits, before the program ends, until its leftover has become the `sleep` or `yes` that holds the pipe (it was a forked shell at that moment, which the tool may find or not), and a `complete` where `partial` is expected now prints the pids of the leftover and whether each runs, the free space of the working directory and the answer's `program_group`, so the next failure on that host says whether the tool or the stand-in was early. Not shown to be the cause.
- **Tests.** The stop case of the `ios-ileapp` and `android-aleapp` recipes (`tests/pack-mobile-recipes.test.ts`) took a process sent SIGKILL that its parent had not yet collected (a zombie, or a process in the middle of dying) for a running one: it is now given up to 3 seconds to be gone or a zombie. On a macOS runner: the pipe-cut cases of `package_verify` and `audit_events` on the `darwin` host accept a flooder that the tool found and ended (it looks at the processes it saw below the program there); the 600,000-file walk of `recovery_key_scan` and the 100,000 homes of `shell_history` are skipped there by name (`SLOW_BIG_TREES`: making them takes minutes and cut the file at its 300 seconds); `container_inventory` expects two read errors, not three, of a parser that reads a list 100,000 levels deep; the answer of a recipe or tool that runs a program is `partial` on a host that cannot adopt orphans in the shell suites of the mobile pack (`pack.test.sh`), `pack-recipes` (disk-timeline) and `pack-tools` (unified_log); the 100,000-deep JSON case of the backup-destruction correlator names the case it fails in. Not decided: that case ended without an answer after 60 seconds on macOS with Python 3.14, which could not be run here.
