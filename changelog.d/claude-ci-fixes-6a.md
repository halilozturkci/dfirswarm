### Fixed: a stop signal that lands inside a write of a paging file no longer costs the one JSON answer (memory-forensics); the three RE directory tools end without the interpreter's teardown; the tests measure what they mean to

- **The memory pack's paging block (all eight tools: `mem_registry`, `vol_views`, `mem_profile`, `mem_fs`, `mem_carve`, `vol_readiness`, `carve_handoff`, `isf_intake`; memory-forensics 1.15.10).** `keep_partial()` runs from the stop handler, in the main thread, between two bytecodes of `add()`. When the signal fell inside a write of the page's own file, `flush()` raised `RuntimeError: reentrant call inside <_io.BufferedWriter>`, which the block did not catch (it caught `OSError`), and the handler's "best effort" last word swallowed it: exit 143 with an empty standard output, no document (a crash without JSON). Found in CI on Node 24 (`tests/pack-memory-vol-views.test.ts`) and reproduced here in 1 run of 12 with the traceback; 40 runs after the fix pass. The block now catches the error and cuts the kept `.partial` file back to its last newline (a stop between a line and its newline, or inside a flush, left a cut line there as well). `vol_views` also keeps the answer safe from a failure while one file is kept: each kept page and the raw output are kept apart. The same error was not caught either where the block drops a page (`abort()`), or in the tools' own file writers that a stop closes (the table of `isf_intake`, the values file of `mem_registry` and `vol_views`' raw output, the slice of `carve_handoff`, the results of `mem_carve`): those catch it now too (`tests/pack-memory-isf-intake.test.ts`, the SIGTERM case, failed once under load, which that reading explains but a run did not show). A case in `tests/pack-shared-stop.test.ts` runs the block of all eight with a file object whose `flush` and `close` are reentrant, for `keep_partial()` and `abort()`; the pin of the block is updated.
- **`elf_directories`, `macho_directories`, `pe_directories`** (reverse-engineering 1.16.8, tool versions 5, 5 and 9). The call ended through the interpreter's teardown, which resets the signal handlers to their defaults before it frees what the call held. A stop signal that landed there killed the process by its default action (exit `null`, not 128 + the signal) with a whole answer already printed: `tests/pack-re-stop.test.ts` met it in about one run of eight (`elf_directories` finishes at about the time the seeded delays end), reproduced here with SIGHUP, and on Node 24 in CI. A signal sent the moment the whole answer had been read killed the process in 200 of 200 runs before the change and in none after it (exit 0). The call now flushes standard output and ends with `os._exit`; a signal before that point is answered by the handlers as before. A second hole in the same case, found by the repeated runs: `emit` set the flag that says the answer is being written before it had serialized the answer, so a stop that landed in the `json.dumps` of a large answer found the flag set, wrote no document of its own, and ended with exit 128 + the signal and nothing on standard output (`elf_directories SIGHUP at 1531 ms: no answer`). The answer is now serialized first. The failure message of the case now says which signal killed the process.
- **Tests only.** `tests/pack-triage-coverage-verification.test.ts`: the peak memory of the 10 MiB line case is read from `VmHWM` of the process itself; `ru_maxrss` also carries the peak of the process node started it from (the child shares node's memory map until its exec), which is where a growth of 6 MiB (and 14 MiB in CI) over a run that read the same bytes came from. The tool reads that line in pieces of at most 1 MiB; its own peak differed by a few KiB in every run. `tests/pack-cloud-timeline-export.test.ts`: the time-limit case uses the smallest limit the tool takes (1 second) instead of 4, because the whole input takes 4.2 seconds on a hosted Mac and the run finished `complete` there. `tests/pack-re-stop.test.ts` is in `tests/node-tests.deep` (17 carriers of about 17 seconds each on the hosted macOS runner, cut off at 300 seconds as one file there).
- **Not decided: `journal_export` in the pack-tool container** (`errflood` of `export`, `setsid` of `verify`: `complete` over a leftover that is already gone, `left_behind` 0). It could not be made to fail in the same image here (`--init`, the image's `node` user, 2 CPUs, under load, the shard). The stand-in now records what each leftover is (its state and parent) as the program ends, and the failure message of the process-apply cases prints it, so the next failure on that host says whether the leftover was alive when the program ended.
