### Fixed: tests only: a failing fuzz no longer leaves runs behind; a slow runner's partial scan and a starved reader are measured for what they are

- **`fuzzTool` (`tests/windows-tool-contract.ts`).** Its six workers ran on after one set failed; the test that expects the failure (`a traceback on a top-level []`) then removed its directory while the other workers still started tools, and `spawn python3` failed with `ENOENT` (the missing working directory) after the test had ended, which failed the whole file on the hosted Mac. The first failure now stops every worker from starting another run, `fuzzTool` returns or throws only when all of them have ended, and the helper starts the tool with the interpreter of `tests/host-gates.ts` (`PYTHON3`) like the other tests.
- **`tests/pack-ransomware-limit.test.ts`.** On a hosted Mac `ransom_note_scan` ran out of its own `max_seconds` after 37,125 of the 100,000 files and said so (`time_limit.reached`, status `partial`; the rows it shows and the paging file agree). The test now accepts that prefix on a host that is not Linux, when the tool says so and the status is `partial`; on Linux it holds the tool to the whole tree as before.
- **`tests/pack-mobile-forensics.test.ts`, the slow reader.** The three tools' stall clock is set to 8 seconds in the case instead of 4. The tool ended with 141 on a hosted 2-vCPU Ubuntu runner because the test's reader took nothing for 4 seconds, which is what the clock exists for; the tool delivers the whole answer to a steady reader (the case passes under three busy loops on two CPUs). The tools are unchanged.
