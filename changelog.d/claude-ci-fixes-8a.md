### Fixed: a stop signal that lands as a call ends no longer kills it by the signal's default action (network-forensics), and the hidden file of a result page is registered before a stop can find it (windows-forensics, encrypted-containers, network-forensics)

- **The ending of the network pack's tools (all eleven, network-forensics 1.14.13).** The CI run of `main` on the hosted Mac ended `tests/pack-network-pcap-summary.test.ts` ("the tool keeps its own clock") with `null !== 130`: a SIGINT that landed after the call had printed its answer, in the interpreter's teardown (which resets the handlers to their defaults), killed the process by the signal's default action. Same family as the reverse-engineering directory tools (round 6), but here the whole pack carried it: `__main__` of every tool ended through the normal teardown. Every tool now ends with `_leave(code)` (flush standard output, then `os._exit` with the exit code the call had; `fail()` and a returned status still give their own code). The three tools that print one document at the end (`pcap_summary`, `beacon_score`, `network_log_summary`) had a second hole: a signal that landed after the answer was printed, and before the call ended, still ran the handler, which wrote a second document ("no summary had been answered yet", a false claim after a whole one). They now serialize the answer first, then set a flag (`ANSWERING`) that the handler reads, and the handler lets the answer finish. The seven tools that already print through a signal-holding `answer_out` (`zeek_run`, `suricata_run`, `capture_transform`, `flow_reader`, `tls_decrypt`, `quic_inspect`, `conn_series`) and `pcap_extract` get only the `_leave` (corrected in round 10: `pcap_extract` printed its success answer with a plain `print` and its last word armed, so a stop after it rewrote the receipt as interrupted and printed a second document; the shared ENDS block now holds the signals at its first write). `tests/pack-network-stop-after-answer.test.ts` sends each of the three signals the moment a complete document has been read, six times each, for all eleven tools (a success where no outside program is needed, a refusal otherwise): 0 of 18 may die by the signal and the answer stays one document; before the change the three summary tools died in the first round. It also pins the ending in all eleven scripts.
- **The hidden temporary file of a result page (the `NoReplacePage` of the SHARED PAGE block, 40 tools: windows-forensics 21 (1.7.34), encrypted-containers 6 (1.14.8), network-forensics 5 (1.14.13), ransomware-response 8 (1.13.7)).** `LosslessPage.add()` makes the file with `tempfile.mkstemp` and names it in `_tmp` on the next line; a stop signal between the two found no file to remove and left `.<name>-*` behind. The macOS CI run met it in `usn_journal: SIGTERM at temp` (the case sends the signal the moment the file appears; it passed on the rerun). `NoReplacePage.add()` now holds the stop signals while the file is made and registered; the signal waits and is answered by the handler that removes the file. `tests/pack-page-stop-registration.test.ts` sends the signal right after `mkstemp` returns, in each of the tools that can be driven that way: the old block left the file in 1 of 1 runs, the new one leaves none. `usn_journal` itself had neither hole of the network pack (it prints through `print_answer`, which holds the stop signals for the rest of the call); the ransomware-response tools carry the same block (a test pins it byte-equal to the windows pack's) and now carry the changed `add()` too (ransomware-response 1.13.7), although their own `LosslessPage` already holds the signals around the same two lines: the holds nest.

- **Round 10b: a file archive_extract writes is closed on every path, and a member the file system refused at its last flush is not `extracted` (computer-forensics-base).** The hosted Mac's shell suite (Python 3.14) found a traceback on standard error under a file-size limit: `Exception ignored while finalizing file <_io.BufferedWriter name=7>` ... `OSError: [Errno 27] File too large`, at `exit_code = _code(stop)`. `finish_files` and the member writer called `flush()` and `close()` in one `try`: a flush the file system refused skipped the close, and the file was closed later by the garbage collector, whose flush failed again; Python 3.11 and 3.12 say nothing of that outside development mode, 3.14 prints it. - **Round 10c: the two ends of a call, one block at the top of every tool and recipe (`SHARED ENDS`, in place of `SHARED LEAVE`), after the independent review of the pull request's head.** The review found the same P1 in nine more shapes, all one cause: a stop signal answered by a handler at a moment the tool had already committed to its answer, or with no handler at all. Python runs a handler on the main thread whichever thread the kernel delivered the signal to, so the main-thread masks the answer writers used held nothing while another thread ran (the encrypted-containers watchdog, yara_scan's reader); the writers cleared the last word, or set the flag their handler reads, before they serialized, and a stop in that time ended the process with nothing printed (`print_answer` of six computer-forensics-base tools, `claim_answer` of the encrypted-containers tools); the macOS tools' handler raised inside the error branch of `__main__` (a traceback, no answer); a handler whose last word writes only a file (linux_triage, journal_export, the PROCESS block with no last word set, the cloud tools' handler, the windows-artefacts recipe) ended the call with no answer at all; and linux_triage and journal_export installed their handlers after reading and checking the arguments (journal_export after a walk of up to max_seconds), so a stop there killed them by the signal's default action. One block now holds both ends: it is the first thing in the file, installs a handler that answers a stop with one document (`answer_a_stop`: status failed, interrupted, no claim about what was read or written) until the tool's own replace it, defines `hold_stop_signals()` (the signals blocked and given a handler that does nothing, which holds on every thread; a due handler runs on the way in and never raises out), and the ending (`_code`, `_leave`, the wrapped standard output). Every writer of a final answer calls the hold before it commits to the answer (before it clears a last word or sets an answering flag: 90 places in 101 scripts, one rule), every error branch of `__main__` calls it first, and every handler whose last word may print nothing answers with `answer_a_stop` before it ends the process. The encrypted-containers hard stop no longer ends a call whose answer is claimed, whatever asked for it (a watchdog that had read its due time before the claim, with a stop noted, killed it in the middle of the answer). linux_triage and journal_export install their handlers first. beacon_score and network_log_summary no longer put the default action back after their reading phase (a stop while the answer was measured or serialized killed them with no answer, or cut it). `_leave` exits 120 when standard output could not be flushed and the call's code was 0, as the interpreter does, and `_code` writes a SystemExit's text to standard error, as the interpreter does. `tests/pack-stop-after-answer.test.ts` adds a stop while each tool waits for its arguments (one document, exit 128 + the signal); `tests/network-signal-inject.py` counts `atexit` among the imports before a tool's own early handler.
