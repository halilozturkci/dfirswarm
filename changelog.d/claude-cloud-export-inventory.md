### Added: cloud-forensics has a recipe that inventories an export set (`cloud-export-inventory`)

Before a negative rests on a supplied cloud export, the examiner has to say what the export covers. The new recipe `cloud-export-inventory` (`inventory`, not started automatically) reads a directory or a list of files (JSON, JSON Lines, CSV and gzip of those) and, per file, states the format, the provider and the tenant, project or account its records name, the record count, how many records a reader of the pack takes (the `cloud_normalise` adapters, `cloudtrail_parse`, `ual_parse`, `signin_analyse`) and how many none takes, the time range the records carry, the markers of a next page (`nextPageToken`, `NextToken`, `nextLink`, `@odata.nextLink`) and whether the count equals a result cap (5,000 or 50,000 rows, or the `result_size` the caller recorded). For the set it compares the interval requested in a small `acquisition.json` the caller writes (who exported, the query, the permission, the interval) with the interval returned, counts duplicates within and across files, names gaps of a day or more between the files' ranges and pages named `page-K-of-N` that are missing.

Export completeness is stated apart from logging completeness: `coverage.json` says the recipe assesses the first only, and that a clean set is "no reason to doubt found", never a complete log. `coverage.json` (with `index.tsv`, `files.tsv` and `findings.tsv`) is written from the first moment and after every step, each input has its own status, an earlier run's receipt is never overwritten, a stop signal leaves the partial receipt and one line of JSON, and one deadline covers the reads. The recipe starts no program and prints no record value; the two tables that can hold names are marked `secret_bearing`. `logs/what-exists` names the recipe. Pack: cloud-forensics.
