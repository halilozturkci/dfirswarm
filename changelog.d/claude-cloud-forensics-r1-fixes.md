### Fixed: the cloud pack's three tools keep their time limit and their claims, whatever they are given

An independent review fed `cloudtrail_parse`, `signin_analyse` and `ual_parse` hostile and foreign input and found the same faults in the block of code the three share. Each is fixed once in that block (and in the tool's own code where the fault was there), with a test that fails on the head the review was made on (`tests/pack-cloud-hardening.test.ts`).

- **A filter pattern can no longer hang a tool.** `identity` and `user` refused only patterns whose repeats were unbounded, and timed a test only when a pattern had two or more unbounded repeats, so `(a?){30}a{30}`, `(\w{1,20}){1,10}@`, `(.{0,40}){0,40}@` and `(.*){5}x` ran until the process was killed. Every test of every pattern is now timed, whatever its shape, and one that takes more than a quarter of a second fails the call, named. The manifests said so; now it is true.
- **The time limit holds inside a record, and the answer is JSON before the manifest's timeout.** The deadline was read between records, and inside one only for strings over 64 KiB, so one 16 MiB record of 65,000-character strings with `time_limit_seconds: 1` took 207 s and wrote 640 MB, one CSV row of 1,000 long cells of 15 MiB took 49 to 63 s under a limit of 10 s, and a 63 MiB row took 196 to 335 s; twenty such rows under the default limit took 631 s, past the 600 s a call has, so a job's SIGTERM came before any answer. The deadline is now read inside the scan of a string, between the stretches of a string that are withheld and between the fields of a row; a record it cuts is counted, located and listed ("the time limit ended the read inside this record"), the read ends partial, and the answer is written. A CSV line is held to `max_record_bytes` (16 MiB) as a JSON record is, where it was 64 MiB. A text with more than 2,000 credential-shaped stretches has the rest of it withheld as one stretch (the values file keeps it whole), where it wrote a line for each. `time_limit_seconds` is at most 480 (it was 580) and 420 by default (it was 540), so the work after the deadline fits in the 600 seconds a call has.
- **A file of another provider is not a complete read.** `signin_analyse` accepted any record with one of five keys, so a GCP audit entry or `{"time": …, "msg": …}` was "complete" with every event of unknown outcome; `cloudtrail_parse` accepted any record with one of five keys, so an Azure activity record or an Event Grid event was "complete". A sign-in must now say two of who tried, a result, an address, an application, an authentication requirement, a client and a place; a CloudTrail event needs an `eventName` that is a string with an `eventSource` or a `userIdentity`. The records that are not are rejected, located and listed, counted in `records_not_sign_ins`, `records_not_cloudtrail_events` and `rows_not_audit_records`, and the status is `partial`, or `failed` when nothing was read.
- **A number JSON cannot hold, a record of the wrong shape and a record nested very deeply no longer end the run.** `1e999` made `ValueError: Out of range float values` (or, past a line limit, wrote `Infinity` into an `out_file` that is declared JSON Lines); an integer of more than 4,300 digits made `ValueError` in an array or an envelope; a list under `userIdentity.arn`, `parameters: 5`, a `latitude` of `"inf"`, a `RecordType` of `"²"` and a `ResultCount` of `1e999` each made `TypeError`, `ValueError` or `OverflowError` and no answer but an error. A number that does not fit is kept as the text it was written as; a record that cannot be processed for any other reason is counted, located and listed ("the record could not be processed (…)"), the read goes on, and the status is `partial`. A list nested 800 to 990 deep made `RecursionError` on Python 3.11 in the length of the value it was withholding; a record nested more deeply than the JSON decoder holds stopped the reading of the rest of its array. Both are handled, and the record after a record too deep to read is read.
- **A file skipped for its name no longer makes a read "complete".** A directory with `b.log` or an extensionless CloudTrail file next to `a.json` was `complete` ("every record of every supplied file was read") with `skipped_by_name_count: 2`. It is `partial`, and the basis says so.
- **Nothing is printed where an answer says it is withheld.** A `Name`/`Value` pair where a string was expected (`eventVersion`, `Operation`, `UserId`, `ClientIP`, `RecordType`, `applicationName`, an `errorCode`) was printed as the text of a Python dictionary in a table key or a reason; a table key is now text, and a list or an object is its kind and size. A key shaped like a credential (a URL with a password in it, 40 base64 characters) was escaped (`~1` for `/`) before it was withheld, so it was printed whole in the pointer of a withheld value; each key is withheld before the pointer is joined (the values file keeps the real pointer). `signin_analyse` printed a `userId` that is the only name of an account in lower case, whole, in its leads and in `analysis_account`, and kept it in the temporary database; the account is now printed withheld, and the database holds a digest. A number under a credential's name (`{"pin": 0}`, `{"otp": 1}`) was taken for "nothing" because `0 == False`, and is withheld.
- A file or directory walk reads the time limit too, and the names of pagination keys it prints are withheld.

The three tools' versions are raised and the pack's version with them.
