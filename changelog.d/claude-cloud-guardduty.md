### Added: cloud-forensics reconciles GuardDuty findings into update chains (`guardduty_findings`)

A sixth tool in the cloud pack reads GuardDuty finding exports (the GetFindings API response, a JSON array, JSON Lines, or the S3 export, gzip included) and writes one finding per finding id: a finding GuardDuty updated over time is one row with the number of records that were exported, the occurrences GuardDuty counted (`Service.Count`, first, last, smallest and largest, and how often it went down), its state (active or archived, from the latest record, with the transitions between records), the severity and the documented band of the latest, the first and last `UpdatedAt`, the event window, the detector, the Regions and accounts, the records that disagree with each other (listed, not merged away), and the latest record, cleaned. Every record of every chain is in a versions file, located by file, record and line.

The coverage file says which Regions, accounts and detectors the findings name and which time ranges they cover, and reads the account and Region from a path laid out as GuardDuty writes an export. Every answer says that no finding is not no activity, and an empty export says so again with the reasons the AWS pages give (archived findings are not exported by default, the export settings are regional, findings are kept for 90 days, updated findings are exported at a set frequency). The tool cannot tell a suppression rule from an archive by hand, because the Service fields the API reference lists hold no suppression marker, and it says so. It reconciles findings and exports only; corroborating a finding against the raw evidence is the examiner's work.

The field lists were read from the AWS documentation pages named in `tests/fixtures/guardduty/SOURCES.json` on 2026-11-04. Those pages do not say which key case the S3 export uses, so both forms are read and the form seen is counted. `aws/cloudtrail` now names the reader. Pack: cloud-forensics.
