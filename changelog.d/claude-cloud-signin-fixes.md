### Fixed: signin_analyse runs its analysis under a clock, names the result codes it counts as failures, and says when a file proves both date orders

The analysis after the read (the leads per account, over a temporary database) had no clock: the read stops at `time_limit_seconds` (420 by default, at most 480) and the call's timeout is 600 s, and nothing bounded what came after. The analysis now has a clock of its own that ends 540 s after the call began, whatever the read used, which leaves the timeout a margin of 60 s for the account in flight and the answer. It is read before each account and inside the database's sort. When it runs out, the status is `partial` (never `complete`), `coverage.users_not_analysed_by_clock` counts the accounts whose turn did not come, `coverage.users_not_analysed_by_clock_named` names the first 25 of them in the order accounts are analysed in, the leads of the accounts that were analysed are kept, and the status basis says the leads of the others are absent, not empty. `tests/cloud-clock-inject.py` gained `INJECT_ANALYSIS` (the analysis clock out when it starts, or after N accounts) so the tests do not depend on how fast a machine is. Measured on a synthetic export of 2,000,000 events over 200,000 accounts: the read stopped at its 480 s limit after 1,210,385 events, the analysis took 5.1 s and the whole call 485 s at a peak of 51 MiB, so on that machine the read's clock, not this one, is what ends a very large export; the analysis clock is the bound for a slower disk or a larger account count.

The result codes outside the tool's list of six prompts (50074, 50076, 50079, 50125, 50140, 50158) were counted as failures without the manifest or the skill saying so. They are named now: any other non-zero code, 50072, 50097 and 50199 among them, counts as a failure when no `Status` word decides and feeds a burst; their meanings were not checked against Microsoft's current reference. A value that is neither a number nor a success or failure word (the text `unverifiable`, say) is neither: success null, counted in `unknown_outcome`. One test per code holds this.

When a file proves both date orders (a row that can only be day/month/year and a row that can only be month/day/year) and also holds an ambiguous row, the refusal said "no unambiguous string in the file proves the order", which is false there. It now says the file proves both orders, gives both counts (`rows_only_day_month`, `rows_only_month_day`) and asks for `date_order`, as ual_parse does.
