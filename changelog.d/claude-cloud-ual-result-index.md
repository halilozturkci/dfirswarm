### Fixed: ual_parse counts repeated, missing and out-of-range ResultIndex values

The export check compared `ResultCount` with the number of rows and with the highest `ResultIndex`, so a search exported with repeated and missing indices whose highest index equalled `ResultCount` read as whole: indices 1, 1, 3, 4 ... 100 against a `ResultCount` of 100 gave `complete`. ual_parse now keeps every `ResultIndex` of a file against the `ResultCount` beside it (a bitmap of one bit per index, so the order of the rows does not matter: 5,000,000 distinct indices were held in an allocation peak of 1.9 MB, and the largest count the tool tracks, 2^28, takes 34 MB), and a repeat, a gap or a value outside 1 to the count is a named pagination problem: `pagination_markers` carries the count, the rows, the distinct indices, the number repeated, missing and outside the range, and the first 25 of each, and the status is `partial`.

Rows that carry different counts are different searches and are checked apart, so one file holding several searches is not flagged for it. Rows with a `ResultIndex` beside rows without one are named. A `ResultCount` the tool does not check the indices of (more than 64 distinct counts in a file, or a count too large for the bitmaps, which together hold at most 2^28 bits) is counted and named, and the read is never `complete` on indices that were not checked. A count above the rows the file holds was already reported by the `ResultCount` sentence; it is not reported twice.
