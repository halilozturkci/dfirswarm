### Changed: a recipe's detect step can answer "cannot tell", and the census and the job service keep it

The detect contract of a recipe is now written down (`docs/packs.md` section 8, `docs/protocol.md`): exit 0 applies, exit 1 does not, exit 2 cannot tell (`applies: "unknown"`), any other code is a failed detect. The census (`scripts/evidence_catalog.py`) records exit 2 as "its detect step could not tell (exit 2)", where it said "its detect step failed (exit 2)", and the job service's `detect_answered` rows carry `applies: true | false | "unknown"` (before, `applies` was `rc === "0"`, so a detect that could not tell was a plain `false`). Every consumer reads the third state: only `true` starts a recipe (`scripts/job-service.ts`, `scripts/preparation.ts` already starts on exit 0 only), the derived-catalogue counters in `scripts/evidence-store.ts` count `true` as applied and `"unknown"` as `undetermined` (before, an `"unknown"` would have been counted as applied), and the message an agent gets when no recipe catalogues a source says "could not tell" for exit 2.

The 16 detects were audited. linux-target and windows-artefacts already answered exit 2 with `applies: "unknown"`; collection-intake already exited 2 but printed `applies: false` and now prints `"unknown"`. The rest claimed "does not apply" (exit 1) for a target they could not read, or for a program or time they lacked, and now exit 2 with `applies: "unknown"`: ad1-items, archive-members, disk-timeline, android-aleapp, android-backup, android-backup-apps, ios-filesystem and ios-ileapp (the file cannot be opened or read, or a scan stopped at a bound before it could tell), network-capture, capa-floss and static-binary (unreadable), disk-volumes (neither mmls nor fsstat is in the image) and memory-windows (vol is not in the image, or windows.info did not answer in time). A file they opened and found to be another kind still exits 1. Their `run` paths treat `"unknown"` as not supported. Recipe versions are raised and their `sha256` is current; base, mobile, network, reverse-engineering and triage-collection are re-sealed. `tests/detect-three-states.test.ts` holds the mapping, the census text and nine recipes on a missing target and on a text file.

A fix round added: detect and run of ad1-items, archive-members, android-backup and android-backup-apps no longer wait for a writer on a FIFO (the open is non-blocking, the type is read from the descriptor, and anything but a regular file answers exit 2 with `applies: "unknown"` for detect and a failed JSON for run); windows-artefacts answers "unknown" for a FIFO or a device; disk-volumes, memory-windows, capa-floss, static-binary, linux-target and network-capture print the third state or a JSON for a target they cannot open and for a usage error; `tests/recipe-fifo-target.test.ts` gives every recipe a FIFO, a directory and a link to a FIFO for detect and run. The open inside the readers that run opens after detect (tarfile, zipfile and the AD1 segment reader by name) is guarded by the regular-file check of the target made just before, not by a non-blocking open: a path swapped for a FIFO between the check and the open is not covered.
