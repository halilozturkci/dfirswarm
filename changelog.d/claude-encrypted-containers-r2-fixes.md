### Fixed: archive_probe no longer says "complete" or "protected: false" for a wildcard name, an archive in front, or a local header that disagrees; recovery_key_scan answers once on a full disk (encrypted-containers)

A second independent review of the encrypted-containers tools found four answers that were wrong by the pack's own bar and one that printed two documents. Each fix has a test that fails on the tools as they were.

- **`archive_probe` passes `-spd` to 7-Zip.** 7-Zip expands `*` and `?` in the archive's name as well, even after `--`: a plain file called `?.7z` next to an encrypted `a.7z` was listed as five members, protected, with the sibling's path read as a member. The listing is also refused as the archive's when 7-Zip's output is not one archive's (a second member section, a line of a record with no `Path`, a repeated key: a build that prints a member name's line break as it is can forge them), and a warning on exit 0 (data after the end of the archive) is `listed_with_warnings`, not "without warnings"; in all three `protected` is never `false`.
- **The document reader that exists is named.** `next_reader` said a structural reader was "not available yet" and "planned for the reverse-engineering pack"; `doc_structure` ships there. Both `archive_probe` and `crypto_id`, the manifest and the `archives/protected` skill now name it, as a tool to look for in the run's inventory (the pack does not depend on the reverse-engineering pack).
- **An archive in front of the one read is found beyond the last 64 KiB.** A second archive appended to the first, with a directory larger than the last 64 KiB, was `complete` with `protected: false` while 7-Zip listed the first archive (five of six members encrypted). A ZIP signature at byte 0 with the archive read beginning further on (a self-extracting stub starts with a program) is `archive_in_front`: `partial`, `protected` not `false`.
- **The local header's flags are compared with the directory's.** A member the central directory called plain and its local header called encrypted (which 7-Zip reports as encrypted) gave `protected: false`. Bit 0 of every member's local header (30 bytes at the offset the directory gives) is compared; a disagreement, or no local header there, is named in `local_header_flags` and the answer is `partial` with `protected` not `false`. On 700,000 entries it costs 0.6 s CPU (19.8 s to 20.4 s at `--cpus=1`).
- **`recovery_key_scan` prints one JSON document when it cannot write.** A page file that could not be written (a full disk, a quota) printed its error, and then the values file's unflushed bytes failed to flush and a second document followed. The page's error takes the answer like any other, and a values file that cannot be flushed does not replace an answer on its way out. Shown with a real `ENOSPC` on a small tmpfs.
- **Smaller:** a Zip64 end record with extensible data is read (it was reported "over the bound"); an End record with disk numbers is named `split_archive`; a device node, pipe or socket is "not a regular file" and not "no such file" (`archive_probe`, `crypto_id`; the manifest no longer offers "a partition"); the LUKS skill no longer says `crypto_id` prints none of the file's bytes beside the header facts it prints.
- **The answer is derived from an account of the whole file, not from the absence of a contradiction.** Two verifications of this change found the same two bugs through variants (an archive in front, and 7-Zip's output), because each fix looked at one signal and each signal had a variant (a ZIP signature at byte 0, a sound End record found by a backward scan, keywords on lines of 7-Zip's output). `complete` and `protected: false` now follow from this:
  - **Front.** The first member is the lowest local header the directory names, so offsets that count from the start of the file (`zip -A`, `zip -F`) and offsets that count from the start of the archive give the same bound. The bytes before it are searched for anything shaped like an archive: a local header or a directory entry with a known method and names that fit the file, an End record that is not the empty one, a 7-Zip start header or a RAR block whose CRC is right. The archive in front need not have a sound End record (damaged, missing, no directory, a signature record in between, a comment running on, Zip64 with 450 bytes of extensible data are all found). A self-extracting stub is none of these, even one that holds the signatures as constants (unzipsfx, 7zCon.sfx, a ZIP library). A search the clock or more than 20,000 signatures cut short is `front_unsearched`. Both are `partial`, `protected` not `false`. A 1 GiB stub costs 2.4 s.
  - **7-Zip as a second reader.** Where 7-Zip is installed and reads the file as a ZIP, it must list the same members and the same number of encrypted ones; a file it reads as another archive format, or a listing that does not finish, is `partial`. A file it cannot open, or reads as a program (a stub), is not compared. On 700,000 entries it costs 6 s.
  - **7z.** `protected: false` comes only from a listing that 7-Zip finished without a warning: a listing the clock cut said `false` when the members read so far were plain (it now says `null`, or `true` if one was encrypted). The warning is decided from every line (the five kept for display were filled by a member name with line breaks), a line in a record that is no `key = value` is odd output, and "cannot open without a password" is believed only where the start header shows an encrypted header and not from a line that echoes the file name (a truncated plain archive called `wrong password.7z` was `complete`, `header_encrypted`).
  - A Zip64 end record with extensible data behind an unadjusted stub is read, and an End record that ends the file and cannot be checked, with a record in its comment, is named.
