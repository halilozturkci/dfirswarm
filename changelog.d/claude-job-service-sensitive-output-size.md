### Security: a sensitive job's answer no longer tells its outputs' exact size or sha256

A tool that writes a sealed values file only under a withheld condition (the `contains` filter of `sqlite_freespace`: 299 bytes for the right guess, none for a wrong one) told the asking agent one bit per call through the job's byte count, and the file's sha256 confirmed a guess. The job service showed both in `job_run` and `job_status` (the total, and `bytes` and `sha256` for each listed file), in the post that says the job is done, and, as the total, in the reuse hint another seat gets. For a job whose outputs are sensitive (run with `secret_output`, declared by the tool's manifest or not, or derived from such an output) the answer now names each file and gives a size bucket instead: everything under 1 MiB is one bucket, so an empty file and a small one look the same, then powers of two. It carries no byte count, no sha256 and no `same_as` (an earlier output "byte for byte" equal to the file would confirm a guess). The sealed manifest, the journal line, `job.json`, custody, the ledger's citations, the report and the console keep the exact bytes and digests, and a job that is not sensitive is shown as before. A seat's VM still mounts `store/` read-only and can list a sealed file; the change is to what the harness tells and posts. A tool must still not let a values file's size follow a withheld value; the tool-side fix for `sqlite_freespace` is separate.

The same holds while the job runs and in the places next to the sealed answer. `job_status` on a running job that is sensitive, or reads a sensitive output (decided when it starts, no longer only when it seals), gives the output directory and the logs as size buckets, with no file count, byte count or newest file (the header's and the regroup's words for a stuck job likewise); the host still assesses moving, quiet and stalled from the exact samples. The stderr length beyond the tail it shows is a bucket. A ledger locator that misses a sensitive output says one sentence for every miss and every size, where it used to name the file's length, a nearby position or how the bytes read. The derived catalogue no longer offers what a sensitive job made. A `sha256:` ref to a sensitive output is still accepted (the digest names a file in the read-only store in any case), and the number and names of the files and stdout stay whole: both are written down in `docs/packs.md` and `docs/protocol.md`. `sizeBucket` no longer loops on a size that is not finite.
