### Added: the macOS pack's `macos_triage` tool and `macos-artefacts` recipe over mac_apt

- **`macos_triage`** runs the pinned `mac_apt.py` (1.33.2, amd64 worker image only) in the input mode the caller names (AFF4, AXIOMZIP, DD, DMG, E01, MOUNTED, SPARSE, UAC, VMDK or VR) and gives each plugin `parsed`, `empty`, `unsupported` or `failed` from mac_apt's own log, because mac_apt exits 0 after errors it has logged. The input is checked against its type before the program starts (a folder for MOUNTED; the signature of E01, SPARSE, VMDK, DMG; a zip; the suffix of a collection; a link is refused). A FileVault password is only a sealed file (mode 0600) handed to mac_apt as `-pf`, never read by the tool and never on a command line; any argument the tool does not know is refused. The program runs in the tool's own process group under the shared process block with its working directory, temporary directory and home inside a run directory of its own, and its stdout, stderr and log are kept whole. The answer records the version, the argv with placeholders for paths, the plugin list and, per plugin, a status, a fixed reason and the log line it started on; no log text is copied into it. The tool is `complete` only when mac_apt exited 0, its log (read from `Log.<time>.txt`) has its start line with the pinned version and its finish line, every requested plugin is parsed or empty and no error line or traceback sits outside a plugin. A line counts as an error line when it holds the uppercase level word ERROR or CRITICAL or any of error, exception, traceback, failed, cannot, could not, unable, corrupt, malformed or invalid in any case, so a lowercase `error: could not open database` or `Failed to parse database` inside a plugin's run makes the plugin `failed`; `parsed` still rests on the absence of such a line in a log format that was never observed, and the answer says so. FAST and ALL can never be complete, because nothing read here lists the plugins they expand to. Where mac_apt is not installed (the arm64 image) the answer is `failed` with the packaging reason. The manifest declares `secret_output: required`.
- **`macos-artefacts`** (`purpose: broad_extraction`, `auto: []`) tells the input type from the object (an Expert Witness, sparse, VMDK or UDIF image, a raw APFS container or HFS+ volume, a raw disk with an Apple GPT partition, or the root of a macOS volume), runs mac_apt over it, writes `coverage.json` first (partial) and replaces it whole at the end, writes `plugins.tsv` and `index.tsv`, marks every file it wrote `secret_bearing`, and never writes over an earlier run: it refuses, touching nothing, when `plugins.tsv`, `index.tsv`, `mac_apt.stdout`, `mac_apt.stderr`, `coverage.json`, `mac_apt/` or its scratch directories already exist, and creates its files exclusively without following a link. `plugins.tsv`, `index.tsv` and `coverage.json` are marked `secret_bearing` too. On arm64 its detect exits 1 with the reason; with an object that looks right and no `mac_apt.py` on PATH it exits 2.

What was read and what was not: mac_apt was not installed or run to build either. The argument shape, the log file name and the texts of the start, plugin start, plugin end, plugin exception and finish log lines were read from the v1.33.2 source (GitHub, 2026-11-04). The prefix of a log line, the wording of a plugin that finds nothing or does not take the operating-system version (so `empty` and `unsupported` rest on an assumed wording), the per-plugin file names of the output formats, the console copy of the log and mac_apt's behaviour on an encrypted image without a password were not, and are unverified. The tests drive both with stand-in programs shaped from the lines that were read. `triage/system-profile` names the tool, and the `mac_apt.py` entry in `requires/host.json` no longer says that nothing of the pack drives it.
