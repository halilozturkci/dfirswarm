### Fixed: memory-forensics mem_fs ends the processes that still hold its engine's pipes (Linux)

`mem_fs` listed the engine's descendants once, when the clean-up started, and ended only those. A process the engine had daemonised (double-forked away) before that moment, or forked after it, was not in the listing and kept running after the call. On Linux the clean-up now also finds the processes that hold one of the pipes the tool made for the engine (its stdout and stderr, named in `/proc/<pid>/fd` as `pipe:[inode]`), ends each with SIGTERM and then SIGKILL (2 s each), and names each in the answer's `clean_up.pipe_holders` (pid and how it ended; one that could not be ended is a named `cleanup` problem). Each holder's start time and pipe are checked again just before the signal, through a pidfd where the kernel has one, so a pid reused a moment earlier is not signalled; this tool, pid 1 and the tool's ancestors are never signalled, and the kill set is never wider than the holders of those pipes. The search for holders and every read of the process table stop at 2 s and say so (`search_complete`, a `cleanup` problem). A process that closed its copies of the pipes is not found, and off Linux, or where `/proc` cannot be read, nothing is searched: the manifest says so. The clean-up bound is restated: 100 s where `/proc` is read, 112 s where the process table falls back to `ps` (which is now also ended with a limit after its kill), so 480 + 2 + 112 = 594 s stays inside the 600 s timeout.

New cases in `tests/pack-memory-engine-descendants.test.ts`: an engine that daemonises a pipe holder leaves it running on the earlier code and the new code ends and names it, a process beside the tool that holds a pipe of its own is untouched, and the identity checks (a reused pid, the tool's own pipe, an ancestor) are exercised on the functions themselves.
