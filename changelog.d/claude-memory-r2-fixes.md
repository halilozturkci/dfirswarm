### Fixed: memory-forensics tools keep a job's output under `$OUT`, count a failing row wherever it sits, and leave with the exit status of the answer they wrote

The independent second-round review of `mem_carve`, `mem_fs` and `mem_profile` found the following; the clean-up of the `mem_fs` engine (a descendant that holds the engine's pipes, a hung unmount helper, the bound of the clean-up) and the shared paging block are fixed in the shared-blocks branch and are not touched here.

- **In a job the output is `$OUT` and nowhere else.** The manifests said `results_to` (`mem_carve`) and `mount` (`mem_fs`) are "in a job, under `$OUT`", but only `extract_to` was held to it: a `results_to` of `work/<id>/hits.jsonl` was written there, and a `mount` of `work/<id>/mem` put the engine's two raw logs (engine text, unsealed) beside it. Both are now refused as JSON before anything is created or any engine is started (`results_to must be a file under $OUT in a job`, `mount must be a directory under $OUT in a job`), in a job run as secret output or not. Outside a job nothing changes.
- **`mem_fs` `list` says `partial` when a row that failed is beyond the inline page.** The entries that could not be read (their `lstat` failed) were counted among the rows of the inline page only, so a listing of 5,000 names with a failing row past `limit` was `complete`. They are counted while the rows are built.
- **A `mem_fs` `list` that missed its deadline stops its worker and names the rows it kept.** The worker went on to the end after the call had given up, and placed a file of rows under `tool-output` that the failure answer did not name. It now stops at the next row, and the failure names what was kept (`partial_results`).
- **An answer that was written is not turned into a signal death.** The interpreter's shutdown puts every signal's default action back before it ends; a SIGHUP that arrived then ended the process by the signal (one run in forty) although the one complete document was out. The three tools now leave with `os._exit` after the flush, with the exit status they would have had. A stop that arrives before the interpreter has run the first lines of the tool (tens of milliseconds at the start of a process) still ends it with no answer; that cannot be answered from inside the file, and the docstrings and the manifests of `mem_carve` and `mem_profile` now say so instead of calling the window microseconds wide.
- **`mem_carve` flushes an explicit hit list as it writes it.** A `results_to` is flushed to disk every 256 MiB inside the clocked sweep, so the flush at the end of a sweep has at most that much left, whatever `max_results_bytes` is. The temporary list kept when no `results_to` is given is flushed once at the end by the shared paging block, and the time that takes at the 16 GiB cap was not measured: the manifest says so.

Pack memory-forensics. Tests: `tests/pack-memory-r2-fixes.test.ts`.
