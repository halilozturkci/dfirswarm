### Fixed: memory-forensics texts say what the code does

The README and the `processes/preserve-regions` leaf said without condition that the mount is gone when `mem_fs` returns; they now say what the tool's manifest says: the mount is released when the call returns, unless the clean-up failed, and then a named `cleanup` problem says the mount may remain. The `mem_fs` manifest carries the start-up sentence its two siblings carry (a stop that arrives before the interpreter has run the tool's first lines ends it with no answer; no engine had been started). The `mem_fs` manifest and docstring give the clean-up bound for both hosts: at most 88 s where `/proc` is read and 108 s where the process table falls back to `ps` (480 + 2 + 108 = 590 s stays inside the 600 s timeout). Question 6 of the `memory-triage` goal asks for what a disk parser read only when the windows-forensics pack is loaded; otherwise it asks for the hits, their validation, and that no parser read them. No tool code changed.
