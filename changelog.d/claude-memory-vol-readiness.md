### Added: `vol_readiness`, and the YARA binding in the Volatility environment (`memory-forensics`)

- **`vol_readiness`** says, before an examination, whether Volatility 3 can be used here and, with an image, on that image: offline, and never a plugin's result. Four views, each `ready`, `blocked` or `unknown`: `plugins` (the plugins `vol --offline --help` lists, as listed, and whether the names asked for are among them), `symbols` (a Windows kernel's table by PDB name, GUID and age from `windows.info`'s Symbols row, or, when the table is missing, from the address the engine asked for, with `isfinfo` searched for the GUID; for Linux and macOS each banner found by `banners.Banners` matched character for character against `isfinfo`'s banner columns, only the release word printed), `yara` (whether `yara` or `yara_x` imports in the Python on the first line of the `vol` script, run from `/` so that a file in the run directory is not what imports) and `fuse` (`/dev/fuse` opens and a `fusermount3` or `fusermount` is on PATH; absence is `blocked`). The verdict is `blocked` if any requested view is, otherwise `unknown` if any is, otherwise `ready`; the status is `partial` whenever a requested view is `unknown`.
- **Offline, and nothing from the capture on disk.** Every Volatility call is built with `--offline` and no parameter changes that. The outputs of `windows.info`, `banners.Banners` and the engine's log are read from pipes, judged by the shared SHOWN rules and dropped; the only file is the whole plugin list when it is longer than `limit`. A program is ended at its own time or at its output cap, with what it started, in the tool's own process group; SIGTERM, SIGINT and SIGHUP end the programs and answer once with `failed`, `interrupted` true and the views that had finished.
- **Shared blocks copied byte for byte:** WITHHOLDING, SHOWN and PAGE of the memory lineage, and the general PROCESS block (the tests that hold the carriers equal list the new carrier).
- **The YARA binding is declared.** `requires/python.txt` pins `yara-python==4.5.1` for the Python environment that runs `vol`, so Volatility's `windows.vadyarascan` and `linux.vmayarascan` can work after the owner's image rebuild; `patterns/yara`, the README and the `yara` entry of `requires/host.json` no longer say that no requirement installs one. Not checked: the package's wheels for arm64 and for the image's Python 3.11, and the licence label, which is the project's LICENSE file and not the package metadata (it was not fetched); there is no hash until the image build can lock one.
- **Not run:** against the real Volatility. The tool's reading of the `--help` listing, of `windows.info`'s Symbols row and of `isfinfo`'s header and banner columns follows Volatility 3's documented output and the tests' stand-ins; a first run on an image that has `vol` (the test that does so is skipped here, and says why) is the check.
- Tests: `tests/pack-memory-vol-readiness.test.ts` (a stand-in `vol`: the listing, asked names, a table found and a table missing, banners matched exactly, a near release, a forged release word, a failing probe, a hang, SIGTERM at a program that ignores it, two signals, a missing `vol`, the binding present and absent and a planted module, FUSE absent, the whole list on disk, a flood of output, hostile parameters), and the carrier lists of `tests/pack-memory-shared.test.ts` and `tests/pack-memory-f2-shared.test.ts`. Each fails on the base, where the tool is missing.
