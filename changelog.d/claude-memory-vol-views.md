### Added: `vol_views`, one named question put to the installed Volatility with the engine's whole output kept (`memory-forensics`)

- **`vol_views`** runs ONE plugin of the installed Volatility 3 on an image, offline, and returns what the engine printed with its scope and a status. `question` names a plugin as `vol --offline --help` lists it (a module name such as `windows.pslist` is enough when one class is listed under it); a name that is not listed is refused as JSON, naming it, and a module with several classes is refused, naming them, so no invented plugin can run. `readiness` is the `ready` answer of `vol_readiness` for the same image, passed as a file under the run directory; it is read, not verified, and the tool still lists the plugins itself. `pid` and `dump` become the plugin's `--pid` and its own dump option only when the plugin's `--help` lists them. It serves the questions the kickoff recipe does not ask, Linux and macOS once a table is validated, and reruns; the `memory-windows` recipe is untouched.
- **What is kept.** Every line of the output is split at its tabs (the quick renderer's separator, which the SHOWN rules take for a control character) and each cell is judged by the shared SHOWN rules, then paged: `limit` lines in the answer and the whole judged output in a file the answer names with its size and sha256. The raw output, and the files the plugin exports with `dump`, are memory content: they are written only with `write_values` in a job run as secret output (directory 0700, files 0600, created exclusively under a hidden name and placed without replacing an earlier file), with their sizes and sha256 in `$OUT/vol_views/manifest.jsonl` and never in the answer. The manifest declares `secret_output` for `write_values`, and the tool refuses as JSON, before it looks at the image, outside a job or in one that is not secret output; `dump` without `write_values` is refused.
- **Status.** `complete` only when the plugin ran to its end with exit 0 and its whole output was read, judged and kept; `partial` when it was ended (its time, more than 1 GiB of output, 64 MiB of log), when the log says pages were missing (a heuristic over its wording), when a line over 1 MiB was not judged, when no row was printed, or when the clock ended a digest or a listing; `failed` when the plugin exits non-zero, with the first lines of its log judged. A complete status says nothing about the image: an empty or short output is an absence only after the plugin completed with the matching table.
- **Offline, and bounded.** Every Volatility call carries `--offline` and runs from the directory `/` in the tool's own process group; the programs are ended at their time, at their output cap, or by SIGTERM, SIGINT and SIGHUP (status `failed`, `interrupted` true, the files being written kept under a name ending in `.partial`). Shared blocks copied byte for byte: WITHHOLDING, SHOWN, PAGE and the general PROCESS block.
- **Not run:** against the real Volatility; the tests' stand-in prints the quick renderer's table as Volatility 3 documents it.
- Tests: `tests/pack-memory-vol-views.test.ts` (the question resolved against the listing, canaries in process names and command lines, an unlisted and an ambiguous question, the receipt in every way it can fail and accepted when it is the real `vol_readiness` answer, `pid` and `dump`, the secret job with its raw output, exports and manifest, a long output paged with its digest, the output cap and a hang, a failing plugin, an empty output, a missing page, SIGTERM at a program that ignores it, hostile parameters), and the carrier lists of `tests/pack-memory-shared.test.ts` and `tests/pack-memory-f2-shared.test.ts`. Each fails on the base, where the tool is missing.
