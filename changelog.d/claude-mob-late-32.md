### Added: mobile-forensics, backup_materialise

- A tool that lays an unencrypted (or already decrypted) iOS backup out as a derivative under `$OUT/derivative/files/<domain>/<relativePath>`, for a selection (domains, paths, or `all`), with every file tied to its Manifest.db row: the original file id, the domain and path as printed and as base64 of their bytes, the Manifest row, the Size the Manifest records, the SHA-256 of the blob and the state of the blob. The whole account is a result file, one line per row. It reads the map with manifest_db's row reader (row order, a `-wal`/`-journal` applied in a working copy, every statement under the progress handler), opens every blob through directory descriptors without following a link (a link, a directory or a FIFO is refused and counted), rejects a hostile `relativePath` (`..`, an absolute path, a NUL, a component over 255 bytes) and resolves name collisions, case-folding ones included, explicitly. It does not decrypt, and the derivative is not the phone.
- `copy_content` (false by default: a plan that writes only the result file) writes content and is a `secret_output` mode of the manifest: it is accepted only in a job run as secret output and is otherwise refused as JSON before anything is made. A path component shaped like a recovery password is the placeholder on every channel, including the names under the derivative; its real name is only in a 0600 values file. A second run in the same `$OUT` names identical files again and never replaces one.

### Added: mobile-forensics, heic_inspect

- A tool that makes a JPEG or PNG preview of a HEIC or HEIF original under `$OUT/heic_inspect` and ties it back to the original: the size and SHA-256 of both, the dimensions, the image count, which item is primary, and the backend's settings and errors. One backend per run (`heif-convert` in the tool's process group, or `pillow-heif` in a child process), recorded in the answer, with no fallback to the other. A pixel or size limit is checked on the original's own boxes before any backend starts, and an original that declares no size for its primary image is refused. The program's output is watched: it and what it started are ended at its time, past an output cap and on a stop signal.
- A bounded standard-library walk of the ISO-BMFF boxes (the `ftyp` brands, then under `meta` the handler, primary item, items, locations, properties and references, and a grid's own structure) without a decoder. A size of 0, a size past the file, a size below the header, counts beyond what a box can hold, overlapping or outside extents and nesting are bounded and reported with offsets; every box and problem is a line of a result file the answer names. The metadata comes from the original with `exiftool`, never from the preview: the answer carries presence and counts, and the values are written only on `write_values` in a job run as secret output, to a 0600 file.

### Added: mobile-forensics, ab_layout

- A tool that maps an unencrypted Android `.ab` backup (header versions 1 to 5) onto the layout ALEAPP reads under `$OUT/ab_layout/derivative` (`data/data/<package>/...`, `data/user_de/0/<package>/...`, the package's `_manifest` kept apart) and says, in a banner file and in the answer, that it is a derivative of an adb backup and not an acquisition. The tar is streamed once under a decompression budget, with the zlib end marker, the tar's two end blocks (a lone zero block is read past and counted) and anything after them checked. The mapping table is in the manifest with its basis: the author's recollection of AOSP's FullBackup domain tokens, not checked against the source.
- Unknown domains, links, hard links, devices, FIFOs, directories and `shared/` are listed and not extracted; hostile member names are rejected and listed; duplicates and case-folding collisions each get their own name. Every member is a line of a result file with its name as spelled (and its bytes in base64), offset, size and state. `copy_content` (false by default, a plan) is a `secret_output` mode; an encrypted payload is refused after its header and no password is read.

### Changed: mobile-forensics, android-backup-apps

- The recipe is no longer declared unavailable. It detects an unencrypted `.ab` (header versions 1 to 5), lays the backup out as the `ab_layout` tool does (the logic is copied into the recipe) under `derivative/`, and runs ALEAPP over the layout with `-t fs` in the recipe's process group, with the `modules.tsv` receipt of `android-aleapp`, a `coverage.json` written before ALEAPP starts, and `ab-members.tsv` for every member of the backup. The result is a derivative of an adb backup and says so in `derivative/DERIVATIVE.json` and in `coverage.json`. An encrypted backup is refused as failed and no password is read; a stream that is not whole (a missing end block, a lone zero block, bytes after the end) or a member that is rejected or left out for a reason that is not by design makes the run partial. The recipe does not withhold recovery-password-shaped member names (the `ab_layout` tool does). The README and the leaf `extractions/what-you-have` no longer call the route unavailable.
