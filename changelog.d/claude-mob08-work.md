### Changed: mobile-forensics, ios-ileapp

- The recipe also takes an unencrypted iOS backup directory (Manifest.db and Manifest.plist as regular files; Info.plist and Status.plist are read when they are there). The directory is given to iLEAPP's own backup reader (`-t itunes`), which maps the backup's hashed names back to the domain and path the phone knew them by; the backup is not laid out first. Before iLEAPP starts, the recipe reads the backup's `IsEncrypted` flag and the first bytes of `Manifest.db`: an encrypted backup, or one whose encryption cannot be established, ends as `failed` and iLEAPP is not started, because it would ask for a password. No password option is ever passed, and the program gets no terminal. `coverage.json` names the route in `input`, with the backup's encryption and completion state; a backup whose `Status.plist` does not say `finished`, or that has no `Info.plist`, is `partial`.
- A `backup_materialise` derivative (its `derivative.json` banner) is refused, not given to `-t fs`: what the iLEAPP modules' search paths make of a backup's domain and path layout was not established. Which backups iLEAPP's `-t itunes` reader supports is iLEAPP's own decision; its refusal is in the kept log and the run is then not complete. The route was written from iLEAPP's `ileapp.py` at the pinned release and tested with a stand-in program, not with the real one.
