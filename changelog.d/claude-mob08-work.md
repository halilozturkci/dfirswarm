### Changed: mobile-forensics, ios-ileapp

- The recipe also takes an unencrypted iOS backup directory (Manifest.db and Manifest.plist as regular files; Info.plist and Status.plist are read when they are there). The directory is given to iLEAPP's own backup reader (`-t itunes`), which maps the backup's hashed names back to the domain and path the phone knew them by; the backup is not laid out first. Before iLEAPP starts, the recipe reads the backup's `IsEncrypted` flag and the first bytes of `Manifest.db`: an encrypted backup, or one whose encryption cannot be established, ends as `failed` and iLEAPP is not started, because it would ask for a password. No password option is ever passed, and the program gets no terminal. `coverage.json` names the route in `input`, with the backup's encryption and completion state; a backup whose `Status.plist` does not say `finished`, or that has no `Info.plist`, is `partial`.
- A `backup_materialise` derivative (its `derivative.json` banner) is refused, not given to `-t fs`: what the iLEAPP modules' search paths make of a backup's domain and path layout was not established. Which backups iLEAPP's `-t itunes` reader supports is iLEAPP's own decision; its refusal is in the kept log and the run is then not complete. The route was written from iLEAPP's `ileapp.py` at the pinned release and tested with a stand-in program, not with the real one.

### Added: mobile-forensics, backup_decrypt

- A tool that decrypts an encrypted iOS backup (iOS 13 or later) with the library `iphone_backup_decrypt` 0.11.2, pinned in `requires/` with the sha256 of each file PyPI lists (its dependency pycryptodome is held at the version the pack's other locks use), from `password_ref`, a 0600 file the job was given. The library runs in a child process of the tool, in its process group, ended at the tool's own clock and by a stop signal; the tool only looks at the password file, and the child reads it and hands the text to the library in memory. The password is on no command line, in no environment variable, on neither output channel of the child, in no path, JSON key, error or file; an exception of the library is reported by its class name only. The manifest declares `secret_output: "required"`, and the tool refuses to run outside a job run as secret output.
- The decrypted `Manifest.db` and one decrypted file per file row are written under `$OUT/backup_decrypt-<id>/decrypted/`, mode 0600, created exclusively and never replaced, named by the file id (no name from the Manifest is used as a path), with a result file of one line per Manifest row. `verified` means the decrypted `Manifest.db` opens as SQLite and each file row has the length the Manifest records as its Size; it is not a claim that a file's content is what the phone held. `wrong_secret`, `secret_unavailable`, `unsupported_format`, `backend_unavailable` and `partial` are told apart (the backend does not say whether a wrong secret or a key bag it does not read failed, and the tool does not claim to). A row the backend could not select with certainty is listed as `ambiguous_selection` and not decrypted. Key bags, class keys and manifest keys are a presence and a length, never printed.
- Not shown here: the library has been exercised only through a stand-in for its three documented calls (`EncryptedBackup`, `save_manifest_file`, `extract_file`); it was not installed or run on a real backup. Its MIT label is the owner's decision; PyPI carries no licence field. The README, `extractions/backups`, `extractions/backup-detail` and `extractions/what-you-have` no longer say no decryption is provided.
