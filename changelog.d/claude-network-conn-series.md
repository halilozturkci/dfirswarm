### Added: network-forensics: `conn_series`, connection observations and a start-time series for `beacon_score`, from a Zeek conn.log or a capture

- **A tool that reads a Zeek `conn.log` or a capture.** A `conn.log` (TSV with `#separator`, `#set_separator`, `#empty_field`, `#unset_field`, `#fields` and `#types`, or JSON lines) is read as a stream with no program; a capture is listed by `tshark -T fields` (declared in `requires_optional`: a `conn.log` needs no program). Zeek is not started. Each unique connection is a row with a locator (the log line and byte offset with the uid, or the first frame), start (raw and UTC), duration, bytes and packets, state, service and the time semantics: Zeek's `ts` is the first packet of the connection, not one event per exchange. The whole table is a JSON Lines file (mode 0600, never replaced by a smaller rerun); the answer pages it.
- **A series for `beacon_score`.** The start times, sorted, one epoch per line, in a second file `beacon_score` accepts as `timestamps_file` (the test feeds it to the real `beacon_score`); `beacon_score_arguments` is what to pass. A SYN observation is not taken for a connection start.
- **Identity.** A retransmitted SYN (the same initial sequence number as the open connection) is not a second connection; a new SYN on endpoints still open is port reuse and is. UDP, and TCP without a SYN (flagged `midstream`), are the endpoints plus an inactivity gap (`udp_gap_seconds` 60, `tcp_gap_seconds` 3600). IPv6 is read like IPv4. A repeated uid, as after a concatenated rotation, is one observation. `set[...]` and `vector[...]` are split on the set separator, `-` is unset, `(empty)` is empty, and a header block that repeats applies to the rows after it.
- **The window and the coverage.** `window_start` and `window_end` carry an explicit zone (start inclusive, end exclusive, on the connection's start); a time with no zone is refused unless `assume_utc`. `sensor_coverage_confirmed` is carried to `beacon_score` only as given and only with `window_end`; the tool never assumes it.
- **Filters on the shown text.** `host`, `port`, `proto` and `service` apply to the text the answer prints; a withheld `service` value never matches, so it cannot be probed by guessing (the test has the oracle twin).
- **Bounds and measurement.** Lines over 1 MiB, with a NUL, not UTF-8, not JSON, before `#fields` or with the wrong column count are counted and skipped, and the answer is partial; a gzip log is refused. At most 3,000,000 observations are kept (`beacon_score`'s own limit); open connections are bounded at 1,000,000 with the oldest closed early. A log of 5,000,000 rows (497 MB) read in 288 seconds on one clock, 514 MB resident, kept the first 3,000,000 and was partial. The tool's own clock (`max_seconds`, default 900, at most 1000) is below the manifest's 1200; SIGTERM, SIGINT and SIGHUP end it with partial JSON and exit 128 plus the signal.
- **Not verified here:** no Zeek and no tshark were available, so the logs are built from Zeek's documented fields and a stand-in `tshark` prints documented output; the field values of real builds were not checked, and the manifest says so. One test runs the real tshark when installed and is skipped, with its reason, when not.
- **Shared blocks.** WITHHOLDING, PROCESS, PLACE, PAGE and STOP, copied byte for byte.
- **`beacons/periodicity`** gains one sentence that points to the tool.
- Pack raised: `network-forensics` (minor).
- Tests: `tests/pack-network-conn-series.test.ts`: TSV and JSON logs, headers and types, rotation, the window and zones, filters, canaries in `service` and `uid`, hostile logs, captures with retransmissions, port reuse, UDP gaps, IPv6 and midstream flows, `beacon_score` reading the series, four simultaneous runs, the clock, three stop signals and the manifest.
