### Fixed: the network pack's readers answer inside their own clocks (a megabyte of `&`, a file of block types, a log read after the engine), and a signal always gets its partial JSON

Found by an independent verification of the pack on its current main; every item below has a test that fails on the code before it.

- **`network_log_summary`** read its clock every 256 lines, and one line just under the default 1 MiB limit cost 0.5 to 1.8 seconds in the withholding block's query loop (a megabyte of `&` after a `?`), so the clock was late by minutes: 60 such lines with `max_seconds` 10 took 104 seconds and answered `complete` (Linux container, one CPU, Python 3.11); 420 lines ran past the manifest's 600 seconds with nothing on stdout. The clock is now read every 256 lines and after every 64 KiB of lines, inside the loop that skips the rest of a long line, and, for gzip, after every 8 KiB read of the file under it (Python's gzip walks the members of a stream inside one read: 300,000 empty members cost 5.4 seconds before the first line could be looked at; three million now end at `max_seconds`). A target or referer over 64 KiB keeps its scheme, host and path part and has its query and fragment withheld whole, by their length (`<over-long query or fragment withheld N characters>`, the block's own rule for a text over the limit, applied in the tool because the block is shared); the line stays in the table with its offset and length, and `write_values` keeps the original. The same bound is in `pcap_extract` and `zeek_run` for the URIs they print. The same 60 lines: 3.8 seconds; with `max_seconds` 2, 2.2 seconds and 20 lines, `partial`.
- **`pcap_summary`**: every distinct pcapng block type the tool does not know was a key of a counter and was printed inline: 6,000,000 blocks of 12 bytes (72 MB) cost 2,188 MB of memory and a 126 MB answer; a 300 MB file would have crashed without JSON. The types are tallied in bounded memory (4,096 held, the rest merged into the spill file in batches, nothing dropped), fifty are inline (`unsupported_block_types`), and every type with its block count is in a file the answer names (`unsupported_block_types_file`, by type, with `unsupported_block_types_total` and `_not_listed`): the same file now takes 22 MB of memory and answers in 5.9 KB (11 seconds before in the container, 26 now, because every type is written to the file, 252 MB for the 72 MB capture). The clock is now also read every 4,096 pcapng blocks of any kind, so blocks that carry no packet end at `max_seconds` too (they never reached the loop that looked at it). The finishing margin is 30 seconds, not 15 (the tail after the finish cut took 7 seconds on a slow disk with 14 million tuples, 8 seconds under the limit). When the endpoint sums were cut, `endpoint_aggregate_count`, `_returned` and `_omitted` are `null`, not 0. A `tool-output` that is a symbolic link is refused before anything is read.
- **`pcap_extract`**: the stop handlers were installed at the start of `main`, but the last word that prints the partial JSON only after two tshark preflights and the receipt setup: a signal in that window (31 of 120 at random offsets within 900 ms) ended the tool with exit 128 plus the signal and nothing on stdout. The last word is set first; until the receipt exists it says which stage the tool was in and that no export pass had started.
- **`beacon_score`**: `timestamps_file` was opened without looking at what it is, so `/dev/zero` (or a pipe) was read for ever; it must be a regular file, refused as JSON like every sibling tool's input. The skip of a line too long to be a time is under the clock. A series nested 100,000 deep (Python 3.14 parses it where 3.9 to 3.13 refuse it) was an "unexpected failure: RecursionError" from the text built for the record of a rejected value; it is a rejected value now. A `tool-output` that is a symbolic link is refused.
- **`zeek_run` and `suricata_run`** read the engine's logs back with no clock, while the answer had to be printed before the manifest's 1200 seconds: the margin was `1200 - timeout_seconds` (100 seconds at the largest `timeout_seconds` for `zeek_run`) and for `suricata_run` `1200 - (30 + 120 + timeout_seconds)`, as the build information and the configuration test were not counted. Reading now has a clock of its own that ends 30 seconds before the manifest's limit, counted from the start of the tool, so everything that came before is out of it. A log (or `eve.json`) still being read when it runs out is read in part and said so (`zeek_run`: `reading_cut_by_its_clock`, `logs_read_in_part`, `logs_not_read`, `read_to_the_end` and a problem naming the line and byte; `suricata_run`: `eve_read_to_the_end`, `eve_reading_cut_by_its_clock` and a problem), the file is whole in `out_dir`, and the answer is `partial`. Measured with stand-in engines (no Zeek or Suricata is installed here): a 72 MB Zeek log of a million rows is read in 9.5 seconds and, with the clock forced to 3 seconds, in 3.3 seconds with 328,696 records and `partial`; 600,000 EVE lines, 6.6 seconds, and 3.4 seconds with 297,984 lines.
- **Both**: a stop signal that arrives while the final answer is written no longer adds a second document after it (15 of 100 signals did, in `suricata_run`): signals are held for the write and the tool ends with that one document, exit 128 plus the signal.
- **The `network-capture` recipe** counted the rows of each finished listing, and the truncated packets of `packets.tsv`, in Python with no clock; they are under the recipe's own clock (it ends 30 seconds before the recipe's 3600), and a count that could not finish is `null` with the status `partial`, not a number that looks whole.
- **Words**: the README no longer says that a flow export is identified and its semantics stated by the pack's tools (the capture skill says how to identify the producer, and nothing parses a flow export). The manifests say all of the above.

Not done here, and why: the shared withholding, process and paging blocks are untouched (a signal that lands between starting an engine and recording it, a signal in the first milliseconds before the handlers exist, and a `tool-output` symbolic link inside the shared paging class are for the change that owns those blocks); the output of `pcap_summary` is still not capped (the lists are whole on disk, by design: 3.5 times the capture's size for a capture of nothing but distinct unknown block types, and 12.6 times for millions of conversations).

Measured on macOS with real tshark 4.6.9 where tshark is used, Python 3.12 and 3.14, and in a Linux container with one CPU and Python 3.11; differential fuzz against the code before this change: 300 (log summary), 400 (pcap summary), 400 (beacon score), 300 (`zeek_run`) and 300 (`suricata_run`) random cases, no difference in any answer or table, and 40 captures of up to 20,000 block types in which the file holds exactly what the old inline map did.
