### Security: the encrypted-containers pack no longer prints a recovery key's shape or hash, and no skill tells an agent to hash a secret into the ledger

`recovery_key_scan` returned, for every BitLocker recovery password it found, the first two digits of each of the eight groups (sixteen characters of the secret) and an unsalted sha256 of the whole value, in an ordinary tool answer; its note said values were not printed. The worker prompt forbids a hash of a secret anywhere, and any characters of a short one; a "shape" such as the first two digits of each group counts as characters of it. Both fields are gone. The answer is now a locator: finding id, file, offset, length, kind, encoding, and `passes_structure_check` (renamed from `complete`: eight groups divisible by 11 with a quotient below 65536 is a plausible transcription, not a key that opens anything). `write_values: true` writes the values to `$OUT/recovery-passwords.jsonl` (mode 0600, one row per finding, the same finding id), and only when the tool runs as a job; outside a job it refuses and writes nothing. The skill says the job runs with `secret_output: true`. This is the reference implementation of the secret-safe output pattern, written down in `docs/packs.md` ("Secrets and sensitive output") for the other packs to copy: a locator in the answer; a value only on an explicit flag, in a job, in a file under `$OUT`; tests that assert the absence of any group, run of digits, 64-hex string or masked shape in the answer and in every file it names.

`keys/where-they-hide` told the agent to record a found key's hash in the ledger; `volumes/bitlocker` put the recovery password on `dislocker`'s command line (the trace records every command line) and treated a FUSE view as a sealed image; the README said the scan returns "a shape and a hash", and the goal template said "a hash and a location appear instead". All four are rewritten: where a key was found, its kind, a non-secret identifier, the authority, the method and a sealed reference go in the ledger, never a value, a fragment or a hash; opening is a `secret_output` job that takes the secret from a sealed file through a user-space reader and writes the decrypted volume under `$OUT`; where a reader can take the secret only on its command line, the report says so.

### Fixed: the encrypted-containers pack's tools stop returning plausible wrong answers

- **`recovery_key_scan`** counted a file it could not read as scanned and returned no findings for it; it read only the first 8 MiB of each file without saying what it left; it dropped any directory named `dev`, `sys` or `proc` at any depth, ignored a directory it could not list, followed no rule about links and special files, and held every finding in memory. It now reads each file as a stream, counts files attempted, read, partial and failed with the bytes not read, names every file or directory it skipped, failed on or read in part (links and special files are not followed; only the top of a Linux root is excluded, and said so), pages findings and exceptions losslessly, and keeps what it found before a read failed. A value is found unless it is glued to more digits (`key_<value>` was missed, because `\b` is no boundary between an underscore and a digit); a path component shaped like a recovery password (a file named after the key) is withheld from every printed path and from the digest that names a paging file, and only the sealed values file keeps the real path; the values file is created first, so a file or link already at its name is refused by name before anything is scanned, and with nothing found it stays an empty file saying `written: 0`.
- **`crypto_id`** read each LUKS1 key slot's `stripes` from inside the salt (4000 came back as 2694881440) and returned the LUKS2 label as its UUID, and its test built the fixture at the same wrong offsets. It reads the specified fields (also the key material offset), reads the LUKS2 UUID, label, header size and checksum algorithm from the 4096-byte binary header, names a header cut short instead of reading a short slot table, calls a LUKS version other than 1 and 2 unsupported, bounds its entropy sample, and prints raw bytes only with `include_head_hex`. Every answer says the next reader and what is not determined, and "not encrypted, or not a scheme this tool knows" is gone. A file that merely begins with `CS` (a CSV) is no longer called Apple Core Storage: only the signature at offset 88 counts. An empty file is said to be empty. The manifest no longer promises LUKS2 slots or document flags.
- **`archive_probe`** called a PDF without the `/Encrypt` marker "openable with nothing", a PDF with it protected, an Office file without an `EncryptionInfo` string "not encrypted", and read printable strings of a 7-Zip header as a member list. PDF and Office are now markers with offsets (`protected: null`, `protection: heuristic`), 7-Zip is listed through the installed `7z` (bounded, no password prompt, each member's flag, `header_encrypted`) with the start header's CRCs checked and the byte search kept as a hint, and RAR is identified with its protection undetermined. A PDF or an OLE file is searched whole and says so (`bytes_searched`, `search_complete`: `max_metadata_bytes` does not bound it, because a PDF's marker sits at its end), and a 7-Zip header's printable strings are merged by offset and written straight to the paging file instead of being collected first (peak memory over a 16 MiB header of two million strings: 384 MiB before, 40 MiB now). ZIP is found from the End Of Central Directory record, read by the tool itself rather than through `zipfile.is_zipfile` (Python 3.14 refuses a record whose declared directory is bigger than the file, which the tool took for "not a ZIP"), so empty and self-extracting archives are listed, a central directory above `max_metadata_bytes` is not loaded and the answer says so, the AES extra field is parsed, and DOS times carry their raw words and `timezone_unknown` beside a separate recorded UTC time.

### Changed: the encrypted-containers pack's skills, README and requires say what each tool shows and does not show

`identify/headers`, `volumes/bitlocker`, `volumes/luks-filevault`, `archives/protected` and `keys/where-they-hide` are rewritten in the defender's voice: what an artefact shows, what it does not, what corroborates it, every negative bounded by what was searched; a LUKS slot is not a person; no signature and high entropy do not identify VeraCrypt; `fvdeinfo` is for Core Storage and is not assumed to read APFS; a PDF can be encrypted and open with an empty password; a member list is not an exfiltration finding. The password-recovery paragraph is now only the gate and gives no method. Each skill names the tools and programs its front matter lists and the other way round, so the pack leaves `tests/pack-links.pending`; programs no skill names yet are in `pack.json`'s `unreferenced_ok` with the reason. `requires/host.json` drops the brew routes that installed Python bindings in place of command-line tools and those for `bdeinfo` and `cryptsetup`, for which no Homebrew formula is known ("no macOS install route is declared"), and says what each program does and does not do; `pyAesCrypt` is pinned. A new suite, `tests/pack-encrypted-containers.test.ts`, builds its fixtures from the LUKS1, LUKS2 and ZIP layouts, the recovery-password format and real 7-Zip archives.
