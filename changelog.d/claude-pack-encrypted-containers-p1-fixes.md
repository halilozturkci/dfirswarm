### Fixed: archive_probe, crypto_id and recovery_key_scan are bounded, stop cleanly, print less of the evidence and carry status (encrypted-containers)

The three Phase-1 tools had two bounds that did not hold, a key file printed whole, names and header text printed raw, and no clean stop. Each is fixed at its cause and has a test that fails on the tools as they were.

- **`archive_probe`: `max_metadata_bytes` held for every ZIP.** The tool followed a Zip64 locator only when the End record held the 0xFFFF markers, while Python's `zipfile` follows it whenever it is there, so a file whose End record said "1 entry, 47 bytes" and whose Zip64 record said 3,000,000 passed the check and was then loaded whole: 141 MB took 19.6 s of CPU and 1,107 MB of memory (8 bytes of memory per byte of file). The Zip64 record is read wherever a locator is (as `zipfile` reads it), a directory declared over the bound, over the file, or with more entries than the bound holds is not listed (`not attempted`, `partial`), and the directory is now read by the tool itself in blocks of 1 MiB, so memory no longer follows its size: the same file answers in 0.1 s and 24 MB; a 600,000-entry directory inside the bound lists in 9 s and 50 MB. Because the tool reads the entries itself, one member name that is not valid UTF-8 no longer fails the whole listing (`listing: failed`, which hid which members were encrypted): the name is shown escaped and the others are listed; a directory that breaks off part way is listed as far as it goes (`listing: partial`). ZIP dispatch no longer asks `zipfile.is_zipfile` at all (a signature or an End record decides).
- **`recovery_key_scan`: a clock, and a scan that is not slow.** There was none: at 19.7 MB/s the 600 s limit was reached at about 12 GB, and a kill left no answer, no coverage and a half-written values file. The tool has `max_seconds` (default 480, 1 to 540) and stops at it and on SIGTERM, SIGINT and SIGHUP: it finishes its pages, closes the values file (whole rows only), and prints one answer, `partial`, `interrupted`, that names every file it did not read, every entry of a directory it did not look at and every directory it did not enter (`coverage.entries_not_started`, `directories_not_entered`, `files_stopped`), exit 128 + the signal. If it cannot finish within five seconds of a signal (a read that never returns) the stop is hard: the temporary files go and a short `interrupted` answer is printed. The scan searches for the dash that follows a group instead of trying every byte with a look-behind, and finds exactly what the patterns found (1,000 differential cases and 400 more in the test, 0 differences, including windows that split a value): 537 MB of random data took 27.6 s of CPU and takes 0.6 s.
- **`crypto_id` prints no raw bytes.** `include_head_hex` printed the first 32 bytes of the file, a usual key file size, whole in the answer; the parameter is gone and a call that passes it is refused with that said. The header's text was printed raw although the manifest and three skills said it printed none: the LUKS cipher, mode and hash are now printed only from the closed lists of the names cryptsetup and the kernel use, the UUID only in the UUID form, anything else as `<unrecognised header text withheld>` (`header_fields_withheld` names the field), and the LUKS2 label and subsystem, which are free text, through the names rule below. The claim in the manifest and the skills is corrected.
- **`recovery_key_scan` echoed up to 4 MiB of file text per finding as the private key's "type"** (six such files: 18.9 MB of output). The PEM header is matched as at most two capital words of 2 to 10 letters before `PRIVATE KEY`, and the type is reported from RSA, EC, DSA, OPENSSH, ENCRYPTED, PGP, none, or `other`: the header's own text is never echoed.
- **Names, paths and header strings were printed raw** (a recovery-password-shaped member name 100 of 100, an AWS key id and `password=` too, in `archive_probe`; the same classes in a path component of `recovery_key_scan`, whose identifier rule missed 12-digit numbers, 24 letters, grouped ids, 7-character ids and full-width ids). The three tools share a `NAMES` block (and the network pack's `WITHHOLDING` block, copied byte for byte, for the token shapes): every path and member name is judged component by component, every header string and diagnostic as text, and the part that is shaped like an identifier or a secret is replaced by a fixed marker (`<identifier-shaped text withheld>`, `<secret-shaped text withheld>`, `<recovery-password-shaped name withheld>`), with no length and no fragment; the rest of the name stays. A second check, written apart from the first (eight groups of six digits, a PEM marker, a named secret, vendor prefixes, long hexadecimal or letter-digit-flipping runs), reads every string of an answer and of every row of a paging file once more, replaces what the first let through, and makes the answer `partial`; a test removes the first layer and shows it holds. This covers the member names and 7z header strings and diagnostics of `archive_probe` and its `path`, `crypto_id`'s `path` and header text, and the `file`/`path` fields of `recovery_key_scan`.
  - **What the rule withholds, measured** on 1,000 random draws per shape planted as `docs/<id>.txt` (the test: 300 per shape in each of five slots: whole name, directory, middle of a name, free text; each shape is asserted at the rate stated): 0 printed of UUIDs, hexadecimal ids of 16, 32 and 64, numbers of 10 digits or more, a recovery password with dashes, spaces, dots, underscores, no separator or one to three of any other characters between the groups (an en dash, a comma, a colon, a pipe, a tab: the groups are joined by anything that is not a letter or a digit), also with one decimal digit glued to the first or the last group (it was printed whole in every draw: the look-around that asked for no digit beside the value is gone), also when it is cut at the separators of a path (`123456-123456/123456-...`, two groups to a component over four components, one group to a component), written full-width or split by invisible characters; AWS access key ids, `password=` and `api_key:` assignments, user-info, groups of four capitals and digits joined by `-` or `.`, and letters and digits of 8, 9, 12, 16 or 40 characters that hold a capital, a small letter and a digit. Printed in some draws: **uniform** draws of letters and digits (each character as likely a capital, a small letter or a digit as any other) of 8 characters about 2.5%, of 9 about 2%, of 12 about 1%, of 16 about 0.6%, of 24 at most 0.1% (1 draw of 1,000) and of 40 none (the table in the first version of this change said 0 for 8, 12 and 40 characters and 1.4% and 0.6% for 9 and 16: the zeros held only for draws forced to hold a capital, a small letter and a digit, and the two rows came from two kinds of draw); lowercase letters and digits of 8 about 7%, of 12 about 2.4%, of 16 about 0.4%; 24 random letters 1.5% to 2.6% (draws of 1,000, repeated); a 16-character base32 id 2.2% to 3.4% (by alphabet); four groups of four lowercase hexadecimal digits joined by underscores 4% to 9% (by how the draws are made); an id of 12 or 16 characters whose letters are half Cyrillic or Greek look-alikes about 1% (they are read as the Latin letters they imitate; 53% and 38% before). **Not recognised, by design, and asserted:** an identifier of 7 characters or fewer, a number of 9 digits or fewer, a lowercase-only run of up to 22 letters (it reads as a word), an all-capital letters-only run of any length (24 capitals are printed whole), three groups of four or five capitals and digits joined by `-` or `.` (printed whole: a rule for them also withholds 0.3% more of the names of a library tree, upper-case constants such as OpenSSL manual page names), a recovery password cut by anything other than a separator, or with a letter in it or glued to it (the groups then show: with a letter inside, six of eight groups are visible in about two draws in three), a number of 10 digits written 3-3-4, an e-mail-like lowercase string, a secret of any other shape. Withholding is by shape: a secret of another shape is printed, and a file whose secrets matter is read in a job run with `secret_output: true`.
  - **The output check alone** (the first layer removed) now also replaces hexadecimal of 16 digits or more (it passed all of it), user-info and recovery passwords written full-width or split by invisible characters (NFKC first). It still passes, and a test says so, numbers of 10 to 20 digits, identifiers of up to 23 characters, about one in five base64 keys of 32 bytes, every recovery password whose groups are joined by anything but a hyphen, underscore, dot, space or nothing, and every recovery password cut over the components of a path: only the first layer withholds those (the second layer holds the headline secret for those five separators on one component only), and a rule for digits in the check would replace the byte counts the tool states in its own messages.
  - **What it costs an examiner:** names that are not secrets lose a part. Of 137,808 file names of a documents tree 6.9% have a part withheld (10-digit timestamps, UUIDs, hash-named files) and 0.6% of its 17,408 directories; of an application tree 15.8% and 3.1% (a word with a digit inside, such as `libmp3lame`, is withheld in part; `System32` and a few such Windows names are let through). The identifier rule is the interim one (NFKC first, a digit-only run counts from 10 digits, a letters-only run counts unless it reads as words); the shared-block work decides the final one.
- **One answer, whatever stops the tool.** All three stop on SIGTERM, SIGINT and SIGHUP with one JSON answer and exit 128 + the signal (they were empty, exit -15/-2/-1, a traceback for SIGINT); `archive_probe` ends the 7z it started (it survived a SIGTERM and a SIGKILL of the tool) with the shared process block of the network pack (a parent-death signal on Linux, the process tree killed on a signal or at `max_seconds`); no temporary file of a paging file is left in `$OUT` on any exit; a file the tool cannot read is an error answer, not a traceback (`crypto_id` and `archive_probe` on an unreadable file); a directory as the path says "is a directory". `archive_probe` has `max_seconds` (default 100, below the 120 s timeout): it ends the 7z and says what was not read.
- **Every answer carries `status` and `status_basis`**, errors included (`complete`, `partial`, `failed`; `interrupted` for a stop): all three had none.
- **Paging files are written as the other fixed packs write them:** a result file that is there is never replaced (a rerun with other limits, or one the clock stopped, takes the next free name and the earlier, larger file is kept byte for byte), and a file name that is not UTF-8 no longer stops `recovery_key_scan` with a `UnicodeEncodeError` on Linux (paging and values file are ASCII JSON; the values file is written one row per write).
- **Text the withholding rule is given is bounded.** The token rule of the shared block (a byte copy of the network pack's, held equal by a test) re-reads all the text in front of a `/` once for each flagged piece after it, so its time grows with the square of a long run of name characters, and U+FF0F FULLWIDTH SOLIDUS, which NFKC folds to `/`, brought it every ZIP member name: a ZIP of 101,546 bytes with one entry kept `archive_probe` busy for 290 CPU seconds with `max_seconds` 100 and a manifest timeout of 120 (a ZIP of 40 KB for 9.5 s; a 7z header string of 41 KB for 226 s). What the rule is given is now bounded first, in the names block of this pack's three tools: a string of more than 4,096 characters (as written or after NFKC), a path of more than 8,192, or a string with a `/` and a run of more than 256 name characters is withheld whole (`<text too long to judge withheld>`) and not judged; the slowest string inside the bound that a search found took 0.13 CPU s (0.10 s on Linux; 0.04 s over a sweep of the two families), and the ZIP of 101,546 bytes is answered in 0.05 s. The block's own quadratic is not changed here (its copies are held equal across packs): it is repaired at its source and copied again everywhere in the cross-pack change that follows the open pull requests (tracked as E1b), and this bound stays in front of it. `archive_probe` also reads the clock for every ZIP entry and every 7z header string (it was every 1,000 entries and every 1,024 strings), so what is cut is cut at `max_seconds`.
- **An End record in a ZIP comment is not the archive's.** The last signature in the last 64 KiB was read whatever its comment length said, so a 22-byte End record of 0 entries in the comment made an archive of six members, five of them encrypted, "complete, not protected, 0 entries" (7-Zip lists the six; Python's `zipfile` gave the same 0 as the tool). The records whose comment ends exactly at the end of the file, and whose directory starts with a directory signature, are the candidates; with more than one that disagree, the one that declares the most entries is read, the others are named (`end_records_disagree`) and the answer is `partial` with `protected` not `false`; an empty archive's record at the end of a file that holds a sound non-empty archive before it is treated the same way, and so is a sound record of a whole archive that lies before the one that ends the file (a second archive appended to the first: 7-Zip lists the first, with a warning about data after the end, `zipfile` the last; the tool answered `complete`, 1 entry, 0 encrypted, not protected, for six members of which five were encrypted). The archive's start is worked out from its own directory offset, so a stored ZIP inside a member (a jar that holds one) is not another archive; on 957 real archives under /Applications and /opt/homebrew (jars, zips, wheels) the change is 0 answers, all `complete` before and after; only the last 64 KiB of the file is searched for the earlier record. With no record that ends the file, the last one is read and the answer is `partial` and says so (`trailing_bytes_after_comment`, `end_record_comment_overruns_by`); trailing zero bytes are counted and noted only (`trailing_zero_bytes`). `protected: false` is now said only of a list that is whole, whose count agrees with the End record, and of an End record nothing contradicts (it was said of a `partial` list whose count differed).
- **`max_seconds` holds against a read that does not return.** The deadline was tested between reads, and the five-second hard stop was armed by a signal only, so a read that blocked (a file on a share or a cloud volume that is not there, a pipe nobody writes) kept the tool past the clock and the manifest timeout with no answer: with a read that blocks, `max_seconds` 3 was still running at 40 s, and a 9.8 GB archive that was kept on a cloud volume blocked for more than 200 s with `max_seconds` 100. The deadline now arms SIGALRM for `max_seconds` + 5 s (cleared on every path that answers or fails) and starts a watchdog thread that needs neither a signal nor the read to return: either prints ONE JSON answer, `status` `partial` with `hard_stopped` true, and the tool ends (exit 0); the first to claim the stop wins, and the main thread prints nothing once it has been claimed. All three tools have it (`crypto_id` has a fixed limit of 100 s, below its timeout of 120). A page fault in a mapped file stops the interpreter and the thread with it, so `archive_probe` no longer touches a mapped page first: every part of a 7z header, and a PDF or OLE file in windows of 8 MiB, is read through the descriptor before it is used (a stall is then a stalled read, which the watchdog ends), and the markers and the first `/V`, `/R` and `/P` are searched window by window, across the edges of the windows.
- **`recovery_key_scan` reads the clock for every finding.** A window of 4 MiB that holds nothing but findings took 2 to 4 seconds to work through between two reads of the clock: `max_seconds` 8 ended at 12.7 s on a 67 MB file of recovery passwords (6.6 s over), and SIGTERM during such a window used 5.0 of the 5 seconds of grace and ended as the hard `interrupted` answer without coverage. The clock is read for each finding; findings not yet worked through count as unread (`bytes_read` is the offset of the first, `bytes_unread` the rest): `max_seconds` 8 ends at 8.06 s, and SIGTERM answers `partial` with the coverage in 0.03 s.
- Smaller: a failure the last resort catches in `recovery_key_scan` printed the exception text as it was (it goes through the names rule now, as in the other two tools); the error answer for a result that cannot be written (`archive_probe`, `recovery_key_scan`) carries `status_basis`; 7z's own message "wrong password" is looked for before the member list only, so a member named like it is not read as a header message; the cache of judged strings is bounded by its size (16 MiB of text) as well as by its number; the claim that `crypto_id` prints no bytes of the file is stated as it is (the header's numbers, the sample's entropy and a LUKS2 label that is not identifier-shaped are printed).
- Documented, not changed: a program that the 7z started itself survives a SIGKILL of the tool (the parent-death signal covers the 7z only, on Linux; on macOS there is none and the 7z survives); the hard stop is the clock's, not the work's (the timer stays armed while the answer is sealed, so an answer too large to seal within `max_seconds` + 5 s is replaced by the short partial one, and a page fault in a mapped file or a read that sits in uninterruptible I/O, such as a cloud-evicted file or a dead share, cannot be ended until the system call returns: not tested with such a file); `limit` has no upper bound (a `limit` of a billion puts every row on stdout); a ZIP member with method 99 and the encryption flag clear is `protected: false` (7-Zip and `zipfile` agree), and the flags of the local headers are not compared with the central directory's.
- Tool versions: `archive_probe` 3, `crypto_id` 3, `recovery_key_scan` 4 (the parsers `archive_probe/3`, `crypto_id/3`, `recovery_key_scan/3`); pack 1.6.0. The pack's goal reads "the hash of the unlocked image (a hash of evidence, not of a secret)".
- Tests: `tests/pack-encrypted-containers-fixes.test.ts` (every finding, on the Zip64 fixtures built from the APPNOTE layouts, a stand-in `7z` that waits, a clock that runs fast and a file system that reads slowly) and `tests/pack-encrypted-containers-names.test.ts` (the blocks byte for byte, 300 draws per shape in five slots with the rates above asserted, the shapes that are printed asserted, every regular expression of the blocks timed on 4,096 and 32,768 adversarial characters, the output check with the first layer removed, the bound on what the rule is given, the cache bound, the look-alike letters) and `tests/pack-encrypted-containers-followups.test.ts` (the two families that made the token rule quadratic, as ZIP names and as 7z header strings and listing lines, each answered in under 2 CPU seconds; the clock read per entry, per string and per finding; an End record in a ZIP comment, after the archive and at the end of it, and a second archive appended, with a jar that holds a stored ZIP and an archive behind a stub as the cases that stay complete; a read that never returns, ended by SIGALRM and, with the signals blocked, by the watchdog thread alone, for all three tools; a mapped 7z header whose pages do not arrive; the timer disarmed on every path, and an error answer (`fail`) that claims the stop under the lock as the answer does, with the watchdog's moment placed by hand; the unexpected-failure text; a result that cannot be written).
- Not done here: the ZIP flags of the local headers are not compared with the central directory's (a cost of one read per member); the PDF and OLE search maps the whole file and has no partial answer past the clock beyond the markers found so far; the p7zip 16.02 listing format was not available to check. `encrypted_survey` and `ransom_note_scan` (ransomware-response) are another pull request's.
