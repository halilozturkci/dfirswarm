### Security: the memory-forensics pack no longer tells an agent to hash a secret into the ledger, and `mem_fs` no longer returns memory content in an answer

`credentials/material` told the agent to record a recovered secret's hash in the ledger (the worker prompt forbids a hash of a secret anywhere), put `aeskeyfind`'s keys on an ordinary job's stdout, and promised that a key scan's answer carries "the key's sha256 to record"; it also said "memory is where credentials are in the clear". It is rewritten: what to write about material is where it sits, its kind, its length and what it would grant, with a reference to a sealed output, never a value, a fragment, a masked shape or a hash; every job that can print or write a credential, a key, a command line, an environment block, shell history or the bytes around a match runs with `secret_output: true`; presence, reachability, access and exfiltration are four questions with their own evidence; the tool library's two AES scanners, which still print a digest of the key, are named with that warning. `triage/volatility`, `patterns/yara`, `strings/discipline`, `triage/no-framework`, `processes/injection` and `network/state` each carry a "Sensitive output" line and point at it.

`mem_fs` returned the whole text of any file it read, decoded with replacement characters, in its answer. It now follows the secret-safe output pattern of `recovery_key_scan` (`docs/packs.md`, "Secrets and sensitive output"): the answer is a locator (virtual path, output file, size, status) with no content and no digest; content is written only on `write_values: true`, only when it runs as a job, only under `$OUT/mem_fs` (mode 0600, created exclusively, never over an existing file), with sizes and digests in `export-manifest.jsonl` beside it; outside a job the request is refused before MemProcFS starts.

### Fixed: the memory-forensics pack's tools stop producing plausible wrong answers

- **`mem_carve`** cut a plain Prefetch record at its `SCCA` signature, four bytes after the record starts, so the Windows pack's Prefetch parser refused every plain record it handed over. A hit now has a `signature_offset` and an `object_offset` (null when the four bytes before `SCCA` are not a Prefetch version), a `validation` (header plausible, implausible, truncated, or unknown for a signature only) with the header's own declared length where it has one, the length requested and the length available, and the sweep's coverage. Hits are found in offset order, so `max_extract` takes the earliest candidates and the answer counts the ones it did not extract (it took them in signature-table order before). The preview is bounded by default (200) and every hit is kept in a JSON Lines file the answer names (`results_to` without `limit` held every hit in memory and in the answer). An extract is created exclusively, mode 0600, and never through a link: it wrote through a symbolic link planted at its target name, and now refuses and counts. Each extract's sha256, and the digest of the hit-list file, are in `extract-manifest.jsonl` in the extract directory and no longer in the answer.
- **`mem_fs`** has `list`, `text` and `export` modes. `export` copies the named virtual files byte for byte (nothing was byte-exact before, and the mount was gone before an agent could read it); `text` writes one UTF-8 file and refuses a binary one instead of decoding it with replacement characters; the engine's stdout and stderr are kept as files on success (they were discarded); one deadline holds over startup, reads, export and cleanup, and a failure names the phase and what the host has for FUSE; a file over `max_bytes_per_path` is counted, not cut; a virtual path that resolves outside the mount (a link) is refused for that item, and a link loop or a failed read is that item's status, so the answer is one document whose counts add up to the items requested (the check ended the worker thread alone and left an error document ahead of the answer, with the items after it uncounted). Whether MemProcFS contacts a symbol server is the job's network policy; the tool passes it no flag, and the pinned binary's behaviour was not verified.
- **`mem_profile`** called any file without a known header "flat physical memory (no container header)" and counted the sample's structures once for every window that covered them (a 12-byte file with one `regf` counted three). It says "unrecognised" and why, rejects an empty file, merges the sampled ranges and scans each on its own (no match is made across two windows that are not adjacent), reads an ELF core's byte order from `e_ident` and no longer fails on a short header, walks every range of a LiME file with its physical addresses and file offsets, checks a crash dump's run table for order, overlap, adjacency and the file's size and gives each run both `physical_start` and `file_offset`, bounds `scan_mb`, and renames `pages_4k` to `file_pages_4k_estimate` (it is the file length over 4096, not a count of captured pages), and gives a crash dump's `SystemTime` raw (`system_time_filetime`) beside the ISO time with its seven fractional digits (the 100 ns tick was dropped), naming a value past the year 9999 in `problems` instead of turning it into null. Each manifest says what it does and does not measure and carries `use` hints where one is defensible.

### Changed: the memory-forensics pack's skills say what each tool and plugin shows and does not show

All nine skills are rewritten or revised in the defender's voice, with observation, inference and conclusion apart and each negative bounded. `processes/injection` no longer calls a private executable region with a PE header "injected code": it is a candidate with named alternatives, and the dump-and-hash step is a sealed export that cites the job. `triage/volatility` uses the canonical `windows.malware.malfind.Malfind` and `linux.malware.malfind.Malfind` (the old names are deprecated forwarding classes in Volatility 3 2.28.2, and their dump options differ: `--dump` and `--dump-regions`), corrects the `isfinfo` filter advice (the filter applies only with `--live` in 2.28.2), keeps `--offline`, and says to inspect the `memory-windows` recipe's executed command and coverage until the base pack's change removes its online retry. `patterns/yara` says Volatility's YARA plugins need a Python binding no requirement installs, and which regions they skip. `acquire/images` stops saying every capture is a smear and that a snapshot is best, and gives no AVML command line it could not check. `triage/what-you-have` puts verification first and separates a container offset from a physical address. `triage/no-framework` stops promising "page-file structures" and names the Windows parsers as `mentions`, since this pack does not depend on the Windows pack. `network/state` no longer says "instant of acquisition" or treats a DNS cache as attribution. Every skill names the tools and programs its front matter lists and the other way round, so the pack leaves `tests/pack-links.pending`; `gcc` and `make` are in `pack.json`'s `unreferenced_ok` with the reason. `README.md` and `requires/host.json` say what `mem_fs` needs (`/dev/fuse` and a `fusermount`), that `avml` run in an analysis VM captures that VM, and that the YARA binding is not installed. New suite `tests/pack-memory-forensics.test.ts`, with fixtures from the formats' own layouts (a plain Prefetch record, DUMP_HEADER64, LiME range headers, an ELF identification) and a stub `memprocfs`, 23 cases, each of which fails on the old tools.
