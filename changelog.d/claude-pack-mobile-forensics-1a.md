### Security: the mobile pack's tools stop printing message text, protobuf strings and key material

`sqlite_freespace` returned the text of every fragment it found in a database's free space (deleted messages, and whatever else a free page held), `protobuf_peek` returned the text of every string field, the hex of every bytes field and a list of the strings, and the adb-backup recipe wrote the key-derivation values of an encrypted backup's header into `backup.json`. The three tools, and the recipe, now follow the secret-safe output pattern of `recovery_key_scan` (`docs/packs.md`, "Secrets and sensitive output"). `sqlite_freespace` answers where each fragment is (finding id, page, kind of region, byte offset, length in bytes and characters, encoding) and never its text. `protobuf_peek` prints a top-level varint and nothing else that holds a value: not the text of a string, not the bytes of a bytes field, not a number under a length-delimited field (binary bytes parse as fields now and then, and their "numbers" were its content: 12 of 16 key bytes of a token were printed that way), not a fixed-width value; each has its offset, length and reading and a finding id. A length-delimited field whose bytes are printable text is text, never a nested message (a tag byte is a printable character, so a 72-character token read as nested printed five of its characters as field numbers and lengths), and any other is read as a nested message only when it parses whole, has at least two fields, writes every varint in its shortest form, orders its field numbers ascending and keeps them at 300 or below (random bytes pass about once in 3,300; real Biome messages 17,871 times in 17,872); a binary value that does parse that way shows that structure, which is derived from its bytes. A window is held to the same rule: aimed (with `offset` and `length`) at the payload of a field the tool withheld, a window is that payload, so its rows, field numbers and varints are printed only when it is a message of at least eight bytes that meets the rule, and any other gets a status and counts, no row and no number in its reason. Both write the text, bytes or numbers only on `write_values: true`, only when the tool runs as a job (it is told to run with `secret_output: true`), to a 0600 file under `$OUT` created before anything is read (an existing file or link is refused, as JSON, and a second run in the same job does not overwrite the first), and refuse the request anywhere else. A file that is not SQLite is described by its size and the entropy of its first 4 KiB: its first bytes are no longer printed (they were content, or a SQLCipher salt). `manifest_db`, which reads more of a backup's plain files than it did, reports the key bag and the manifest key of `Manifest.plist` as present with a length, never as a value, a digest or a head, and a file's wrapped key only as present. The adb-backup recipe reports an `AES-256` header by its shape (lengths and the number of rounds) and no longer writes the user salt, the checksum salt, the IV or the master key blob into `backup.json`: they are what an offline attack on the backup's password starts from; a header line that is not a scheme word is reported as its length. All three tools withhold a path component shaped like a recovery password on every channel (the answer, the files it names, an error, a file id), give every call its own paging file (two calls that print alike no longer share one), keep the rows read before a failure in a file the error names, and write strict JSON (a number that is not finite is `{"_float": text}`) with JSON escapes, so a file name that is not UTF-8 no longer stops them. The tests plant the text, the bytes and the key material in the encodings a tool could print them in (raw, UTF-16, hex, base64, a sha256) and assert they are in neither the answer nor any file the tool wrote, apart from the values file, for `sqlite_freespace`, `protobuf_peek` (text, bytes and numbers) and `manifest_db` (the key bag, the manifest key, a wrapped file key); the adb-backup recipe's files are checked for the header values as written.

### Fixed: the mobile pack's helpers stop returning plausible wrong answers, and say what they did not read

- **`sqlite_freespace`** reported every "freeblock in page" fragment 4 bytes before its text (it scanned from `block + 4` and recorded `block` as the base), so a location cited from it was wrong. Every fragment is now read back from the file at the offset it reports and compared (`offset_verified`), and a freeblock fragment names its freeblock's own offset. It matched ASCII-range text only: it reads UTF-8 in any language and UTF-16 text (the database's own byte order, at either byte parity, for Latin, Greek, Cyrillic, Armenian, Georgian, Hebrew, Arabic, Devanagari and Thai; CJK, kana, Hangul and emoji only in longer runs, as a lower-confidence reading, and a candidate that mostly covers bytes already taken is not reported), and says which encodings it scanned. It trusted the file: the header is validated (page size, usable size, format versions, the declared size against the file), a partial last page is named, the freelist is walked with a cycle check, bounds and a comparison with the header's count, every freeblock chain is checked for order, bounds and loops (a loop was read 4096 times and stopped in silence), lock-byte and pointer-map pages are skipped and counted, the reserved bytes of a page are not read as its content, and the time limit covers the filter too (a filter that backtracks cost 5 seconds per fragment past a limit of 1). The status is `complete`, `partial` or `corrupt`, and a `-wal` or `-journal` that holds bytes is listed, said not to have been read, and makes the status partial; its manifest and note no longer say that is where the newest rows are.
- **`manifest_db`** converted times by trying the Unix epoch and then the Apple one and keeping the first whose year fell in 2005 to now plus two (a Unix time from 2004 was null, and the same value read differently as years passed). The epoch is now told (`epoch`: `unix` by default, or `apple`), the raw seconds are returned beside the ISO time, and the earliest and latest non-zero value read are in the answer, with `epoch.consistency`: how many times fall after the backup's own date or before 2007 under the epoch applied (the wrong epoch is a 31-year shift, not a range of decades). It took its metadata from the first dictionary that had a `Size`: it reads the keyed archive's root (`$top.root`, followed through UID references with a depth bound and a cycle check) and says per entry when the column is missing, not a keyed archive or malformed. It read a missing `IsEncrypted` as unencrypted and reported an encrypted backup as empty: the encryption state is `encrypted`, `not_encrypted` or `unknown`, an encrypted backup's `Manifest.db` is listed when it opens as SQLite (each entry `payload_encrypted`), and when it does not the answer says the listing is not available and what the file was. It joined every file id to a path (`../x` landed outside the backup) and knew only the sharded layout: an id is joined only when it is 40 hexadecimal digits and the path stays in the backup, both layouts are looked for, and each blob is present, missing, a directory, a link (never followed), not applicable or refused. It never read `Info.plist` or `Status.plist`: the device, the backup's version and date and its completion state are reported. It held every row and returned every one; the listing is an inline page and the whole in a file the answer names, in a stable order, with running earliest and latest times instead of every time kept. A `Manifest.db` with a `-wal` or a `-journal` is copied with them to a working directory under `$OUT` and opened there, never in place; a `Manifest.db` that is a link is refused and a companion that is a link is not followed (and the status is partial). A TEXT cell that is not UTF-8 no longer stops the listing, and a damaged page ends it with what was read kept and `read_error` named (status partial).
- **`protobuf_peek`** read the whole file and then sliced it from `offset`, accepted any `max_depth`, called a message with a group `looks_like_protobuf`, accepted a varint of any length and a field number outside the format's range, gave nested fields offsets relative to the nested buffer, and named a zigzag reading `as_signed`. It reads a bounded window (`length`, 8 MiB by default, 64 MiB at most) and says what lies after it and where to continue, checks the structure as the encoding defines it (a varint is at most ten bytes, a field number is 1 to 536870911, wire types 6 and 7 do not exist, a field that runs past its message is an error with its offset), reports a group as `unsupported`, returns absolute offsets and full field paths, names the zigzag reading and adds the two's-complement one, holds to `max_depth` (32 at most), `max_fields` and `max_seconds` and says when one ended the parse, and says `consistent_with_protobuf_wire_format` of a whole window that parsed (and not that it is protobuf).
- **`ios-ileapp` and `android-aleapp`** said `complete` ("iLEAPP ran every module") for a program that exited 0 and wrote any TSV, whatever its modules did; moved the one report folder out of the scratch directory and deleted the rest of the scratch tree; ran from the run directory, which is read-only in a job; and dispatched a zip by `zipfile.is_zipfile`, whose answer changed between Python 3.11 and 3.14. Each run now reads the program's own log, in the shape a real iLEAPP v2026.4.1 run prints (checked over twelve real runs' logs: 1,139 modules each; `[n/N] name [module] artifact started`, `... completed` or `... failed after`, `Found N records` with thousands separators (`Found 205,098 records`), `No file found`, `No data found for`, `Unsupported version for X for iOS 16.3`), for one outcome per module (`modules.tsv`: `completed`, `no_record`, `unsupported` for a module whose own gate does not take the operating-system version, `errored`, `errors_logged` for a module that completed but wrote a line with a word of failure: error, exception, failed, unable, could not, cannot, corrupt, malformed, invalid, permission denied, no such table, skipping and the like, `unknown`) and is `complete` only when the program exited 0, wrote a TSV report (a file under a `data/` or `media/` folder is a copy of a file the program read, and is labelled so in `index.tsv`), the log was recognised, every module is completed, no_record or unsupported, no line outside a module speaks of an error (a locator is given, never the text), stderr holds no line that the log shape does not explain, the log says how many modules it parses (an `Artifact to parse` line or the `[n/N]` prefix) and that many started, and its processing-completed line is there; the two streams are read as one account. Otherwise `partial`, naming the first modules. No log text is copied into the receipt. A module with no source file or no data is `no_record`, never "the artefact is absent". ALEAPP's log shape was not checked against a real run: a log that differs leaves every module unknown and the run partial. The program runs with its working directory and its temporary directory under the output (an output given as a relative path works), and every file it writes beside its report folder, in its working directory or in its temporary directory is kept and counted. A tar is recognised before a zip (a tar header whose checksum holds, or a compressed stream), so a tar whose last member is a zip is not run with `-t zip`; a zip is recognised by its own signature or by a readable end record (a zip with data before its first header is still one). A tar is scanned for the marker header by header beside the library, and an extended header that declares more than 16 MiB is not read. A log line is read to a bound and the rest skipped. A run never writes over an earlier run's report or coverage: it refuses and leaves both as they are.
- **`android-backup`** decompressed each piece of the payload without a bound on the output, accepted any numeric version and any encryption scheme, never checked the end of the stream, and called a backup cut at a member boundary complete. The output has a budget (`--max-decompressed-bytes`, 32 GiB by default) and a payload that expands past it is `partial`, names the budget and keeps the members listed; the rest of the zlib stream is read, within the budget, so its end marker and checksum are verified (`payload_stream`: reached, not_reached, truncated); the tar is followed header by header apart from the library, so an archive without its end-of-archive block is partial (`tar_end`), a header the library refuses (a checksum that does not match, a number that does not parse) ends its listing quietly and is now said with its offset, the members listed are compared with the headers counted, bytes after the zlib stream's end are counted (`bytes_after_stream`) and make the run partial, and an extended header that declares more than 16 MiB (the library would hold it whole in memory) is not read and is said; a header line that is not ASCII is reported as not ASCII and not by the decoder's message; a run never writes over an earlier run's files; the watch follows what the tar library follows (a pax `size` record, GNU sparse extension blocks), so a valid pax or sparse archive is complete; versions 1 to 5 and the schemes `none` and `AES-256` are read and any other is `unsupported`; a member name that is not UTF-8 is escaped (it stopped the recipe) and its exact bytes, as the tar reader returned the name, are in `path_b64`.
- **`ios-filesystem`** trimmed every leading dot and slash from a member name, kept only the last size of a database that occurs twice, held every artefact row and database family in memory and died on a member name that is not UTF-8. Names are kept as the tar reader returned them (`path_b64` is the exact bytes, `n` the member's position), every occurrence of a duplicated name is its own row, a database that occurs twice keeps both sizes and both positions (`|` joins them), the artefact rows are written as they are met and the database families are grouped in a scratch SQLite file under the output. The tar is followed as `android-backup` follows it: it is complete only when its end-of-archive block came and the members listed are the headers counted (a tar cut at a member boundary, or ended quietly by a header the library refuses, was `complete`), an extended header over 16 MiB is not read (a 200 MiB GNU long name took 648 MB), a compressed tar is decoded in pieces and its end marker checked, a main database with no SQLite suffix is found as the file a `-wal` or `-shm` belongs to (22% of the companion families of a real iPhone file system had one), `sqlite.tsv` has a `types` column (a link has the size 0 and is not an empty database), and a run never writes over an earlier run's output.

### Changed: the mobile pack's manifests and README say what is and is not measured

The three manifests describe what each tool measures and what it does not (fragments are text and not rows; a window is a window; a listing is a map and not a file system; a `-wal` is not read by two of them and opened in a copy by the third), carry the `use` their input allows (`sqlite_freespace`: the SQLite header; `manifest_db`: the name `Manifest.db`; `protobuf_peek`: none, since protobuf has no universal signature), and declare the new parameters. The README stops saying encrypted backups "return empty databases", that `sqlite_freespace` "recovers deleted rows", that the newest messages are in the write-ahead log and that a logical extraction cannot answer a question about deletion, and says what the pack does not provide: no decryption, and no password read. The two LEAPP recipes' `exclusions` and `covers` say a module the log does not account for is not covered and that the reports are a sensitive output.

Output fields that changed, for anything that reads these tools' answers. `sqlite_freespace`: `fragments[].text` is gone (the text is in the values file), `page_size`, `pages` and `freelist_pages_*` moved under `database` and `freelist`, `write_ahead_log` is `database.journal_mode_on_disk`, `head_hex` is gone from the error for a file that is not SQLite (`entropy_bits_per_byte_of_first_4096` is there), and `companions` is an object of `{bytes, examined}`. `manifest_db`: `encrypted` is `null` when unknown, `entries` is a page (`limit`, default 200; the whole is in `pages.entries.all_results`), `domains` is a list of `{domain, entries}`, `on_disk` is relative to the backup and only for a blob that is present, `created`, `modified` and `changed` are ISO UTC beside `*_raw`, `device` holds `Manifest.plist`'s `Lockdown` keys (the backup's `Version`, `Date` and `WasPasscodeSet` it used to hold are in `manifest_plist`), and `manifest_db_file.head_hex` is gone. `protobuf_peek`: `fields` are flat rows with `field_path` and absolute `offset` (a nested message's children follow it, with `depth`), `strings`, `problems` and `looks_like_protobuf` are gone (`structure` carries the status), `text` and `hex` of a string or bytes field are gone, `value` of anything but a top-level varint is gone (`value_withheld` says why), `as_signed` is `zigzag_reading`. The adb-backup recipe's `backup.json` has no `user_salt`, `checksum_salt`, `user_iv` or `master_key_blob`, its `coverage.json` has `payload_stream`, `tar_end` and `decompressed_bytes`, and `members.tsv` has a `path_b64` column; `ios-filesystem`'s `artifacts.tsv` has `n` and `path_b64` and its `sqlite.tsv` has `path_b64` and `members` (the size columns may hold `a|b` for a repeated name); the LEAPP recipes' outputs add `modules.tsv`, and their `coverage.json` a `modules` receipt.

Two new suites. `tests/pack-mobile-forensics.test.ts` (49 cases) builds its fixtures from the formats' own layouts (SQLite databases made by Python's sqlite3 and walked by the file format's rules, keyed archives made by plistlib in the NSKeyedArchiver layout, protobuf by hand from the wire format) and runs against the tools as they were before the fixes when `MOBILE_PACK` points at a copy of them; `tests/pack-mobile-recipes.test.ts` (38 cases) uses stand-ins for iLEAPP and ALEAPP that print the log lines a real iLEAPP v2026.4.1 run prints and write a report folder the way it does, and tars and adb backups built with Python's tarfile and zlib. All of them fail on the old code (the one for a filter that backtracks never ends there, the old filter having no bound) and pass under Python 3.12, 3.13 and 3.14. `tests/pack-parsers.test.sh` and the pack's own suite read the withheld text from the values file of a job.

### Fixed after review: the mobile pack's helpers close the channels the first fixes left open

- **`sqlite_freespace`**: `contains` was an oracle. It took any regular expression and the answer listed the fragments that matched, so with text you cannot see one call was one bit of every fragment, and a few hundred calls (or an alternation of guesses) rebuilt a token. It is refused unless `write_values: true` in a job run with `secret_output: true`, and then it only narrows the values file: the answer lists every fragment whatever the expression matched, does not say how many matched, and does not place a fragment on which the expression ran out of time. `max_seconds` is finite and at most 270 (a larger value, NaN or Infinity ended the tool at the harness's 300 seconds with no answer).
- **`protobuf_peek`**: a window aimed at the payload a first answer withheld (the answer names its `payload_offset` and `payload_bytes`) printed the payload's varints in full and its keys as field numbers, so 14 of 16 bytes of a token came back; a window is now held to the acceptance rule of a nested reading (above), a window shorter than eight bytes is not accepted, and an error reason carries no number derived from the bytes. Memory follows the window, not the window times the depth (a 63 MB file of 32 nested levels took 2.3 GB). A named pipe is refused instead of waited on, a field the depth budget kept from being tried as nested is counted (`fields_not_tried_as_nested_at_max_depth`), `resume_offset` says where a partial parse can continue, and the payload of a field read as nested is written to the values file on request, so nobody needs to aim a window at it.
- **`manifest_db`**: the listing went through the file-id index, so one damaged page of it cost the whole listing which the table still held (it reads the table in row order); a file cut inside its last page was `complete` (it is partial and says so); `max_seconds` was read every 500 rows, so 200 rows of a backtracking `contains` ran 100 seconds (the clock is read on every row and bounds `contains`); a backup whose `Status.plist` says it did not finish was `complete` (`completion` is finished, not_finished or unknown, and not_finished is partial); `filter` is scrubbed; `epoch.consistency` and the 31-year-shift wording replace "a range of decades".
- **The recipes**: see the paragraphs above (`Found 205,098 records` was read as no record, so a real run's unified-log module was `no_record`; `Unsupported version for` was an error; a log with no count and no end line was complete; stderr's facts were dropped; error lines outside a module and on stderr were not read; a tar whose last member is a zip was run as a zip; `android-backup` listed a quietly ended tar as complete and ignored bytes after the zlib stream; `ios-filesystem` said `complete` over a cut tar, missed 22% of real families and read a 200 MiB long name into memory; `android-backup` and `ios-filesystem` overwrote an earlier run). The tar watch is one block, byte for byte, in the four recipes that read a tar, and a test compares it with the tar library over every format the library writes, whole and damaged.
- **Tests**: the two assertions that failed on Linux (an escape compared with a parsed string, and a 148,903-byte command line) assert on the raw output and take the specification on stdin; the recipes' stand-ins print lines of the shapes in twelve real iLEAPP logs (thousands separators, records beside "No data found", a version gate); the bounded-memory tests run the tool under a peak-memory wrapper.
