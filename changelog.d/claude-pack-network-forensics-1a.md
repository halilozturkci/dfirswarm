### Security: the network pack's tools stop printing object names, request URIs and credentials, and keep their output private

`pcap_extract` wrote every exported object's name into `index.tsv`, and ran tshark without `-q`, which (per its manual) prints a line for every packet, request URIs included, into the `_logs/*.stdout` it kept; `network_log_summary` copied every raw line, the request target and the text of each unparsed line into its tables; `zeek_run` returned records of every log inline, up to `limit` each (`password`, `cookie`, community strings, URL user-info among their fields); `suricata_run` wrote its EVE logs with whatever mode the process umask gave. All four keep their output in a private directory (0700, every file 0600, the engine's own files included), say `out_dir_contains_secret_values` and name `secret_output: true`, and withhold the same strings, by one block of code carried in each (`tests/pack-network-withholding.test.ts` holds the four copies equal and the block to a table of shapes): a token, a key, a JWT, a session id, a Basic or Bearer credential, user-info (after `://`, after `//`, or bare as `name:password@host`) and a base64 token that holds `/` or `%2F` are withheld whole (none of the head of a token is printed), a URL loses its user-info and every query value, and a byte that is not UTF-8 is written as `\xNN`, never raising. It works by shape: a short secret that does not look like a token (a password in a path segment, a `user` column) is not recognised, and a name shaped like a hash, a GUID or a Bitcoin address is withheld wherever it is printed (the real value stays retrievable, below).

`pcap_extract` and `network_log_summary` follow the secret-safe pattern of `recovery_key_scan` in full: `write_values: true` (refused outside a job, created exclusively, mode 0600, before anything runs, given back if the run stops before it wrote a value; a second run in the same job is refused by name and leaves the first file) writes the real names, whole URIs and unparsed lines to one file under `$OUT`. `pcap_extract` moves an object name that is token-shaped or carries a query string (Wireshark names an HTTP object after the end of its request target, so `login.php%3fuser=bob&pw=x` is a name) to `withheld-NNNNNN<ext>`, never onto a name that is there, and always keeps the real name in `withheld-names.jsonl` in the private directory, with or without `write_values`; it writes no digest of an object under 128 bytes. `zeek_run` and `suricata_run` have no values file: Zeek's logs and EVE are the evidence and stay whole in the private, sealed directory. `zeek_run` scrubs every string of an inline record, in any field and any list, except identifiers, hashes, fingerprints, addresses and times, redacts URLs, withholds secret-named fields, an FTP PASS argument and the hash of an object under 128 bytes; `suricata_run`'s inline alerts carry addresses, ports and the rule's signature only.

### Fixed: the tools no longer outlive the program that stops them

`pcap_extract`, `zeek_run`, `suricata_run` and the `network-capture` recipe started tshark, Zeek and Suricata in sessions of their own. The harness ends a tool by killing the tool's process group (`process.kill(-pid, SIGKILL)`), which did not reach them: reproduced with a stand-in, Zeek went on writing `conn.log` into the output directory six seconds after the tool was gone, and tshark kept writing into `$OUT` after a job was sealed; the tools before this change ran their engine in the tool's own group and died with it. The engine now runs in the tool's group (a test ends a tool the way the harness does, by its group, and checks the engine and its child are gone), a deadline kills the whole process tree, on Linux the kernel also kills the engine if the tool dies, SIGTERM, SIGINT and SIGHUP kill what is running and leave a last word (`pcap_extract`'s receipt says `interrupted`, the recipe marks the interrupted step), no thread is used (the code that handles this is one block, held equal in the four files by the same test), and `timeout_seconds` is capped under the manifest's limit (3300, 1100 and 1000), so the tool, not the limit, ends a slow engine; `pcap_extract`'s deadline now counts its two preflights. The same `start_new_session=True` pattern is in other packs' tools (linux `journal_export` and `linux_triage`, memory `mem_fs`, and any tool that starts a child in a session of its own): it is not changed here.

It writes an explicit `suricata.yaml` that also defines the variables rules are written against (`HOME_NET` from `home_net` or the private ranges, and the usual address and port groups: this tool's assumptions, stated in the answer), or uses a `config` of the caller's; a config or a rules file from `inputs/` is refused. ### Changed: the network pack's tool manifests say what each tool reads and does not measure

Each manifest has a `use` (capture magic and extensions, log names), says what is and is not measured, names exactly the parameters its script reads (`tests/pack-network-manifests.test.ts` holds both to the script) and carries its raised version and the sha256 of its script. New suites (`tests/pack-network-*.test.ts`, 106 cases) build their captures from the pcap and pcapng layouts and their logs from the formats' own definitions, never from a tool's output, and stand in for tshark, Zeek and Suricata with programs that print what their documentation says they print: they prove each wrapper's logic and nothing about a real engine (whether a build lists an export type, applies `-Y` to an export, prints `http.file_data` for every body, loads a hashing policy by a given name, accepts the written configuration or produces a JA4 fingerprint is for the build the evidence is read with). The skills, README and `requires` follow in the pack's next pull request, and the two merge together: the README of this pull request alone still states the old 96-byte rule.
