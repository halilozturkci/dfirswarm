### Fixed: zeek_run, suricata_run, pcap_summary and the network-capture recipe stop aborting on one hostile line, print capture text only through the block, and say what they are when stopped

The second half of the network pack's review fixes (the first is the pull request before this one).

- **`zeek_run`**: an empty or longer-than-8-character `#set_separator`, `#empty_field`, `#unset_field` or `#separator` aborted the whole run (`ValueError: empty separator`, 54 of 5,200 fuzz cases); it is now a header problem of that log and its records are counted malformed. A JSON line nested 100,000 deep aborted it with a `RecursionError` (also `suricata_run`, 616 of 5,200 cases); a line nested deeper than 64 levels is now refused before the parser sees it, in both tools, so the same file gives the same answer on every Python (Python 3.14 parses 100,000 levels where 3.9 to 3.13 raise `RecursionError`; the test passes on 3.12 and 3.14). It is counted with its line number and kept whole in the malformed file (`suricata_run`: in `eve-problems.jsonl`, which holds every EVE line that was not read as an event; the answer still shows the first ten). What is printed as written is decided per log and kind of value: `service` is conn.log's analyzer list and a service principal name from the wire in kerberos.log (now scrubbed), `history` and `conn_state` are conn.log's only, an address field keeps an IP address, and the keys of `engine_diagnostics.weird.by_name` are scrubbed. A URL's host goes through the same rule as every other string. `suricata_run`'s inline alert slots are typed (an address, a port, an id) or go through the block, and a bad `home_net` entry is named by position, not echoed. A reporter message over 500 characters is shown with the count not shown and a pointer to `reporter.log`.
- **`pcap_summary`** refused a capture cut off mid-record and summarised nothing. It now summarises the packets before the damage and says so (`status` partial, `capture_read_to_the_end` false, `stopped_reading`). The text a capture says about its machine and interfaces (CPU, OS, application, interface name, description, filter) is printed through the withholding block like the other tools' text. A pcapng block the tool does not decode is measured and skipped, never read (a 250 MB block cost 525 MB of memory; a 160 MB decryption-secrets block now costs no more than the rest of the run, under 100 MB measured), a block it reads whole is held to a packet's size plus its options, classic records whose fraction field is a second or more and records longer than the snap length are counted, and the tool keeps its own clock (`max_seconds`).
- **The recipe** `network-capture` checks every field of every listing against `tshark -G fields` (a field the build lacks is named in the step and left out, not a failed listing), writes a directory of mode 0700 and files of 0600, marks `dns.tsv`, `tls.tsv`, `http.tsv` and `http2.tsv` as secret-bearing (the mark is informational: nothing in the harness reads it), records the field-list step as running while it runs, and says `status_basis`.
- **All of the pack's tools**: every answer carries `status` and `status_basis`, exit 0 means the engine ran, SIGTERM, SIGINT and SIGHUP end each tool with partial JSON on stdout (the recipe prints it too), and the tree-kill no longer waits on `ps` on macOS: it asks libproc for the children (a macOS call), believes an empty answer only when libproc has just listed the engine as the tool's own child (a sandbox that denies the call gives an empty list for a live child), and otherwise asks `ps` for ten seconds (the wait is back to ten: three seconds left the engine's child running for a `ps` that needed four). Only descendants of the engine are killed, and a program that has already been waited for is never walked or signalled (its pid may be another process's by now). The walk below the engine has no bound of its own now (it stopped at 4,096 processes on Linux, which left 3,000 of a 7,500-process tree running). Two cases still leave a tree running, and the block's comment says so: a `ps` that needs more than ten seconds (only where libproc and `/proc` are both absent), and a sandbox that denies both libproc and `ps`. The block is the same text in five files (`pcap_extract`, `zeek_run`, `suricata_run`, the recipe and the base pack's `archive_extract`). `zeek_run` and `suricata_run` declare `secret_output: "required"` in their manifests, and `pcap_summary` carries the shared withholding block (five byte-equal copies; the block itself is unchanged).
- **Words**: the skills tell the reader that only 100 SYN times per row are inline, that a hash, GUID or UUID is withheld by shape and recoverable in a job, that `zeek_run`'s inline view withholds token-shaped DNS labels (read `dns.log` in the sealed output), and where the recipe's tables are; the goal no longer asks for a "jitter", a stop that needs no window, or a clock offset that cannot be measured. The README follows the code. The earlier fragments of this pack no longer claim that four copies of the block exist or count 106 test cases.

Measured with Zeek and Suricata stand-ins (neither program is installed; whether a real Suricata accepts the written configuration, or what a real Zeek writes, is not established here), real tshark 4.6.9, Python 3.12 and 3.14 on macOS and 3.11 in a Linux container. Withholding is by shape; the shared block is unchanged.

### Fixed: the network pack's second review (beacon clock, recipe status, pcap_summary bounds)

- **`beacon_score`**: the tool's own clock covered reading only; the ordering and the measurement after the last value (about as long as the reading, 0.6 to 0.93 times at 3,000,000 events) were unclocked, and on a slow CPU the tool was killed at 60 seconds with nothing on stdout (Docker, one tenth of a CPU, shuffled file: killed at 60 s before; 41 to 49 s with a partial answer now, also at 0.15 and 0.3 CPU, sorted and shuffled). `max_seconds` is now the budget for the arguments, the reading and the measuring together: reading stops at two fifths of it (the tail takes 0.6 to 0.93 times as long as the reading at full speed, but about 1.4 times with a tenth of a CPU), and the interval list ends at it; measured again with a tenth of a CPU, shuffled: 41, 44 and 41 s (49 and 52 s at half the reading share), and 42 s with a twentieth of a CPU (57 s before). A series passed inline (`timestamps`) is parsed whole before anything else, which was outside the clock: three million floats at a tenth of a CPU were killed at 60 s with nothing on stdout (2 of 3 runs, 374 to 428 MB). It is now capped at 500,000 events and 32 MiB of arguments, past which the answer is JSON and says to use `timestamps_file` (3,000,000 inline: refused in under a second); 500,000 inline take 85 MB, and 41 s with a partial list at a tenth of a CPU (3 runs). The 336 MB figure is for a `timestamps_file`. The handlers for SIGTERM, SIGINT and SIGHUP are installed as the first statement of `main`.
- **`network-capture` recipe**: a listing made without a field the installed tshark lacks (named in the step as `fields_missing`) is now `partial`, with the fields named in `status_basis` and in `listings_without_fields`, never `complete`.
- **`pcap_summary`**: interfaces, interface statistics and section options are shown fifty at a time (the rest counted, said in a note, and all in a file the answer names), and a pcapng with more than 10,000 of any of them is read to that point only (partial). 200,000 interface description blocks took 847 MB and a 62.7 MB answer in 1.9 s; they now take 39 MB and a 20 KB answer in 0.14 s. The ordering and writing of the lists after the reading end 15 seconds before the manifest's limit whatever `max_seconds` was (it covers the reading only: 700,000 distinct conversations with `max_seconds` 2 still take about 9 seconds to write): past that the rows stop, the answer is partial, and `listing_cut_by_its_own_clock` says how many were written of how many. With `group: "endpoint"` the summing of the tuples into endpoints is under the same end (it was not: 23.8 s at 1,500,000 tuples before the first row, about 17 million tuples to pass 600 s); if it does not finish no endpoint row is listed, since a sum over some tuples is not an endpoint's sum (1,500,000 tuples with the end forced to 3 s: 82 s before, 41 s now).
- **Words**: `pcap_extract`'s `display_filter` says why the object count could be an oracle on a build that applies the filter to the export (it is not on tshark 4.6.9); `zeek_run` says it prints the names of the log files as Zeek chose them. The shared process block's comment names the right test and the right platform.
- **Not done**: a signal in the first 40 to 85 ms of a tool (interpreter start-up and imports, before `main`) still gets the default action; the old process block remains in `linux-forensics` (three files) and `reverse-engineering` (two files) for a later sync.
