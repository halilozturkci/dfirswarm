### Security: the reverse-engineering pack's document tool no longer prints a credential a document holds, and the pack stops saying the kernel prevents execution

`doc_probe` printed every external relationship target whole. A target is often a credential (user-info in the URL, a signed query string, a token in the path), and the part names it printed can be one too. It now withholds user-info, every query value, the fragment and token-shaped text from a target, and a token-shaped part name from the part list (an extracted part with such a name is written under a name that is not the secret); the length of the target is kept. The whole target goes to `doc-probe-values.jsonl` only when the caller asks (`write_values: true`), only in a job, in a file created exclusively with mode 0600 (a second run in the same job is refused by name and the earlier file is untouched; with nothing to write it stays an empty file and the answer says `written: 0`). The answer names the file and says `contains_secret_values`, and the manifest says to run the job with `secret_output: true`. `extract_to` writes in a job only under `$OUT`, creates each part exclusively with mode 0600 (nothing already there is replaced) and says extracted parts can contain secrets. `pe_info`, `entropy_map` and `fuzzy_hash` print header fields, structural names (import, library and section names), measurements and digests, and echo the path the caller named; none prints document content, a string table or a resource, so none withholds.

The README said the harness enforces non-execution at the kernel. A no-exec mount reduces accidental direct execution of a binary; it does not stop an interpreter from running a script or an application from evaluating a macro (the worker prompt says so). The README now says that, the tools' own texts no longer make the claim, and `triage/quarantine` follows in the skills change.

### Fixed: the reverse-engineering pack's tools stop returning plausible wrong answers

- **static-binary** took "complete" from the exit codes of its two child tools and wrote "complete static structure" into the index whenever `binary.json` was not empty, although `pe_info` can exit 0 with a header problem, a failed import table or one Mach-O slice of several. Each child's output now goes straight to a file; the recipe reads the parser's own `status` (complete, partial, failed, unsupported) and writes `coverage.json` with the parser statuses, the warnings (the parsers' problems), the limits hit, the errors and the structures not read; the index says what each file is with its status beside it and names the complete entropy profile and every table a parser kept whole. The entropy profile went to the caller's `$OUT`, outside the recipe's directory and outside the index; it now goes to the recipe's own directory. Detection checks enough structure to tell an executable from a coincident magic (a whole ELF header with a class and a byte order; a plausible universal-binary table whose first slice begins with a Mach-O magic, so a Java class file is not a Mach-O).
- **pe_info** read optional-header fields against the file's length instead of the header's declared size, bounded the import table by the file and not by its section, rejected a 52-byte ELF32 header, took "stripped" from a section count of zero, found an ELF's dependencies only through sections named `.dynamic` and `.dynstr`, read only the first slice of a universal Mach-O (both fat magics as big-endian), listed `LC_ID_DYLIB` as a linked library and missed weak and re-exported ones, named a nonzero certificate-directory size `signed`, and ended with a note that said a large virtual size with high entropy "is packed". Every field is now read through checked ranges inside the structure that holds it; every answer carries a status (complete, partial, failed, unsupported), the problems found, the limits hit and the structures not read. `signed` is `certificate_table_declared` with the table's offset, size and first entry's header (presence only: nothing is verified). An ELF's dependencies come from `PT_DYNAMIC`, then an `SHT_DYNAMIC` section found by type, with the string table found through the `PT_LOAD` that maps `DT_STRTAB`; `stripped` is true only when section headers are present and none is an `SHT_SYMTAB`, and null when they are absent. A universal binary lists every slice in the byte order its header declares (FAT_MAGIC and FAT_CIGAM, 32- and 64-bit), with its own load commands, linked libraries, segments, entry offset and code-signature location; thin Mach-O files of both widths and byte orders are read. Entropy is measured in chunks against a work budget, a table longer than the answer holds is kept whole in a file, and `size_entropy_pattern` replaces `packed_shape`.
- **doc_probe** read every relationship and code-related member with no budget; found relationships with a regular expression (single-quoted attributes and a prefixed element were missed); skipped an unreadable member without a word; counted `/Type /Page` as a page count and `/Encrypt` as "encrypted"; and told the agent a file "has been renamed" and that an external target "fetches when the document opens". A member is now read under a per-member budget, a total budget and an expansion-ratio limit, and a member that is over a budget, encrypted, corrupt or unsupported is counted and named, never skipped and never extracted cut. Relationship parts are parsed by a namespace-aware XML parser that refuses a DOCTYPE. The ZIP end record (zip64 included) is read by the tool, so no Python version's validator decides what a ZIP is. PDF and RTF results are marker observations with offsets (a PDF name ends at white space or a delimiter: `/JS` is not `/JSON`); the OLE answer is byte markers by encoding. An extension that disagrees with the code-related parts is said as a disagreement ("renaming history, application acceptance and execution are not established").
- **entropy_map** wrote `entropy-windows.tsv` into `$OUT` whatever it measured, so a job that measured two files lost the first profile; compared the threshold on the rounded value (a window of 6.99999 bits counted as 7); kept every window in memory and in the answer without an `$OUT`, and every high-entropy run in memory. The complete profile is now always a file, created exclusively under a name derived from the source or chosen by the caller (a taken name gets a new one and the earlier file is named); the answer holds a preview, the bytes processed, the final window's length, the schema version and whether the pass finished; the threshold is compared unrounded; runs are held up to 1,000 and the whole list is a file past that.
- **fuzzy_hash** ran ssdeep and tlsh with no time limit and unbounded captured output, took the first line of whatever they printed as a digest, and returned a null distance with a null reason when one file had no digest. Each engine now runs under a time limit with its whole output in a log file; a digest is accepted only with its own shape; every engine's result is a status; a comparison that cannot be made names the input that prevented it; each program's argv and what it reports as its version are recorded.

A new suite (`tests/pack-re-*.test.ts`, 96 cases) builds its fixtures from the PE/COFF specification, the System V gABI, `<mach-o/loader.h>` and `<mach-o/fat.h>`, the PKWARE APPNOTE, the OPC relationship schema and the literal tokens of PDF and RTF; 94 of them fail on the previous tools and recipe (the other two keep a behaviour that was right: a missing program is reported in the words the harness reads, and the builders lay structures at the specified offsets).

### Changed: the reverse-engineering pack's manifests, README and requires say what is and is not measured

`pe_info` and `doc_probe` carry a `use` (magic and extensions) so the library hint offers them for the files they read; every tool's description says what it reads, what it does not and what it does not show (no signature verified, no packing determined, no resolved PDF action). The README counts four tools and `file_type` from the base pack (it said five). `requires/host.json` declares `readelf` (binutils, as `strings` is), says in capa's entry that a match is a hypothesis over features it extracts (it said capa reads code "not from its strings"), and gives `gcc` and `make` an `unreferenced_ok` reason in `pack.json`.
