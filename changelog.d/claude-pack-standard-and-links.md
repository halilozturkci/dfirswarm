### Added: a written standard for a pack, and a test that holds the links between its skills, tools and programs

`docs/packs.md` has a new section, "Writing a pack that holds up": what a skill says about an artefact (what it shows, what it does not, what must corroborate it, a bounded negative, a dated time and version), how a tool and a skill handle secret material (no hash of a secret anywhere, no characters of a short one, values only in a `secret_output` file, nothing on a command line of a bundled tool), the contract every bundled tool holds to (fail loudly, bound and say so, detect the format version, provenance in every record, evidence as hostile input, an honest manifest, a regression test with an independent fixture), pinned requirements, and the links between skills, tools and programs. "Skill file format" now says what `tools:` and `requires_host:` list (what the body names), and the `pack.json` example carries the new optional `unreferenced_ok`.

`tests/pack-links.test.sh` checks those links over every pack and its dependency closure. A skill whose body names a tool, program or Python package that only a pack outside its closure carries, a `requires_host:` entry no pack of the closure requires, a `tools:` or `requires_host:` entry the body never names, a tool or program the body names that the front matter does not list, and a `depends` id that is no pack are bugs and fail the suite. A skill may list, under the new front matter key `mentions: [names]`, what it discusses and cannot depend on (a base skill saying what a Windows tool reads): a mention is exempt from those rules, counts as no use, and must name a tool, program or package some pack carries or requires. Three more rules are reports for now: every bundled tool is named by a skill of its pack or of a pack that depends on it; every program in `requires/host.json` and package in `requires/python.txt` is named by such a skill or listed, with a reason, in the new optional `unreferenced_ok: [{name, why}]` of `pack.json`; every skill names something of its own pack. `PACK_LINKS_STRICT=1` (0 or 1, nothing else) turns the reports into failures and ignores the list below.

The shipped packs already have 198 findings of the bug checks, so the default run holds them to a golden list, `tests/pack-links.pending`: one line per known finding (pack, kind, skill path, name), sorted, no line twice. A finding not on the list fails, a listed finding that no longer happens fails (its line goes), and a missing or malformed list fails, so the list only shrinks and a pack's own fixes delete their lines. Names are matched as whole words, a `.` between name characters being part of the name (`dissect.target` is not `target`); the suite's header says where that is wrong. A program named like an ordinary word (`log`, `make`, `strings`) counts only as a command in code (an inline span, an indented line, a fenced block with no language or a shell one). The suite also builds small packs with one defect each to prove every rule catches it, and seals, installs and verifies fixture packs carrying `unreferenced_ok` and `mentions`. No pack's files change.
