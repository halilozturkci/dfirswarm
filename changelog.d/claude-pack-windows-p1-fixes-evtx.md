### Fixed: evtx_query and evtx_carve end on a chunk that loops, read a dirty log to its end, and stop cleanly (windows-forensics)

python-evtx follows a chunk's string and template tables without a bound: a table entry whose next pointer names itself never ends, and nothing in the library has a clock. Both tools gave such a chunk to the library and had no deadline of their own (manifest limits 60 and 600 seconds): four of four runs on forged chunks hit the cap with no JSON, and `evtx_carve`, which writes its result when it finishes, lost every record gathered before the bad chunk.

- **A chunk is checked before the library sees it.** The 64 string chains and 32 template chains are followed with a seen-set; a chunk whose table loops or points outside the chunk is not read, is named (`chunks_not_read`, `chunks_not_read_tables`) and the run goes on to the next. Whatever else the library does is called under a timer of 8 seconds per chunk (`SIGALRM` raising a `BaseException` the library cannot swallow), after which the chunk is given up and named. The whole run has a clock of its own (57 and 590 seconds, under the manifests' 60 and 600): `status: partial`, `walk_stopped_by_time_limit`, and for `evtx_carve` the `resume_start` to go on from.
- **`evtx_query` reads the file to its end, not to the header's chunk count.** On a real dirty log (header count 5, six chunks in the file) it said `complete` with 749 records where `evtx_carve` found 757; a header count forced to 1 gave 149 records, `complete`. A chunk past the declared count that has an `ElfChnk` signature and passes the chunk-header checks is read and its rows say `chunk_beyond_declared: true`; one that has the signature and fails the checks is a problem (`partial`); an all-zero slot is free space; a declared chunk with no signature is named and not read. The answer carries `chunks_in_file`, `chunks_read_beyond_declared`, `header_flags` and `header_dirty`. A file that does not begin with `ElfFile` is refused as such, and a path that is not a regular file is refused as JSON.
- **Result files.** `evtx_query` wrote its result at mode 0644 under its final name, so a stopped run left a half-written file that looked like a result. It writes a private (0600) temporary file and places it at the end without replacing anything (the same bytes are named again, any other result takes the next free `-n`). `evtx_carve` named its files from a digest that held `contains`: hashing a guessed needle into the same list reproduced the printed name (`evtx_query` already kept the needle out of its name). The needle is out of the name; `chunk_limit` and `candidate_limit` are in it, and a rerun that stops sooner no longer replaces a larger result (20 lines became 5).
- **Signals.** SIGTERM, SIGINT and SIGHUP end the tool with JSON and exit 128 plus the signal, also inside a library call that never returns. `evtx_query` keeps what it had read in a file named as a partial (`partial_result_file`, not under the name of a result); `evtx_carve` finishes its result file and answers `status: interrupted` with `resume_start`.
- **`evtx_carve` keeps a record whose XML is not well-formed** (python-evtx does not escape a quote in an attribute) in the result file with `parse_error` and its XML, instead of dropping it with a problem line; it no longer prints every distinct channel inline (at most 100, `channel_count`, all in `all_channels`); and a chunk whose header passes but whose checksums fail and from which no record can be read is a problem line, not a clean find.
- Every answer and refusal carries `status` and `status_basis`. A final answer that holds text which is not UTF-8 no longer risks an encoding error, and an `out_file` that is not text is refused as JSON.
- New tests: `tests/pack-windows-forensics-evtx-bounds.test.ts` (looping string and template tables, a library call that never returns, a stop signal inside it, the time limit, a dirty log, rejected and signature-less chunks, malformed XML, result names, channels, the real python-evtx on the loop and on the dirty log). The evtx_query suite now reads real bytes (a file header and 64 KiB chunks written to the libevtx layout) through the stand-in library instead of a JSON description, so the paths that read the file directly are covered; the test that encoded "complete when every declared chunk is read" now states the new behaviour.
- Not changed here: the shared withholding of event data (command lines, names) and of the identifier slots of these tools; `evtx_carve` still does not read the slack after a recycled chunk's free-space offset (the skill and manifest say so).

windows-forensics is re-sealed and raised by a patch version. The other pull requests of this review (esedb_query, the registry readers) also raise it: the second and third to merge need the merge-prep step. The tool-library copy of `evtx_query` is the pack's tool, byte for byte.
