### Fixed: regkv, shellbags and amcache_apps no longer follow an index that repeats a list, and stop cleanly (windows-forensics)

An `ri` subkey index that names one list of 500 keys 2,000 times made `regkv`, `shellbags` and `amcache_apps` read a million keys from a 61 KB hive (1.2 GB of memory, 160 to 430 MB of output files, `status: complete` for two of the three). regipy follows an index element by element and the tools only checked a key's own list offset for a cycle.

- **Every list is read through the size of the hive.** A hive of N bytes holds at most N/76 key cells and N/20 value cells (an nk cell is at least 76 bytes, a vk cell at least 20). Subkey and value lists are read to that bound over the whole walk, a key named twice in one list is listed once, and what is past the bound is not read but said under `problems`. The same hive now answers 500 keys at 31 MB in 0.1 seconds, `status: partial`, with the reason in `status_basis`.
- **regkv numbers a repeated value name in linear time** (one forward pointer per name; the old loop started again at 2 for each duplicate: 16,000 values of one name took forty seconds, the tool's limit being thirty). A value really called `name (2)` keeps its place.
- **regipy's own messages are not printed.** For a text-typed value that is neither UTF-16 nor UTF-8 (a value under `Policy\Secrets` the tool withholds from its answer) regipy logged the byte and its position on stderr (21% of 16-byte and 63% of 64-byte random values). The messages are counted (`library_messages_withheld`, a problem line) and never shown.
- **Result files.** `shellbags` named its files from a digest of `[hive, roots, contains, max_depth]`: hashing a guessed needle into the same list reproduced the printed name. The needle is out of the name (only whether one was given stays), another needle takes the next free `-n` name. `regkv` put `max_nodes` (and the flags) into the name, and none of `regkv`, `shellbags` or `amcache_apps` replaces a result file that is there: the same result keeps its name, another takes the next free one (a rerun with `max_nodes: 50` had replaced a 1,280-line listing with 815).
- **Problems are lossless:** a page (the first 50 inline for `regkv`, 40 for `amcache_apps`) with the whole list in `all_problems`; `amcache_apps` cut its list at 20 with only a count. A missing key's sibling names are at most 200 (`subkeys_there_count`).
- **A time limit and signals.** Each tool stops at its own limit (27, 115 and 85 seconds, under the manifests' 30, 120 and 90), says `status: partial` and names the branches not opened. SIGTERM, SIGINT and SIGHUP end the tool with JSON (`status: interrupted`, exit 128 plus the signal) and remove the temporary file it was writing (before, the hidden temporary files stayed). Every answer and refusal carries `status` and `status_basis`.
- `amcache_apps` keeps a value whose name is one of its own fields (`layout`, `key`, `volume`, `sha1_raw`...) as `value:<name>` instead of letting it replace the field. `regkv` says a big-endian DWORD (a type regipy returns no data for) is not in its answer, and its manifest has an example.
- New tests: `tests/pack-windows-forensics-registry-bounds.test.ts` (an index repeated 300 times, 16,000 values of one name, a value list that repeats one record, a value regipy cannot decode, result names, no-replace, problem pages, the time limit, SIGTERM; twice, against a stand-in regipy and the real library). The hive writer in `tests/windows-hive.ts` can write an `ri` index and a repeating value list. The shared blocks (place, page, stop, hive bounds) are held identical across the three tools.

windows-forensics is re-sealed and raised by a patch version. Two other pull requests of this review (esedb_query, the event-log readers) also raise it: the second and third to merge need the merge-prep step. The tool-library copies of `regkv` and `amcache_apps` are the pack's tools, byte for byte.
