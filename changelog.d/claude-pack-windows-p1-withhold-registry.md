### Security: regkv, shellbags and amcache_apps withhold names, paths and data by shape (windows-forensics)

`regkv`, `shellbags` and `amcache_apps` printed key names, value names and data, shell item names and Amcache paths and hashes whole whatever they held (100% for every shape in the review's canary harness), and `regkv` withheld only by value name and place. Stacked on the pull request that bounds their lists.

- **One boundary on every way out.** A shared `BOUNDARY` block (the owner-approved hybrid: an allow-list for identifier-shaped fields, a deny-list for free text, an independent backstop) judges every key and value of an answer, of an error answer, and of every row of every file the tool writes. A name, path, key or URL is shown as it is only when it fits a plain grammar (a path component by component; GUIDs, SIDs, addresses, 0x numbers, times and hexadecimal ids up to 24 digits are plain); free text has token-shaped runs, user-info, the value after a secret's name, vendor-prefixed tokens, padded base64 and PEM keys withheld, on a copy with invisible characters taken out; a second check, written apart from both, reads it back, and a string it replaces makes a complete answer `partial` and is listed under `boundary.replaced_at`. A withheld text is `<withheld N characters: reason>`.
- **Slots.** Registry key names and paths are keys, value names are keys (many are paths), value data is free text, binary data is hexadecimal (decoded and judged by its printable text), shell item names and Amcache paths are paths, Amcache hashes are digests. The existing name-and-place withholding of `regkv` (SAM, LSA secrets, `Password*` values) is unchanged and runs first. The names of a missing key's siblings are listed in the hive's order, no longer sorted by their text.
- `shellbags` matches `contains` against the path as printed (after the layers and the backstop), and its result file names never depended on the needle.
- **`write_values: true`** writes the originals of everything withheld to `<tool>-values.jsonl` (mode 0600, created first, never replaced). It is accepted only in a job the harness runs as secret output: the manifest declares `secret_output: {"when_args": [...]}` and the tool checks `SECRET_OUTPUT=1`, and it is refused as JSON anywhere else before anything is made.
- **Measured** (the same grammar and rules as the owner-approved hybrid design, here as the shared `BOUNDARY` block, after the review fixes below; rates, not guarantees): 988 random plants per shape, 76 in each of 13 slots (text, host, name, path, key and URL, in a command line, a path, a key path, a URL path, query and fragment, and in XML), in five independent runs (4,940 plants per shape). Printed whole in 0 of 4,940 plants of each of these shapes, and no piece of 12 characters of one printed: prefixed tokens (GitHub, GitLab, Stripe, SendGrid, Google, npm, AWS key ids), JWT, PEM keys (one line and several), connection strings, user-info (an `@`, a `/` or a `+` inside the password, a random user of any length), NUL, zero-width and full-width splits, upper-case and glued prefixes (a GitLab token glued to hexadecimal digits too). AWS-shaped secret keys of 40 characters: 0 whole and 1 piece of 12 characters in 4,940 (the review of the previous round found 2 whole and 3 pieces in 4,940 plants of that shape, so the rate is small and not zero). The shapes that are not zero, as the range of the five runs over all slots together, with the worst single slot beside it (76 plants, so one plant is 1.3% and a slot is a noisy figure): base64 keys of 16, 20 and 32 bytes 0.0% to 0.3% (worst slot 1.3%; up to 3.9% in the review's end-to-end runs); random base62 of 20 to 40 characters 0.0% to 0.3% (worst slot 2.6%); random lower-case letters of 24 **9.2% to 10.6%** (worst slot 14.5% to 21.1%); a 16-character base32 seed **9.8% to 11.7%** (worst slot 15.8% to 21.1%). In a binary slot (a hexadecimal REG_BINARY value or table cell) the backstop decodes the hexadecimal and replaces every hex-encoded shape it claims (480 of 480 plants, on its own), but random bytes that hold no text are printed (200 of 200), and so is a hexadecimal secret written as text there (a 32-digit one in a table cell: 97%).
- **What it costs an examiner** (strings with any part withheld), measured on the user's own evidence with this block: a real 72 MB SOFTWARE hive (245,895 keys; 3,000 strings sampled from each class, the same sample judged by the block of the previous round and by this one): key-name components 3.7% withheld in part (4.1% before; the backstop replaced 0.4% of them, and none now), value names 1.0% (1.1%), REG_SZ data 0.9% (0.9%); one `Microsoft\Windows\CurrentVersion` listing to depth 3: 780 of its first 2,000 inline subkeys were replaced by the backstop (WinSxS component names, whose hash it took for a random run), now 0, and 3,094 of the 50,711 keys of that walk now 8; a full walk of that hive takes 4.0 s of CPU without a boundary, 17.0 s with the previous block and 20.2 s with this one. Real event logs (175 logs, 64,716 records of Security, Application, System, PowerShell, GroupPolicy and others): see the event-log line below. The corpora of generated names and the attack-sample logs quoted by the first version of this text were not measured again, and their figures (9,950 generated names, 17 of 1,040 whole event records) are withdrawn.
- **Not recognised, by design, and asserted by a test so that the sentence stays true:** a plain password or passphrase, a pronounceable passphrase, a UUID-shaped key, a hexadecimal secret of up to 24 digits in a name or of any length in a binary slot, random binary data with no text in it, anything under 16 characters in a name (75% to 100% of such plants are printed). Withholding is by shape; a file whose secrets matter is read in a job run with `secret_output: true`. Strings the shape rules change that are not secrets: numbers of 19 digits or more (handles, a Chrome field-trial handle, a mojo pipe name), unlabelled hexadecimal runs of 32 digits or more (the native-image directories), and the query values of a URL in a URL slot.
- `tests/pack-windows-forensics-boundary-registry.test.ts`: 300 random canaries of 14 shapes planted in a value's data, a value name, a key name, binary data, a shell item name and an Amcache path/publisher/value name (real regipy and the stand-in), the share printed whole asserted per family, the unclaimed shapes asserted to be printed, the backstop shown to replace the shapes it claims with the sanitiser removed, the values file and its refusals, and names and data an examiner must read shown unchanged.
- The block text is the same in every tool that carries it and in the tool-library twins, and is marked `SHARED BOUNDARY` so that the shared-block work can converge it with the other withholding blocks.

- **Review fixes (the shared block, byte-equal in every tool that carries it).** An independent review found the following; each is fixed once in the block and asserted by `tests/pack-windows-forensics-boundary-block.test.ts` on every tool of this pull request that carries it.
  - *A run of backslashes took quadratic time.* The two patterns that take out escaped invisible characters retried at every backslash of a run (64,000 backslashes: 47 s; a 128 KB hive with one such value: 38 s against the tool's limit of 30 s); a lookbehind makes them linear (64,000: 0.06 s; 262,144: 0.25 s). The same scan of every pattern, with 50 repeated shapes, their pairs and ten prefixes at two sizes (5,704 combinations), found one more quadratic pattern that the new order of the layers exposed, a JWT header of unbounded length; it is bounded. The test drives 224 of those combinations and asserts the growth, not the time.
  - *Renaming many names that become one placeholder was cubic.* 6,000 random 24-character value names took 77 s and 108 MB of output; each placeholder is counted now (0.3 s in the block). The keys of a dictionary that are not text are sealed as text instead of stopping the serialiser.
  - *The report of where a replacement happened printed the withheld key.* `boundary.replaced_at[].at` was built from the raw keys, so a key the first layer had withheld came out whole whenever a value under it was replaced by the backstop (38 shapes x 480 plants: 81 whole canaries). It is built from the keys as they are shown, or from positions, and read once more by the backstop.
  - *The deny-list ran before the position and prefix rules and cut the context they need.* A random user of 16 characters or more of `user:password@host` was replaced and the password left (599 of 600 plants in a text or host slot printed it; 346 of 1,000 over six slots), and a GitLab token glued to 11 or more hexadecimal digits printed whole in 7% to 10% of the plants of every slot but names. Layer 2 now reads the string first, in every slot (0 of 1,000 for each, by the layers alone, by the backstop alone and together), and a user the deny-list replaced is still found by its placeholder.
  - *User-info with a `/` or `+` in the password* (1.2% printed overall, 5.3% in a path slot), a user over 64 characters, and a named value that goes on past `&`, `;` or `,` (`Password=abc&Jt6FUw^Q$%a` printed the tail, 2.4%): the URL form takes a password up to the last `@` that is followed by a host (not a port), and a value ends at a separator only when a `name=` follows it. Pieces of 12 or 13 characters of an AWS secret key (3.6% printed its first 16 characters), a `ya29.`, `SG.` or `AIza` token (1.0% to 1.8%) that two cuts left between them are caught by the check below.
  - *The backstop was not independent of the layers.* It read only the text the layers left, skipped every typed field, did not decode hexadecimal and took prefixes in one case. It now reads the original as well: a window of 12 characters of anything it calls secret in the original that is still in what was shown replaces the string (the words of the text itself are subtracted first); a typed field must hold the characters of its type; hexadecimal is decoded and its printable text read as text (the 480 hex-encoded plants above); the vendor prefixes are read in any case (`GHP_`, `akia`); a value that is not text, a number or a container is sealed as the text `str()` makes of it instead of reaching the serialiser; and a placeholder is only a placeholder when its reason is one of a fixed list (a string that only looks like one was invisible to both layers). The status basis of a backstop-partial answer no longer begins with `; `.
  - *Other.* The values file keeps 16-byte digests, at most 200,000, of the originals it has written, not the originals. A signal that arrives while the final answer is being written is held until it is whole, so a second JSON is not started. A PEM key in free text is withheld whole by the first layer and no longer makes the answer partial through the backstop.
  - *Throughput.* Each rule of the first layer is tried only when the text holds a character or word it cannot match without, chains shorter than 16 characters are skipped before they are judged, and the verdict of a word is remembered: the block's own benchmark (an event row with 1.3 KB of XML) went from 771 to 1,721 rows a second, 4,257 records a second for `evtx_query` against 1,462 before (25,958 without a boundary), with the same result on 60,000 file paths and 40,000 lines of source text (the strings it changes are the same).
  - *`shellbags` and `regkv`.* `shellbags` with `contains` answered `complete` with no entry when the needle was in text the boundary withheld; entries that did not match and have text withheld in their path are now counted (`contains_blind_entries`), the answer says why in `status_basis` and is `partial`. The count is the same whatever the needle is, so it is no way to test a guess. `regkv` lists the subkeys of a key in the order the hive stores them (alphabetical by the raw names), so the order of withheld names among their siblings is evidence order, not computed by the tool (documented, not changed). `regkv` with 6,000 random value names in one key answers in seconds (see the test), not in 77 s.
- **Review round 3 (the shared block, byte-equal in every tool that carries it).** The sha256 of the block is `09a08dadc51811df8f66a82159e35ca6382598145401e4f4cffc919b0f05c7e2`, over the UTF-8 text from the first character of `# BEGIN SHARED BOUNDARY` to the last character of `# END SHARED BOUNDARY`, no newline after it (the slice the block-equality tests compare); the figure quoted for the block earlier could not be reproduced by any slice and is withdrawn. A second independent review found the following; each is fixed once in the block and asserted by `tests/pack-windows-forensics-boundary-block.test.ts` on every tool of this pull request that carries it, and, where it shows end to end, by the tool's own suite.
  - *`contains` was an oracle on text the backstop hides.* The filter looked at the text after layers 1 and 2, but the answer is sealed once more by the backstop and the residue check, so a true 10-character piece of a 40-character key that only the backstop replaces gave `events_matched: 1` and a wrong needle `0` with `status: complete` (about 40 x 64 queries recover the key). `contains_check` now looks at `sealed_text`, the exact text the answer prints (layers, then backstop; nothing is counted, listed or written for it), and the blind count is taken on the same text: a true piece, the whole secret and a wrong needle give the same matches, status and blind count (block test: 16 of 16 plants; end to end `evtx_query`, `evtx_carve` and `shellbags` with a key that only the backstop replaces, found among 2,400 planted). The sentences that said the filter 'is applied to the text that is shown, never to what is withheld' (manifests, skills, the block's comment) now say what is true. `print_order` sorts by the same printed text, so a name the backstop replaces is not listed by its raw text either.
  - *A hang in the residue check (`_S_PEMBODY`).* A lazy window of 100,000 characters was tried at every `PRIVATE KEY-----` of a string, and no test below 100,000 characters can see it: one value of 262,144 characters took 10 to 12 s, three of them in a 1.6 MB hive 36.8 s against `regkv`'s limit of 30 s, and a row of three such cells in `esedb_query` 30.3 s (its deadline is read between rows). PEM bodies are found with `str.find` now, at most 64 of them and at most 20,000 characters each: the same hive takes 0.5 s and the same row 1.2 s. The block test drives strings of 110,000, 262,144 and 1,048,576 characters, each led by a token that makes a layer change the string (so that the residue check runs), with 20 shapes of PEM, JWT, vendor-prefix, named-secret and base64 atoms, and asserts CPU seconds.
  - *Sealing had no clock.* The residue check collected every prefix match and walked up to 512 characters past each before cutting the list to 64: 16 values of 256 KiB made of `eyJ` took 20.4 s of CPU (30.2 s in the review, on a loaded machine) against `regkv`'s 30 s (the unprotected tool: 0.1 s), `password=` repeated 10.3 s for 8 values. Collecting now stops at 64 pieces, the JWT window is 300 characters (2,000 before), and `seal`, `row_object` and `answer_object` run on a clock: `SEAL_BUDGET` (10 s) from the outermost call and never past the tool's hard stop (`seal_stop_after`, the manifest's limit less two seconds). Past it every remaining string except one of 15 plain characters or fewer is replaced whole (`<withheld N bytes: backstop: the judging time ran out>`), counted, listed, and the answer is `partial`. The same hive now: `eyJ` x 16 values of 256 KiB 4.8 s (it took 20.4 s), `password=` x 3 values 1.1 s (2.5 s), PEM markers x 3 values 0.3 s (28.3 s).
  - *The residue check replaced event XML for an attribute named like a key (false positive).* `_s_pieces` took every padded-base64 match without the shape guard the backstop and layer 2 use (a length that is a multiple of 4 and a digit, `+` or `/`), so any record with another cut in it and an identifier of 15 letters or more before an `=` (`RelatedActivityID=""`, `EventSourceName=`, `processorArchitecture=`) had its whole XML replaced and the run made `partial`. The guard is there now (block test: 120 records, 120 replaced before, 0 now). On the real logs: the same 175 logs (64,716 records, up to 4 MB each: Security, Application, System, PowerShell, GroupPolicy and others) with the tool of the previous round and with this one: the XML replaced whole by the backstop 5.6% -> 2.0% of the records (Security 6.7% -> 0.1%, Application 8.8% -> 0.5%, GroupPolicy 4.0% -> 0.0%; what is left is real base64, certificates and `$defaultCreds`), runs ending `partial` 84 -> 45 of 175 (Security 13 -> 3 of 19).
  - *The order of a listing followed the rank of the raw names.* A hive stores a key's subkeys alphabetically, so a withheld name listed where the hive puts it sat between its neighbours and its first letter was bounded to the gap. `print_order` (the order of the text the answer prints, equal placeholders in a random order that is new every run) now orders the subkeys, the keys of a recursive listing and the values of `regkv`, the inventory keys and values of `amcache_apps`, the BagMRU slots and the names listed for a missing key of `shellbags`; the manifests say what the order is based on. Twin trees (plain names Alpha to Uniform, three withheld names starting at d, n and t in one tree and at b, x and z in the other) show the same places for the placeholders and no rank correlation over six runs of each.
  - *Rates and the component store.* The documented rates (8.5% for lower-case letters of 24, 11% for a base32 seed, 'none printed' for AWS keys) were lower or more absolute than the measurements; they are restated above from five runs with the worst slot next to the overall figure. The names of the Windows component store (WinSxS: `amd64_microsoft-windows-ndis-minwin_31bf3856ad364e35_0.0.0.0_none_<16 hex>`) were replaced by the backstop in bulk because their hash looked random; the backstop now judges a name, key or path with such a component taken out (lower case, a 16-digit token, a language or `none`, a hash of 8 to 16 digits; the placeholder of a 32-digit hash stands for one), and nothing in free text. The claimed shapes stay at 0 of 4,940 whole in the five runs above, and a secret dressed as a component (upper case, a long random word, a token as a word) is not exempt (asserted).
  - *Other.* A full-width token written as hexadecimal (UTF-8 or UTF-16 data) is read like a plain one (width folded before the printable views; 50 of 50 were printed). A `version`-typed field must have the shape of a version in the backstop too (a base62 string starting with a digit: 200 of 200 now flagged, 0 of 200 before). `sk-` is recognised with its first digit anywhere in 40 characters (the backstop alone missed 2 in 650). A field name with an acronym in the plural inside (`NumberOfGPOsDownloaded`, `NumberOfGPOsApplicable`) is a plain name. When any part of a free-text string is withheld, its line breaks, tabs and invisible characters are not kept in the text shown (it is judged without them; documented in the manifests); a string with nothing withheld is shown exactly as it is.

windows-forensics is re-sealed and raised by a patch version; the other withholding pull requests of this review also raise it, so the later ones need the merge-prep step.
