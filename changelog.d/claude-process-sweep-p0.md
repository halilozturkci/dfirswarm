### Changed: the shared PROCESS block ends what a program leaves behind, in all 62 carriers (the general and the windows text)

A program that exited by itself and left a process (one in a session of its own, or one that held none of the tool's descriptors) kept writing a file the tool then reported as `complete`; four review rounds found it tool by tool. The block now handles it once. On Linux `spawn()` makes the tool a subreaper (`PR_SET_CHILD_SUBREAPER`) before the first program, so what a program leaves is a child of the tool, and a new `settle()` ends it: stopped, what it started stopped with it, killed and reaped, for at most 3 seconds with the clock read for every process. It runs when a program leaves `ACTIVE` after it ended or was killed (`ACTIVE` is now a list whose `remove` does it), at the end of `communicate_bounded`, and inside `kill_all` (the stop signal). It never touches a program `spawn()` started (Popen keeps its `returncode`), a child the tool already had, a process kept with `spawn(argv, leaves=True)` or `process_keep(pid)`, or anything that is not a child of the tool; while a second program is running nothing is ended and the verdict is unproven. `process_verdict()` and `process_apply(answer)` are in the block: a carrier that calls `process_apply` where it prints its answer gets `program_group` (`subreaper`, `left_behind`, `unproven`, `notes`) and a `complete` answer turns `partial` when something was left or that cannot be ruled out; no carrier calls it in this change, so answers do not change here, only the files stop changing after they are measured. In the merged batch the carriers do call it: the macOS ones in claude-process-sweep-p1, windows-forensics in claude-process-sweep-p2, the network tools in claude-process-sweep-p3, the computer-forensics-base tools in claude-process-sweep-p4, the encrypted-containers tools in claude-process-sweep-p5, the mobile, linux and memory tools in claude-process-sweep-p6, and the reverse-engineering, ransomware-response and virtualization-backup tools in claude-process-sweep-p7 (read each fragment for which of its tools report a file a program wrote and which only a pipe). Where nothing is adopted (the kernel refuses, or the host is not Linux) only what the tool saw below a program is ended and the verdict is unproven; `NONLINUX_UNPROVEN_DOWNGRADE` is the one line that decides whether that alone makes an answer partial off Linux. `docs/packs.md` (section 8) says what a carrier calls and what the block does not reach; `tests/pack-shared-process-settle.test.ts` holds the cases for both texts and the audit's three repros.

### Changed: computer-forensics-base, encrypted-containers, linux-forensics, macos-forensics, memory-forensics, mobile-forensics, network-forensics, ransomware-response, reverse-engineering, virtualization-backup-forensics and windows-forensics carry the new PROCESS block

Every tool and recipe of these packs that starts a program through the block (and the tool library's `esedb_query`, `extract_stream` and `yara_scan`) has its leftovers ended before it reads what the program wrote; a late writer in a session of its own, a double fork, a chain, an orphan and its children, and a late append to a log by name are ended and reaped, and the tool's own children, the programs it started and a daemon kept on purpose are left. The reverse-engineering `capa-floss` recipe's own helper that asked for the subreaper is renamed (`own_subreaper`) so that it does not shadow the block's `become_subreaper`, and its `sweep_orphans` counts what the block ended, so an engine that left a process is still `partial`; `clr_inspect`, `unpack_safe` and `fuzzy_hash` count what the block ended in their own `left_behind`, so they still answer `partial` (not `complete`) for a program that left a process, and they no longer say that a process in a session of its own cannot be ended. The names `STARTED` and `CHILD_SECONDS` were already taken in the base tools, so the block's registries are `SPAWNED` and `LEFTOVER_SECONDS`. Every carrier's manifest carries the new script digest and a version one above the old (a recipe's by a patch), the four linux tools' `PARSER` label follows their manifest version as that pack's test requires, and the tool library's README lists the three twins' new versions. Each pack's version moves by a patch.
