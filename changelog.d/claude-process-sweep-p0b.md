### Fixed: the shared PROCESS block no longer keeps every byte a process holding a program's pipe writes after the program has ended (all 62 carriers, the general and the windows text)

- **A leftover that floods the pipe at full speed no longer holds the call for seconds and gigabytes.** `communicate_bounded` used `Popen.communicate`, which keeps every byte the pipes deliver, so a process a program left behind (a `setsid` child looping `os.write(1, ...)`) made one call hold gigabytes (1.2 to 5 GB measured) and run well past the second the READMEs and the changelogs promise; a caller such as `tcrypt_header` then decoded and parsed all of it. The block now reads the pipes itself and looks at the program after every read. From the moment the program has ended (or was killed at its deadline) it takes at most one second (`PIPE_GRACE`) and 1 MiB (`POST_EXIT_BYTES`, both pipes together), whichever is used up first; at the byte cap it stops reading, ends the holder (`reap_orphans`, `settle()`) and lets the pipes go. The measured case (a flood after the program exited): about 0.1 s and 20 MiB instead of seconds and more than a gigabyte.
- **The cut is said.** A call cut at the byte cap is counted in `PIPE_CUT["cut"]`, a note in `process_notes()` (so in `program_group.notes`) says it, and `process_apply` turns a `complete` answer `partial` with a sentence in `status_basis`. The return value of `communicate_bounded` is the same three-tuple, so no carrier changed; what the caller parses is the program's own output plus at most 1 MiB of what the leftover wrote. The silent holder and the slow writer are still let go about one second after the program ended, and a large legitimate output (50 MiB from a program that exits cleanly) is still returned whole.
- **What is not capped.** While the program is still alive the block keeps every byte, as before: a program's own output is its caller's to bound, and no output cap is known that all 62 carriers could take, so a flood that starts while the program still runs (or that a live program itself writes) is read until the program has ended or its deadline. The timing is unchanged apart from the post-exit cap. A reader that decodes or parses the output still bounds what it keeps itself.
