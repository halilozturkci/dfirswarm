### Fixed: keychain_open and apfs_inventory no longer answer complete over a file that a child of the program wrote or may still write; the macOS carriers use the shared settle() instead of a copy of their own

- **keychain_open and apfs_inventory call `process_apply`.** The reader of `keychain_open` (a shim that hands chainbreaker the items file as an inherited descriptor) or `fsapfsinfo` (whose stdout and stderr are kept as files) could exit 0 and leave a child that held that file and wrote to it later, in the tool's group or in a session of its own; the shared block already ended such a child before the file was counted and hashed, but the answer still said `complete`, with a file cut where the child was ended. The answer is now `partial` when `settle()` ended a leftover (`program_group.left_behind`, a line under `problems`, and for `keychain_open` the outcome stays `opened`), and every answer carries `program_group` (`subreaper`, `left_behind`, `unproven`, `notes`).
- **Where the absence of a leftover cannot be proven, a tool that reports a file a program wrote is at most `partial`.** On a host that is not Linux, or where the kernel refuses `PR_SET_CHILD_SUBREAPER`, `keychain_open`, `apfs_inventory`, `macos_triage` and the macos-artefacts recipe answer at most `partial` and say why (`program_group.unproven`, `problems`). `unified_log` already did so with its own check. The tools of the pack that run no program (`plist_read`, `fsevents_parse`, `knowledgec_query`, `macos_tcc`, `macos_login_items`, `safari_history`, `segb_read`) are not held to it.
- **macos_triage and the macos-artefacts recipe drop their own subreaper and group sweep.** The block's `spawn()` makes the tool a subreaper and `settle()` ends and reaps what the program left when it leaves `ACTIVE`, before the log, a size or a hash is read; the answer is made `partial` through `process_verdict()` and `process_apply()` (the recipe's coverage.json carries `program_group` at its top level; it was under `plugins.program_group`). The file check (a file that grew a second later, or a process outside the group that holds one open) stays in both, because it finds a writer that is no descendant of the program, which `settle()` cannot. `unified_log` is the one carrier of the pack without the block (it starts its reader with its own code and the macOS stop text) and keeps its own subreaper and sweep.
- Pack raised: `macos-forensics` 1.9.2 over the batch (keychain_open 3, apfs_inventory 5, macos_triage 3, the macos-artefacts recipe 1.0.2). Still open (listed, not chased): the stdout, stderr and items files hold what a leftover wrote before it was ended (the answer says so); a writer that is no descendant of the program (started through a service manager) is found only by the file check of `macos_triage` and the recipe, not in `keychain_open` and `apfs_inventory`; `unified_log` keeps a second copy of the sweep until it carries the block.
