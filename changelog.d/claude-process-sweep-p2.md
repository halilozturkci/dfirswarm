### Fixed: the windows tools that report a file a program wrote no longer answer complete over it when the program left a process behind, or when that cannot be ruled out

The shared PROCESS block already ends what a program leaves behind (`settle()`) before a tool sizes, hashes or reads what the program wrote; the windows-forensics tools now say so in the answer. Every answer of the tools below carries `program_group` (`subreaper`, `left_behind`, `unproven`, `notes`), and a tool whose answer would be `complete` is `partial` when `settle()` ended a leftover (the file is stable, but it may be short: what the process would still have written is missing) and, on a host that is not Linux or where the kernel refuses `PR_SET_CHILD_SUBREAPER`, when the absence of a leftover cannot be proven. `extract_stream` (the output, its size and sha256), `vss_stores` (stdout_file and stderr_file, a line under `problems`), `esedb_query` (the export; `process_problems`), `sigma_hunt` (the engine's result file), `srum_reader` (SrumECmd's and target-query's files), `yara_scan` (yara's standard error file and the match list), `lnk_jumplist` (JLECmd's CSV) and the windows-artefacts recipe (target-query's files, and a receipt that would be `complete`; `coverage.json` carries `program_group` at its top level, and a dissect-target row that left a process ends `partial` with a `process` field) answer so, and so do their tool-library twins `esedb_query`, `extract_stream` and `yara_scan` (byte for byte).

- **Which tools answer `partial` on a host that is not Linux, and why.** Those that report a file a program wrote: the eight above. `lnk_jumplist` is held to it only when JLECmd ran (lnkinfo prints on a pipe; a process it leaves is ended and counted in `program_group.left_behind` but the status does not change). A JLECmd that left a process is `not_run` for that jump list (its CSV may be short and is not compared) and the status is `partial`.
- **Tools that report only what a program printed on a pipe are not held to the non-Linux rule.** `registry_recover` (regfexport's counts; the recovered copy and the records are written by the tool itself) and `vss_materialise` (the copies are what icat printed on a pipe, which the tool wrote) keep their status where the host cannot adopt orphans (`program_group` says so). A process that holds the pipe is still ended: a copy loop and a count loop no longer wait for it until their own clock. `vss_materialise` answers `partial` when `settle()` ended a leftover of `vshadowinfo`, `fls`, `icat` or `fusermount`, and keeps nothing that came through such a pipe as a copy (`copy_status` `left_behind`); the `vshadowmount` call keeps `spawn(leaves=True)` (a FUSE daemon the tool unmounts itself) and its daemon is not counted. `registry_recover` ends a process that holds regfexport's output after one second, and says the counts are not trusted and not compared (`independent_reader.regfexport.why_not_finished`).
- **`esedb_query` records it in the export's manifest.** An export made while esedbexport left a process behind is answered `partial` by the call that made it and by every later call that reuses it, with the words of the call that made it; an export whose manifest has no such record (made by an older version of this tool) is made again. The version probe (`esedbexport -V`) and the recipe's `target-query --help` and `--version` now run through the block (they were `subprocess.run`), so a process they leave is ended too. `yara_scan` releases its reader thread by ending a process that holds yara's output pipe (the P0 change), and the answer is `partial`.
- **Not changed, stated.** A writer that is no descendant of the program (one started through a service manager) is found by none of this. The version probes that run before the first program of a tool (`sigma_hunt` and `yara_scan` ask the engine for its version with `subprocess.run`) still end only their direct child. The bytes of a late writer that exits while the tool is still reading the same pipe cannot be told from the program's: `vss_materialise` and `registry_recover` do not claim to.
