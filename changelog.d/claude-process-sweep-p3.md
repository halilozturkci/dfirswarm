### Fixed: the network tools that read files a program wrote no longer answer complete over a file that a process the program left behind may still write

- **zeek_run, suricata_run, capture_transform, pcap_extract, flow_reader and the network-capture recipe call `process_apply`.** The program (Zeek, Suricata, editcap or mergecap or tcpdump or text2pcap, tshark, nfdump, capinfos) could exit 0 and leave a process that held one of the files the tool then reads, counts, hashes or places (a log, `eve.json`, a derivative, an exported object, a kept stdout or stderr file), in the tool's process group or in a session of its own, or one that held no descriptor and wrote the file by name. The shared block already ended such a process before the file was read; the answer still said `complete`, with a file cut where the process was ended. The answer is now `partial` when `settle()` ended a leftover (`program_group.left_behind`, a line under `problems`, or under `errors` in `pcap_extract`, whose receipt.json says the same, or in the status basis of the recipe, whose coverage.json carries `program_group`), the `status_basis` no longer says the files are whole, and every answer of these tools that ran a program carries `program_group` (`subreaper`, `left_behind`, `unproven`, `notes`); a refusal and an early failure before a program ran carry none. The dry runs of `zeek_run` and `suricata_run` are held to the same rule, because they read and hash files the engine wrote.
- **Where the absence of a leftover cannot be proven, such a tool is at most `partial`.** On a host that is not Linux, or where the kernel refuses `PR_SET_CHILD_SUBREAPER`, a clean run of the six says why (`program_group.unproven`, a line under `problems`) and is `partial`; the owner's rule for a tool that runs a program and reports a file the program wrote.
- **conn_series, quic_inspect and tls_decrypt report what tshark printed on a pipe and are not held to that.** They carry `program_group` and answer `partial` for a process `settle()` ended (it may have held the kept messages file), but an unproven host alone does not make them `partial`. `pcap_summary`, `network_log_summary` and `beacon_score` start no program and carry no process block. None of the network tools starts a container; the programs run as children of the tool, so a leftover is a descendant the subreaper adopts.
- Pack raised: `network-forensics` 1.14.7 over the batch (zeek_run 16, suricata_run 15, capture_transform 4, pcap_extract 12, flow_reader 3, quic_inspect 3, tls_decrypt 3, conn_series 3, the network-capture recipe 1.3.7). Still open (listed, not chased): the kept files hold what a leftover wrote before it was ended (the answer says so); a writer that is no descendant of the program (started through a service manager) is found by nothing here; `conn_series`, `quic_inspect` and `tls_decrypt` still wait for end of file on tshark's pipe, so a process that holds the pipe silently runs the pass to its own clock (bounded by it) instead of being ended after the pipe grace. The `network-capture` recipe's `tshark -G fields` read is the same kind of reader: a process that holds its pipe stalls it to its own clock (300 seconds, `min(300, ...)`, then the run goes on) and is ended then, not after the pipe grace.
