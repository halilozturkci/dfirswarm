### Fixed: the reverse-engineering, ransomware and virtualization tools that run a program no longer answer complete over what a process the program left behind may still write, and three pipe readers no longer hold a call to its clock for a leftover

- **clr_inspect (with `decompile`), unpack_safe, fuzzy_hash and the capa-floss recipe report a file a program wrote, and now carry the shared block's verdict.** The block already ended a process the program left running (a child in the tool's group, in a session of its own, after a double fork, or holding no descriptor at all) before the file was read; the tools' own holder scans only found a process that still held the file, in the tool's group. Where the tool is a subreaper (Linux) the block's `settle()` does that work and the scan is kept only to look for a process that is no descendant of the program (it is also kept as the way to end a holder where the subreaper is off). The answer is `partial` with `program_group` (`subreaper`, `left_behind`, `unproven`, `notes`) and a line under `problems` (`errors` in the recipe's coverage.json) when a process was ended, and `limits_hit` names `process_left_behind` in clr_inspect and unpack_safe. A process the version probe of `ilspycmd`, `upx`, `ssdeep` or `tlsh` left counts too. The capa-floss recipe drops its own subreaper and its loop that killed every descendant, which the block's settle() replaces.
- **Where the absence of a leftover cannot be proven, such a tool is at most `partial`.** On a host that is not Linux, or where the kernel refuses `PR_SET_CHILD_SUBREAPER`, a clean run of these four says why (`program_group.unproven`, a line under `problems` or `errors`; `limits_hit` `process_not_ruled_out` in clr_inspect and unpack_safe) and is `partial`: the owner's rule for a tool that runs a program and reports a file the program wrote. `fuzzy_hash` is held to it when it keeps the engines' logs (they are named in the answer), which is its normal case.
- **authenticode_verify, doc_structure's second reading, ransomware_family_match and snapshot_chain_check (with `qemu_img`) report what a program printed on a pipe and are not held to an unproven host.** They carry `program_group` (a call that started no program carries none) and answer `partial` for a process `settle()` ended: what it would still have printed is not in what was read. `ransomware_family_match` was decided earlier not to be held to the non-Linux rule, and this keeps that: a clean run on a host that cannot adopt orphans stays `complete` (tested).
- **The static-binary recipe carries `program_group` in coverage.json.** It runs `pe_info` and `entropy_map`, two tools of this pack that start no program (tests/pack-re-process.test.ts bans a program anywhere else in the pack), so it is `partial` only for a process `settle()` ended and not for an unproven host. This is the one place the owner's rule is not applied as written, because nothing the recipe runs can leave a program behind; it is one line to hold it to the rule instead. The other tools of the pack (pe_info, pe_directories, elf_directories, macho_directories, go_buildinfo, marshal_inspect, doc_probe, entropy_map) start no program and are unchanged, as are the twins in the tool library.
- **The three hand-written pipe readers (clr_inspect's version probe, authenticode_verify, doc_structure's second reading) no longer hold a call to its whole clock for a leftover that keeps writing.** They looked at whether the program had ended only when the pipe was idle, so a leftover that wrote a line every 10 ms held `run_program` to its full `seconds` and `timed_out` was reported true for a program that had exited 0 (measured with a 20 s clock: 20.06 s and `timed_out` true; now 1.07 s and false). The program is now looked at at the top of every pass, its pipe is given one second after it ended (`PIPE_GRACE`) and let go, and `settle()` ends what holds it. A leftover that floods the pipe after the program ended used to be reported as the program printing past the cap (`capped`); it is now `flooded`, the reading stops after 1 MiB of it, and authenticode_verify and doc_structure say so. A program that never exits is still ended at its clock (`timed_out` true).
- **A matrix of pipe shapes holds every pipe reader of the three packs to its clock.** tests/pack-re-pipe-matrix.test.ts drives each reader (the three hand-written ones, the shared block's `preflight` and `communicate_bounded` in ransomware_family_match, snapshot_chain_check, the capa-floss and static-binary copies, and the two recipes' file readers) with a silent holder, a stderr-only holder, a stdin-only holder, a writer every 10 ms, a writer every 0.7 s, `yes`, a program that never exits and a program that exits 3 leaving a holder, and the four tools that read a pipe end to end: each answers inside its clock with a truthful `timed_out` and the leftover dead.
- Tests with real abandoned children (plain, stdout holder, setsid, double fork, rewrite, periodic; hold, tick and setsid for the pipe readers; a sitecustomize-made setsid child for the recipe) fail on the batch head and pass here: tests/pack-re-process-apply.test.ts, 64 cases, with the non-Linux and refused-prctl hosts.
- Packs raised over the batch: `reverse-engineering` 1.16.3 (clr_inspect 3, authenticode_verify 3, doc_structure 10, unpack_safe 3, fuzzy_hash 11, capa-floss recipe 1.0.10, static-binary recipe 1.1.9), `ransomware-response` 1.13.4 (ransomware_family_match 3), `virtualization-backup-forensics` 1.7.5 (snapshot_chain_check 12).
- Still open (listed, not chased): a leftover that is no descendant of the program (started through a service manager, a socket or another PID namespace) is found by none of these, except by the holder scan where `/proc` shows it holding the file; the kept files hold what a leftover wrote before it was ended; a leftover of a version probe counts in `program_group.left_behind` and makes the answer `partial` though no file of the run is affected; the shared block's `communicate_bounded` keeps what a flood writes in the second after the program ended (ransomware_family_match and snapshot_chain_check read it; a flood holder cost 14 s in one probe), which the block's own cap on bytes after the exit is to bound.
