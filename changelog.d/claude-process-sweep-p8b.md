### Added: the process sweep's coverage is a checked fact (tests/process-sweep-coverage.json and its test), and docs/packs.md says what the sweep covers and what it does not

- **A registry of every carrier.** `tests/process-sweep-coverage.json` has one entry for each file under `packs/` and `tool-library/` (outside `tests/`) that starts a program: the 62 copies of the shared PROCESS block, the files that start a program by code of their own, the tool-library twins and the shell recipes (80 entries). Each says its class, where that class is stated, and the test files that run a real abandoned child for it, or the gap. The classes: `held` (41: reports a file a program wrote or that the tool hashes or reports; calls `process_apply` or the function of its own that does the same, and is at most `partial` where the absence of a leftover cannot be proven), `pipe-only` (18: reports what a program printed on a pipe; `partial` for an ended leftover, not held to the unproven rule), `local-mechanism` (16: not on the block; `unified_log`, the disk-timeline recipe, `mem_fs`, five hand-written pipe readers of the base pack, three shell recipes, five library-only tools with a plain `subprocess.run`), `twin` (5: byte copies of a pack file), and `no-program` (none today; the class exists so that a file the discovery finds by mistake can be said not to start a program).
- **A test that fails when a carrier is skipped.** `tests/process-sweep-coverage.test.ts` is static (it reads about eighty sources, no program runs) and fails for a carrier found by the discovery (the block marker, `Popen(`, `subprocess.`, `os.spawn`, `spawn(`, any shell file) that is not in the registry, or a registry path that is gone or starts no program any more; a `held` tool whose file does not call what its `apply` names; a `held` or `pipe-only` tool with no call that makes a `program_group`; a listed test that is missing or does not mention the tool, or a `held`, `pipe-only` or `twin` entry none of whose tests has an abandoned child (setsid, double fork, late writer, holder, leftover); a `no-program` entry that starts a program; a twin that differs from its pack file; and a count of block carriers that differs from the census (62). Its checking function is exported and the test tries it on damaged copies of the registry (an entry removed, a claim broken), so a check that stopped checking fails.
- **Eight carriers do not make a cut pipe `partial`, and the registry says so.** A tool that reads a program's pipe through the block's `communicate_bounded`, `preflight` or `run_to_files` and neither calls `process_apply` nor reads `PIPE_CUT` leaves its status alone when a leftover floods the pipe past the 1 MiB cap (the cut is said in `program_group.notes`): `linux-target`, `audit_events`, `package_verify`, `conn_series`, `quic_inspect`, `tls_decrypt`, `lnk_jumplist` and `vss_materialise` carry `pipe_cut_gap`; `ransomware_family_match` does it through `process_notes()`, which it puts into its partial reasons (`cut_through`). The test fails for a new tool in that state, and for a `pipe_cut_gap` that has become stale. No pack code changes here.
- **Why there is no all-carrier late-writer run.** Each tool takes its own arguments, inputs and stand-in programs, so one table would repeat the per-pack suites, which already run a real abandoned child (plain, stdout holder, setsid, double fork, rewrite, periodic) against every wired tool: `tests/pack-*-process-apply.test.ts`, `tests/pack-re-pipe-matrix.test.ts`, `tests/pack-macos-abandoned-child.test.ts`, `tests/pack-macos-escaped-child.test.ts` and the base pack's `test_process_apply.py` and `test_pipe_shapes.py`. The registry names, for each carrier, the suites that do, and the test holds that.
- **docs/packs.md** (section 7, "What a program leaves behind", and a new short part in section 8) is brought to the final state: what the block does (`spawn`, `settle`, `process_verdict`, `process_apply`, `process_keep`, `leaves`), the post-exit cap of 1 MiB and one second with `PIPE_CUT`, the held and pipe-only rule and the unproven-host rule with `NONLINUX_UNPROVEN_DOWNGRADE`, what is not covered (a writer that is not a descendant, a flood that starts while the program is alive, the start-up window before the handlers, the tool-local mechanisms), and that the registry and its test, not a pack's changelog, decide which tools are covered. The sentence that a carrier with a reader thread settles before it joins the reader is removed: `yara_scan` does, the other readers do not.
- Findings the registry makes visible, listed and not chased: `apfs_inventory` reports what `fsapfsinfo` printed on a pipe and is held to the unproven rule; `backup_decrypt` is held although its child is this repository's own Python; five library-only tools (`fls_root`, `hdfs_node_icat`, `icat_root`, `sigscan_e01`, `volrun`) and `master_icat` have no leftover handling and no abandoned-child test.
