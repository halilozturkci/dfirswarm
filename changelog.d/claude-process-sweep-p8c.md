### Fixed: a pipe cut at the shared block's byte cap now makes the answer of eight more tools `partial`

The shared process block reads at most 1 MiB (and one second) more from the pipes of a program that has ended, then ends the holder and lets the pipes go; a call cut that way is counted in `PIPE_CUT["cut"]` and noted in `process_notes()`. A tool that calls `process_apply` turns a `complete` answer into `partial` for it. Eight tools read a pipe through the block and do not call `process_apply` (the process-sweep registry listed them as `pipe_cut_gap`): a flooding leftover that was not found (a host that cannot adopt orphans, so `left_behind` stays 0) left their answer `complete`, with the cut only in `program_group.notes`. The bytes read from that pipe can carry what the leftover wrote. Each now reads `PIPE_CUT` itself and says what happened.

- **`package_verify` 5 and `audit_events` 6 (linux-forensics), `conn_series`, `quic_inspect` and `tls_decrypt` 5 (network-forensics).** The tool's own `program_group_problems` gives a sentence when `PIPE_CUT["cut"]` is set: a process that held a program's pipe after the program ended went on writing, the tool read no more than 1048576 bytes of it and let the pipe go, so the version line read on that pipe may contain bytes the program did not write. It is in `problems` or `status_basis` and the answer is `partial` (`ok` false). These tools are pipe-only: the unproven-host rule is not applied to them, and a clean run on a host that cannot adopt orphans stays `complete`; only the cut and an ended leftover matter. The only pipe they read through the block is the version probe's (their rows, counts and files come from readers of their own); `PIPE_CUT` is one count for the whole run, so a cut while the version was read makes the whole answer `partial`, which is the accepted over-statement. `conn_series` with a `conn.log` starts no program and is unchanged.
- **The `linux-target` recipe 1.1.15.** `detect` names the OS from target-query's text; a cut on that pipe keeps `applies` (the name was accepted only as one word, so junk cannot have made it) and the exit code, and the line says `status: partial` with the sentence instead of `complete`. `run` reads the wrapper's pipe through the block and writes `summary.json` and `runner.stderr` from those bytes; a cut is added to the recipe's own verdict (`group_problems`, with the wrapper's summary composed as before): `coverage.json` and the printed line are `partial`, the sentence is in `errors`, and it says that the receipt itself is read from `artefacts/summary.json`, which the wrapper wrote.
- **`lnk_jumplist` 12.** lnkinfo prints on a pipe and is not held to the unproven rule, and JLECmd's output goes to files (so it has no pipe to cut). A cut in lnkinfo's pipe makes that call's output unusable: the link keeps lnk_parse's reading and `integrity.lnkinfo` says `ran: false` with the reason (it counts under `lnkinfo.not_run`), and the whole status is `partial` with a sentence, because "agrees with lnkinfo" cannot be claimed for it. Chosen over marking the rows, which are lnk_parse's own. Because `PIPE_CUT` is one count, the status reason is given for every cut.
- **`vss_materialise` 6.** A cut in the pipe of `vshadowinfo` or `fusermount` (the programs that must leave nothing) is counted by the tool itself and makes the answer `partial`; the store list, identifiers and creation times were read from that pipe. The vshadowmount daemon is started with `leaves=True` and is left on purpose: a cut of its pipe is not counted and does not make an answer `partial`. The copies come from icat's pipe, which the tool reads itself; that rule (`copy_status: left_behind`) is unchanged.
- **Tests that fail on the batch head and pass here** (a setsid writer, started after the program printed, floods standard output or standard error; hosts linux, darwin (`sys.platform` patched) and prctl-refused; on the last two nothing finds the flooder, `left_behind` is 0 and only the cut is left): `tests/pack-linux-process-apply.test.ts` (`package_verify` and `audit_events` version probes, the recipe's detect and run), `tests/pack-network-quic-inspect.test.ts`, `-tls-decrypt.test.ts`, `-conn-series.test.ts`, `tests/pack-windows-process-apply.test.ts` (lnkinfo, vshadowinfo, the daemon). A clean run is still `complete` on all three hosts. `tests/process-sweep-coverage.json` has no `pipe_cut_gap` left (the eight carry `cut_through`, the function that puts the cut into their reasons), its check (h) is unchanged, and its negative self-test now runs on a scratch copy of `audit_events` without `PIPE_CUT`, since no real entry is in that state any more.
- Packs raised: `linux-forensics` 1.12.7 (package_verify 5, audit_events 6, the linux-target recipe 1.1.15), `network-forensics` 1.14.9 (conn_series, quic_inspect, tls_decrypt 5), `windows-forensics` 1.7.32 (lnk_jumplist 12, vss_materialise 6). The shared PROCESS block is not touched.
- Still open (listed, not chased): the cut is a count for the run, not a place, so a cut during a version probe makes the whole answer `partial` (the rows of those tools are not affected); in `package_verify`, `audit_events` and the three network tools the program's main output is read by a reader of the tool's own, not through the block, so a flood there is bounded by that reader and not by `PIPE_CUT`.
