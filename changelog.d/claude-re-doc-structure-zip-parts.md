### Fixed: doc_structure reads a ZIP central directory that is past its limits in parts, and its scans each keep a share of the clock

A ZIP whose central directory declared more than 100,000 members, or more than 64 MiB, or more entries than its size can hold, was answered with the limit and no member listed: padding the directory hid every member. The directory is now read in parts, a block of 1 MiB at a time, and every member it holds is listed in the parts table (the name through the sanitiser, with its real name kept in the private names file when it is withheld; the sizes, method, DOS time and flags; the first `limit` rows in the answer and the whole table in its file) and counted under `members.listed`. None is opened, so `members.not_attempted` is the declared count and the answer is partial; the limit names how many members were listed and how many of the declared ones were not, why the listing stopped before the declared count when it did (bytes that are no entry, the end of the directory, the clock), and how many of the directory's bytes are entries.

After the member listing the scans share the rest of `max_seconds` instead of running one into the next. The relationship parts that can declare a VBA project stop at 90% of it, the check of every member for the compound file signature at 95%, and reading the VBA project parts keeps the last 5%; a scan that stops says which one it was and is a limit and a problem. Before, the signature check could use the clock up and leave the VBA project the package declares unread ("the clock ended before every member the package declares as its VBA project was read"). A case that measured wall time under a loaded host (the 118 KB PDF of four object streams: 21 s idle, 70 s loaded) measures the tool's CPU time, and the case that expects a complete answer within the tool's wall clock is skipped, saying so, when the host was too loaded to meet it. The tool is version 4 in this release. Pack `reverse-engineering`.
