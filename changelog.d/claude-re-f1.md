### Fixed: a name made of many `/`-joined random-looking pieces no longer takes minutes to withhold, in every tool that carries the shared withholding block

The block that withholds token-shaped text grew each flagged span across a `/` by searching the whole text before it again for every piece it took, which costs about the cube of the length: 500 pieces (13 KB) in a `.docx` relationship target took doc_probe 41 s, twenty library names of 3.9 KB each took pe_info 22 s (about 75 minutes at the 4,096 names an ELF may list), and nothing in either checked the tool's own clock, so the call ended with no answer. The growth is now one pass over the pieces of the text, each judged once, with the result of a walk remembered for the next one; 1,000 pieces take 0.02 s and the largest text examined (2 MiB of such pieces) under two seconds, and the spans are the same as before on every generated text the old code was compared with. A text over 2,097,152 characters is withheld whole, by its length (`<over-long text withheld N characters>`), and not examined. The block is the same text in the network, computer-forensics-base, virtualization-backup-forensics, reverse-engineering, encrypted-containers, memory-forensics and ransomware-response packs and the tool library (24 tools), changed in all of them together; the reverse-engineering tools that bound a faster copy after the block (doc_structure, pe_directories, capa-floss) no longer need it and use the block's own. doc_probe's relationship callback and pe_info's DT_NEEDED and Mach-O load-command loops now look at `max_seconds`, and say how many names were not read. Packs `network-forensics`, `computer-forensics-base`, `virtualization-backup-forensics`, `reverse-engineering`, `encrypted-containers`, `memory-forensics` and `ransomware-response`.

### Fixed: doc_probe reads a file by the strongest claim its bytes make, and lists the directory a ZIP end record names as well as the one the library reads

A file that began `{\rtf` and held `%PDF-1.4` in a control group was probed as a PDF only and came back complete with its object markers never looked for; a PDF with a ZIP appended was complete with the ZIP never examined. The magic number at offset 0 now decides (OLE, ZIP, RTF, PDF, then a PDF header or an RTF group start within the first 1,024 bytes), every other format the bytes claim, including a ZIP end record at the end of the file, is read as well under `also_read_as`, and a problem names both, so the answer is partial. For a ZIP the standard library reads the directory that ends where the end record starts, and 7-Zip, Office and libarchive read the one at the offset the record names: when they differ both are listed (`other_directory`, with its members as a table, the members only one names counted, and its code-related parts), and the answer is partial; a record whose offset leads to no readable directory says so. `limit` is at most 100,000, the relationship callback and the PDF and RTF marker scans look at `max_seconds` before each pass, and the tool is version 4.

### Fixed: pe_info withholds an import library name like every other library name, and its entropy pass stops at `max_seconds`

A PE import library name such as `http://user:password@host/a.dll?token=...` was printed whole, in the import table and in the table file, while the ELF and Mach-O library names and the PE export name went through the display function that withholds user-info and query values. The import library name now goes through it (listed in `withheld_fields` as `import_library`, with where it lies in the file). The entropy pass looked at no clock: a 1.5 GB section with a raised `max_entropy_bytes` took 31 s with `max_seconds` 1 and came back complete. It checks the clock at each 1 MiB, leaves the range unmeasured with the reason and the bytes read, and the answer is partial; `max_entropy_bytes` is at most 4 GiB. The tool is version 3.

### Fixed: fuzzy_hash's SHA-256 pass has a clock, and a comparison the budget did not allow is a problem

The SHA-256 of an input ran before any budget logic and without a clock, so a very large input was hashed until the harness killed the tool. The pass now ends at the call's budget: the file gives `sha256: null`, `sha256_status: not_attempted` and the bytes hashed, a problem says so, and `same_sha256` is null for two digests that were not made. A `tlsh -c` comparison skipped because the budget was spent between the digests and the comparison left the answer complete; it is a problem and the answer is partial. The tool is version 3.
