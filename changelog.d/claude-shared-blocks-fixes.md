### Fixed: tools that run a program no longer leave its tree behind on a stop signal or hang on a pipe it left open; a stop signal gets an answer from the first moment and never cuts one

- **A signal that lands between the fork and the book-keeping ends the whole tree.** A tool that starts an engine enters it in a list before it can be ended; a SIGTERM, SIGINT or SIGHUP that arrived after the engine was forked and before it was in that list ended the tool with exit 128 + the signal, said the engine was ended, and left the engine and everything it had started running (on macOS the whole tree, on Linux everything below the engine; the kernel's parent-death signal reaches only the engine). The signal handler now also ends everything below the tool itself, and what the tool started and lost: when the tool leads its process group, as the harness starts it, every other member of the group that is no longer below the tool. A process outside the group, and a tool run by hand in a shell's group, are never touched. An engine that is being listed is stopped first, so it forks nothing more between the listing and the kill. This is the shared process block of the network, linux, reverse-engineering, virtualization, base, encrypted-containers and windows packs, the windows recipe's own handler and the encrypted-containers tool's hard stop.
- **An engine that ended and left a program holding its pipes does not hold the tool.** The short programs a tool runs for a version or a build line (and the one-shot programs of the base, windows and linux tools) were read until the pipe closed; after the deadline the tool waited again, without a limit, for the last holder to let go, so a helper that inherited the engine's stdout and stderr made a finished call run as long as the helper lived. The pipes are now read in short turns: once the program has ended they are given one second, what it wrote is kept, what the tool lost is ended, and the call goes on. `mem_fs` had the same defect with its own pipes (it closed a stream a drain thread was blocked in, which waits for the last holder, so a 700-second helper made a call with a 2-second timeout last 700 seconds against the manifest's 600); it no longer closes a stream a thread is reading, ends what the engine left after it has stopped the engine, and states the real bound of its clean-up (95 seconds, not 65). Each step of the `mem_fs` clean-up is bounded and none can end the others: an unmount helper that does not answer is named as a problem of the clean-up, not raised as an unexpected failure.
- **A stop signal gets an answer from the start of the module, and the answer is never cut.** The handlers of the windows, ransomware, macos and encrypted-containers tools were installed when `main()` started, after the whole module had been read; a signal in that gap ended the tool with no JSON (or a KeyboardInterrupt traceback). They are installed where the shared stop block runs, with a minimal answer until `main()` installs the tool's own (only the start of the interpreter and the compiling of the file still come before). A second signal while the first is answered does nothing. The ransomware tools print their answer, and their failure answers, with the stop signals held, so a signal that comes while a multi-megabyte answer is being written no longer ends the process in the middle of it.
- **`memory-forensics`: a page that cannot flush its temporary file still removes it.** On a full disk or past a quota, closing the page's file raised before the hidden temporary file was unlinked, so `mem_carve`, `mem_fs` and `mem_profile` left `.<tool>-<hash>.jsonl-<random>` in the output directory. `abort()` now unlinks in a `finally` and raises nothing.
- Each fix has a test that fails on the code it replaced: a signal injected between the fork and the book-keeping, an engine whose descendant holds the pipes (a stand-in that starts a `sleep` inheriting its stdout and stderr), a signal at the end of the stop block in every carrier, a signal while the answer is written (the tool is blocked in the write), a page whose flush fails (a file-size limit), and a bystander process that must stay alive in each case.
