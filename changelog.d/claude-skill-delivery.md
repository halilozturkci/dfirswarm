### Changed: a run's packs reach every agent's prompt as an index, and the `skill` tool delivers plain Markdown once

The documentation said the pack index "goes in front of the agent once". The code did not do it: the index came back only when an agent called `skill()` with no id, the tool's own guidelines were never delivered, and the worker prompt never mentioned skills. Over 67 recorded runs (458 seats), 88 % of the seats never called the tool, and four recent runs had no fetch at all across 157 compactions. What changed:

- **The index is a section of every seat's system prompt**: the kickoff renders each pack's `skills/INDEX.md` (`extensions/skills.ts`, `scripts/seat-prompt.ts`) into `<sandbox>/.pi/APPEND_SYSTEM.md`, one line per skill with a pack's entries under its id and version, and Pi appends that file to its own prompt sections. Pi keeps those sections across a compaction and for the run a hand-off starts, which a tool result is not and which the prompt `before_agent_start` forces is not either: that prompt lasts only for the run a user prompt starts (shown through the real CLI in `tests/skills-e2e.test.ts`), so the extension only adds the section to a prompt that lacks it, and a seat that got it that way is told so. The budget, in estimated tokens (bytes / 4.245): an entry 40, a pack's index 1,000, the run's 2,500. A pack over its budget, or a run over the run budget, shows each pack's router only; a pack with no router is shown whole, and the kickoff and the `skills_index` trace row say what was shown, what was over, which entries pass 40 and where the section came from.
- **A pack may name one skill its router** with `router: true` in the skill's front matter (`scripts/pack.sh` refuses any other value and a second router, and writes a `Router:` line into `skills/INDEX.md` only when there is one, so no sealed pack's index changed). The routers themselves are not built here.
- **`prompts/worker-system.md` has a Skills section**: look in the index before working an artefact class, load the note with `skill(id)`, say in one line the rules you will apply, hold at most three bodies, `skill_done(id, note)` when a topic is finished, load again after a compaction what is still needed. The kickoff goldens carry it.
- **`skill` returns the body as plain Markdown** (no front matter, no JSON envelope: about a fifth fewer tokens per delivery), under a one-line header that names the pack and the cost. `needs` come back as ids with their token counts and are never loaded for the seat. The id is as the index lists it, or `pack:id`; an id more than one pack carries is listed as `pack:id`, and a bare one is served by the first pack and says which others have it. A body the seat already holds is answered "already in your context, loaded at turn N" instead of being sent again; a compaction empties that, and the hand-off header lists the notes the seat had loaded. A wrong id gets suggestions, not the whole id list. The tool's id example was the wrong shape (`windows/execution/prefetch`; 17 of 143 calls failed on a prefixed id) and so was `docs/packs.md`'s.
- **The two tools take turns.** Pi runs the tool calls of one assistant message at the same time; `skill` and `skill_done` now run one after the other in the order the message lists them (not `executionMode: "sequential"`, which would hold the message's `bash` calls back too), so a second `skill(id)` of the same message is answered "already in your context" and the three-note reminder counts the message's calls.
- **What a seat holds is read off the session.** At a compaction and when a process starts on a session that already has some, the ledger is rebuilt from the entries Pi says are in the model's context (`buildContextEntries()`): a compaction keeps the newest part of the history, so the bodies in it stay held, and a restarted seat is no longer sent a body its session already holds, with its turns counted on from the session's. A `skills_compacted` row says which bodies each compaction took out and which it kept.
- **A wrong id gets a close match or none.** A leading segment that starts a pack id of the run (`windows/...`) is dropped, dashes do not count, and only an exact id, the same last two segments, the same last segment or a directory of that name is named; nothing close says so and points at the index. Before, `windows/ntfs` was answered with a note about Windows memory.
- **The index is checked by its content, not its heading.** A prompt that has the heading but not this run's index (a custom prompt with a one-line heading; a file written for other packs) is a fault on the board and the trace, and the run's index is added after it. When the extension has to add the index, `skill()` with no id answers with the index instead of a pointer, and the hand-off header carries it, because a run a hand-off starts loses it. CRLF front matter is stripped; an index that lists nothing for a pack that counts skills is a fault; the tool's examples name no pack.
- **The goal files no longer tell the agents to call `skill()` for the index.** The sentence is out of the 46 `library/` entries and the calibration generator, and `tests/library.test.ts` refuses it: the index is in the prompt, and a seat that obeyed the sentence read it again (a pointer in full mode; the whole index, which defeats the router budget, when the prompt shows routers only).
- **Every load on the trace carries the file's sha256** (the value `pack.json`'s checksums hold) **and its token count**, with the pack, the turn, the front matter's `tools` and `needs`, and whether it was a re-load after a compaction.
- **`skill_done(id, note)`** records that a seat is finished with a body and marks it releasable in the seat's ledger. Nothing is released yet: `SkillLedger.releasable()` is where an unloader takes it up.
- **The kickoff passes Pi `--no-skills`** to every agent (host panes, the probe, a VM's launch script), which keeps Pi's skill directories (`~/.pi/agent/skills`, `~/.agents/skills`, `.pi/skills`, the `skills` setting) out of a seat's prompt. Verified in Pi 0.87.1's source (`dist/cli/args.js`, `dist/core/resource-loader.js`) and by a test that plants a skill and reads the seat's first prompt. It does not reach a skill path an operator's extension adds or context files (`AGENTS.md`); `docs/usage.md` says what still enters.

### Added: the context audit and the console's Packs tab count what each seat did with the skills

`scripts/swarm.sh context <id>` gains a skills table and findings: whether each seat's prompt carried the index, the bodies it loaded and their token cost, how many a later row names or uses (a proxy, and labelled as one), how many a compaction summarised out of its context, how many it loaded again, the ones it marked done and the calls that named no skill. The Packs tab shows the same, per agent, counted over the whole trace (the view's trace is a tail, so the old per-skill counts were short on a long run). The code is shared (`ui/src/lib/skill-metrics.ts`). An index counts only when Pi's own prompt carried this run's whole (not the extension's, not a stale file's); "taken out by a compaction" reads the `skills_compacted` rows and says when a trace only has `compact_done` rows (an upper bound); loads from rows written before the harness recorded a skill's tools are counted and said, because for them only a mention of the id can show use.
