### Added: virtualization-backup-forensics: a guard on `_S_LINE`, and the free-text and false-positive rates of the one BOUNDARY text, measured

`_S_LINE` (`[ \t]*line[ \t]+[0-9]`, the second check's "line N" pattern) is still in the one BOUNDARY text, in all 16 carriers, and is quadratic under `.search` on a run of spaces or tabs (2.6 s at 32 KiB). Every carrier calls it with `.match` at one position, which is a linear step. `tests/pack-boundary-s-line.test.ts` pins that: it scans every `run.py` under `packs/` and `tool-library/` that defines the name, and fails on any use that is not `.match(` or `.fullmatch(` (a `.search`, a `.sub`, a bare use); it proves itself on a planted source. The tools' manifests (versions 6, 8 and 6) and the pack (1.2.1) are resealed; no tool code changed.

The rates below were measured on the text as it is now, with a script kept outside the repository: the tool loaded as a module, each string judged by `seal_text` as the field kind says, random plants from a fixed seed, 95% Wilson bounds. The three tools give the same figures for free text and for the corpus (they carry one text).

### Added: virtualization-backup-forensics: `backup_audit_normalise` reads Proxmox Backup Server task log files (format `pbs_task_log`), and every answer carries its provenance

The Proxmox Backup Server writes one log file per task (`tasks/<XX>/<UPID>`): lines of `<RFC 3339 time>: <message>`, the last one `TASK OK`, `TASK WARNINGS: <count>`, `TASK ERROR: <message>` or `TASK unknown`. The shape was read from the Proxmox source that writes and reads these logs (proxmox-rest-server, `worker_task.rs`, the master branch served by git.proxmox.com) and the Proxmox Backup documentation (the page "Backup Client Usage", whose title read "Proxmox Backup 4.2.8-1 documentation"), both retrieved 2026-11-03. The documentation lists no message texts, and shows `TASK OK` only once; the line shape and the closing lines come from the source. The reader is built from that, and has not been checked against a real export; the fixtures of its tests are synthetic.

- A line is `<RFC 3339 time>: <message>` or a bare `TASK ...` line; any other line (no time, a localised time, a time with a space for the `T`) is counted `unparsed` and located, never guessed, and makes the answer `partial`. A log that does not end with a `TASK` line, and an empty file, are `partial` with the reason. A line over `max_line_bytes` is located and not read. The clock is tested on every line.
- A time with an offset is converted and its basis says so; a time with no zone stays raw unless `time_zone_offset_minutes` is declared, and is never assumed to be UTC.
- The category of a message (retention_gc, retention_prune, retention_remove, verification, sync, backup_start, backup_end, other) comes from a keyword table of this tool, and the event says that; the closing line is a `task_end` with its result. A datastore name in a few message forms is the event's `object`. The message text is not printed (its length is), and goes to the `write_text` file of a `secret_output` job.
- `format: auto` does not recognise it: a timestamped first line is no unambiguous signature. The reason for an unrecognised file names `pbs_task_log` when the first line has that shape.
- Every answer now has `provenance`: for each format read, the product, the source kind, `schema_basis` (`vendor_documentation` for this format, `synthetic_fixtures` for the Proxmox task index and vzdump log readers, `caller_declared_mapping` for a declared format), `validated_against_real_export: false`, and what the reader was built from.
- The tool is at version 7 and parser `/3`. `backup_destruction_correlate` of the ransomware-response pack reads only `backup_audit_normalise/2` answers and refuses `/3` by name (its manifest says `/3` is not read until it exists): it needs its own change before it reads this tool's answers. The pack is at 1.3.0; the README and the skills still say a Backup Server task log is not read (their change is a later one).

New: `tests/pack-virtualization-pbs-task-log.test.ts` (13 cases: a clean log, provenance, an unknown line, a missing closing line, zoneless time, retention events, a failed task, a 10 MB line, NUL and invalid UTF-8, a million lines within `max_seconds` with the whole list on disk, SIGTERM, canaries, the `auto` hint). All 13 fail on the code before this change.

### Added: virtualization-backup-forensics: `backup_audit_normalise` reads Proxmox Backup Server configuration files (format `pbs_config`)

`datastore.cfg`, `prune.cfg`, `sync.cfg`, `verification.cfg` and `remote.cfg` are read as settings records (section type, object id, property, value), from the Proxmox Backup documentation page "Configuration Files" (its title read "Proxmox Backup 4.2.8-1 documentation"; retrieved 2026-11-03). The page lists the properties of each type, and shows its examples indented with spaces; it does not say whether a tab is allowed, so both are read. The reader has not been checked against a real file; its fixtures are synthetic.

- `format: auto` recognises the file by its documented name together with a first section of that file's type; a file of another name is named with `format: pbs_config`.
- The retention settings (`keep-hourly`, `keep-daily`, `keep-weekly`, `keep-monthly`, `keep-yearly`, `keep-last` as numbers; `gc-schedule`, `prune-schedule`, `schedule`, `notify` as written) are marked `retention_setting`. A `keep-*` that is not a whole number, or a `notify` that is not `gc`, `prune`, `sync` or `verify` set to `never`, `always` or `error`, is unparsed.
- A section type or a property the page does not list is counted `unparsed` and located (the property lines of an unread section too), with no event, and the answer is `partial`; so is a section that lacks a property the page requires (for example a `prune` section with no `schedule`).
- The value of a comment (free text), of a password and of any property whose name says key, token, secret, credential, passwd or passphrase (`password` in `remote.cfg`, the encryption-key properties of `sync.cfg`) is not printed: only its length is. It goes, with the section and property, to the text file of a `secret_output` job (`write_text`). Every other value is sealed like any other string.
- The tool is at version 8 and the pack at 1.4.0; the parser stays `/3` (the shape is additive).

New: `tests/pack-virtualization-pbs-config.test.ts` (9 cases: each file type, retention settings, unknown section and property, auto recognition, the password and a canary in every property of `remote.cfg` and `sync.cfg`, NUL bytes and invalid UTF-8, a 10 MB line, a million properties within `max_seconds`, SIGTERM). All 9 fail on the code before this change.

### Added: virtualization-backup-forensics: `backup_audit_normalise` identifies Proxmox Backup Server data blobs (format `pbs_blob`), without decrypting or inflating them

A data blob is an 8-byte magic, a 4-byte little-endian CRC32 of the bytes after the header, and the payload. The four magics (uncompressed, compressed, encrypted, encrypted and compressed), the header sizes (12 bytes, 44 for an encrypted blob), the CRC and the manifest's field names were read from the Proxmox Backup source (pbs-datastore: `file_formats.rs`, `data_blob.rs`, `manifest.rs`, as served by git.proxmox.com), retrieved 2026-11-03. The reader has not been checked against a real datastore; its fixtures are built from the layout.

- `format: auto` recognises the four magics (no text file begins with them). A chunk index (`.fidx`, `.didx`) is not a data blob and stays unrecognised.
- Each blob is an event with its kind, size, stored and computed CRC and what became of its payload. A CRC mismatch makes the answer `partial`. The CRC of an encrypted blob is `not_checked`: the source read shows the CRC taken over the bytes after the header, but not the header size the code uses for an encrypted blob.
- An encrypted blob is identified and never decrypted. A compressed blob is identified, its payload is checked for a zstd frame start and counted, and not inflated (zstd is not in the standard library; a pinned dependency is the owner's decision). Both make the answer `partial`, with the reason.
- An uncompressed `index.json.blob` of up to 16 MiB is read as the snapshot manifest: one event for the snapshot (type, id, `backup-time` as UTC) and one per file (name, size, checksum, crypt mode). An entry that is not `{filename, size, csum of 64 hexadecimal digits}`, JSON that is not a manifest, and a nesting bomb are `unparsed` and located. An unknown field is tolerated and counted. An uncompressed `client.log.blob` is read line by line as free text (its lines are not printed). A payload over 16 MiB has its CRC checked and is not read.
- A truncated header, and a magic that is none of the four, are named and not read. The tool's table of field kinds takes `filename` as a path and `csum` as a digest (the table is the tool's own, outside the shared block).
- The tool is at version 9 and the pack at 1.5.0. Nothing is written but the usual paging files.

New: `tests/pack-virtualization-pbs-blob.test.ts` (9 cases: the four kinds, a CRC mismatch, an encrypted blob not decrypted, a compressed blob not inflated, a truncated header, an unknown magic and a chunk index, canaries in file names and log lines, hostile payloads, a 100,000-file manifest within `max_seconds`). All 9 fail on the code before this change.

### Added: virtualization-backup-forensics: `backup_audit_normalise` presets as data, a JSON array reader (`declared_json`), and the Proxmox Backup client's snapshot listing

A preset is a named set of the declared-mapping parameters (`mapping`, `category_map`, `result_map`, `time_format`, `columns`, `record_tag`, `delimiter`, `has_header`) held as a reviewed JSON file under `tools/backup_audit_normalise/presets/`. The tool reads presets from that directory only (a regular file, never through a link, at most 64 KiB), by the file names listed in `run.py` with the sha256 of each (the job service checks only `run.py`'s hash, so the presets' hashes live there): a file that is missing, is not the listed bytes, or does not hold the listed product and name is refused by its file name, and nothing is read with it. `product` selects a preset (and `preset` names one where a product has several, a new parameter); the answer says `preset: <name>@<revision>` and carries the preset's provenance; a preset and a mapping of the caller's own are not mixed (refused by name), and a preset's mapping goes through the same check as a caller's, so it targets only the keys a mapping may name. An unknown product is refused by name as before.

`declared_json` reads a JSON array export element by element: the buffer holds one element and the next read, never the file (the read doubles up to 8 MiB while an element is cut by the buffer's end, so the work is linear), under `max_line_bytes`, `max_file_bytes` and the clock. An element that is not an object is `unparsed` and located by record number; a syntax error, a cut file, a trailing comma and an element over `max_line_bytes` end the read at that element (an array cannot be skipped over without being read), counted and located, and the answer is `partial`. A caller can use it with a mapping of their own.

The first preset, `proxmox_backup_client_snapshot_list`, is for `proxmox-backup-client snapshot list --output-format json`. The Proxmox Backup documentation page "Backup Client Usage" (its title read "Proxmox Backup 4.2.8-1 documentation", retrieved 2026-11-03) names the command and its `--output-format` option but shows neither the option for this command nor its fields; the fields come from the Proxmox Backup source (`pbs-api-types`, `SnapshotListItem`: `comment`, `verification`, `fingerprint`, `files`, `size`, `owner`, `protected`, and a flattened `BackupDir`, taken to carry `backup-type`, `backup-id` and `backup-time` as the snapshot manifest names them). The preset maps `backup-time` (epoch seconds) to the time, the backup type to the action, `backup-id` to the object, `owner` to the actor and `comment` to the message. A listing has no per-snapshot action or result, so every snapshot is labelled `backup_end` (a backup the datastore holds, not one shown to restore) and its result stays `unknown`; the `verification` field is not read, as nothing read confirms its shape. The preset is not checked against a real export.

The tool is at version 10 and the pack at 1.6.0. New: `tests/pack-virtualization-presets.test.ts` (10 cases: the preset on a clean array, an unknown field and a missing or odd time, a tampered preset (one changed byte, a link, a missing file), an unknown product and the refusals, `declared_json` with the caller's mapping, a strict array reader, nesting and size bombs, a million-element array within `max_seconds`, SIGTERM, canaries in ids, owners and comments). All 10 fail on the code before this change.
