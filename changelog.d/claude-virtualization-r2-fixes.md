### Fixed: virtualization-backup-forensics pack: the findings of the independent R2 review (a clock inside every long line and file, no `complete` over a record that was not read, qemu-img never opens a file outside the set, an answer that is bounded and keeps its status, write_text tied to secret_output)

An independent review of the pack (1.1.3) found findings that could hang a tool past its manifest timeout, say `complete` over something it had not read, open a file outside the set, or leave the answer without its `status`. The three tools are at version 2. Timings are one CPU (`docker run --cpus=1 --network none`, node:22), wall seconds, on a host whose load average was about 100, so absolute figures are inflated; the CPU time equalled the wall time in every run. "Before" is origin/main at 3e6d4314.

- **The audit tool reads the clock on every line, and the worker id is unescaped at C speed.** `backup_audit_normalise` tested the clock every 1,024 lines, and `systemd_unescape` was a Python loop over every character of a Proxmox Backup Server worker id (0.05 s for a 420 KB id), so 1,100 PBS UPID lines with a 420 KB worker id ran on to line 1,024: 51.6 s here (81 s in the review) against a manifest timeout of 60. The four readers (task index, vzdump log, CSV, JSON Lines) now test the clock on every line, and the unescape is a split on the escapes (the same text as the loop on 200,000 generated strings); the same file reads whole in 19.2 s.
- **`snapshot_chain_check` no longer says `complete` over a record it did not read.** Shapes that ended in a complete chain and a complete run: a descriptor of more than 20,000 lines whose parent and extent come after them, an embedded descriptor over 1 MiB, a QCOW2 backing file name outside the file, an external data file named past the 64th header extension, a `parentCID` that is not a number, an extent line in a shape the tool does not read (an unquoted name, a lower-case keyword, a negative size, a trailing token) and no extent line at all. Each now gives the chain the status `record_incomplete` (new, after `broken`), makes the file `partial` with the reason, and writes a `descriptor_problem` marker. A QCOW2 header whose extension runs past the first cluster, whose backing name is over 1023 bytes, or that sets the external-data-file bit and names no file is the same. The chain row of a text descriptor over 1 MiB no longer says `complete` beside a partial run, and `other_lines` of a descriptor is shown. On the review's oracle (300 random chains with neutral variations, seed 14) 29 chains lost their parent to padding past the line cap while every chain row said `complete`; none does now (each such descriptor is `record_incomplete`, which the oracle counts as a disagreement with the truth of the unpadded chain: 63 of 300, all of them padded descriptors).
- **A line that was not read is a gap.** A `.vmx`, `.vmsd`, `.conf` or `storage.cfg` line of 64 KiB or more, and for the chain tool the 500,001st line of a `.vmx` or `.vmsd`, was dropped and the answer said `complete` and "nothing was left out". The file is `partial` now, and its reason gives the number of such lines and the first.
- **`qemu_img: auto` never gives qemu-img a file that names a file outside the set.** A sparse VMDK of capacity 0 is read by qemu-img through its embedded descriptor, which names its extents; the tool gave it such a file and qemu-img opened the outside extent. A sparse VMDK of capacity 0, or whose embedded descriptor names anything but its own file as written, is not given to it (`qemu_img.skipped.sparse_vmdk_names_other_files`). A relative path is passed as `./path`, so that a name beginning with `json:`, `nbd:` or `-` is a path.
- **The inline lists of an answer are cut by size, losslessly, and the answer keeps its `status`.** `limit` can be 100,000, and the answer is judged, serialised and read back within the run's clock: 200,000 descriptors with `limit` 100000 made a 271 MB answer in 62.9 s with every key withheld and no `status`; 2,000,000 JSON Lines records with `limit` 100000 made 73.7 MB in 53.9 s, again without `status`. The rows shown inline now stop at about 512 KiB per list whatever `limit` says (`pages.<list>.inline_cut_by_size`); the whole list is in the paging file, as it already was past `limit`. The same runs: 48.9 s, 7.0 MB, `status` complete; 50.1 s, 1.3 MB, `status` partial.
- **`write_text` needs a job run with `secret_output`, as the manifests say.** The shared text file only checked for a job; the job service gives a secret job's process `SECRET_OUTPUT=1`, and the base pack's tools refuse without it. The three tools refuse now and write nothing.
- **The inventory reads the clock inside a file.** One 16 MiB Proxmox `.conf` was one clock check; it is a check every 256 lines and every 64 records now, and a file the clock stops is a `partial` row of `sources` that says so. Three such files with `max_seconds` 10: 13.7 s before, 10.1 s now.

Not changed: the process block's wait for a descendant that keeps the pipe of a finished engine open (a block other packs share), the free-text shapes the review lists as carried over, the quadratic `_S_LINE.search` the tools never call with `search`, and a signal that arrives before the interpreter has compiled the script (the first 0.1 s), which no code in the script can answer.

The empty descriptor area of a split sparse extent (what qemu-img writes for `twoGbMaxExtentSparse`) is no descriptor, not one without extent lines, so a healthy split disk stays `complete`; the `parser` field of the answers says `/2`. The tests are `tests/pack-virtualization-r2.test.ts` (14 cases, all failing on origin/main); the suites that wrote a values file in a job now say the job is a secret one. Fuzz with the review's generators: 1,000 chain sets, 1,000 inventory sets and 1,000 audit files, no issue (one JSON object, exit 0 or 1, inputs unchanged, no seeded token shown).
