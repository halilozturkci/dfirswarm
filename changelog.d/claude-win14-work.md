### Added: windows-forensics lnk_jumplist reads a Jump List's DestList a second time with JLECmd, where it is installed

Eric Zimmerman's JLECmd (2026.10.6, MIT, run through dotnet) is pinned in the pack's `requires/host.json` as an optional download, like MFTECmd, EvtxECmd and RECmd. `lnk_jumplist` runs it once per automaticDestinations-ms whose DestList it read, in its own process group, under its own clock (a run ends 6 seconds before `max_seconds`) and with an output cap (no file JLECmd writes may reach 32 MiB), and compares the CSV with its own read field by field: the entry count, and for each entry the path, the access time, the pin state and the application id of the file name. Each DestList entry row now has `integrity.jlecmd`, `agree`, `disagree` (with the field and both values) or `not_run` (with why); a disagreement makes the status partial; a JLECmd that is absent, fails, runs out of time, reaches the cap or writes a CSV it cannot read is `not_run`, said in the status basis, and never `agree`. The container check in the standard library stays. A customDestinations-ms, a lone link and a DestList read only in part are not given to JLECmd. The `artifacts/jumplists` skill names it. JLECmd's own option names and CSV columns were taken from the pinned build's help text and metadata; the build could not be run where this was written (no dotnet), so the real-run test skips there.
