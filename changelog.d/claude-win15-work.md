### Added: windows-forensics reads UserAssist, BAM, DAM and ShimCache (`userassist_bam_shimcache`)

One tool reads UserAssist (NTUSER.DAT), BAM and DAM (SYSTEM) and ShimCache / AppCompatCache (SYSTEM) into records, each with its raw bytes (`raw_hex`) beside the decoded fields, the `layout` and the `layout_basis`, and `unsupported` with the bytes kept when a value or an entry does not fit a known layout (UserAssist values of 72 and 16 bytes, BAM and DAM values of 24 bytes, ShimCache in the Windows 7 32-bit and 64-bit, 8.0, 8.1 and 10 layouts). The decoding is the tool's own, from the published layouts, and the offsets are not checked against real hives; the regipy plugins are not used, and no second reader (RECmd, RegRipper) cross-checks the records: `cross_check` is always `not_run`. A UserAssist hive does not name its owner, so `sid` is null unless `owner_sid` is passed. The filters `contains` and `sid` look only in the text the answer prints, and a record not matched whose printed text holds a withheld part makes the answer partial (`contains_blind_records`). Every answer states the interpretation limits (presence is not execution, a ShimCache time is not an execution time, a user whose hive was not collected is not a user with no entry). `tests/pack-windows-forensics-userassist-bam-shimcache.test.ts` is the new suite.

### Changed: the windows-forensics skills and the recipe no longer say the pack has no UserAssist, BAM, DAM or ShimCache reader

`execution/userassist`, `execution/shimcache` and `registry/readers` name `userassist_bam_shimcache` (and say its offsets are unverified and that nothing cross-checks it). The `windows-artefacts` recipe does not run the new tool; it keeps dissect.target's output of the `userassist`, `bam` and `shimcache` functions as a second reading, and its `not_covered` list and `recipe.json` exclusions say so.

### Added: windows-forensics links scheduled tasks to their registration and execution evidence (`persistence_normalise`, tasks)

A new tool reads Task Scheduler XML files (UTF-16, UTF-8 or UTF-16BE by byte order mark, or UTF-16 with no byte order mark decoded by the tool itself; a DOCTYPE or ENTITY declaration is looked for in the decoded text and in the bytes with their NULs taken out and refused before any parse, so nothing is expanded; a pipe, a link or a file over 8 MiB is never read), the TaskCache of a SOFTWARE hive (Tree, Tasks and the Plain, Boot, Logon and Maintenance groups; DynamicInfo decoded by its length with the layout and its basis, `unsupported` with the bytes kept when it fits neither; Actions and Triggers kept as bytes, NOT decoded: the package asks for their documented layouts and none could be checked against a real hive, so none is guessed) and an `evtx_query` result file (Security 4698 to 4702 and TaskScheduler/Operational 106, 140, 141, 200 and 201), into one item per task. Mismatches (an XML file with no TaskCache entry, a TaskCache entry with no file, a Tree entry with no SD value) are observations about the inputs, not verdicts, and are stated only when both sides were given. Command and Arguments are withheld by shape and written whole only in a `secret_output` job. The answer says "WMI repository: not examined". No second reader (RECmd, RegRipper, Dissect) is started; the manifest says so. `tests/pack-windows-forensics-persistence-tasks.test.ts` is the new suite (a TaskCache of 100,000 tasks among its cases).

### Changed: `persistence/tasks-com-wmi` and `persistence/mechanisms` name `persistence_normalise`

The task leaf now says the tool links the XML, the TaskCache and the events, that its observations are not verdicts, and that the WMI repository is reported as not examined.

### Added: `persistence_normalise` also reads service keys and autorun keys (version 2)

New inputs `system` (every ControlSetNNN Services key: ImagePath, Start and Type with their documented labels, Parameters ServiceDll, FailureActions as bytes, the control set and whether it is the current one), `software` (now also Run and RunOnce with the Wow6432Node view, Winlogon Shell and Userinit, AppInit_DLLs and LoadAppInit_DLLs, the Image File Execution Options Debugger and the Active Setup StubPath; a SOFTWARE hive with no TaskCache is read for these) and `ntuser` (that user's Run and RunOnce). Every item names its `mechanism` (scheduled_task, service or autorun) and the answer gives the state of each hive read under `hives` (the single set of top-level hive keys of version 1 is gone). Command lines (ImagePath, ServiceDll, Run values, Debugger) are withheld by shape and written whole only in a `secret_output` job. No second reader (RECmd, RegRipper, Dissect) is started, because the tool keeps the STOP signal layer, and the manifest says so; `cross_check` is `not_run`. `tests/pack-windows-forensics-persistence-services.test.ts` is the new suite. `persistence/mechanisms` names the tool and what it does not read.

### Fixed: `userassist_bam_shimcache` and `persistence_normalise` count what they did not read, and a very long list no longer overruns the time limit

At its own time limit the tools said one value (or one entry) was not read when the rest of the key, the later keys and the later sources were not read. They now state a true lower bound ("at least N value(s) were not read"; the keys and directories not started are counted apart, and what they hold and the sources after the stop are said not to be counted), and `persistence_normalise` reads until a tenth of its limit (at most 30 seconds) before the end and writes what it read within the rest, so a time-limit answer carries the items already read and counts those it could not write. The ordering of a list by the text shown, which was not bounded by the clock, is now bounded: a list of more than 100,000 items, or one that does not fit half the time left, is listed in a random order and the answer says so (a BAM key of 1,000,000 values ended with JSON at 85 seconds, four runs at once at 87, where it had run past 90). A ShimCache count of entries not read was already true and is unchanged.

### Fixed: `persistence_normalise` refuses a DOCTYPE or ENTITY declaration in UTF-16 text with no byte order mark

A task file in UTF-16 with no byte order mark (or UTF-16 text after a UTF-8 byte order mark) was read as UTF-8, its NUL bytes hid the declaration from the check, and the XML parser then detected UTF-16 itself and expanded the entity. The tool now decodes the text itself (a byte order mark, or the pattern of the NUL bytes), refuses NUL bytes that are not UTF-16 text, and looks for the declaration in the decoded text and in the bytes with their NULs taken out.

### Fixed: `persistence_normalise` keeps a service, TaskCache or autorun value of an unexpected type instead of dropping it

An ImagePath, ServiceDll, DisplayName or ObjectName of type REG_BINARY, REG_MULTI_SZ or REG_DWORD (and an Actions, Triggers, DynamicInfo, Path or Tree Id value of the wrong type) was dropped without a word, and the service was reported as having no ImagePath and no ServiceDll in a complete answer. The value is now kept as given (`image_path_value` and the like, with `..._value_type`), listed under `unsupported_fields`, and the answer is partial; the observation `no_imagepath_and_no_servicedll_value` is stated only when no such value exists in any type. The status words name the right noun for an unsupported autorun value, a result-file row with a list or object as `event_id` no longer aborts the read, a result-file line over 8 MiB is counted and dropped, and the `items_by_registration` keys are readable words.
