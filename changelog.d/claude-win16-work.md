### Added: powershell_blocks reassembles PowerShell script block logging records (event 4104) into blocks

`powershell_blocks` in the windows-forensics pack takes an `.evtx` file (read with the chunk code `evtx_query` and `evtx_carve` carry) or a JSON Lines file of `evtx_query` rows, and groups the 4104 records of `Microsoft-Windows-PowerShell/Operational` and `PowerShellCore/Operational` (kept apart) by source, Computer and ScriptBlockId, in the order of MessageNumber. Per block it gives the expected against the observed fragments, the missing numbers as ranges, duplicates (and whether the copies match), MessageTotal values that disagree, numbers out of range, the Path and Level fields and the length of the text, and per fragment the EventRecordID and the record's byte offset in a file. The answer and its files carry metadata only: the text is never evaluated, decoded or shown, and no hash of a block is written. Listing the blocks has a clock of its own (48 seconds), and the blocks it did not reach are counted and make the answer partial; an answer with extra copies of equal text names them in `status_basis`. `write_text` writes the reassembled text to a 0600 file under `$OUT` and is accepted only in a `secret_output` job. What it keeps is bounded (200,000 fragments in 100,000 blocks, a JSON Lines row of 16 MiB, its own clock) and a bound that cut something makes the answer partial and names the number. Not verified here: a real PowerShell log; the reader is exercised on events built to the documented layout, and python-evtx is not installed where the tests run. The `logs/powershell` skill now names the tool where it said the pack had no assembler. The pack goes to a new patch version, the tool counts in the READMEs and the block census follow, and the shared blocks of the tool are copies of the ones `evtx_query` and `evtx_carve` carry.

### Added: vss_materialise copies chosen files out of chosen shadow copies, and always unmounts

`vss_materialise` in the windows-forensics pack lists the stores of a raw volume or disk image with `vshadowinfo`, mounts the selected ones with `vshadowmount` (FUSE) under its own directory, finds each selected path in each `vssN` with the Sleuth Kit's `fls` (component by component, case-insensitively, no deleted entry, no link followed) and copies it with `icat`. Each copy is hashed as it is written, placed without replacing an earlier file and tagged with the store number, identifier and creation time `vshadowinfo` printed; the answer says which store has which path and whether each copy is the same as the file in the live volume. The mount is unmounted in a `finally`, at the tool's own deadline and on SIGTERM, SIGINT and SIGHUP. Without FUSE the answer is JSON with `blocked: no FUSE` and nothing is written. A copy that could not be written whole is removed and never named as a copy; a refused write stops the copying and says nothing about the evidence. SAM, SECURITY and NTDS.dit are copied only with `copy_credentials` in a `secret_output` job, with no digest printed or written. The mount is waited for once (5 seconds in all), a directory listing is read to a 16 MiB cap, and `copies` counts the files copied. Not verified here: a run against a real shadow copy and a real FUSE mount; the tests use stand-ins for `vshadowinfo`, `vshadowmount`, `fusermount3`, `fls` and `icat`. The `filesystem/shadowcopies-open` skill now points to the tool where it told the agent to mount by hand.
