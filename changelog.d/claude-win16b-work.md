### Added: windows-forensics srum_reader reads SRUDB.dat through SrumECmd and dissect.target and says which backend produced each row

The new `srum_reader` tool runs Eric Zimmerman's SrumECmd (2026.10.1, MIT, run through dotnet; pinned in the pack's `requires/host.json` as an optional download like the other Zimmerman tools) and dissect.target's `target-query -f srum --json`, whichever is installed, each in the tool's process group, under a share of the tool's own clock and with its output in files. Every row is kept as JSON Lines in a file the answer names, with its `backend`, table and source row; per table the answer gives the row count, the retained interval (earliest and latest row time), the counters with the unit the column name states, the table's time semantics, and how many application, user and profile ids did not resolve (kept in the row, flagged and counted). With both backends present the row count of every table both name is compared (`agree`, `disagree`, or `not_compared` for a table it cannot match by name); a backend that is absent, fails, runs out of time, is unsupported on the host or writes a shape the tool does not know is `not_run` or `not_compared`, said, and is never `agree`. The tool reads the ESE header of SRUDB.dat itself (the database state, and the log and checkpoint files beside it): a database that is not in a clean-shutdown state is `partial` unless it is dirty, logs are beside it and SrumECmd said it replayed them. `status` is `partial` for a table or file that could not be read whole, a time that could not be read, bytes that are not UTF-8, disagreeing backends and an exhausted clock. Application paths, user names and profile names pass the shared boundary.

What this does not do, and what was not checked: the pinned SrumECmd build prints that it needs Windows' own ESE libraries and exits on a non-Windows host, so in a Linux image it reads nothing (`unsupported_platform`) and only dissect.target, which reads a collection directory, can give rows there. SrumECmd's option names (-f, -r, --csv, --temp, --dt), its CSV file names and columns, the console lines parsed for the database state and the log replay, and the dissect.target record shape were taken from the pinned build's strings and metadata, not from a real run: no dotnet, Windows or dissect.target was available where this was written, so the tests use stand-in backends and no real SRUDB.dat was read (the real-run test is gated and skips). `execution/srum` and `execution/esedb` name the tool; `esedb_query` stays the route for raw tables. The windows-artefacts recipe's texts say that SRUM rows are read by `srum_reader`, which the recipe does not run.
