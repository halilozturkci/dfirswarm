### Fixed: a FIFO, a link or a directory at the name a result is placed at no longer holds a tool, and the comparing of results has a clock

- **A FIFO at a result's own name no longer blocks the tool for ever.** `same_bytes` (called by `place_without_replacing` in the shared PLACE block of the windows lineage and the shared PAGE block of the memory lineage, and by the `publish` of the cloud, base and triage tools) compared sizes by path and then opened both files. A FIFO planted at the final name (`mkfifo work/s1/hits.jsonl`, then `mem_carve` on a clean image with `results_to` naming it) is 0 bytes, as is the empty temporary file of a run with no hit, so the size check passed and `open()` of the FIFO blocked until `SIGKILL` (it swallowed `SIGTERM`). Both files are now opened with `O_NONBLOCK|O_NOFOLLOW`, looked at with `fstat`, and read only when both are regular files of one size; a FIFO, a link, a device or a directory at a name is another result's, so the next name (`hits-2.jsonl`) is taken, and an identical rerun still gets its old name. A link at the final name is no longer followed by the comparison either (the base and cloud `publish` copies named the link as the result when it pointed at a file of the same bytes).
- **The comparing of one placing has a clock.** `place_without_replacing` compared every earlier list of the same size in turn (up to 999 names) with no clock. It now has `PLACE_COMPARE_SECONDS` (5 s) in all for one call; past it an earlier result that has not been compared is taken as different, and the result takes the next free name. Nothing is replaced; what stays open is that an identical rerun may then be named anew.
- Carriers: the PLACE block (33 carriers), the memory PAGE block (3), and the unmarked `same_bytes` and `_same_bytes` copies of the cloud, base and triage tools and their tool-library twins (20 more). `unified_log` keeps its own `same_bytes`: it compares members of one staged tree after every special file has been refused, and places no result.
- Packs raised: `windows-forensics`, `memory-forensics`, `encrypted-containers`, `ransomware-response`, `cloud-forensics`, `computer-forensics-base`, `triage-collection`; the tool-library twins and their README rows follow.
- Test: `tests/pack-shared-residuals.test.ts` runs the block's own text from a carrier of each lineage, the unmarked copies, and `mem_carve` end to end with a FIFO planted at its `results_to`; each fails on the code it replaced and passes on this change.

### Fixed: a hard stop between taking a result's name and filling it leaves no empty file; a stop by signal answers failed with interrupted true; a signal in the page clean-up gives one answer

- **PLACE (33 carriers) and the memory PAGE block (3): no empty file at the final name.** `place_without_replacing` took the name with an exclusive create and then moved the finished file over it; a stop in between left an empty file at the final name, and later runs took `-2`. The name is now taken with a hard link of the finished file (it fails when the name is there, as an exclusive create does, and never follows a link), so the name never holds an empty file, SIGKILL included; the hidden name of the page is removed after the link. Where the file system refuses the link, the older exclusive create and move is used, and a stop that unwinds (an exception) takes the empty name back while it is still the empty file the call made. Still open there: a stop that ends the process without unwinding (SIGKILL, the handlers of the STOP block) between the create and the move leaves the empty name, and the next run takes `-2`; and a stop in the few interpreter steps between the create and the book-keeping.
- **STOP, windows lineage (30 carriers) and encrypted lineage (5): `"status": "failed", "interrupted": true`.** The early answer (the minimal last word printed before `main()` installs the tool's own) said `"status": "interrupted"`, which is not one of `complete|partial|failed`, and differed from the tools' own last word. It now says `failed` with `interrupted` true and a one-sentence `status_basis`; the manifests of browser_history, indx_carve, jumplist, lnk_parse, mam_scan, mft_records, prefetch_mam, recyclebin_i, usn_journal, utf16_urls and archive_probe say the same. The windows-forensics contract harness (`tests/windows-tool-contract.ts`) takes `failed` with `interrupted` true as the stop answer. Still open: the tools that print their own stop answer outside the STOP block (windows esedb_query, evtx_query, yara_scan, vss_stores, extract_stream, sigma_hunt and the windows-artefacts recipe, the reverse-engineering fuzzy_hash, the memory tools, the macOS lineage, and any other that a search for the quoted status word finds) still say `"status": "interrupted"`; the start-up window before the first handler is unchanged.
- **PAGE, memory lineage (3): the abort loop runs under the signal guard.** `fail()` dropped the pages' hidden temporary files in a loop that ran before the answer's signal guard was entered, so a signal landing in it raised in the middle of the loop (no answer, a page's file left). `abort_pages()` in the PAGE block holds the guard (`GUARD["depth"]`) around the loop and `fail()` calls it; the signal is held and the failed answer is the one answer.
- Packs raised: `windows-forensics`, `ransomware-response`, `reverse-engineering`, `encrypted-containers`, `memory-forensics`; library twins and README rows follow.
- Tests: the cases are in `tests/pack-shared-residuals.test.ts` (a SIGKILL and an unwinding stop after the name is taken, SIGTERM in the early window of both STOP lineages, a signal in the abort loop of each memory tool); each fails on the text before this change.

### Fixed: a tool no longer signals a pid that is not the process it listed, no longer reads a ps that failed as an empty tree, and stops a fast forker as the walk finds it

- **Identity is checked before a kill (both PROCESS lineages, 29 carriers: 18 general, 11 windows).** `kill_tree`, `kill_all` and `reap_orphans` signalled pids from an earlier walk, so a pid that had ended and been reused could be signalled. Each pid other than the program itself is now read again just before the signal: `same_process(pid, ident)`, where `ident` is the start time (`/proc/<pid>/stat` field 22, counted after the last `)`, on Linux; libproc's `PROC_PIDTBSDINFO` `pbi_start_tvsec` and `pbi_start_tvusec` on macOS; `ps -o lstart=`, to the second, where neither answers). The parent is not part of it (a child is re-parented when its parent ends), so the function is the one linux-target's own handler uses (its format is the same; the recipe's own copy of the function is overridden by the block's equal one and its handler is unchanged). A pid whose start time could not be read when it was listed is signalled only if it can be read now and is in the tool's group; a plain `ps` listing with no start time (a minimal `ps`) is checked only for the pid still being there. `reap_orphans` also compares the start time a pid had when it was seen below the tool.
- **A ps that cannot list is not an empty tree.** `list_descendants` raises `TreeNotListed` when `ps` fails, lists nothing, needs more than `PS_WAIT` seconds, or `/proc` cannot be read or takes more than `TABLE_SECONDS`; the program itself is still ended, and `process_notes()` (and the stderr bytes `communicate_bounded` returns when it ended the program at its deadline) say that the tree could not be listed. `descendants()` stays for callers that cannot take an exception (a signal handler): its list is empty and carries `not_listed = True`.
- **The deadline walk stops each process as it finds it.** `kill_tree` and `kill_all` stop (SIGSTOP) every process the walk finds, parent before children, repeat the walk for what the stopped ones had forked (at most `MAX_ROUNDS` rounds and `WALK_SECONDS` seconds), and then kill the stopped set; a tree still growing at the bound is named in `process_notes()`. Every read of the process table checks the clock per entry, and the set of pids the tool has seen is capped at `SEEN_MAX`.
- Still open, listed in the block header: a pid that ends and is reused between the identity check and the signal (two calls); the Linux rule that a member of the tool's own group that holds the tool's pipe is ended; on macOS a daemon that holds the pipes of a finished program is not found; a tool SIGKILLed between the stop and the kill leaves the program and the stopped set stopped (the harness ends the tool's group, and with it the stopped ones in it); the macOS libproc reader is written from `<sys/proc_info.h>` and not run on macOS here; the answers of the carriers say what `process_notes()` holds only where each carrier's own code reads it (the per-pack packages that own the answers add that: the block does not change the lines of a carrier outside it); the start of the interpreter, before any handler is in, is a window a signal can land in.
- Carriers: computer-forensics-base (archive_extract, timeline_super), encrypted-containers (archive_probe, password_recover, tcrypt_header), linux-forensics (linux-target, journal_export, linux_triage), mobile-forensics (android-aleapp, ios-ileapp), network-forensics (network-capture, pcap_extract, suricata_run, zeek_run), reverse-engineering (capa-floss, static-binary, fuzzy_hash), virtualization-backup-forensics (snapshot_chain_check), windows-forensics (windows-artefacts, esedb_query, extract_stream, lnk_jumplist, registry_recover, sigma_hunt, vss_stores, yara_scan) and the library's esedb_query, extract_stream and yara_scan. Packs raised: all eight; library twins follow.
- Tests in `tests/pack-shared-residuals.test.ts`: a pid whose start time changed before the kill is left alone (and the unchanged one is ended), a pid seen below the tool that another process has taken is not ended by `reap_orphans`, a `ps` stand-in that fails and one that sleeps past `PS_WAIT` (no `/proc`, no libproc) give a note that the tree could not be listed, and a fast forker below the program leaves no descendant in five tries; each fails on the text before this change.

### Residuals that are not fixed, by block

- STOP: the tools that print their own stop answer outside the block still say `"status": "interrupted"`; the start-up window before the first handler.
