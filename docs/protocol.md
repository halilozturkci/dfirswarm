# The protocol

What is on disk and on the wire: the sandbox layout, posts, claims, the write guard, the done sentinel, the budget, the event log, file history and the registry. This is the contract the harness enforces.


Everything below is enforced or written by `extensions/protocol.ts`.

### Sandbox layout

```
runs/<id>/
  SWARM.md                     the contract (rendered at start)
  team.json                    {swarm_id, n, agents:[{id, role, model?}], models}   the spawner writes `worker`
  names.json                   {names:[{id, name, doing?, at}]}: what each agent said to call it, through `name`; harness-owned
  budget.json                  live spend, see below
  layout.json                  Herdr pane ids, tabs, split failures (spawner)
  netguard.pid                 sidecar pid while running; the last agent to finish stops it
  netguard.port                the sidecar's port (one per swarm)
  idle-nudge.pid               the idle watchdog's pid while running (scripts/idle-nudge.sh)
  .pi/SYSTEM.md                worker system prompt
  .pi-sessions/<id>/           Pi session files per agent (also a reaper activity signal); a seat's VM sees its own and no peer's
  .runtime-cache/              Node's compile cache for the run's host processes (NODE_COMPILE_CACHE); outside work/, so never indexed or packaged
  bin/pi                       netguard PATH shim
  tools/<name>/manifest.json   a forged tool: name, description, params, runtime, entry, by, version, sha256
  tools/<name>/run.py|mjs|sh   its script (harness-owned; written only by make_tool)
  inputs/                      read-only copy of what --inputs named (no write bits; harness-owned); several sets, one at inputs/<name>/ each
  inputs.json                  its manifest: source, every file with size, sha256, sha1 and md5, enforce, guard, quarantine (and sets, for several)
  .inputs-pristine/            the clone the harness heals inputs/ from
  catalog/                     --catalog: the first pass over the inputs (partitions, body files, timelines, memory lists), read-only
  toolbox.json                 --toolbox: the forensic tools found on the host, and the missing ones with install commands
  ledger/entries.jsonl         `record`: one line per event, indicator, finding or answer, append-only
  ledger/attestations.jsonl    a second author of an entry, or an `attest`: chained, append-only
  ledger/disputes.jsonl        `dispute`: why an entry does not hold, or its withdrawal; chained, append-only
  ledger/sweeps.jsonl          the store sweeps: what the hub found searching every output for a coverage record's looked_for strings, and each evidence addition's reverse sweep; chained
  ledger/ledger.md             the ledger rendered by the harness after every record: timeline, indicators, findings, answers
  leads/leads.jsonl, leads.md  the lead register: a chain of events, and its rendering after every change
  leads/finish.jsonl           the finish: the coordinator's lease, its prepares, the report's reviews, resolutions, readiness and check results (a chain)
  questions/questions.jsonl, questions.md   the question register: a chain of events, and its rendering
  requests/requests.jsonl      the operator requests' chain (extensions/requests.ts): every request of a person, with its id (R-n) and lifecycle
  requests/requests.md         the same, rendered
  operator-requests.jsonl      one line per request as it stands, rendered from the chain (the file every older reader reads)
  network/policy.json          the case policy as the kickoff recorded it (its sha256 in the custody anchor)
  network/grants.jsonl, fetches.jsonl   the dynamic network's requests, decisions and grants, and every fetch (two chains, ADR 0012)
  store/imports/ev-<n>/        evidence added after the kickoff (swarm.sh evidence add): out/, manifest.json, material.json
  store/imports/mat-<n>/       material the operator supplied (swarm.sh material add, swarm.sh tool-supply, a question's attachment): the same
  work/<agent id>/             an agent's own scratch and extracted evidence (no claim needed)
  work/extracted/, work/quarantine/   --quarantine: no-exec at the kernel, execute bits stripped
  package/                     `swarm.sh package`: the hand-over with MANIFEST.txt
  .zsh/, .bash/, .fsguard/     the pane hooks (zsh, bash) and plan for the kernel guard (when one is available)
  threads/main/000001-<id>.md  posts, append-only, one file each
  threads/<name>/meta.json     {name, purpose, created_by, created_at, members}
  inbox/<id>/cursors.json      per-agent, per-thread: highest post id read
  work/                        the artifact(s); work/<agent>/.browser/*.png from playwright
  locks/<sha256(path)>.json    live claims
  locks/.table.lock/           mkdir mutex for lock-table changes (pid, ns, owner token inside)
  history/<sha256(path)>/      000001.bin … + index.json (rev, ts, agent, bytes, sha256)
  done/agents/<id>.done        this worker exited
  done/agents/<id>.dead        this worker was reaped
  done/SWARM_DONE              the collective is finished
  done/ALL_AGENTS_DEAD         reap.sh: every seat is marked done or dead and there is no sentinel (reason all_agents_dead); a failed stop, never a finish
  traces/events.jsonl          append-only event log (not in a seat's VM: the veil over traces/ is empty)
  traces/netguard.log          ALLOW/DENY lines
  tool-output/<id>/<stamp>-<tool>.{out,err,text}.log
                               the whole output of a tool call whose result reached the
                               model as a prefix; named on the trace row with bytes and sha256
                               (a seat's VM sees its own tool-output/<id>/ and no peer's)
runs/registry.json     {runs:[…]} written by swarm.sh
```

Agent ids are spawner-assigned: `<swarm id><2-digit index>`, e.g. `s1a2b00`, `s1a2b01`; the violation probe is `<swarm id>pv`. Ids must match `[a-z][a-z0-9_-]{0,31}` (Herdr-safe). Callsigns agents pick in chat are cosmetic; locks and done files use ids.

### Posts (`post`, `inbox`)

`post(body, tag, thread?="main", to?="all")` appends `threads/<thread>/<000001>-<from>.md` under the table lock, id = max id in that thread + 1:

```markdown
---
id: 7
thread: main
from: s1a2b01
to: all
tag: claim
name: disk-triage
---

Taking work/hello.txt. Will append my id and release.
```

`name` is what the author has said to call it, through the `name` tool, and
it is written only once the agent has said. An id belongs to a single run;
the name is what a reader of the board is actually following, so it travels
with every post and the console and the summary show it next to the id.
Nobody assigns it: the agent reads the goal and the board and decides.

A post the harness writes is `from: system`. Under `--isolation microvm` the
harness code that announces a violation or a notice runs inside the seat's
VM, which the seat's guest root controls: such a post carries `via: <seat>`
in its frontmatter, and `inbox` and `wait` give it to peers as
`from: "system via <seat>"`, the seat's word and not the harness's.

Tags: `intro`, `ask`, `claim`, `result`, `hold`, `veto`, `stop`. Unknown tags are rejected on write and read as `ask`. Thread names are sanitised to `[a-zA-Z0-9_-]`. Posts are never edited; `threads/` is not in the write path anyway because posting is a tool, and the prompt forbids `edit`/`write` there. Posts carry no timestamp; the file mtime is the clock the UI and reaper use.

`inbox()` with no argument returns unread posts from the primary thread plus
every thread the agent belongs to, advances that thread's cursor, and reports
`swarm_done`. Cursors are **per agent, per thread** (`inbox/<id>/cursors.json`):
a single counter used to advance past unread ids in other threads and hide them
for good. `inbox(thread)` reads one thread. Agents may also just `ls
threads/main` — the unstructured escape hatch is the point.

One delivery carries at most `--inbox-page-chars` characters of post text
(40,000 by default, `SWARM_INBOX_PAGE_CHARS` in the pane, `inbox_page_chars`
in the registry), **whole posts only**: a post is never cut, the delivery
stops before the post that would break the bound, and only the delivered
posts move the cursors, so what stayed behind is still unread. The result says
`remaining` and, when it is above zero, a `note` that nothing was cut and the
next call brings the rest; `wait` returns at once while anything for the agent is unread. A post on `main` addressed only to other agents (its `to` names teammates and not this one) does not wake a `wait`; it stays unread and the next delivery carries it, and the result counts it as `passed`. A post to all, to this agent by id or by the name it chose, or to no one on the team wakes it, and so does any post in a side thread it is in; `every_post: true` wakes on everything. On the BelkaCTF #6 run 586 of 1,291 wake-ups were for posts addressed only to someone else.
The event row lists every delivered post's id and sender, whole, and
`remaining`. On the Linux run s3096 two `wait` results carried 578 posts each,
64k tokens, which is what this bound is for; `0` removes it.

`thread_open(name, purpose)` starts a side thread and joins it; `thread_join(name)`
subscribes without posting, which is how a reviewer follows a slice it is not
working on. Posting to a thread joins it. Membership is what decides whose
inbox a thread reaches, so a thread nobody joined is visibly abandoned rather
than silently ignored.

`wait(seconds)` blocks until a post lands in one of your threads, the sentinel
appears, or one of your leases lapses — and returns the unread posts. Idle
agents used to spend a full provider round on every `bash sleep 30; cat
done/SWARM_DONE` poll; on the last live run here a third of all tool calls were
that loop.

### Claims (`claim_file`, `release_file`)

Claim key = sandbox-relative path (escaping the sandbox throws). Lock file `locks/<sha256(key)>.json`:

```json
{ "path": "work/hello.txt", "owner": "s1a2b00",
  "reason": "appending my id", "seconds": 120,
  "claimed_at": "2026-09-16T08:24:39.280Z", "expires_at": "2026-09-16T08:26:39.280Z" }
```

`claim_file(path, reason, seconds?)`. A claim is a **short lease with a
reason**, not an open-ended lock:

- `reason` is required and public. Peers see it on a conflict, `claims` lists
  it, and a violation report quotes it. It also forces the agent to say what it
  is about to do before it does it.
- `seconds` defaults to 120, caps at 600. Re-claiming renews; a legal
  `edit`/`write` renews on the owner's own terms. A short lease means a dead
  agent's claim clears in two minutes instead of blocking the swarm.
- Another owner with a live lease → `{ok:false, conflict:true, owner, reason, expires_at}`.
  A conflict is normal traffic, not a violation.
- A **protected path** — the sentinel, the board, the locks, the traces, the
  contract, `team.json`, `budget.json`, `names.json` — is refused outright. An
  agent that could write `budget.json` could lift its own spend cap; one that
  could write `names.json` could rename its peers.
- Symlinks are resolved before the check, and protected names match
  case-insensitively, so `work/b -> ../budget.json` and `BUDGET.JSON` are both
  refused.
- `claims()` lists every live lease with its reason and remaining seconds.
- `release_file` drops your own lease. `done`, `session_shutdown` and the
  reaper drop everything an agent owns.
- All lock-table mutations run under `locks/.table.lock` (exclusive `mkdir`,
  10 s wait). The holder rewrites `beat` inside it every 3 s, so a lock that
  has not changed for 15 s has no live holder unless that holder has stalled (SIGSTOP, swap, a
  laptop asleep). A stale lock is broken, except that a holder is kept while
  its pid is live and it recorded the same `ns` as the waiter: the pid
  namespace and boot id on Linux, the boot session (`kern.bootsessionuuid`) on macOS. A
  waiter that cannot check the pid — another pane's pid namespace, another
  VM, a lock with no `ns` — goes by age alone. A break happens under
  `locks/.table.lock.break`, which re-checks the lock first, so two waiters
  cannot both break one lock. Age is read on the filesystem's clock: the
  lock and `beat` are stamped by the filesystem, and so is a probe file
  (`locks/.probe.<token>`) the waiter writes next to them, so a lock stamped
  through an NFS client is not aged on the host's clock. (In a microVM run no
  guest takes this lock: the run is read-only in the VMs, and only the hub,
  `reap.sh` and `swarm.sh say` take it, on the host.) The
  heartbeat stops once the lock is no longer its holder's. A holder removes only a lock whose `owner`
  token is its own, and warns (`DFIRSWARM_TABLE_LOCK_LOST`; on stderr from
  bash) when it finds its lock was taken over. `reap.sh` and `swarm.sh say`
  use the same mutex from bash, and hold it for a few seconds at most.
- What the table lock does not guarantee. Each of these needs a process to
  stall or die inside a window of a few filesystem calls:
  - A holder that stalls past 15 s where its pid cannot be checked (another
    pane's pid namespace, another VM) loses its lock. It finds out before its
    next write in `claimFile`, the budget fold, `record` and file history,
    which fail with `TableLockLostError` rather than commit, and at release,
    which warns. The check and the write are still two steps.
  - A holder whose recorded pid is reused by another live process in the
    same namespace keeps a dead lock standing; waiters time out after 10 s.
  - Clearing a stale `.break` repeats the break race one level down: two
    waiters that both judge it stale can both remove it, the second removing
    a `.break` the first has just taken.
  - Release renames the lock to `<lock>.released.<token>` before judging it,
    so it removes only what it judged its own. If the renamed lock turns out
    not to be its own, it is renamed back unless a new lock has appeared at
    the path meanwhile; that step has a gap of its own.

### Write guard and `claim_violation`

The prompt asks agents to claim before writing; the guard is what makes it true. `pi.on("tool_call")` in `agent-swarm.ts` intercepts `edit` and `write`, extracts the path (`path`, with `filePath`/`file_path`/`file` as fallbacks) and calls `guardWrite`. The call is **blocked** (`{block:true, reason}`) and a `claim_violation` event is logged when:

- `AGENT_ID` is unset,
- the tool input has no path,
- no live lock exists for the path (`claim violation: work/hello.txt (no lock)`),
- the live lock belongs to someone else (`result.owner` names them).

On a legal write the hook first copies the current bytes into history and
renews the lease; `tool_result` records the result and logs `file_history`. If
the renewal comes back a conflict — the lease lapsed and someone else took the
path while the agent was thinking — the write is refused rather than allowed to
stomp the new owner's work.

**`bash` cannot be guarded this way.** A shell command can write anything, and
reading the command text to guess whether it will both misses and
false-positives. So the harness brackets every shell call with a hash of the
paths worth watching — every live claim, plus `SWARM.md`, `team.json`,
`layout.json` and the sentinel — and compares afterwards. A change that is not
accounted for by a recorded revision is snapshotted, logged as a
`claim_violation` with `via: "bash"`, and announced on the board by `system`:

> ⚠ CLAIM VIOLATION: `s1a2b01`'s bash call modified `work/pelican.svg` while
> `s1a2b00` holds a live claim on it ("landing v2"). The result was snapshotted
> as rev 7 (`2f7b1230`). The previous revision is in file_history and can be put
> back with file_restore.

The write is **not** reverted: the claim's owner decides, and reverting from the
harness would also undo whatever else that command legitimately wrote. See
[ADR 0001](adr/0001-detect-bash-writes-rather-than-block-them.md).

`budget.json` is not content-watched — every agent rewrites it every turn, so
watching its bytes would blame whoever happened to be running a shell at the
time. Its **caps** are fingerprinted instead, which the harness never changes
mid-run, so lifting your own spend cap through the shell is still caught.

The watch reads a file again only when its size, mtime or ctime has moved
since the last snapshot; a run whose extractions reach a gigabyte would
otherwise pay over a second of hashing per shell call. It covers at most 500
files under `work/`, eight levels deep. Past that the harness says so once
per agent, as a `watch_truncated` event and an `ask` post to that agent: a
shell write to a file the watch left out is not detected or snapshotted.

### Read-only inputs (`inputs/`, `inputs.json`, `inputs`)

`--inputs DIR` copies a directory into `inputs/` and the harness keeps it as it was: `edit`, `write`, `claim_file` and `file_restore` refuse any path that is or resolves into `inputs/` (`read-only input: …`); the bash watch covers every file there through a stat cache, and a change, deletion or addition found after a shell call is healed from `.inputs-pristine/` and logged as `inputs_violation` with a `veto` post on the board; where the host allows it the pane runs with `inputs/` read-only at the kernel (`scripts/fsguard.sh`), and each agent records what it measured as `inputs_guard`. The `inputs` tool lists the manifest. `done` records an `inputs_check`. Several `--inputs` land each at `inputs/<name>/`, named in the manifest's `sets`; a set held in place is a link there, and every check walks through it. The whole design is in [inputs.md](inputs.md) and ADR 0005.

### Ledger (`record`, `ledger`, `ledger/`)

`record(kind, value, ts?, source?, evidence?, confidence?, supersedes?, refs?)` puts one fact in the swarm's ledger with its provenance. `kind` is `event` (a dated event; `ts` required: ISO 8601 with its zone, `Z` or an offset such as `+03:00`, or a date alone, which is that day at 00:00Z; a time without a zone is refused rather than read in the host's zone, since the zone is part of the evidence; stored as UTC, with the text as written kept as `ts_raw` and shown beside it in `ledger.md`), `ioc` (an indicator: an address, a hash, a path, an account), `finding` (a conclusion) or `absence` (a search that found nothing: `value` is what was looked for, `source` what was searched, `evidence` the query, the tool and its version, and the scope, such as allocated files only or unallocated space and slack too, and the time range; all three are required, since an empty result holds only for that query and that scope; optional to use, and nothing asks for it); `confidence` is `high`, `medium` or `low`. Version 3 (from 2026-09-26, after Fable and Codex read 1,040 entries of 14 runs) adds two kinds — `hypothesis` (a proposition under test, with `status` `open`, `supported` or `refuted`; `open` when not given; it never answers a goal section) and `limitation` (what the examination could not establish, with `reason` `not_examined`, `unavailable`, `failed`, `partial` or `excluded`) — and optional fields, each checked and in the chained core when present: `answers` (up to 8 goal section ids, `3` or `Q3`), `rel` (up to 10 links `{to: seq, kind: supports | contradicts | duplicates | derived_from | adds_part | irrelevant | inconclusive}`; the entry must exist, a duplicate must name the entry that stands, and `adds_part`, `irrelevant` and `inconclusive` name a question's answer: with `supports` and `contradicts` to an answer they are a late import's delta, [ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "Late evidence: the reverse sweep and the delta"), `sensitive` (it, or what it cites, holds a credential, a key or personal data), `clock` and `precision` (on a dated entry: which clock the time came from, and `date`, `minute`, `second`, `subsecond` or `unknown`; a date alone is recorded as `date`, never as midnight), `basis` (`observed` or `inferred`), `completion` (on an absence: `complete`, `partial` or `failed`; a search that did not complete is told to record the rest as a limitation), `attribution` (`{subject, subject_type: account | device | person | unknown, basis_refs}`, its refs resolved), `locators` (`{ref, at}`, where in one of the entry's refs) and `because` (with `supersedes`: why the correction corrects). A version 1, 2 or 3 ledger verifies as it always did; an older entry after a newer one breaks the chain, and a version the harness does not know is refused (version 4 below). A second author recording an entry with the same content is an attestation, appended to `ledger/attestations.jsonl` (chained: each line names the sha256 of its core and the one before) and folded into `authors` when read: `entries.jsonl` is never rewritten. The same sentence with other provenance or fields is its own entry, and is told of the other (link it with `rel` `duplicates`, or supersede it). An entry citing the kept output of a job that did not succeed is taken and told so, except a finding, which says why in `qualifies`, and a complete search, which it cannot support (version 4 below). Every entry lands in `ledger/entries.jsonl` (append-only, under the lock table's mutex) and the harness re-renders `ledger/ledger.md` — the timeline in time order, the indicators, the findings, each with its authors — after every record. `ledger(kind?, limit?)` lists the entries. A correction is a new entry with `supersedes` set to the `seq` it corrects (a number, `"7"` or `"#7"`): nothing is deleted, `ledger.md` marks the corrected entry "superseded by #N" where it stands and the correction "corrects #M", and `ledger` lists `superseded_by` on the corrected entry. `supersedes` is part of the entry's chained core, so a correction cannot be moved to another entry without breaking the chain. `refs` names the run's objects the entry rests on (at most 20): `input:<path>`, `job:<id>/<path>` (a path in the job's output, with or without `out/`, or its sealed `stdout.log`, `stderr.log`, `pip-before.txt` or `pip-after.txt`), `import:<id>/<path>`, `member:<generation>#<n>`, `sha256:<hex>`, `tool:<seat>/<file>` (a whole output the harness kept under `tool-output/<seat>/`), `trace:<sha256>` (one line of `traces/events.jsonl`, by the sha256 of its bytes without the newline), or `unresolved:<why>` when none can be named. `tool:` and `trace:` are a brain's own output, and are sealed before the entry is taken (in a run with the job service; without one they are refused, and the work is run again as a job): `tool:` resolves to the trace line, attributed by the collector to that seat (never a claimed or unverified line, never a spill), whose result names the file as a kept output with its sha256 and size; `trace:` to the line with that hash; either line must be on the chain (the next line's `prev` names it, or, the last, the trace's anchor). The kept bytes are hashed at once and refused when they differ from the trace's digest; then an import job over the hub's snapshot of them, checked against the digest again at its start, seals them, `store/imports/<job>/` publishes them with `import.json` (the ref, the digest, the trace line and its provenance: seat, tool, the tool's sha256 where the line records one, args, `ts`, `recv_ts`, `sid`, `seq`) and a `brain_output_sealed` journal line, and the entry cites `import:<job>/<file>` in place of the `tool:` or `trace:` ref (its answer says so); so do `attribution.basis_refs`, an alternative's `test_refs`, `qualifies` and an attest's or a dispute's `refs`, one seal per ref. The same ref is sealed once. What the trace did not capture — no line, another seat's, an edited line, bytes that changed since — cannot be sealed, and the refusal says to run the work again as a job. `catalog_search` output needs no seal: cite its `member:`. Each is resolved when the entry is written (the input in `inputs.json`, the file in the job's sealed manifest, the member in the generation's list, the blob in the store); one that does not resolve refuses the entry, with the nearest names. `refs` is in the chained core when present, so a ref added, removed or changed later breaks the chain. A finding with no refs is taken, and the answer carries a note asking for them; the same entry recorded again with refs, where the standing one has none, becomes its correction (it cannot be merged into a core that has none), and with other refs than the standing one's it is merged and told that its refs were not added. `ledger.md` and the report show the refs; custody resolves them again and counts the standing findings by what they rest on: refs (those that no longer resolve named, those that only say why none can be named counted), a path of the run's objects in the prose only, or nothing, which it names as an audit gap. Refused, with the reason: a `seq` that does not exist (the entry's own included), an entry already superseded (correct its correction instead, so the corrections stay one line), a correction that says everything its target says (the same sentence with another confidence, other refs or another status is a correction: 18 of 33 refusals on the recorded runs were that), a value that is not a whole number. A refused `record` keeps its whole arguments on the trace. A correction is never merged into an equal entry. `ledger.md` gives the timeline and indicators a `#` column, counts the corrections in its header, and lists absences in a "Searched, not found" table. The report and the summary keep a corrected entry as recorded and mark it, and show absences in their own section, never as findings. Both directories are harness-owned: a shell write there is a `claim_violation`. An entry over the limits is refused with the reason, never cut: the value at 2000 characters, the source at 1000, the evidence at 4000; the ledger holds 5000 entries.

One kind is never an agent's: `external`, material that entered the run from outside the evidence (a capture the fetch service sealed, `source_class: external_capture`; ADR 0012), written by the harness with its `source_class` and `provenance` in the chained core. An agent's `record kind=external` is refused; an agent cites it and records what it establishes. `ledger.md` lists it under "External material". Its hash goes on the trace on a `harness_record` line of the process that wrote it (the hub's own line in a microVM run; the operator's CLI's, as `scripts/lib/trace.sh` `trace_emit` writes one, when `evidence|material add` runs with no hub; a host pane's), and so does a person's hint recorded as a hypothesis in the asker's name. Custody holds the ledger to those lines beside the record tool's and the hub's `recordEntry` lines: every version 2 or later entry has its hash on one of them, or the ledger check fails (`not_on_trace`); in a microVM run only the harness's own line counts (`agent: "system"`, never one a seat claimed); a merged duplicate writes no entry and no line. Before 2026-09-29 no line carried a harness-authored entry's hash, and those runs fail the check as they always did.

**Version 4** (from 2026-09-27, after two rounds between Claude, Fable and GPT-6-Astra on a report that interprets). A finding is an observation and what its finder makes of it, recorded while the artefact is open. `basis` and `confidence` are required on it, and so are `indicates` (what the observation means, and the step from one to the other, one to three sentences) and `confidence_why` (where the data came from, whether the method is reliable for it, how specific the observation is, whether the sources depend on each other: the quality of the evidence, not a count, and nothing in the harness weighs it); an inferred finding lists `alternatives` (`{explanation, status: rejected | open, why, test_refs?}`, the `test_refs` resolved like `refs`) or says in `alternatives_none_why` why none was considered; `significance` is optional. A finding resting on a ref whose job did not succeed (as `resolveRef` reads the job's status) needs `qualifies` `[{ref, why}]` for each such ref, saying why those bytes are still usable; `qualifies` names only such refs, and an `absence` resting on one is refused unless its `completion` is `partial` or `failed` (a failed job's output cannot show that something is absent). The finding-only fields on another kind are refused with the reason. The hub writes `method` into every new entry with refs: one canonical record per cited job or import (keys sorted, no times: `job`, `job_kind`, `status`, `exit`, the `command`, or the `tool` with `tool_sha256` and `args`, or the `recipe` with `recipe_sha256` and `target` by its ref, the `image` and `image_digest`, the `declared_scope`, the `network`, the `profile`; for an import its `source` and who produced it, whose making is not recorded; a `member:` ref by its generation's recipe job), so the line alone says how its objects were made. It describes recorded execution, not the reads a tool made, and what the run did not record is `"unknown"`. `tool:` and `trace:` refs join the method derivers once their grammar is fixed with the job service. `because` stays for `supersedes` only. The core of a version 4 entry is version 3's plus these fields, each when present; what an entry says (`ledgerContent`, which decides a merge) now includes `indicates` and `qualifies`, and an answer's every field. Each version's core is dispatched explicitly and keeps the bytes it was chained with; an unknown version's core is its whole line, and the verifier refuses it. A finding written before version 4 is rendered "interpretation not recorded"; a supplemental interpretation is a new entry, never an edit.

`kind=answer` is the swarm's answer to one question of the goal (`section: question:<id>`; `3`, `Q3` and `question:3` are the same), its `summary` or its `narrative`. `value` is the answer; `reasoning` how the entries lead to it, citing `E-<seq>` for every claim (a range `E-12–E-15` too); for a question, `confidence` with `confidence_why`, `alternatives_open` and `would_change` are required; `contrary` names the entries that say otherwise and `limitations` the limitation entries that bound it (by seq); `inconclusive: true` says the ledger cannot answer it. An answer takes no `refs`, `ts`, `answers`, `rel` or finding field: it rests on entries, not objects. The hub turns every citation into an edge `{seq, hash}`: `support` (each `E-<seq>` in `value` and `reasoning` that is not contrary or a limitation), `contrary` and `limitations`, all in the core. Every claimed support is checked when the answer is recorded: it exists; a superseded entry is cited only beside the correction that stands, and supports nothing (it explains history); a disputed entry, or one resting on a failed job's output without its own `qualifies`, only with the answer's `qualifies` `[{ref: "E-<seq>", why}]`, which names nothing else; an answer that no longer stands on its own support cannot be cited. A question's answer rests on at least one standing finding, search or limitation that names its question in `answers`; a summary or a narrative on one standing entry. One answer stands per section: a second is refused, a revision `supersedes` the first (an answer corrects only an answer to its own section, and a non-answer never corrects an answer). The token check never refuses: the hashes, paths and registry keys, times, NTFS inodes, IP addresses and accounts (an address, `DOMAIN\user`, a SID) in the answer's `value` and `reasoning` that none of its cited entries holds are written into the entry as `unsupported_tokens` and told in the note, after normalisation (hex lower-case; a path's separators as `/`, its case folded, a drive letter dropped; a time to the second in UTC when it says its zone, a date or a time to the minute matching any time within it; `inode-128-1` by its first number). A cited answer lends its own cited entries, never its words. It finds omissions, not entailment: a conversion or a sum needs its derivation recorded as an entry. `ledger.md` lists the answers with what they rest on, and `ledger` lists every entry with `attested_by`, `disputed_by` and, for an answer that no longer stands on its support, `problems`.

`attest(seq, how, refs?)` says an agent other than the entry's authors re-derived it: `how` is what was re-derived from which sealed object and what was only read, `refs` the objects (resolved). It is a version 2 line of `ledger/attestations.jsonl` (`{v: 2, act: "attest", seq, target: <the entry's hash>, by, at, how, refs}`, the `how` inside the hashed record); a second author recording an entry word for word is now `act: "same_content"`, the only act folded into `authors`. A version 1 line after a version 2 one, or a version or act the harness does not know, breaks that chain. `dispute(seq, why, refs?, withdraw?)` says why an entry does not hold, or with `withdraw: true` takes the agent's own dispute back; it is a line of its own chain, `ledger/disputes.jsonl` (`{v: 1, act: "dispute" | "withdraw", seq, target, by, at, why, refs}`). Neither is written for the agent's own entry (a wrong entry of one's own is corrected with `supersedes`) nor for a superseded one; an agent that disputes an entry withdraws before attesting it. Both are hub-written in a VM run, the line's hash on the hub's trace line, and re-render `ledger.md`. An answer resting on an entry that is superseded (its correction not cited) or disputed (and not qualified) after it was written no longer stands, and neither does any answer resting on that one: the mark is transitive, recomputed from the ledger and the acts whenever they are read (`answerProblems`).

**Results and the negative bar** ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md)). An answer to a question carries `result`: `established` (a standing finding settles it), `partial`, `bounded_negative` (nothing found within what was searched), `not_determinable` (the evidence cannot say), `out_of_scope` or `premise_not_supported`. It is required on a new question answer; one recorded before it reads as it always did, and `inconclusive: true` is taken as `not_determinable`. `established`, `partial` and `premise_not_supported` rest on a standing finding (a premise is shown not to hold by what was found, never by a search that found nothing; one resting on a search alone in an older ledger meets the negative bar and is examination-limited). The answers check maps the results to its outcomes: `established` and `premise_not_supported` answer the question; `bounded_negative` answers it only on a question that asks whether something exists, over coverage the hub found complete, reviewed, and is examination-limited otherwise; `not_determinable` is inconclusive; `partial` and `out_of_scope` are limited; its machine line names each result. A negative is bounded and says so: an answer's value, whatever its result, is refused when it says flatly that something did not happen ("did not happen", "never occurred", "did not take place", "is proven absent" and their like) unless it carries `asserts_absence: true`, which is taken only with `bounded_negative`, on an existence question, resting on a coverage record whose computed coverage is complete and whose `detection_opportunity.trace_expected` is `yes`. The report states a negative's conclusion from its coverage records, never from the agents' words (no phrase list holds every wording): "No evidence that <proposition> was found in <objects, time range>." (or "It cannot be determined from <scope> whether …"), unless it earned "it did not happen"; the agents' words follow, whole, marked as not the conclusion, then "This is a bounded negative …" with its coverage rows.

`kind=coverage` is what a negative was searched over, a ledger kind of its own rather than fields on `absence`: a `not_determinable` answer often has no absence, one negative spans several searches, and the review is of the whole. `value` is the proposition searched for, `refs` the objects (resolved like any refs), `answers` the question; `time_range`, `search_method`, `settings`, `coverage_actual`, `skipped`, `failures` (each bounded at 2000 characters and refused past it, never cut), `result_refs` (the entries and job outputs the search produced), `alternatives` (what is still open), and `detection_opportunity` `{trace_expected: yes | no | unknown, why}`. The hub adds `inventory_rev` (the sha256 of `inputs.json` and the catalogue's generation records) and computes `coverage` (`complete` or `partial`) with `coverage_detail`: every object the record names, by digest where it has one, against what the jobs behind `result_refs` (and the jobs its interpretations name) declared as their inputs; a job over everything covers each object and is said to. It counts objects and never judges relevance, and it names objects as the job scopes do: a digest is the input or stored file that has it, a store path is its job's output by the manifest's digest, a catalogue directory holds its members, and a directory of the run's objects (an evidence directory, a job's whole output, a generation) may itself be the record's object. The record binds its entries among its results by hash (`result_bound`): a result superseded, disputed or changed since takes the record out of standing (`coverageProblems`); the gate names `coverage_stale`, fixed and never named, and a review of it, or of the answer while it rests on it, counts for nothing. These fields are refused on any other kind, and they are in the chained core when present. A `bounded_negative` or `not_determinable` answer on a material question cites a coverage record that names its question. A material negative (such an answer, or its coverage record) stands unreviewed until a seat that recorded neither attests it with `review` `{detection, reproduced, other_route}`, each `{done, text}`: whether it challenged the detection assumptions, reproduced a decisive check, and tried a materially different route, and what it did or why not; `review` is required on a negative and refused on anything else, and it counts as the critic's act. The ledger gate names `coverage_missing`, `negative_unreviewed` and `wording` defects, `ledger.md` and the report show "negative (unreviewed)" until then, and the finish line refuses `done` while one stands.

A coverage record may also carry `areas` `{allocated, deleted, unallocated, slack, secondary}`, each `searched`, `skipped` or `not_applicable` (every area named when it is given; a skipped one said in `skipped`), and, behind a `not_determinable`, `acquisition_ask` (`R-<n>`, an acquisition request of the run, checked) or `acquisition_none_why`; all in the chained core when present ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "After the first calibration run"). A question of the register carries `completeness` (the asker's `completeness`, else its words: "every", "all", "each", a complete list, set or inventory; "at all" does not count), and an established or partial answer to it rests on a standing coverage record for it that names its areas, or the gate names `completeness_uncovered`. Evidence added after the kickoff (the ledger's `external` entries of class `acquired_evidence`, `evidenceAdditions`) makes stale every standing `bounded_negative`, `not_determinable` or `partial` answer (and a premise rejected on a search alone) until the new evidence was examined for it, another seat reviewed that, and the examination says how the evidence bears on the answer: it cites a coverage record for its question recorded after the addition's entry that names the import among its objects and that another seat attested, or an entry other than a coverage record resting on the import (its refs, results or jobs name it) that another seat attested; and the entry that examined the import carries a delta: an entry recorded after the addition whose refs name the import's objects, among the results of that reviewed coverage record, or cited by the answer (or as its contrary) and attested by another seat, with a `rel` to the question's answer of kind `supports`, `contradicts`, `adds_part`, `irrelevant` or `inconclusive` (`deltasFor`; a citation of the import is not an examination of it, and a delta on an entry nobody else looked at, beside a coverage record somebody did, clears nothing). `negativeReview` counts no review made before an addition for an answer recorded after it. Once the addition is committed, never inside it, the import's files, and only they, are searched for every coverage record standing then with `looked_for` (the reverse sweep, version 2 lines of `ledger/sweeps.jsonl`, `of: "import"`, bound to the addition's external entry by its hash, each hit bound to the records whose strings it holds, `bears_on`), a pass at a time; its hits are said in each pass's board post by question when it completes, in the words of each `evidence_stale` they bear on, and as the warning `late_evidence_hits` on a question whose answer the addition does not stale and does not reach an entry that names the hit object; they hold nothing by themselves. The gate names `evidence_stale` ("new evidence since its coverage (ev-n); re-examine against it", with the records recorded before the addition's entry, those after it that do not name the import, those waiting for a review, an examination with no delta, the entries that interpret the import with none, and those that carry a delta outside the reviewed examination), whether or not the addition named the question, and `evidence add` names the answers it stales (`stale_answers`). Both are fixed and never named; `completeness_uncovered` is never excused by an acceptance, and `evidence_stale` only by one made after the addition's entry (the acceptance records the ledger's head, `ledger_seq`; `acceptanceExcuses`), whose reply lists what the finish line still holds on the question (`still_held`, every defect in `ACCEPTANCE_NEVER_EXCUSES`). A `not_determinable` whose coverage names neither an ask nor why none is a warning (`no_acquisition_ask`): the answers check prints it as `WARN:` and carries it in its machine line (`warnings`), the finish gate collects it, and the verdict's note repeats it; it holds nothing. Under the case policy's `more_evidence: no` an ask would be declined at once, so the warning's fix, and the reply to such an answer, give `acquisition_none_why` naming the policy (`NO_MORE_EVIDENCE_NONE_WHY`, read through `casePolicyMoreEvidence`), never an ask. Two more warnings are said the same way ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "After the run s993d40"): `partial_all_parts_established`, a partial answer every review of which holds every part it weighed established, one attesting it established (a case premise is named in the answer, "rests on the case premise that …", never held open), a part any review marks `not_asked` left out of "every part", when the warning says what the question does not ask and to record the answer established with it among its limitations (never a promotion: the answer stands as recorded); and `lead_findings_uncited`, each standing, undisputed finding or event the answer does not reach, directly or through what it cites (`answerReach`), that two seats hold and the lead register recorded under a lead of the question (`questionLeadEntries`: a lead's jobs' interpretations, and what its closes and confirmations name), or that names the question in its `answers`, or whose `rel` supports or contradicts an entry the answer cites, or is a delta on it (`answerCites`, `DELTA_REL_KINDS`: a `duplicates` or `derived_from` rel ties nothing); or one seat's that names the question and another question's standing answer reaches (relies on); all listed by `E-<seq>` with that tie (`questionUncited`; a lead register whose chain is broken gives no leads, and the ledger's own ties still count). Readiness carries the gate's warnings apart from its items (`warnings` in words, `warned` whole). Each warning is delivered where the decision is made ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "Warnings where the decision is made"; `finish.ts` `warningsAt`, over readiness's own inputs, `gateInputs`): in the reply to the record that writes the answer (`warnings`; their codes on the trace as `warned`), in the review offered for it (a material negative's, as the offer reaches its seat) and the reply to an attest on it, on a coverage record a negative rests on, or on an entry a warning names, in the reply to a lead's close or confirmation for each question whose warnings the act changed (`closeChanged`: the gate with and without its events, on one snapshot), and in `finish status`; the same words at every point (`warningWords`), and none holds.

The store sweep ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "After the round-13 scoring"; `extensions/store-sweep.ts`): a coverage record names `looked_for` (the literal strings a hit would contain, each 3 to 200 characters, at most 20, the same string in another case once) or `looked_for_none_why`, in the chained core. When the record is written the hub searches every output the run holds (each sealed job output and `stdout.log`/`stderr.log`, each import, each capture, each file under `tool-output/<seat>/`; not the inputs) for them: ASCII case folded, UTF-8 and UTF-16LE, streamed whole, the same bytes under several names read once (a sealed object is known by its manifest's sha256, a kept output or a job's log by its inode and, when another object has its size, by its content: a kept output and the import it was sealed as are one object, named when either is). The result is a line of `ledger/sweeps.jsonl`, hash-chained like the attestations and bound to the record by its hash: `{seq, target, state: clean | hits | partial, terms, searched: {objects, bytes}, hits, named_hits, echoes, unsearched}`, each hit `{ref, term, count, first_offset, encodings, also?, origins?}`; `hits` are in objects neither the record's refs nor the outputs among its result_refs name (a search's own output echoes what it looked for), `named_hits` in objects it names. Echoes ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "Echoes: authored, not derived"; `hitOrigins`): a hit in an object the record does not name, every name of which was made by the run's own words, is in `echoes` and holds nothing, each with `origins` (`{name, by, why, reads?}`, `by` the maker: `trace:<sha256>` of the line that kept the file, `job:<id>`): `registers` (a command whose words name only the run's registers and harness files, `RUN_REGISTERS`: ledger/, leads/, questions/, requests/, threads/, board/, inbox/, traces/, done/, locks/, SWARM.md, operator-requests.jsonl, team.json, names.json, budget.json, layout.json), `harness` (kept by one of the harness's own events from a seat's model words outside any tool call, `HARNESS_KEEPERS`: the self-compaction's), `searched` (the maker's own words, the run paths in them blanked, name the string, and it read nothing but what is accounted for). Accounted for: a register, or an object the record names in which the same sweep found the same string; never an input. A maker that read only what is accounted for, an object at least, without naming the string, is said among the named hits with its origins (`named_sources`, `reads`). A kept output's maker is the trace line that kept it, attributed to the seat whose directory holds it and on the chain (`keptOutputOrigins`), and what it read is the run paths its words name (`runPathsIn`); a job's is its record, and what it read its declared inputs (a job that saw everything, or reached the network, read what cannot be told); a sealed import is made as the output it sealed was. A maker that names no path, or a path that is neither a register nor an object the record names (the root, a parent, a hidden entry, a variable, a path outside the run, work/, catalog/…), leaves the hit standing. A line from before 2026-09-30 has no `echoes`. Each line names the version of the sweep's rules it was written under (`rules`, `SWEEP_RULES`; `SWEEP_RULE_CHANGES` says what each version changed and whether a line from before it can be read again from what it recorded); a line with none, from before 2026-09-30, is older than any versioned one. When the hub starts (a kickoff or a resume), and at the answers check and the finish gate (`reconcileSweeps`), every coverage record whose latest line is older than the current rules is read again under them ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "Re-reading after a rules change"; `rereadSweeps`): one line appended on the chain with the current `rules` and `reread` (`{from_version, reason: "rules changed", of, at, how: read | searched}`: the version the line read again was written under, null for none; its hash; when; and how), its hits sorted anew from what the line recorded (`resplitSweep`, nothing searched; `started_at` and `at` stay the search's) or, where a change needs bytes the line did not record, its record searched again within the sweep's budget. The trace gets a `sweep_reread` line and the board one post naming the records read again and the gate's sweep holds that changed. A line under the current rules is left alone, so the step is idempotent. A record with `looked_for` and no line is pending. The gate reads them (`sweepHolds`) for a negative the bar holds, a partial answer on a material question, and an answer asserting absence: `sweep_pending` and `sweep_hits` are fixed, never named, never excused by an acceptance; `sweep_partial` is excused by the operator's acceptance of the question. A hit object is examined, not only named ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "After the runs s9722fa and sb1b3c8"; `unexaminedHits`): an object in the `hits` of a sweep of an earlier coverage record for one of a record's questions, which the record names (in refs, by a directory holding it too, or among its object results), is cited in its `result_refs` by a standing finding, event, absence or limitation whose refs name the object itself (or another name of the same bytes) and whose `at` is at or after that sweep's; one without holds as `sweep_hits` (the hold's `unexamined`: each object, its other names, the strings, the record whose sweep found it and when), whether or not the record names `looked_for`, and the record's reply names them when it is written. The answers check and the finish gate run a sweep lost with its process (`reconcileSweeps`); a broken sweeps chain fails the answers check. A negative's review offer carries the sweeps and asks for the answer to be checked against the whole store. The reverse sweep of an evidence addition (`computeImportSweep`, `startImportSweep`, `readImportSweeps`, `importSweepWhole`) is described with `evidence_stale` above: the same byte search over the import's files alone, for the strings of the records standing at the addition (`recordsStandingAt`). It runs after the addition commits, in the hub's background (`reverseSweepInBackground`, a pass per addition not done at each round, never awaited) or, when the CLI made the addition with no hub, as a detached step (`scripts/reverse-sweep.ts`, `runReverseSweeps`, one at a time under the `reverse-sweep` lock); `swarm.sh evidence <run> list` continues one left undone. A pass has a budget of its own (`reverseSweepBudget`: `SWARM_REVERSE_SWEEP_MAX_SEC`, 120; `SWARM_REVERSE_SWEEP_MAX_BYTES`, 2 GiB); the objects it leaves are named on its line with `left` and searched by the next pass, whose line carries `pass` and `continues` (the hash of the line it continues); an object larger than a pass's budget is searched by a pass of its own, one over the store sweep's byte budget is named and not searched. Every line names what is not searched yet; an addition's sweep is the union of its passes (`importSweepWhole`), and each pass is posted on the board when it completes. `readSweeps` returns the coverage records' lines only.

**A source's broad extraction** ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "A source's broad extraction before a negative on it"; `extensions/preparation.ts`, `scripts/preparation.ts`). A pack's recipe says its `purpose`: `inventory` (it lists what a source holds; a recipe that says nothing is one) or `broad_extraction` (it parses the whole source into a searchable form), with the `capability` it prepares (its id when none) and its `exclusions`, what it does not hold; one the job images cannot run says why in `unavailable`, has no `auto`, and is refused by name with that why. The census asks every broad extraction about every input and lists each that applies in `catalog/plan.json`'s `preparations` (`input`, `recipe`, `capability`, `version`, `auto`: whether the kickoff runs it, `unavailable`, `target`); evidence added later is asked by the system's detect pass over each file, and no detect pass runs a broad extraction its pack does not mark `auto`. Each round the hub (`reconcilePreparation`) writes, once each, the receipts the records call for: `{type: "preparation", state, source: {sha256, ref, name, bytes}, recipe, recipe_version, recipe_sha256, capability, job?, lead?, generation?, manifest: {sha256, files, bytes} | null, exclusions, why?, by, when?}` with `state` planned (queued as a job, or offered as a lead), attempted (its job started), produced, partial or failed (its job ended; `exclusions` adds what this run of it did not cover), or declined (declared unavailable, refused by the kickoff's queue, whose `kickoff_queued` line now names what it refused and why, or a seat's decline). Every recipe job whose recipe is a broad extraction has its receipts, whoever asked for it. One not marked `auto` is offered as a lead (`openPreparationLead`: by `system`, unheld, `answers: []`, `material: false`, `routes: [{source, method: "recipe <id>"}]`, `objects: [source]`, and `preparation: {sha256, ref, capability, recipe}` on its open event), one per source digest and capability, and not when the same capability over the same bytes is queued, running, sealed or on the record. A seat's close of it deferred, infeasible or needs_operator is the preparation's decline (`by` the seat, `why` the close's ref and why), and so is a close any other way (resolved, duplicate, negative) while no job of it is queued or running, its `why` saying how it was closed and that nothing ran it; a preparation lead whose extraction reached an outcome by any route is closed by `system`, `withdrawn`, citing the receipt, while no seat holds it (a held one is its holder's to close). A hold's fix never points at a closed lead (`holdFix`, with the closed preparation leads `preparationFacts` carries). The gate (`ledgerGate`, from `preparationFacts`): a material negative that says the event did not happen, or cites a coverage record the hub found complete that names the source or a directory holding it, is held as `preparation_pending` while that source has a capability planned or attempted and never released; produced, partial, failed or declined releases it, and so does the operator's acceptance (not in `ACCEPTANCE_NEVER_EXCUSES`). Every other material negative whose coverage reaches such a source (naming it, a member of its catalogue, or outputs made from it, followed back through the jobs' declared inputs) while it has not produced is warned, `preparation_missing`, at every point `warningsAt` delivers. A negative's review offer opens with the state of each source it rests on (`negativePreparationWords`). The finish revision's parts gain `preparation` (each receipt) in a run that has one.

A downgrade: an answer that supersedes one whose result is established or partial with a result of not_determinable or bounded_negative carries `downgrade: {evidence, why}` (entries E-<seq> that stand, other than the answer it supersedes, or objects that resolve), in the chained core; without it the record is refused, and `downgrade` on any other answer is refused too. A doubt with no counter-evidence stays a dispute, with a lower strength or confidence. `downgradeCheck` reads links only: at least one entry of the evidence bears against the earlier chain (the earlier answer and its support): a finding or event whose `rel` contradicts one of them, a hypothesis with status refuted whose `rel` names one or that corrects one, a supporting entry under a dispute in force or contradicted by a standing finding or event, or a correction (`supersedes`, at any depth) of a supporting entry; otherwise the refusal names each entry and why it does not bear (a limitation, a coverage record, a search that found nothing, a finding that contradicts nothing). And no finding or event of the earlier answer's support recorded for its question may still stand (not superseded, under no dispute in force, contradicted by no standing finding or event); while one does, the refusal names them and says to answer partial.

The gate at done is the goal's (`scripts/check-answers.ts` without `--report`, the ledger gate `ledgerGate`): each named section (`--sections 1,2,summary,narrative`, a brief's questions with `--sections-in inputs/CASE.md`) has its standing answer, and a question's answer rests on a standing finding whose refs resolve now (bytes checked where the run sealed them), a complete search when the goal says the question asks whether something exists (`--existence`; for any other question a search documents the search and the section is examination-limited), or a limitation (examination-limited). A mechanical defect is a section with no answer, an answer that no longer stands on its support, an answer disputed, an answer no agent other than its author attested or disputed, or an open contradiction: two standing entries linked `contradicts`, weighed by no standing answer (one holding both, one of them as `contrary`) and named by no standing limitation (which names an entry by `rel` or by `E-<seq>` in what it says). Each is printed with what fixes it; the check fails while any is not named by a standing limitation (citing `E-<seq>` of the answer, or with `answers` naming a section left unanswered), so the first `done` is refused with the fix and the next passes once each defect left is named. A named defect is still reported, and the release counts it; the check passes on it, and the finish line still holds `done` on it under every stop policy (the gate's `holding`): a limitation never makes an unsupported answer supported, and never ends a run. The chains of the ledger, the attestations and the disputes must all verify. `--report` keeps the check goals used before version 4 (each section of the report rests on the ledger).

An attest of an answer to a question (`attest(seq, how, refs, strength, answer_review)`, [ADR 0015](adr/0015-one-seat-finishes-and-work-is-offered.md)) says how strongly the review holds it: `strength` `established` or `best_candidate`, and `answer_review` `{reproduced, read, parts: [{part, established, why}], inference, alternatives, other_family: {checked, text}}`, both in the attestation's hashed record. `alternatives` is `[{explanation, why, evidence}]`, each alternative explanation the reviewer weighed, why the evidence rules it out, and the entries that show it (`evidence`: E-<seq>, each checked against the ledger, the attest refused for one that is not there). An alternative counts (`alternativeCounts`) only with an entry named and with an explanation and a why that are neither empty nor a placeholder nor the same words; `established` names at least one that counts, and an established attest that names none (a text, as an older review's, or filler) is recorded `best_candidate` with the reason in `capped`, and the reply says so; the same seat's later established review is recorded (any other repeat is not). The confidence the run records (`recordedConfidence`) is the stated one, except that on an answer recorded under the rule (`confidence_rule: 1`, hub-written into the answer's chained core) a high stands only on an established answer another seat attested established naming an alternative that counts: any other high is recorded medium, the reply to the answer says so, and the report, the metrics (`confidence`) and the calibration score show the recorded one with the stated one beside it. An answer without `confidence_rule` was recorded before the rule and keeps its declared confidence, shown "as declared". A medium or low confidence, a part the review holds not established, or a route the answer's `would_change` names that nothing took (a planned route of its question no job under it examined, named by its source; a lead id not closed resolved, negative or duplicate) allows only `best_candidate`, and the hub writes why into the record (`capped`). An answer that claims established (`claimsEstablished`: its result established, or recorded before results and not inconclusive) and that every review holds a best candidate is examination-limited in the answers check ("a best candidate, not established", listed as `best_candidate` in its machine line) and never answered; an answer with one established review is answered. The one test (`heldAsBestCandidate`) is read by readiness, the answers check (and through its machine line the finish gate) and the report; a partial answer, a negative, out of scope and a premise shown not to hold are never held as best candidates. On a partial answer the cap is its own ([ADR 0015](adr/0015-one-seat-finishes-and-work-is-offered.md), "After the run s9722fa"): a review part may carry `declared_open: "E-<seq>"`, a limitation the answer cites or a coverage record it rests on (`declaredOpenBy`, checked at the attest; refused on an answer that is not partial), and only a part held not established without it caps the review; the answer's confidence and the routes its `would_change` names do not. A source-first review ([ADR 0015](adr/0015-one-seat-finishes-and-work-is-offered.md), "A source-first review"): `answer_review` may carry `discriminator` `{rival, test, favours_if, outcome, refs}` (the strongest rival, the test that separates it from the answer, the result that would favour each, what it showed, and the E-<seq> or object it rests on: each entry checked against the ledger, each object resolved, never the answer under review, nor only entries the answer already cites, the attest refused otherwise), `reproduced_at` `[{ref, offset, length?, value?}]` (up to 10; where each literal value it vouches for was read: a sealed object, the byte offset where the value begins, and the value, which must be among the words of the answer (its value and reasoning) or of an entry it reaches (its support and what those cite, `answerReach`, `chainWords`), at least three characters, or a length whose bytes are read back and must be words of the answer) and `derivation` `{job, inputs}` (for a derived value: the job that derived it and the objects it read), each in the hashed record only when given. The hub checks each locator against the sealed bytes at its offset (`checkLocator`: the ref resolves to a sealed object of the run, and the value is there in UTF-8 or UTF-16LE, ASCII letters in either case; a bounded read at the offset and 256 bytes either side, to say where the value is when it is not at the offset, never a scan and never a whole hash) and a derivation against the run (`checkDerivation`: a sealed job that ran to its end, each input resolving and among what the job declared). An established attest of an answer that claims established, on a material question, with no discriminator that counts (`discriminatorCounts`: no placeholder, the rival not the test's words, a ref), with a locator that does not verify, or with a derivation that does not resolve, is recorded `best_candidate`, each reason in `capped` (codes `no_discriminator`, `locator_unverified`, `derivation_unverified`; `reviewEvidenceCaps`), and the reply says how to fix each (`REVIEW_CAP_FIX`). One with neither a locator nor a derivation is warned, never capped (`unlocated`; the gate's warning `no_locator_or_derivation`, on an answer held established by source-first reviews none of which locates a value or names a derivation, in the attest's reply and finish status; `REVIEW_UNLOCATED_FIX`); the metrics count each answer that claimed established recorded partial after a capped attest (`reversals.partial_after_cap`). A partial answer's review is checked, a locator that does not verify is said, and nothing is capped for it; a best candidate asked for is not capped again. Byte presence proves presence, not attribution: the discriminator is what weighs attribution. A negative's review is unchanged, and an attestation from before strengths reads as it always did.

Claim and open-part rows ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "Claim and open-part rows"; `extensions/premises.ts`): an answer to a question may carry `parts: [{id, part, status: established | open, refs, open_by?}]` (at most 20; `id` 1-16 letters, digits, dot, dash or underscore), each part the question asks as the answer reads the revision its `question_rev` names: established on the entries in `refs` (at least one), or open with what bounds it in `open_by`, an acquisition request `R-<n>` (kind acquisition), a lead `L-<n>`, or a standing limitation or coverage record `E-<seq>` (a limitation named there joins the answer's `limitations`). `open_by: P-<n>` is refused: a premise is never an open part. The rows' entries are citations, as the reasoning's are. A partial answer with no open part is refused ("record it established or name what is open", `PARTIAL_NEEDS_OPEN_PART`), and so is an established one with an open part; the other results may carry rows. In the chained core only when present. A review part may carry `id` (the answer's row it weighs; one the answer does not carry, or an id on an answer without rows, is refused) or `missing: true` (a part of the question the answer leaves out: never with `established: true`, an id or `declared_open`), each in the attestation's hashed record only when given; a part without an id reads as before. On a partial answer a part its own row holds open does not cap the review, as `declared_open` does not; a missing part caps an established review on any answer as a part held not established does, and is warned of (`part_omitted`) while the answer stands. An open part is a part the question asks: detail beyond it, an example category the evidence does not show, an exhaustiveness it does not demand and a hedge on direction are limitations (the record tool and `PARTIAL_NEEDS_OPEN_PART` say so; a complete set is held to its completeness coverage). A review part may carry `not_asked: true` (a part the answer holds that the question does not ask: established false, never with `missing`, in the hashed record only when given): it caps nothing, on any answer. Where an answer is rendered (the report's §1 table, §2 chain and §5 answer, the console's question view, `questions/questions.md`, and the release, whose report is the same render), each of its parts is shown established on what it rests on or open with what bounds it, a review's `not_asked` mark beside the part it marks (matched by id, else by its words; one that names no row said apart), and a partial answer leads with a plain line, "Asked parts: N of M established. Open: K[, which a review marks as not asked]." (`answerPartsStanding`, `partsStanding`, `partsSummaryWords`: a part is asked unless a review marks it not asked; a part a review names missing is asked and not established); when every asked part is established, "every part the question asks is established" is said beside the partial label, which is unchanged ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "What the report shows of an answer's parts"). An answer without rows renders as before. The question view carries it as `answer.standing` (the rows with `not_asked_by`, the counts, `summary`, `plain`).

A part at the limit of the evidence ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "A part at the limit of the evidence"): a row may be `status: limited` with `limited_by: E-<seq>`, a part the question asks that the evidence in scope cannot settle. The entry is a standing coverage record whose `answers` name the question, or a standing limitation whose `reason` is `unavailable` or `excluded` (it joins the answer's `limitations`); a limitation `not_examined`, `failed` or `partial` bounds an open part, never a limited one, and `limited_by: P-<n>` is refused. `open_by` on a limited row and `limited_by` on another are refused. A limited row keeps the answer partial as an open one does: a partial answer needs an open or a limited row (`PARTIAL_NEEDS_OPEN_PART`), and an established answer with a limited row is refused. A limitation whose reason is unavailable or excluded takes a negative's review (`limitBoundKind`), and `limitedBoundReview` (over `negativeReview`) says whether a seat that recorded neither the bound nor the answer reviewed it; that is shown, and gates nothing. A review part may carry `at_limit: true` (by id, established false, never with `missing` or `not_asked`, in the hashed record only when given): it caps nothing. Where an answer is rendered, a limited row says what shows it and whether another seat reviewed that (`answerPartsStanding` with the ledger: `rows[].bound`, `limited`, `limited_unreviewed`), and the plain line counts it apart. `swarm.sh metrics` lists them (`claims.limited`).

A locator is not coverage ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "A locator is not coverage"): on an established attest of an answer to a material question whose `answer_review.reproduced_at` names objects, the hub follows each object to the run's input files (`preparation.ts inputReach`: an input is its own source, a catalogue member leads to its generation's target, a job's output through the declared inputs of the jobs that made it; a job over everything leads to none). For each input reached, a standing coverage record for the question whose results still stand must name the input or a directory holding it, say every area `searched` or `not_applicable`, and cite among its `result_refs` a job whose declared inputs reach the input (`rivalAreasUncovered`); otherwise the attest is recorded best_candidate with `rival_area_uncovered` in `capped` ("a locator is not coverage: the value was read from input:…, and …"), and the reply gives `RIVAL_AREA_FIX`. A partial answer's review, and one that derives without locating, are not held by it. `swarm.sh metrics` counts the caps (`review_caps.rival_area_uncovered`) and each area's `not_applicable` across standing coverage records (`coverage.areas_not_applicable`); replay's `review_caps` projection reads the rule over recorded reviews.

An answer to a question may cite premises (`premises: [{id: "P-<n>", rev, stance: assumed | supported | contradicted | unresolved, refs?, conditional?, scope?: {entities?, times?}}]`, at most 20, one per premise; [ADR 0011](adr/0011-questions-are-a-register-with-their-askers.md), "Premises"), in the chained core only when present, and in the fingerprint a summary is bound to (and the conclusion fields) only when present. Checked under the registers' lock: each premise in the register, not withdrawn, at the revision cited; a proposition under test assumed only with `conditional: true`; a premise whose scope names questions assumed without a condition only by an answer to one of them; a citation's `scope` inside its premise's (each entity the premise's, each range inside one of its ranges); `supported` naming a standing, undisputed finding or event in `refs`. A summary or a narrative takes neither `parts` nor `premises`. The gate `premise_inconsistent` (`premiseConflicts`, `rebuttingRefs`) holds the sections of both answers while one standing answer assumes a premise revision, without a condition, and another contradicts the same revision, over scopes that overlap (`scopesOverlap`: unless both name entities and share none, or both name times and no two ranges meet, a date closing a range reaching to its day's end; a citation's scope is its own, or its premise's at the revision it cites), and the contradiction names no standing, undisputed finding or event; fixed, never named; the fix names the four ways out (revise an answer, name the rebutting finding, narrow a scope, answer conditionally). A premise withdrawn, or a revision revised since, holds nothing (`premise_withdrawn` and `premise_revised` warn the answers citing it); on a question the operator marked not material the conflict is a warning (`premise_inconsistent`, "warned, never held"); an acceptance of the question excuses it in readiness, `still_held` and the answers check alike (`acceptanceExcuses`). Named, the pair holds nothing: the premise goes to the operator as a request of kind `premise`, and the answer that assumes it is warned (`premise_disputed`). An answer citing a premise at a revision it has moved past is warned (`premise_revised`), one citing a withdrawn premise too (`premise_withdrawn`). The reply to the record says each conflict the answer meets, and the dispute it opened with its request id.

A standing dispute stays in force on the correction that stands in its entry's place (`disputesInForce`, marked `inherited_from`): a correction may fix what the dispute named, but only its disputer answers the dispute, by withdrawing it (naming either entry) or disputing again. Answers resting on the correction need it qualified, a coverage record naming it no longer stands, a lead closed on it reopens, the disputer cannot attest it, and an answer corrected over its own dispute is still `answer_disputed`.

A summary or a narrative names the questions it sums up as `Q-<n>` (or `question:<id>`): each becomes a symbolic citation, `question_refs: [{q, section, answer, fp}]` in the hashed core, bound to the fingerprint of the answer that stood (its result, the question revision it answers, and the hashes of its support, contrary evidence and limitations), and the answer is not also cited by its seq; an answer to a question that a summary or narrative cites by its seq (`E-<n>`, as the c10 pilot's did) is bound to that question the same way (`question:<n>`, the answer that stands for it now), and the reply says so. The summary keeps standing through a correction of that answer that keeps the fingerprint (a rewording), and no longer stands when the support, the revision or the contrary evidence changes; an answer's contrary evidence is held to its standing as its support is (a contrary entry superseded since the answer weighed it, its correction not weighed with it, or disputed and not qualified, takes the answer down, and with it the summary citing its question, without the answer being recorded again); a question it cites that is withdrawn or re-scoped since is a gate defect. A summary citing a question with no standing answer, or one whose answer no longer stands, is refused.

#### The codes the answers check names

The answers check (`ledgerGate`, run by `scripts/check-answers.ts`, readiness and the finish gate) holds the finish line on a defect, says a warning where the decision is made, and records a capped attest as a best candidate. Every code, with where it is raised, the design that states it and the tests and contract fixtures that exercise it, is in the generated register [docs/rules.md](rules.md) (`scripts/rules.ts`). The oldest defects, named here because the sections above describe them in words:

- `no_answer`: a section the goal requires (a question, `summary`, `narrative`) has no standing answer.
- `answer_support`: a standing answer no longer stands on its support: an entry it cites is superseded, disputed, gone, or no longer the entry it bound.
- `answer_disputed`: a standing answer is under a dispute in force, its own or one inherited from the answer it corrects.
- `no_critic_act`: no seat other than the answer's authors has attested or disputed it, nor reviewed it as a negative.
- `open_contradiction`: two standing entries contradict each other (`rel contradicts`) and neither is superseded or weighed in an answer.
- `coverage_missing`: a material negative (a bounded negative, not determinable, or a premise rejected on a search alone) rests on no standing coverage record.
- `negative_unreviewed`: a material negative, or its coverage record, has no review by a seat that recorded neither.

### Catalog, toolbox, quarantine (`catalog/`, `toolbox.json`, `work/extracted/`)

Three kickoff options for evidence work, all recorded in the registry:

- `--catalog` takes the census of the inputs (`scripts/evidence-catalog.sh`, a wrapper for `scripts/evidence_catalog.py`) and catalogues them with the packs' recipes (`recipes/<name>/` in a pack: a `recipe.json` — id, version, object, order, min_bytes, optional `suffixes` and `magic` (bytes at an offset: what a file a job made must have to be offered to it by the derived catalogue; the harness compares them and knows no format), runtime, entry, `auto` triggers, limits, outputs, what it covers, and its `purpose` (`inventory`, or `broad_extraction` with the `capability` it prepares and its `exclusions`, and `unavailable` with why when the job images cannot run it; below) — and an entry answering `detect --target T` and `run --target T --out DIR`, writing its own `index.tsv` and `coverage.json`). computer-forensics-base ships `disk-volumes` (for a disk image: `partitions.txt` and, per filesystem partition, `fsstat.txt`, a body file, a path list and a `mactime` timeline; an image with no partition table read at sector 0 under `p0`), `memory-windows` (Volatility's `windows.info`, `pslist`, `psscan`, `cmdline`, `netscan`, `malfind`, `dlllist`), `archive-members` (a tar, zip or 7z member list, `members.tsv`, nothing extracted) and `ad1-items` (an AccessData AD1 logical image, found by its `ADSEGMENTEDFILE` header: every item in `members.tsv`, archive-members' columns first, with its locator (its address, which names it alike in a partial and a whole read), the modified, accessed and created times, the MD5 and SHA-1 the image records, the SHA-256 of each file's content and whether it matches them, every metadata entry in `attributes.tsv`; nothing extracted: the pack's `ad1_extract` tool, run as a job, writes the files out, and the derived catalogue takes them from there). Every input gets a row in `catalog/coverage.tsv` with its status and why; each step is time-boxed (`SWARM_CATALOG_STEP_TIMEOUT`, default 900 s) and keeps its stderr whole beside its output. In a microVM run with the job service the census only plans (`catalog/plan.json`) and the recipes run as jobs once the hub is up: each result is a generation (`catalog/gen/<g>/`, with `generation.json`), each change a revision (`catalog/revisions/<n>/`, `MANIFEST.json` written last), announced on the board with the tag `result`; a disk's files are also linked at `catalog/<input>/`. The derived catalogue, on unless `--no-derived-catalog`, does the same for what jobs make: each file of a tool, command or import job, whatever its status, is offered by content (sha256; an object already offered, answered, catalogued or given as an input is skipped, named) to the derived recipes whose `min_bytes`, `suffixes` or `magic` take it, and only to those. Its work runs as the requester `derived`, the lowest lane: one job at a time, started only when no other job waits, the largest objects first, 32 object–recipe pairs a detect pass, within 300 worker-seconds each 10 minutes and at most 50 derived generations (`--derived-limit N`) and 2 GiB of them a run. A pass's answers are read whatever its status; a pair it did not answer is asked once more, then named. A complete derived generation is posted to all, a partial one to the agent whose job made the object with the recipe's reasons, and a complete catalogue of a readable form (a volume decrypted from an encrypted one, within three jobs of lineage) is linked to the partial one, which the revision index and `catalog_search which=generations` show. Otherwise the recipes run before any agent starts, into `catalog/<input>/`. `catalog/README.md` starts with a `Summary:` line and indexes every file with its row count and size; `SWARM.md` gets the same under "Evidence catalog". The census files are `chmod a-w`, and every VM sees `catalog/` read-only.
- `--toolbox dfir` runs `scripts/toolbox.sh`: `toolbox.json` holds `present` (name, version, use) and `missing` (name, use, install command) for the Sleuth Kit, Volatility 3, regipy, python-evtx, yara, exiftool, sqlite3, strings and python3; `SWARM.md` gets a "Toolbox" section so the agents start knowing what they have. `--toolbox-required` turns a missing tool into a `BLOCKER`. In a microVM run whose image has `/etc/dfirswarm/tools.md` (images/install.py writes it), `toolbox.json` records it as `tools_md` and `SWARM.md` gets a "Programs" paragraph that points at that file inside the VM instead of the table: the image describes itself, and the contract names no program.
- `--quarantine` creates `work/extracted/` and `work/quarantine/`, adds `--noexec` for both to the pane's `fsguard.sh` wrapper (seatbelt `process-exec*` deny on macOS, a `noexec` bind mount on Linux) and sets `SWARM_QUARANTINE=1` in every pane, on which the harness strips execute bits from any file written there after a `bash` or forged-tool call. An interpreter told to read a file (`python3 sample.py`) is not stopped by either — the contract says so and the prompt tells the agents what the directories are for.

### Tool jobs and the store (`job_run`, `job_status`, `catalog_request`, `store/`)

In a microVM run with the job service (the default; `--no-jobs` and host runs have none), the hub runs tool work in throwaway worker VMs (`scripts/job-service.ts`, ADR 0010). The seat's calls are `jobSubmit`, `jobStatus` and `catalogRequest` on its socket; who asks is always the seat. A job is a command, a pack or forged tool with its arguments (checked against its manifest; its script's sha256 against the manifest's), a recipe over one object, a detect pass, or an import: a file or directory an agent made under `work/` or `tool-output/`, copied into the job's `$OUT` as it is now, each file hashed before and after the copy up to 2 GiB (size and mtime above), links and special files named and left out; the record says the source was live and its producer not stopped (`copied_live`, `producer_fenced: false` in its stdout.log), and a file that changed while it was copied fails the import. What a worker sees is the job's scope, kept apart in the spec and on the journal as said (`job-scope.ts`): `inputs` left out is `default-all` and `["all"]` is `all` — the worker sees what a seat sees, read-only: `inputs/` (no-exec), `store/`, `catalog/`, `tools/`, `tool-output/`, the packs and all of `work/` (`work/extracted/` and `work/quarantine/` no-exec; the record says it is live and may change) — and a list, possibly empty, is `declared`: resolved at submission (`input:<path>` through `inputs.json` and the set it belongs to, a directory as `input:<dir>/`; `job:<id>[/<path>]`, `import:<id>[/<path>]` and `sha256:<hex>` through the store; `member:<gen>#<n>` as its generation; `work/…` and `tool-output/…` by `lstat`), a declaration that does not resolve refusing the job with the reason and never widening to fit, a segment set expanded from the census's `input_collection` record (every set the census saw is in `catalog/plan.json` `collections`), a recipe's or detect pass's target paths added. The worker of a declared job is given a view the hub builds beside its staging directory, outside every VM, mounted at the run's path: a declared directory of the evidence or a job's whole output bound as it is (at most 8), and so an evidence set or a directory of it whose every name in `inputs.json` is in the scope (the view's entry says why), a file of the evidence in a scope that covers part of a set cloned from a descriptor (APFS clonefile, a reflink) or linked from the run's one copy checked against `inputs.json` (never a hard link to the evidence), a store file linked, cloned or copied, an agent's file or directory cloned or copied from a descriptor opened without following a link, the path held to the same inode afterwards, and hashed (a link or special file under a declared directory named and left out); `tools/` and the packs as code. Its `job_started` carries `scope` (`kind`; for a declared one the objects, files and binds, and `store/jobs/<id>/scope.<attempt>.json`, the declared, expanded and accessible manifests, by its sha256); `vm.ts` holds every share before it binds it (plain absolute paths, a directory, a view's device and inode as built, a view holding only directories and regular files) and checks each again after the VM is made, before anything runs. What a job read within its scope is not observed. It writes only its own `$OUT` (`<sandbox>/.jobs/<id>`); no network unless the job asks for the operator's allowlist (plus PyPI with `--allow-install`, with pip's list kept before and after); no credential, never the board, the inbox, the ledger or the sessions. The hub makes and runs each worker through a short-lived child process (`vm.ts worker-once`), never its own msb SDK, one worker made at a time; a worker msb refused to start before anything ran is removed and made once more, the first error kept as `boot_retry` in `job_finished`. Each step is a line of `store/journal.jsonl` — `job_accepted` (spec, requester with the name and doing it had), `job_started` (declared scope as said, `scope` with its kind and manifest, accessible mounts, `observed: "unknown"`, network, image), `job_finished`, `job_fenced` (only once the maker process is gone and msb neither inspects nor lists the worker; `late: true` when the backstop or the service's stop confirmed it afterwards, `by: "stop"` when the stop did, the hub's own stop or `vm.ts seal-left` after it), `job_unsealed` (a job whose worker was still not confirmed gone when the service stopped: its staging directory, never read, and why; custody names it with that why until the stop seals it), `job_committed` (a job the hub left running, sealed after it by the stop, has none of `job_finished`: its `job_fenced` by the stop is followed by `job_committed` with status `stopped`, or `cancelled` when the stop had asked for that) (status, outputs, the manifest's sha256, the logs' sha256), `generation_committed`, `revision_published`, `preparation` (a source's broad extraction, a receipt per step: below), `job_notified`, `job_returned`, `jobs_degraded` and `jobs_recovered` (three jobs in a row ran in no worker, and every seat was told; the next one ran), `note` (an examiner's note added after the run with `evidence-store.ts note`, never an edit), `job_deduplicated` (a second request for the same recipe over the same object, answered with the earlier job; its agent is told when that job is done), `job_similar` and `job_same_as` (the reuse hints, below), and the derived catalogue's lines: `derived_offered` (a job's files offered, skipped as known, or taken by no recipe), `detect_answered` (a derived pass's answers and what it left), `detect_unanswered`, `derived_deferred` (its rolling budget binds), `derived_bounded` (a ceiling of the run, told to all) and `generation_related` (a partial generation's readable form), `brain_output_sealed` and `brain_output_refused` (a cited `tool:` or `trace:` output sealed as an import, or why not); `generation_committed` carries its target's sha256, its trigger and its parent's status — each line's `prev` the sha256 of the line before, the head in `<sandbox>.journal-anchor.json` beside the run. A committed job's output is `store/jobs/<id>/out/` (read-only; links, FIFOs, sockets and devices left out and named in the manifest; every file hard-linked to `store/blobs/<sha256>`), with `manifest.json`, `job.json`, `stdout.log` and `stderr.log`. `job_run` answers in the call when the job is done within its wait (default 12 s); otherwise a post tagged `result` tells the seat. A citation of a job's file is `job:<id>/<path>`. Custody verifies the chain against its anchor and every committed file against its manifest; the package exports the record.

While a job runs, the service samples it every half minute and at every `job_status` ([ADR 0015](adr/0015-one-seat-finishes-and-work-is-offered.md), `scripts/job-telemetry.ts`): its `$OUT` staging on the host (files, bytes, the newest file's time and name, control characters replaced; no link followed; at most 10,000 entries walked, and the count says `+` past that), its stdout and stderr sizes, and its CPU and I/O from msb's metrics for the worker VM, or else from a heartbeat the worker script writes to `/job/heartbeat` every 15 s (the VM's non-idle jiffies and disk sectors, the VM running this one job). The samples are kept beside the staging (`telemetry.jsonl`), metadata only. `job_status` of a running job carries `progress`: `moving`, `quiet` (outputs and logs still, CPU or I/O moving; or every signal still with its timeout under two minutes away), `suspected_stall` (all three still for `SWARM_JOB_STALL_SEC`, 600, and its timeout not near) or `unknown` (no CPU or I/O signal, or none current: a heartbeat whose stamp has not advanced for a minute of samples is a loop that died, and a last sample more than two minutes old means the sampler is behind or stopped; stillness is never counted across a gap of more than two minutes between samples), each signal with how long it has been still, `sealed: false`, and the hint that cancelling keeps what the job wrote. Nothing cancels a job but its requester. The header lists a seat's own suspected stalls. A job that fails with exit 127, or whose stderr has a shell's own diagnostic for it (bash's `X: command not found`, zsh's `command not found: X`, or dash's `sh: 1: X: not found` with exit 127), is recorded as `program_missing` `{program, profile, image}` (an application's own `X: not found`, a file or an object it looked for, is not one) (a `job_program_missing` journal line, the job record, its reason and `job_status`), and the console's job detail shows it. A job that ends non-zero on a write its worker refused is recorded as `write_refused` `{error, path, file, line, lines, files}` (a `job_write_refused` journal line and the job record; `scripts/job-write-refused.ts`): its stdout, its stderr and every stderr file it kept in `$OUT` (`*.stderr`, `*.err`, `stderr.log`, `stderr.txt`) are read whole, and a line counts when it says `Read-only file system` (unless the path it names is one the job may write) or `Permission denied` on a path outside `$OUT` and its control directory, a relative path read from the run's directory, where the job starts. Its reason is `exit N: a write outside $OUT was refused (…)`: the error, the path whole, where the line is (`store/jobs/<id>/stderr.log line 3`, `job:<id>/<file> line 2`), how many such lines, that the working directory and the whole run are read-only in a worker, `$OUT` by name and path, and to point the program's log, temp or output options there or `cd "$OUT"`. The match is on the error text alone; no program is named. A job that ends non-zero on a program its worker could not execute is recorded as `exec_refused` `{error, path, file, line, text, lines, files}` (a `job_exec_refused` journal line and the job record; `scripts/job-exec-refused.ts`), and read before `program_missing` and `write_refused`. Three signs count: the exit status 126 (the shell found the command and could not execute it), which is enough by itself, with the shell's own line that names the program when stdout, stderr or a stderr file kept in `$OUT` has one (`Permission denied`, `cannot execute binary file` as `Exec format error`, `bad interpreter` (127 as well on Linux's bash, and no `program_missing`), `Is a directory`; `error`, `path`, `file`, `line` and `text` are null when none does: the program's stderr may have gone into a file of the job's own); at any status, a line that carries the dynamic loader's `failed to map segment from shared object` (the loader's own exit 127 is then no `program_missing`; glibc says it also when the worker had no memory left to map the file, which the reply says); and, at another status, a `Permission denied` that names an existing regular file under a directory a worker mounts read-only (`store/`, `inputs/`, `work/extracted/`, `work/quarantine/`), where a write is refused with `Read-only file system` and an existing file that cannot be opened is one that cannot be executed (a program run by a program that reports its own status, such as a Python subprocess call). A `Permission denied` anywhere else at another status is not read as an execution: nothing in the line tells a program that could not be run from a file that could not be written (a directory made read-only in `$OUT`), and a denied write is the write refusal's. `text` is the line itself when it is at most 2000 characters, else only named by where it is. Its reason is `exit N: a program it ran could not be executed (…)`: the error, the path whole, where the line is, how many such lines, and what to do, which depends on where the program stands (`placeOf`). A supplied program (`store/imports/mat-<n>/`): nothing in `store/` has an execute bit, so copy the program, and every library it loads, into an executable temporary directory inside the job (`mktemp -d` under `/tmp`), make it executable there and run it from the copy. Evidence (`inputs/`, `work/extracted/`, `work/quarantine/`, an evidence import `store/imports/ev-<n>/`): evidence is read, never run, and a job that runs code recovered from it is flagged; for a program to trust, ask the operator for one with `swarm.sh tool-supply`, otherwise reimplement the step. Anywhere else (the job's own `$OUT`, an earlier job's output, no path found): the places nothing runs from, the evidence rule first, and the copy only for a program the operator supplied or one unpacked from it. The shell's other reasons for 126 are quoted and say that the place is not the matter (no copy is suggested). In a base-image VM (msb 0.7.2, as root) a copy made under a `mktemp -d` directory in `/tmp` and made executable ran; `/tmp` is on the VM's overlay root, not a separate no-exec mount. A worker VM, which also mounts the run, was not tested. The match is on the shell's status and lines and the loader's words alone; no program is named.

### The dynamic network (`net_request`, `net_fetch`, `network`, `network/`, `store/net/`)

In a microVM run started with `--network dynamic` (or `open`; ADR 0012), the
seats have three tools, each a call on the seat's own socket (`netRequest`,
`netFetch`, `netView`), so who asks is always the seat.

- `net_request(lead, adapter, params, evidence, purpose, for?, ttl_seconds?,
  max_requests?)` asks for one bounded lookup: an adapter of
  `network/adapters.json` with its typed params (or, without one, one exact
  `url` and `method`, which is decided as uncertain). `lead` is one the seat
  holds; `evidence` names what holds the values sent (`input:`, `member:`,
  `net:<k>/<n>`, `job:<id>/<path>` of a job that declared the sources it read
  and whose command does not hold the value, or `E-<seq>` through the objects
  it cites; an `import:`, a bare `sha256:` and an entry's own words are not
  evidence); `purpose` is text no rule reads. The hub decides it by `scripts/net-policy.ts` in eight steps
  (authentication, schema, case policy, hard denials, credentials and
  sensitive values, the evidence link, enforceability, quotas); the first
  step that refuses decides. Granted: `{grant: "N-<k>", method, url,
  expires_at, max_requests, max_bytes, next}`. Refused: `{request: "NR-<n>",
  reasons: [{step, rule, code, detail, overridable}], operator_item?}`; the
  avenue closes, the lead stays open, and when the operator may override,
  one item per host and lead (`NI-<m>`) is opened or joined. The same
  request (by its digest, everything the rules read) gets the same answer.
  `for: "job"` makes a grant for a job of the seat's (`job_run net_grants`).
- `net_fetch(grant)` uses a grant: the fetch service (`scripts/net-fetch.ts`)
  makes its exact request as `seat:<id>` and seals the answer; the reply is
  the capture's ref (`net:<k>/<n>`), status, headers, size, sha256, the
  ledger entry it became (`E-<seq>`) and the delivered body a page at a time
  (`capture=net:<k>/<n> offset=N` for more; the whole is
  `store/net/<k>/<n>/body`). `net_fetch(capture, offset)` pages a sealed
  capture without a new fetch.
- `network(view)` shows the policy in force, the catalogue (`view=adapters`,
  with each adapter's params and whether its key is configured) and the
  seat's own requests, grants, captures and items.

A job given grants (`job_run net_grants: ["N-<k>"]`, each asked `for: "job"`
by the same seat and not yet bound) has them bound to it when its worker is
made (`bind` on the chain, the grant's principal becoming `job:<id>`); the
worker is booted with the fetch service's port on the host allowed
(`hostPorts` in its `WorkerSpec`; nothing else of the host), its own token in
`SWARM_NET_TOKEN`, `SWARM_NET_PRINCIPAL`, `SWARM_NET_URL`, `SWARM_NET_GRANTS`,
and the helper `/job/net_fetch.py N-<k> [--out FILE]`, which writes the body
and prints the answer. A job with grants is not retried after the hub's
death. A job may declare a capture as an input (`inputs: ["net:3/1"]`).

The records, beside the run's other chains:

- `network/policy.json`: the case policy the kickoff resolved
  (`scripts/case-policy.ts`), read on every decision.
- `network/grants.jsonl`: every `request`, `decide`, `grant` (its terms: type,
  principal, lead, adapter, method, url, host, port, redirects, response
  fields, max_requests, max_bytes, ttl, expires_at, key header name, the
  policy's digest), `bind`, `revoke` (cause `operator`, `lead_closed`,
  `job_ended`), `item`, `item_join`, `item_close` and `contamination`; each
  line `{v, seq, at, by, ev, …, prev, hash}` chained with the lead register's
  code. Written by the hub and the operator's CLI, under `locks/.network.lock`.
- `network/fetches.jsonl`: the fetch service's `attempt` (written and fsynced
  before a byte leaves), `result` (status, bytes, sha256, complete,
  delivered, `published`, `stopped`, `kept` (each file kept beside the run,
  by name, size and sha256), the manifest's sha256, what the response
  exposed; written durably before the capture is published) and `refused`
  lines; the same chain, its own lock. An attempt left without a result (the
  service stopped mid-fetch, or its result could not be written) is given one
  with `published: false, reconciled: true` when the service starts and then
  every minute; custody names any attempt still without one.
- `network/service.json`: the fetch service's port and the adapters whose key
  is configured (names only). The secret that makes each principal's token is
  in the hub's directory (`net-fetch.json`, 0600), in no VM.
- `store/net/<k>/<n>/`: capture `n` of grant `k`: `request.json` (the line,
  the headers sent with a key named and not recorded, the address, TLS
  identity, each hop), `response.json` (status, headers, completeness, an
  oversize refusal, a redirect not followed), `body` (the delivered bytes,
  only for a whole answer), `capture.json` and `manifest.json`, each file
  0444, built in `<sandbox>.netraw/.staging/` and moved here once the result
  line is written. `net:<k>/<n>[/<file>]` resolves like `job:`.
- `<sandbox>.netraw/<k>/<n>/`: beside the run, outside every VM, what was
  received and delivered to nobody: a filtered adapter's whole response
  (`body`) and headers (`headers.json`), a transfer stopped or broken off
  (`body.partial`), an answer withheld because its grant ended before it was
  published (`body.withheld`), and a capture whose result could not be
  written (`unpublished/`). `capture.json`'s `kept` names each by size and
  sha256; custody re-hashes them, the package copies them to `network/raw/`,
  and `swarm.sh purge` removes the directory with the run.

Each capture becomes a ledger entry of kind `external`, written by the
harness (`recordExternal`; an agent's `record kind=external` is refused):
`source_class: external_capture`, `refs: ["net:<k>/<n>"]`, `provenance:
{supplied_by, at, from, sha256, permitted_use, grant, request, lead,
complete}`, both in the chained core. A seat's capture is recorded as it is
fetched, a job's on the hub's next round (every fifteen seconds), which also
revokes the grants whose lead closed or whose job ended, and records
contamination. What is derived from a capture stays external
(`externalLineage` in `scripts/net-broker.ts`), and `check-answers` names each
answer that rests on it, read from what each job resolved (its scope
manifest's paths and digests, or every capture sealed before it started when
its scope was broad), never from how it spelled its inputs. Custody seals both
chains, re-hashes every capture and every file kept beside the run, and names
every attempt with no recorded outcome.

### Names and the per-agent cap (`names.json`, `budget.json` `cap_per_agent_usd`)

`make_tool` answers a near-duplicate before anything is written: same runtime, overlapping parameters and a description made of the same words means the tool already exists, and the refusal names it and its author so the agent can call it instead. Two agents reaching for one capability seconds apart is the common case, and the board announcement always arrives too late for them.

Nobody is given a job. The kickoff prepares the sandbox, the goal and the caps, and stops there: there is no seat, no role and no task list. An agent reads the goal, reads the board, sees what its peers have taken, and calls `name(name, doing)` to say what to call it and what it is taking on. `names.json` holds what each agent said, every post carries its author's name, and the console and the summary show it beside the id. Two agents cannot answer to the same name; an agent may rename itself whenever its work changes, and the board is told.

`--cap-per-agent USD` writes `cap_per_agent_usd` to `budget.json`. On every budget fold the agent's own harness compares its slice against it: over the cap it is steered once (`agent_cap_steer`, a `stop` post from `system` on the board) to post what it has and call `done(reason=agent_cap)`; one grace period later, if it is still running and the swarm is not done, the harness marks it done itself (`agent_cap_stop`) and shuts the session down. The swarm continues.

A seat's name is stable once given ([ADR 0015](adr/0015-one-seat-finishes-and-work-is-offered.md)): a later `name` keeps it (the result says which name was asked for, `asked`) and updates what the seat says it is doing; `names.json` keeps when it first named itself (`first_at`). What a seat works on shows from the leads it holds: `list_team` gives each peer's `holds` and `label` (its name and those leads). When the kickoff staggers first choices (`budget.json` `coordination: {first_choice_stagger_sec, first_choice_bound_sec}`, 20 and 90 by default, `SWARM_FIRST_CHOICE_STAGGER_SEC=0` off), a seat's first choice (its first `name`, `lead_open` or `lead_claim`) waits until the seat before it in team order has chosen, or 20 s after that seat's own turn, a seat marked done or dead skipped, never past 90 s from the run's start, and the answer carries `admission` `{order, waited_ms, turn_at, coverage}`: every held lead with its holder and questions, and the questions nobody covers, as they stand then.

### Shell writes, forge hints and the sentinel nudge

A change the harness sees across a `bash` call is charged to that call only when the command names the path (the key, its basename or its directory), or when the file is no longer changing when the call ends and is not under another agent's `work/<id>/`: a peer's shell job that is still growing a file, and a peer's own scratch directory, are the peer's business, not a violation of whoever's call overlapped it. Two directories under `work/` are outside the watch altogether: `work/.toolchain/` (the package install area of `--allow-install`) and `work/.tmp/` (the panes' `TMPDIR`, where Pi spills a long `bash` output before the harness moves it to `tool-output/`); they belong to everyone, and on run 6 one venv there was 642 implicit claims and seven violations. A `bash` (or forged-tool) write to a `work/` path nobody holds is no longer only announced: the harness takes the claim for the writer (`claim_file` with `implicit: true`, on the trace and in the lock record) so a peer's tool write to the same file is refused for the lease. A shell write to a path a peer holds is still a `claim_violation`. The same holds for `edit`/`write` under the agent's own `work/<id>/`: the guard takes the lease (`own scratch`, implicit) instead of refusing, so the scratch directory the prompt promises needs no claim from any tool. Every shared file still needs one, and `claim_file` refuses a team agent a lease inside a peer's `work/<id>/`, `work/extracted/<id>/` or `work/quarantine/<id>/`: such a lease would turn the owner's own claim-free write into a conflict in its own directory. The operator and the harness are not peers and can still claim there.

The eighth `bash` call by one agent starting with the same command word (`vol`, `fls`, `python3`, …, measured past `cd … &&` and `VAR=…` prefixes) earns one `forge_hint` event and an `ask` post from `system` to that agent: forge it as a tool.

A `bash` (or `powershell`) command that took a minute or more (`SWARM_REPEAT_HINT_MIN_MS`), ended without error and had its whole output kept under `tool-output/<id>/` is remembered by its text with the spacing collapsed. When the same agent runs the same command again, that result carries one extra paragraph pointing at the first run's kept output: grep or read that file instead. Once per command, a `repeat_hint` event; the harness names no tool and decides nothing about the command.

In a run with tool jobs (the contract has its `## Tool jobs` section), a `bash` command that names `inputs/` and runs for as long is told once, with its result, that a job would have sealed what it made (`job_run`; cited as `job:<id>/<path>`, where a file in an agent's own `work/` is not an object of the run), and that quick looks are fine in the shell. Once per command's first word and three times per agent at most, a `job_hint` event; nothing is refused.

A command that runs or evaluates code from an evidence-derived place (`inputs/`, `work/extracted/`, `work/quarantine/`, a job's output under `store/jobs/`, an import under `store/imports/`) is flagged, never refused (`extensions/evidence-code.ts`, the c10 run sd9645b): `runs`, an interpreter, a shell or a browser given such a path as its script (its options first), on its stdin or through a pipe; `evaluates`, a construct that evaluates code (`eval`, `exec`, `compile`, `new Function`, `vm.runIn…`, `vm.Script`, `runpy`, `importlib`, `require`/`import`) given such a path or a name bound to what was read from one. It reads the command's words: quoted text of more than one word is not a command, a method of the same name is not the construct, and what a script reads from its arguments or its environment is not followed. A `bash` command's result carries a note (the rule, why no-exec did not stop it, what to do instead) and an `evidence_code` event; a `job_run` reply carries `evidence_code: {how, what, paths, note}` and its trace row `evidence_code`; the report's job record marks the job ("evidence code may have run", and a row saying what), and Appendix B lists every such job. A path that is an output of the seat's own command job (the job record's requester and kind) is said apart (`own: {paths, jobs}`; `ownJobOutputs`): code the seat wrote there itself is not the evidence's, code that job recovered is, so it is still flagged, and the chip reads "own job's code may have run" when every path is one; `require` of a JSON file is data and is not flagged. A finding recorded without refs whose source or evidence names a `work/` file is told the same by that file's name.

Before every model call the agent's harness takes the caps as it does at a turn's end (`context` hook). A seat the harness has stopped, or one whose swarm the sentinel ended, has its turn aborted and its session shut down before the call goes out, with the same outcome as the stop it replaces and one `budget_precall_stop` line. On the host that is a brake; in a VM it runs under the guest's root and is advisory, and the hub's cap stop and wall clock (or `--model-gateway`) are what hold.

When an agent's `done` creates `done/SWARM_DONE`, or the harness writes the sentinel itself, that process prompts every teammate without a done or dead marker once through `herdr agent prompt` (`sentinel_nudge`, with who was reached and who was missed): an idle pane never makes another tool call, so it would never see the sentinel on its own. `await-done.sh --nudge` does the same from the spawner's side.

The same idleness hurts mid-run: a session that ends its turn after its intro, or after one slice, sits at the prompt until something prompts it. `scripts/idle-nudge.sh` is the watchdog the kickoff starts next to netguard (`idle-nudge.pid`; `--idle-nudge-sec N`, default 180, 0 off): every 30 s it measures each agent's silence from its Pi session files and its last trace event, and an agent past the limit with no marker is prompted to read its inbox and continue its seat, or post its result and wait or call done — at most three times per agent, each one an `idle_nudge` event by `system` on the trace. A prompt arriving (the `hub_prompt` row a seat's extension writes) is not counted as the agent's activity. An agent that only waits is idle too: when its last call other than `wait` and `inbox` (and the rows its harness writes for it) is more than `SWARM_WAIT_IDLE_SEC` ago (600 s; `--wait-idle-sec`), it has waited since, and its last wait is recent, it is nudged as a steer (`why: "waiting"`), which ends the open `wait` (`reason: "prompt"`); an agent waiting on a job of its own that is still running is left alone, and a peer's answer has the whole ten minutes from the ask. A seat whose hand-off compaction is running is not nudged, since Pi takes no prompt then; one open past `SWARM_COMPACT_STALL_SEC` (1200 s; `--compact-stall-sec`) is said once on the board (a `hold` post, `COMPACTION STALLED`) and the trace (`compact_stalled`, `by: "watchdog"`). `swarm.sh stop` kills it; the sentinel ends it.

### Done (`done`, `done/SWARM_DONE`)

`done(reason, output_file, abandon?)` is one seat's call ([ADR 0015](adr/0015-one-seat-finishes-and-work-is-offered.md), `extensions/finish.ts`). `leads/finish.jsonl` (a chain with the lead register's helpers) holds the finish's coordinator lease, `{holder, generation, report, since}`: the first `done` designates the seat that published the report last (its newest revision in `history/`) when it can hold it, else the seat asking; a holder that is done, dead, compacting or silent past the stale limit with no job running is taken over by the next seat's `done` at the next generation (a `hold` post says so). Any other seat's `done` (`finishTurnFor`) returns `{ok: true, finished: false, not_yours: true, coordinator, readiness}`: a `done_deferred` trace row, no board post, no finish line, not a refusal; `markDone` refuses the sentinel from it (`not yours: …`). A seat's own cap (`agent_cap`), an abandon vote and every done once the sentinel exists are not the finish. The finish phase (`finishPhase`): while a coordinator holds the lease and the registers are met but for what is late against the report, closures waiting for their closer's confirmation or resolutions, the finish is being assembled (`phase` events in `leads/finish.jsonl` each time it turns, `ASSEMBLING` in every header and in `swarm.sh lead <run> list`); another seat's revision of an answer (a question's, the summary or the narrative) is then recorded only with `material` (why it changes a conclusion, kept on the entry as `finish_material`), and one without it is refused quietly ("the finish is being assembled by <coordinator>; revise only with material: why": `{ok: false, quiet: true}`, a `record_deferred` trace row, never counted as a refusal); a material revision reopens readiness as any change does, and the coordinator's own revisions are free (the c10 pilot's finish tail ran past ninety minutes as answers kept being revised). The coordinator's `done` is held first by what is late against the report: each result or veto posted after the report was written as the finish began (a result that only restates its author's own answer revision, citing that answer and what it corrects and nothing else, is covered by the revision and needs no resolution) (the lease's `since`), and each objection acked against any version of it, until `finish resolve` answers it (`how: folded | not_material`, `why`; a resolution names the report's digest it was made against) or, for an objection, its objector acks again; these are obligations, kept through every later version of the report, so publishing it again answers none of them and resolving after publishing finds them. `finish ack` (`no_objection`, or `objection` with `why`) is a typed review and never a late post; before any done has named the report, the reviewer names it (`report`, kept on the ack), and its objection holds the coordinator's done that names the same report (the c10 pilot's objection was refused for want of a done, and lost). An ack takes `sections`, the report's sections it covered (a heading's number, `§3`, `Q-3` or its words; none named is the whole report, `whole: true`), and records each with its digest (`sections: {key: sha256}`; `reportSections`: the preamble before the first `## ` heading, then each `## ` heading with its lines, fenced blocks skipped, a numbered heading keyed by its number, the blank lines that end a section left out; versioned: an ack without them is of the whole report at its digest). A review carries over ([ADR 0015](adr/0015-one-seat-finishes-and-work-is-offered.md), "A review carries over"; `reviewStanding`): for the report as it is, a seat's no-objection acks vouch for each section at the digest it had then (a whole-report ack replaces what it vouched before, an objection withdraws the sections it names), a section unchanged stays covered, one changed is asked again, and a whole-report review is asked about a section added or removed; a `carry` event (`{ev: "carry", report, digest, kept: [{by, acks, sections}], reasked: [{by, acks, changed?, removed?}]}`) records it the first time a version's reviews are weighed (the header's turn, a prepare, an ack or a done), and prepare's reply and `finish status` give `reviews` (`sections`, each seat's `standing` direct, carried or reasked with its acks and what changed, `uncovered`, and in status the `invite` and the `carry` seq). An objector's later ack answers its objection only when it covers what the objection named (the whole report, or every section it named). The coordinator prepares the finish before its done ([ADR 0015](adr/0015-one-seat-finishes-and-work-is-offered.md), "Preparing the finish"): `finish prepare` (`prepareFinish`, `report` its path, the lease's when left out; refused while the report does not exist) takes the lease and the boundary exactly as a done does (`takeLease`, shared with `finishTurn`: a first lease designated to the report's publisher, a takeover of an unavailable holder at the next generation, a report named anew), runs no goal check and writes no sentinel, and answers `{mine, coordinator, generation, report, digest, boundary: {since, segment?, carried?}, readiness: {ready, revision, items, limited, warnings?}, late, next}`, recorded as `{ev: "prepare", generation, report, digest, since, segment?, ready, revision, late: [{kind, id}]}`; another seat's prepare is answered `{ok: true, not_yours: true, coordinator, …}`, quietly, as its done is. Before a lease exists there is no boundary and `finish status` lists nothing late; after it, `finish status` gives `coordinator.boundary`, `segment`, `carried` and the last prepare (`prepared`: by, at, generation, digest, how many were late, whether the lease and digest still stand). The boundary is the report's write time when the finish was first taken, never the prepare's time; a prepare again, a republished report and a takeover keep the earliest one. After a resume (`budget.json` `resumes`) the first prepare or done opens the new segment: designated as a first lease is, at the next generation, its `since` the report's time then, and every post late against the report when the run was resumed and not resolved carried on the lease by name (`segment: k`, `carried: [{id, by, tag}]`, versioned fields present only then); an objection needs no carrying, and a post of the continuation's written before its report is not late. `finish resolve` with `items` resolves several at once: `[{post | ack, how: folded, where} or {post | ack, how: not_material, why}]` (a folded item's `where` is recorded as its `why`), with `generation` and `digest` (the report's, its first 12 hex characters or more) and `key` (1 to 200 characters; when left out, `auto-` and the sha256 of the seat, generation, digest and items names it). The batch is validated whole under the finish lock: a stale generation or digest (`stale: {generation?: {expected, current, holder}, digest?: {expected, current, report}}`), or an item resolved already (named with its seq), not late, named twice, or malformed (`problems: [{index, item, problem}]`), refuses it with every id still unresolved (`unresolved: [{kind, id}]`) and records nothing; otherwise one `resolve` event per item, each with `batch`, `generation` and `digest`, and the reply `{key, seqs, resolved, generation, digest, late}` says what is still late. The same batch sent again under its key by the same seat is answered `{replayed: true, seqs, late}` and records nothing twice; another batch under a key used already is refused; a batch whose every item was resolved already (a retry under another key) is answered `{resolved: 0, seqs: [], late, note}`, naming each item's resolution and what is still late, or "Nothing is late against the report: call done", and records nothing. The sentinel is written in one transaction under the finish register's lock (`finishTransaction`): only while the seat still holds the lease at the holder and generation its `done` began with (carried through `done` as `finish`), and only while nothing is late against the report, so an objection acked or a takeover made while the checks ran refuses it (`late against the report: …`, `not yours: …`); the seat's own done marker is written inside it, and nobody takes the finish over once the sentinel exists. The registers' readiness (read from its own snapshot, between two readings of the revision that agree, and cached only then; every material lead disposed and no closure awaiting confirmation, no lead's job uninterpreted, the ledger gate over every question in scope and the summary and narrative the goal names holding nothing, no stale answer, no addition committed and not yet applied; no answer held a best candidate (`heldAsBestCandidate`: it claims established, and every review holds it a best candidate only), under every stop policy, as it holds the done; under `--stop operator` also no route limitation; a disposition that only limits the run, partial, not determinable, a bounded negative, out of scope, a premise shown not to hold or an acceptance, never holds it, whatever its reviews' strength) is computed per state revision, shown in every header (`Finish: …`) and posted once each time it turns (`FINISH READY` / `FINISH NOT READY again`, `readiness` events; the first state is recorded too, never posted when not ready, so `leads/finish.jsonl` exists from the first header and the metrics and the report read readiness from it); `finish status` gives it with the coordinator, the last check, the report's reviews and what is late. When the sentinel is written while the register's last readiness is not ready, `finishTransaction` records `{ev: "readiness", ready: true, at_done: true, revision, why}` in the same transaction, and the metrics measure the tail from it, saying it was the done's. Each run of the finish line is recorded against the revision it ran at (`check` events, the run whole), and a done at that revision takes it rather than running the checks again. The state revision (`stateRevision`) covers the board's verdict posts, the ledger, the attestations and disputes, the leads, the questions, the report's digest (the lease's path), the files at the top of `work/`, every job's state, what of each job's stdout its requester was handed (the bytes still unread of the whole, from the journal's `job_returned`: a page read after a check can add an unread-output defect, and the rest read can fix one), the policy (the stop policy, the caps, a pause, `SWARM.md`, a case record when there is one, and the case policy `network/policy.json`), the operator's decisions (the requests' chain `requests/requests.jsonl` less its delivery bookkeeping, a delivery `claimed` and a notification `notified` or `delivery_failed`, or `operator-requests.jsonl` whole for a run from before the chain; and `operator-hosts.jsonl`) and what was added after the kickoff (each `evidence_added` or `material_added` on the store journal, and each `addition_applied`: an addition committed and not applied holds readiness and the gate, `addition_incomplete`); an ack does not move it, nor does a notifier's round, nor an offer's bookkeeping on the registers (an offer made, delivered, declined, accepted or lapsed: who may take a piece of work first, never what the finish rests on, and a waiting seat's delivery would otherwise make the coordinator's check run again), while a closure offered to its closer to confirm does. A material lead closed deferred, infeasible or needs_operator limits the run until its questions are disposed under the bar and another seat holds its limitation no longer material (`route_review`), or the operator accepted them. Then:

1. heals whatever a background process changed under `inputs/` since the last tool call, verifies `inputs/` against its manifest and records `inputs_check` — before the checks, so a check may grep the trace for it,
2. when `done/SWARM_DONE` does not exist yet, runs the finish line: the goal's `## Checks`, read from the operator's registry by `await-done.sh --checks-json`, the same way the console and the report run them. A host run runs it in the pane, as it always has. In a microVM run the seat asks the hub (`runFinishLine`), which runs it on the host, where the trace the checks read is (a seat's VM does not see `traces/`), and answers the runner's whole result; `markDone` takes that same run when it finished in the last 30 s and the state it was run against still stands (`stateRevision`: the board's result, veto, hold and stop posts, the ledger, the attestations and disputes, the leads), so one `done` is one run of the checks; a run the state moved under is run again, up to three times, and a state that never holds still is a refusal. The finish line is the goal's checks and the harness's gate (`scripts/finish-gate.ts`): a material lead with no disposition (`open_lead`) and a material lead's job with no interpretation (`uninterpreted_job`) refuse `done` with what fixes each. A check that fails is a refusal (`done` event with `ok:false`, a `finish_line` event with `passed`/`total`/`failing`, the first failing check), and the agent is told each check that fails and what makes it pass: what the check printed, verbatim (whole up to 64 KiB, which `--checks-json` hands back for a failing check as `out`, with its size as `out_bytes`; past that its size and that running it prints the whole: this is how the answers check names each defect and its fix), or, from a check that printed nothing, the command itself; and that `done` ends the whole swarm, not its slice. SWARM.md says so under the goal ("How the checks are run"). `abandon: true` is the way out for a task that cannot be met: the sentinel is written with its reason prefixed `ABANDONED:`. One agent's abandon while others still work is a vote, not the end: it is recorded under `done/abandon/<id>.md`, the board is asked, and the agent is told to post what blocked its slice and carry on; the run ends when a second agent abandons too, or when no other agent is still working (each peer has a `.done` or `.dead` marker). Run sfeeebb is the reason: one seat of ten abandoned the case after six minutes because its own slice had not come together. A runner that cannot answer (no registry, an unreadable goal) does not hold the run, but it is never a clean done: `done` proceeds as `verification_unavailable`, its reason prefixed `VERIFICATION UNAVAILABLE:`, and the `finish_line` event says why. Whatever the stop policy, the finish line refuses `done` until every question in scope has a disposition under the bar (established; partial; a bounded negative or not determinable, each on a coverage record another seat reviewed; a premise shown not to hold; out of scope; accepted by the operator; withdrawn), and while a defect a limitation only names stands (`holding`); the refusal names each question with none, what blocks it, and the way to one. Every end names its outcome in the sentinel and the done file (`outcome:`): `completed` (the finish line met and every question established, or settled by a bounded negative that says the event did not happen under the stronger bar), `examination_limited` (met, with a question not determinable, partial, out of scope, a bounded negative short of that, accepted, or a material lead deferred, infeasible or left to the operator: a limitation never reads as an answer), `abandoned` (not under the operator's stop policy) or `verification_unavailable`. A cap or the operator's stop ends a run whatever its questions' state: paused or stopped, never completed. Run `sb36f` is the reason this exists: a nano agent ended a 25 GB case after four minutes by calling `done` when its own slice was finished, with no report written,
3. writes `done/agents/<id>.done` (frontmatter `by`, `output`, `reason`, `at`),
4. creates `done/SWARM_DONE` with the same frontmatter if it does not exist (idempotent; `created_sentinel` tells you who was first), unless `reason` is `agent_cap` — that is one seat leaving, and the swarm continues,
5. releases every lock the agent owns,
6. logs `done` and `agent_stop` events,
7. returns Pi's official `{ terminate: true }` so the session ends without another LLM turn.

Presence of `done/SWARM_DONE` means stop. `before_agent_start` appends to the system prompt "`done/SWARM_DONE` exists. Call done now" when it does, and `inbox` reports `swarm_done` on every call. The spawner-side clock is the file too: `await-done.sh` exits on it; chat "we're done" is not the clock.

### Leads (`lead_open`, `lead_claim`, `lead_release`, `lead_close`, `lead_link`, `leads`, `leads/`)

The swarm's open investigative work (`extensions/leads.ts`), kept beside the ledger and not in it. `leads/leads.jsonl` is an append-only chain of events, each line hashed over the one before (`open`, `claim`, `release`, `close`, `link`, `reopen`, `stale`, `job`, `interpret`, `note`, `route`, `route_review`, the offers' `offer`, `offer_seen`, `offer_decline`, `offer_lapse`, a review offer's `offer_take`, `offer_accept` and `offer_withdraw`, and `keep`, `handoff`, `confirm`; a `wake` from before offers is still read); `leads/leads.md` is rendered from it after every change. On the host each pane writes it under `locks/.leads.lock`; in a microVM run the hub is its only writer, who acts is the channel's seat, and the operator's CLI writes it on the host under the same lock. `leads/` is a protected path, and the shell watch holds the file to growth only.

A lead has an id (`L-<n>`), a title, why it matters, its origin (the entry that opened it, `record(..., opens)`, or the agent), its needs, the questions it serves, whether it is material (the creator says; default true), its holder and generation, its state and, once closed, its disposition and ref. A need is another lead's outcome (`L-3`, which is `L-3:resolved`, or `L-3:negative`), or a ledger entry that does not stand yet (a disputed one; an entry that stands is where a lead comes from, and is refused as a need); never a job. Needs are revised with `lead_link`, and a loop is refused. The states are open, active and closed; blocked is derived (a need not met). A disposition cites what it rests on: resolved an entry that stands, negative an absence, duplicate another lead, deferred and infeasible a limitation, needs_operator the words of the request (also a line in `operator-requests.jsonl`); withdrawn, the harness's alone, the question whose withdrawal closed it. A lead closed on an entry later superseded or disputed reopens. A lead names the questions it serves as `Q-<n>` (it must be in scope) or by the goal's own id.

A lead under a question plans its routes: `routes: [{source, method}]` on `lead_open`, or added with `lead_link` (a `route` event), at most 20, each a source (an object ref or a path under `inputs/`, `store/` or `catalog/`, which the hub can follow; words alone are kept and said to be untrackable) and how it would be examined. The first lead under a question with none is warned; the first under a person's question must carry them; a negative close of a material lead, or of any lead under a material question, is refused without a plan. A negative close records `not_examined`: every planned route of the question's leads that no job of theirs declared (a job over everything examines each, and says so) and no coverage record names. A close held two minutes or less, after one job over one object, with no job that read everything, is a `quick_negative` `{held_ms, jobs, objects}`: a review cue, shown in `leads.md`, in the header until a peer attests the negative, and in the report.

A claim is atomic and takes a new generation; `lead_open(take: true)` creates and claims in one event. A lead held by a peer is theirs until released, or until its holder shows as stale: silent past `SWARM_LEAD_STALE_SEC` (600) on the trace, with no job of its own still to finish and no compaction under way within twenty minutes, or marked done or dead. The first claim of a stale lead appends a `stale` event and tells the holder; a claim after `SWARM_LEAD_RECLAIM_GRACE_SEC` (60) takes it over with a new generation, and the old holder's close or release is refused. A turn that ended in a provider error frees nothing.

Priority is a hint: how many leads and unanswered questions wait on a lead, transitively, then its age. What each agent is told is derived from the files, never stored as a message: `lead_ready` when every need of a lead it holds is met, a need that will not come, its lead marked stale, taken over or reopened, the operator's note, a change to a lead its lead needs, an offer made to it (a ready lead nobody holds, for the seat idle longest: in a `wait` for at least 60 s, holding no lead that is not blocked, no job and no offer), a closure to confirm, and a lead of its parked and offered to a peer. A `wait` wakes on the ones that matter; every `inbox` and `wait` delivery carries the header (open by priority, the agent's own, what is blocked on it, its jobs awaiting interpretation, the questions nobody holds a lead for, each notice), and the idle nudge and the compaction hand-off carry it too. Uncovered questions are derived: the goal's questions (its answers check's `--sections`) with no standing answer and no held lead.

A job is interpreted by an entry recorded with `interprets` naming it (its kind the disposition: a finding shows something, an absence nothing, a limitation that it could not be used); a citation alone is not an interpretation. A job whose stdout its requester was handed only in part (the journal's `job_returned`) waits until the rest is read or the interpretation gives `rest`. A job run under a lead (`job_run(lead)`, or the one active lead its requester holds) is on the lead's record, and a material lead's uninterpreted job refuses `done`; an agent's other jobs are only shown.

Raw jobs are never merged; work another seat did is named instead ([ADR 0017](adr/0017-reuse-is-hinted-and-the-process-is-measured.md), `scripts/job-reuse.ts`). A command or tool job with a declared scope carries `reuse: {op, objects}` on its `job_accepted` line: `op` is `tool:<name>`, or `command:<word>` (the command's leading word past `cd …&&` and `VAR=` prefixes, `null` when it has none), and `objects` the scope as resolved, each file by its sha256 (and where it sits) and each directory of the evidence, the store or the catalogue by its path; an agent's own `work/` or `tool-output/` file is left out (live, and hashed only when the job starts), and a job over everything (`inputs` left out or `["all"]`), a recipe, a detect pass, an import or a seal has none. At acceptance the hub looks for other seats' jobs, under way or committed (not failed, cancelled or committed cancelled, never the harness's or the derived catalogue's), with the same tool, or with the same leading command word, whose objects share at least one of the new job's (the same sha256, the same directory, or a file inside a directory the other read, either way). Each is a `similar` entry `{job, seat, name?, state, status?, outputs?: {files, bytes, path}, lead, objects: same|overlap, shared, match: "same command" | "same leading command" | "same tool and arguments" | "same tool", op, independent?}`, ranked the same operation first, then the same objects, then done and sound, then the newest; the whole list is a `job_similar` line (`{job, by, independent?, similar}`), and the `job_run` answer carries at most 8 of them (`similar`), `similar_more` naming the line when there are more, and `similar_note`. The job runs as asked: the hint is looked for once the job is registered and queued, and a hint that cannot be found or a line that cannot be written holds nothing up (the answer then carries every similar job, since no line names the rest). `job_run(independent: true)` (a command or a tool only; `spec.independent` on the journal) says the job is an intended reproduction: the similar jobs are still named, the note says to keep the result apart until it is in, and the metrics count it apart. At commit, each non-empty file of the job's output whose sha256 is an earlier job's output (the first job to write those bytes; its interrupted attempts' files are not outputs) is a `same_as` entry `{path, sha256, bytes, job, file}`, on a `job_same_as` line and on the job's record. The index it is looked up in is built from the committed jobs' manifests in the background when the service starts, never on the commit path: a commit reads the index in memory, and a job committed while it is still being built has its `same_as` said once it is (the line comes later, the job's record is updated); the job's view shows at most 20 (`same_as: [{path, bytes, same_as: "job:<id>/<file>"}]`, `same_as_more` naming the line), and its post counts them. The files are the job's own either way, sealed and cited as `job:<id>/<path>`. Only a typed recipe over the same object is merged (`job_deduplicated`, above). A journal from before this carries `shadow_key` on `job_accepted` and `job_would_merge` lines (the merge by whole spec that was only measured, retired: it matched no job on the last CTF round); they are read and ignored.

A close `needs_operator` may carry `ask: {kind: "acquisition", source, where, expected_value, urgency: normal|urgent|volatile, questions?, owner?, authority_needed?}` (every text at most 2,000 characters, the questions the lead's when none are named): evidence the run does not have, committed on the close itself. Either way the close is an operator request's commit: the request is derived from it and written to the outbox with its id (below), and the close's answer carries it (`request: {id, kind, state, stage, answer}`), or `request_pending` when it could not be written yet; never a silent failure. A close whose words ask the operator to accept or reject dispositions, made while no done has been refused on a question the operator may accept, stands and carries a `hint`: whether they suffice is what done asks the finish line, and operator acceptance (`swarm.sh question <run> accept Q-n`) is for a question the finish line holds. A `needs_operator` close without an `ask`, on a lead that serves a question, carries `guidance` (`operatorQuestionGuidance`): a question put to the operator says what observation would settle the question and what each possible answer changes; guidance only, the ref's words are not read. Custody seals the chain beside the ledger's, unsigned; the package carries `leads.jsonl`, `leads.md`, `operator-requests.jsonl` and `operator-hosts.jsonl`; the report's §4 says how the investigation proceeded. The operator answers with `swarm.sh lead <run> note L-n "TEXT" [--allow-host HOST]` or the console's Leads tab: the note is an event, the lead reopens, and in a microVM run the host joins `operator-hosts.jsonl`, which the job service reads for each job run with `network=allowlist` (an agent's own VM keeps the network it booted with).

Coordination ([ADR 0015](adr/0015-one-seat-finishes-and-work-is-offered.md); tools `lead_reopen`, `lead_handoff`, `lead_confirm`, `offer`, `route_review`; events `offer`, `offer_seen`, `offer_decline`, `offer_lapse`, `keep`, `handoff`, `confirm`, `route_review`). Each lead has a revision (`rev`, the count of acts that changed it). A `take` whose questions another seat's held lead covers is opened unheld with `coverage` naming the holder (`covered_by` on the lead, which is not offered around), unless `overlap: second_route | verification` and `overlap_why` hold it; a claim of such a lead is refused without them; `objects` are hints, and a job's admission under a lead carries `coverage` (who else works its questions or its declared objects, or declared the same objects in a running job). A need is what has not come yet: a standing entry is refused as one; `lead_link` removes a need only with `why` (kept as `dropped`, withdrawn, never met); each need shows its outcome (`satisfied`, `pending`, `failed`, `invalidated`). `lead_open(consumer: L-n, consumer_needs?)` opens a prerequisite and adds it to L-n's needs in the same act, the whole graph as it would stand checked first (a loop through the new lead's needs is refused and nothing is appended); `product`, `acceptance`, `inputs` (refs, checked), `next_action` on the open and `result_refs` on the close make the product contract. `record(opens)` opens unheld unless an item says `take`. `lead_handoff(id, why, to?, generation?)` lets a held lead go and offers it to the named seat (refused when it is done, dead or compacting) or the one idle longest. A held, ready lead with no job running under it and no act on it for `SWARM_LEAD_PARK_SEC` (600), while its holder has acted within the stale limit and something positive shows it works on another lead since (an act of its on another lead, an interpretation of another lead's job, or a job of its running under another lead; foreground work alone, reading or a shell, is work on the lead it holds), is parked: in every header, offered to an idle seat, kept by its holder's own `lead_claim` (a `keep` event, which ends the offer), and taken over at once by the seat it is offered to (a claim with `cause: parked`). A seat whose held leads are all blocked counts as idle. Offers ([extensions/offers.ts](../extensions/offers.ts)) replace wakes (a `wake` from before is read as one): a ready lead nobody holds (to the seat idle longest not yet offered it at this revision), a hand-off, a parked lead, a reopen after the operator's note (to the previous holder first, when it is available) and a closure to confirm. An offer gives its seat first claim for `SWARM_OFFER_SEC` (60) from `offer_seen` (written when its wait or header delivers it), never past `SWARM_OFFER_MAX_SEC` (300) from when it was made; a claim by any other seat is refused naming the offer; it is accepted by the claim that names it, declined with `offer decline` and why (passed on at once), invalidated by any change to the lead's revision, and lapsed by time, all derived from the chain. A seat that is done, dead, compacting or has an offer standing in either register (a lead's or a question's, read again under the registers' lock for each offer, and across a batch of deliveries) is offered nothing. A person's question offered to a seat holds against every way of taking its work while the offer stands: an open with `take` is opened unheld, and a claim of a lead under it, or a reopen with `take`, is refused naming the offer. When a closed lead's entry is superseded (not disputed) by a correction that changes no conclusion (`sameConclusion`: the same kind, the same conclusion fields the symbolic citation holds, `conclusionFields`: the result, the question revision, inconclusive, asserts_absence; a limitation's same reason; and the same value up to case, spacing and closing punctuation: only its refs, evidence or reasoning changed), the closure is held on the entry that stands, a `confirm` by `system` with the why `repoint (conclusion unchanged): …`. Otherwise, when its closer is available, the closer is offered to confirm the closure, one offer per seat and correction chain (`batch`: the chain's head, E-<seq>; one notice names every closure in it, and `lead_confirm(batch, why)` confirms them in one act), or one lead with `lead_confirm(id, expected_revision, ref?, why)`, on the correction by default or another standing entry of the kind the disposition cites; declined or unconfirmed it reopens (`cause: superseded`, with an `offer_lapse`); a closer that is compacting (before the offer or after it) is away, not gone: the confirmation waits for it until `SWARM_CONFIRM_COMPACTION_HOLD_SEC` (300) past the compaction's start, the offer made again when its window ran out meanwhile, and reopens past that bound; a closer done or dead reopens it at once; a closure waiting for confirmation meets no need and is an `open_lead` defect. `lead_reopen(id, expected_revision, why, take?)` reopens a closed lead (`cause: agent`), refused for a lead the operator closed, one closed withdrawn or under a withdrawn, excluded or proposed question, one in triage, a needs_operator the operator has not answered, and a duplicate of a lead still open; the disputes in force on what it cites are named and stand. `route_review(id, material, why, second_review_why?)`, by a seat that neither closed nor held a limiting lead, is bound to that close (its spell and ref) and to the answers of its questions it saw (`basis`: each question's standing answer or acceptance). Reviews are offered, one seat at a time (the c10 pilot had six seats review one lead within minutes): once a material limiting lead's questions are all answered or accepted and no review saw those answers, and once a material negative has no review, the item is offered (`offer` with `reason: route_review`, `lead`, `basis`; or `reason: negative_review`, `entry`: the answer's seq) to one eligible seat, never its closer, holders or authors (the answer's and its coverage records'), never one done, dead, compacting or with an offer standing: one of another model family than every seat that did the work first (team.json's `model` per seat, its route and release tag dropped, `modelFamily`; a preference, never a requirement, and another model is not a second source), then the one that held a lead under its questions, then one that recorded an entry answering them, then a waiting seat, idle longest. A material negative's offer leads with its packet, source-first (`reviewPacketWords`): the question as asked now (its register id, revision and words, whole), its scope (material, whether it asks whether something exists or for a complete set) and the original sources its answer's coverage records and cited entries lead back to (`originalSources`: inputs, imports and captures as named, a job's output by its declared inputs, followed back); then the answer under review, linked by its seq, the entries it corrects and its coverage records, never quoted; then the state of each source's broad extraction; then what to do. Another seat's `route_review`, or `attest` with `review`, of an item reviewed already (for those answers) or offered to another seat now is answered quietly, `{ok: true, deferred: {item, by | to, until?, why}}` and a `review_deferred` trace row: nothing is recorded and it is not a refusal. A second, independent review says why it adds something (`second_review_why`, kept on the review). A decline passes the item to the next seat. `offer accept` on a review takes it (`offer_take` with `until`): it stays the seat's for `SWARM_REVIEW_HOLD_SEC` (600) rather than the first claim's minute, other seats' reviews of it are deferred to it meanwhile, and it lapses (recorded, `offer_lapse`) if the review is not recorded by then. The review the offer asked for takes it up (`offer_accept`, or the route review naming the offer), the seat's own newest offer of it even one that ran out while it reviewed, and another seat's offer standing for the item is withdrawn (`offer_withdraw`, with why). Before offering, the register withdraws each standing review offer whose item needs no review any more (the answer superseded, reviewed by any route the gate counts, the route reviewed for these answers) and records each that ran out as lapsed. The negatives offered, and listed in the header's negative bar, are the gate's (`negativeByResult`: a premise rejected on a search alone is one; `negativeReview` against the disputes), and the offer names where the review counts (`negativeReviewTargets`: the answer while every coverage record it rests on stands, and each standing record; "attest E-220 or its coverage record E-218 with review …, not answer_review"); a negative resting only on records that no longer stand is not offered. An interpretation carries its entry's hash; a job whose interpretations all stand on superseded or disputed entries waits for re-interpretation (`reinterpret: true`).

### Questions (`question_open`, `questions`, `question_ask`, `premise_propose`, `questions/`; `swarm.sh question`)

What the examination is asked (`extensions/questions.ts`, [ADR 0011](adr/0011-questions-are-a-register-with-their-askers.md)), kept beside the leads and written under the same lock (`locks/.leads.lock`). `questions/questions.jsonl` is an append-only chain of events hashed with the lead register's code (`seed`, `objective`, `open`, `amend`, `priority`, `scope`, `clarify_ask`, `clarify_answer`, `withdraw`, `dispose`, `accept`, `sign` (the register's first form of a signature, still read), `deliver`, `offer`, `triage`, `continue`); `questions/questions.md` is rendered from it after every change. While a run's hub runs it is the register's one writer: an agent's act comes on its seat's channel, and the operator's CLI (and the console, through it) prepares an act, signs it when asked, and hands it to the hub's admission on its admin socket (`--hub-admin`, which `swarm.sh` passes when the run's hub is up), which prepares it again from what was said, checks the signature against that statement, commits it under the lock and delivers it. With no hub running (a host run, or a run that is not going) the CLI admits the act itself under the same lock; the acknowledgement says which (`admitted_by`). `questions/` is a protected path.

A question has an id (`Q-<n>`) and a ledger section (`question:<n>`; a goal question the goal does not number, such as `bonus`, keeps its id as its section). Its record keeps every verbatim revision of its text (an `amend` names the revision it was written against, `expected_rev`, and is refused against any other), an optional neutral formulation attributed to whoever wrote it, why it is asked, its objective (`O-<n>`) or parent (`Q-<n>`), materiality (material: the finish line waits for it; background), priority (urgent needs a reason), what it expects (existence, value, narrative, timeline, list: a hint, never a format), hints (`{ref, value?}`: where to look; a hint with a value is also recorded in the ledger as an open hypothesis in the asker's name), attachments, a suggested seat and a deadline, and its origin: `goal`, `agent` (with the entry that raised it), or a person, `analyst`, `reviewer` or `observer`, with their role, OS account, host and channel, whether they are enrolled, and whether the act is `claimed` or `signed`. Three axes are kept apart: scope (in scope, proposed, excluded), work (admitted, working, clarification needed, paused: derived) and the evidential disposition (its answer in the ledger).

The kickoff seeds the register from the goal (`seed`): each question its answers check names as `Q-<n>` (so `question:N` and `Q-N` are one question, and `lead_open`, `record(answers)` and an answer's `section` take either), and each objective of an `## Objectives` section (a goal's front-matter `objectives:` list is written into one). A goal may name objectives and no questions: the header then asks the first agents to propose them with `question_open`. A register read before any write derives the seed from the goal and writes nothing.

Scope follows declared structure, never a question's words. The goal's questions are in scope. An agent's is in scope when its objective exists or its parent is in scope, otherwise proposed (a triage queue shown in the header and the console); an agent never names a new objective, and has no tool to amend, re-prioritise, re-scope, withdraw or accept anyone's question. A person's: the operator (the host's OS account, not enrolled) and an examiner are in scope by authority, and `--objective new` expands the case (a new `O-<n>`, "scope expanded by <person>"); an analyst's is in scope inside an objective or under a question in scope, otherwise proposed; a reviewer's (a `review_query`) and an observer's are proposed. Admitting and excluding are the operator's and the examiner's; a material question is never excluded by anyone else. An analyst amends, re-prioritises and withdraws their own questions; an observer only proposes and withdraws.

Delivery comes after the chain write, never before, and from the chain itself: each person's question in scope is posted once per revision (`from: analyst:<person>`, `tag: question`, the whole text, addressed to the seat it is offered to so no other seat is woken; every seat reads it at its next delivery), its hint hypotheses recorded, then a `deliver` event; a delivery that finds the post already made (by the exact key in its front matter, `key: question:Q-n:r<rev>`, never by its words) records that post. A revision whose post or hint hypotheses could not be made gets no `deliver` event: the delivery says it is pending, and the next one tries again. An `offer` goes to the suggested seat (when it is available: not done, dead or compacting, and no offer stands for it), or to the most suited idle seat (hints meeting the refs of entries it recorded, leads it held under the same objective or parent, then the one idle longest); it runs through the leads' offer state machine ([ADR 0015](adr/0015-one-seat-finishes-and-work-is-offered.md)): first claim for `SWARM_QUESTION_OFFER_SEC` (else `SWARM_OFFER_SEC`, 60) from `offer_seen`, never past its age bound, declined with `offer decline` (the next seat at once), `offer accept` holding it one more window while the seat opens its lead, and a peer's `take` under it meanwhile opened unheld. Once no offer holds it, the most suited idle seat not yet offered it at this revision offers it to itself from its `wait`. Nobody owns a question. Every header ranks the analyst questions first, whole, then the triage queue and the clarifications not answered; an urgent question is a NOTICE, which wakes nobody, to the holders of leads under the same objective or line of follow-ups, and cancels nothing. Every write path and every header delivers what was committed and not delivered, so a crash between the write and the post is made good at the next read.

A person's question is a hypothesis to test. The first agent lead under it carries `proposition` and `negation` (a directive, the operator's lead, carries `product` and `acceptance` instead, and the first agent to claim a directive under a question no lead has framed gives `proposition`, `negation` and, when the question has no route plan, `routes` with `lead_claim`, kept on the claim event); its answer carries `contrary` or `contrary_none_why`, and `result: premise_not_supported` is an answer. Leading forms, the imperatives "confirm that", "show that", "prove", "demonstrate that" and "verify that" at the start of the question, of a sentence, of a line or of a clause after a semicolon or a colon (after an opening quote, "please" or "can you"), are flagged on the question for the critic and never refused; the same verb inside a question ("what shows that", "which proves") is not. A question's words, reasons and hint values may not carry a value the run marks sensitive (a ledger entry recorded `sensitive`); the refusal names the entry, never the value.

`question_ask(id, what_is_unclear)` records a `clarify_ask` with a durable id (`C-<n>`); the operator request of kind `clarification` in `operator-requests.jsonl` is derived from that event and written once, keyed by its `C-n` (at once, and again at the next header or act if the process died first), and so is the answer's post to the asker (`key: clarification:Q-n:C-n`); the work state is `clarification_needed` until `swarm.sh question <run> clarify-reply Q-n C-n TEXT` (the asker, an examiner or the operator) answers it, which is posted to the asking seat and wakes it. A withdrawal needs a reason: the leads that served only that question close `withdrawn` (the harness's disposition, never an agent's), a material lead holding a standing finding goes to the triage queue instead (`scope L-n in_scope|excluded` keeps it or closes it), its follow-ups go to triage, and nothing in the ledger is touched. A lead holds a finding when a job of its found one, it was opened from one (`record(kind=finding, opens)`, origin `E-<seq>`), it needs one, or it closed on one. These effects are reconciled from the chain under the lock, in the act's own hold and at every later act and header, so a withdrawal whose process died before them is made good at the next read. A withdrawn goal question is no longer one the run must answer: the answers check names it as withdrawn instead of requiring it, and the finish line gives it the outcome `withdrawn`. Every name of a question (`Q-n`, `question:n`, `n`, `Qn`) is resolved to it before any scope, withdrawal or status check, so a proposed, excluded or withdrawn question takes no lead under any of them. An answer to a register question says which revision it answers (`question_rev`, in the ledger's hashed core; absent is revision 1): it is checked under the registers' lock when the answer is recorded, a revision the question has moved past is refused, and once a question has more than one revision the answer must name one. An amendment makes the standing answer stale until it is recorded again for the new revision, as a correction (`supersedes`) naming it, unchanged words included. An acceptance (`accept Q-n --as bounded|not_determinable --why W --expect-rev N`) is the operator's or an examiner's, is refused while a lead on the question is open, holds for that revision only, and limits the run.

**A question that must be established** ([ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "A question that must be established"). A question may carry `must_establish` (a boolean in the act, a signature covering it): `true` on an `open` or an `amend` by the operator or an examiner (`swarm.sh question <run> add|amend --must-establish`), or on a goal question's seeded `open` when the goal's `## Must establish` section names it (a front-matter `must_establish:` list, `[1, 3]` or `- 1: why` lines, is written into one; `goalMustEstablish`; a name the goal does not number requires nothing, and `seedRegister` returns it as `must_establish_unknown`, which the kickoff warns of); `false` on an `amend` with `why`, which releases it. An agent, an analyst, a reviewer and an observer are refused it, and so is a background question (`materiality background` with the requirement, either way round). The fold keeps `must_establish {required, at, by, origin, seq, rev, why}`, changed only by an act that changes it; an act that says what stands already is refused when it says nothing else. For such a question the answers check gives a disposition only to an answer whose outcome is `answered` (established on a standing finding and no best candidate, a premise shown not to hold on a finding, a bounded negative under the stronger bar); partial, not determinable, a bounded negative short of that and out of scope keep their outcome and get none (its line says so). The finish gate marks it `must_establish` and names the requirement first among its `blocks`; the done's refusal gives its ways (establish it, or the operator accepts its limits or releases it) instead of the negative path; readiness holds it while its standing answer only limits the run (`establishesBy`: established, premise_not_supported, or a bounded negative with `asserts_absence`), with an item `question:<n> must be established (required by …)`. An acceptance that stands disposes it as it disposes any question. Every header names each such question not yet established (`Must be established (n): …`), and `questions` list, `questions/questions.md` and `question show` say who required or released it.

A question's evidential disposition follows its answer: whenever the header is built or the register acted on, a standing answer whose result differs from the last recorded is written as a `dispose` event (`result`, the answer's seq and hash), so the register says how each question stands without anyone copying it. `accept Q-n --as bounded|not_determinable` takes a question's limits for one revision and the answer that stood then (its `E-n` and hash, in the event's `decided`); it stands only while both do (`acceptanceStands`). It is refused while a lead under the question is still open, and while its answer is a negative no other seat has reviewed (an acceptance never stands in for the review); an accepted question's negative is held to the bar all the same, and any acceptance makes the run `examination_limited`.

The finish line reads the register in the same snapshot as the leads, and `stateRevision` includes its file: every material question in scope beyond the goal's own is held to an answer as the goal's answers check holds its questions (`open_question`, and the answer's own defects), a stale answer refuses `done` (`stale_answer`), an accepted question is examination-limited, and a proposed one holds nothing. The sentinel is written under the registers' lock against the revision the finish line was judged on: a question admitted after that line refuses the done (run it again), and one admitted after the sentinel (a new question, an admission from the triage, or an amendment that makes a new revision) is recorded `after_done`, a durable follow-up receipt. `swarm.sh resume` takes the follow-ups up as the continuation's work: one `continue` event names them, and they are delivered like any question.

A person's act may be signed (`--sign`): the act's statement (`{namespace: dfirswarm-question, run, ev, target, act, origin}`, canonical) is signed with the enrolled key (ssh, FIDO or PKCS#11, the secret on fd 3 or the terminal) before anything is written, and the signature is carried on the act's own event, so the act and its signature are one line. The act is kept exactly as signed (what the harness decides of it is in `decided`). `swarm.sh question <run> verify` rebuilds each statement from the chain and checks it: the signature's envelope names the person and key fingerprint the signed act names, the key it carries has that fingerprint, the person enrolled on this install under that id holds that key and principal (`wrong-principal` when not), and the signature verifies (against `--allowed-signers` or `--ca` when given). It fails on `bad` and `wrong-principal`, and on an act that says it is signed and carries no signature. A directive is not signed: `--sign` on `lead direct` is refused. An act with `--as` and no signature is a claim, and says so; an act with no `--as` is the OS account's, `enrolled: false`, never promoted. The operator's record carries each act twice: the attempt, and the outcome naming the event's seq and hash. Custody seals the chain beside the leads', unsigned as a whole; the package carries `questions.jsonl` and `questions.md`, verified and redacted like the leads.

**Premises** ([ADR 0011](adr/0011-questions-are-a-register-with-their-askers.md), "Premises"; `extensions/premises.ts`). A premise (`P-<n>`) is an event on the same chain, `premise_add`, `premise_propose`, `premise_revise`, `premise_admit` or `premise_withdraw`, with `p: P-<n>`, the premise's revision in `rev`, what the actor said in `act.premise` (`{id?, text?, locator?, class?, scope?, as?}`, what a signature covers; its target the premise's id) and `act.why`, and what the harness decided in `decided` (`class`, `authority`: goal, operator or agent, `locator` when none was given). Its words are kept verbatim at each revision, with its locator and its scope (`{entities?, times?: [{from?, to?}], questions?: [Q-n]}`, each optional and bounded, the questions in the register). Its class: `given` (not proved again, never an open part), `supplied_assertion` (assumed as asserted), `proposition_under_test` (examined like any claim, assumed only conditionally). The goal's `## Premises` section (a front-matter `premises:` list is written into one) is seeded with the questions, each a given, a trailing `[scope: questions 1, 2; entities E; times FROM..TO]` read as its scope. The operator and an examiner add (`swarm.sh question <run> premise add`, a given unless `--class` says otherwise), revise against the revision read (`--expect-rev`), admit an agent's proposal (`premise admit P-n --as given|supplied_assertion`: its class changes, its revision does not) and withdraw (with why); an analyst, a reviewer and an observer are refused. An agent proposes with `premise_propose(text, locator, why, scope?)`: a proposition under test, the same words twice refused with the premise that says them. Every premise act is told once to every seat (a notice, no wake), and the header lists the premises that stand, whole. `questions` view `premises` (and `show` with `P-<n>`, with its history), `questions/questions.md` (a Premises section, each with the standing answers that cite it) and `swarm.sh question <run> premise list|show [--json]` read them. A chain with no premise event reads as before.

**What a question presumes** ([ADR 0011](adr/0011-questions-are-a-register-with-their-askers.md), "What a question presumes"). A question may carry `presumes` (at most 2000 characters, in the act's words, a signature covering it): what it takes as happened. Its asker says it on an `open` or an `amend` (`swarm.sh question <run> add|amend --presumes P`, the console's question form, an agent's `question_open(presumes)`); the goal says it in a front-matter `presumes:` list (`- 7: <what it takes as happened>`), which the kickoff writes into a `## Presumptions` section and the seed reads (`goalPresumes`; a line naming no question seeds nothing); an agent says it with a clarification, `question_ask(id, what_is_unclear, presumes)`, once and only while none is recorded (refused otherwise, naming the recorded word; the clarification's operator request carries it). An act on anything else with `presumes` is refused. The fold keeps `presumes {text, rev, at, by, origin, seq, via: open | amend | clarify}`; an amendment with `presumes` alone makes no new revision. A person's question presumes the proposition its first framed lead states (with its negation), or its own words while no lead has framed it; a goal's or an agent's question with no `presumes` presumes nothing (`questionPresumption`, `presumptionsOf`; the views carry it as `presumption {q, section, text, source: presumes | framing, by, lead?, negation?}`). Its answer is reviewed against the fixed rival "the question's premise is not supported": `answer_review.premise_tested {outcome, refs}` (an outcome that says something, and at least one ref: an entry in the ledger, never the answer under review, or an object that resolves), and the answer may carry `premise_tested {outcome, refs}` itself (a question's answer's only; its entries are citations; in the ledger's chained core, and the review's in the attestation's hashed record, only when present). An established attest of an answer that claims established, on a material question that presumes something, whose review does not test the premise, or tests it in a placeholder, is recorded best_candidate with why in `capped`; the reply gives the fix (`reviewEvidenceCaps`, code `premise_untested`; `PREMISE_TEST_FIX`). A partial answer to such a question that neither it nor a review of it tests is warned, `premise_untested`, wherever warnings are delivered, and never held (`ledgerGate`'s `presumes`). `questions/questions.md`, `question show`, the agents' `questions` list, the question's post and the console's card say what a question presumes; the report's §2 chain says it, and each answer says each premise test on the record or that none is. `swarm.sh replay --presumes Q[,Q…]` amends the named questions in the copy to presume their event in synthetic words, and says what the rule would have warned and capped.

### Operator requests and the case contract (`requests/`, `operator-requests.jsonl`, `swarm.sh requests|evidence|material`)

What the run asks of a person, what may come into it and what it may be used for ([ADR 0014](adr/0014-the-case-contract-says-what-comes-in-and-what-is-asked.md)).

**Requests.** `requests/requests.jsonl` (`extensions/requests.ts`) is an append-only chain hashed with the lead register's code, written under its own lock (`locks/requests`), each write flushed before anything is said of it. Its events: `open` (`rid` `R-<n>`, `kind` lead | acquisition | clarification | decision | network | premise, `key` where it came from: `lead:L-n:<close seq>`, `clarification:Q-n#C-n`, `network:NI-n`, `decision:D-n`, `premise:P-n@r<rev>` (a standing answer that contradicts that premise revision on a standing, undisputed finding: one request per premise revision, answered when the premise is revised or withdrawn, or on the request, withdrawn when no standing answer rebuts it any more); `line`, the request as every older reader has seen it; `ask` and `questions` for an acquisition; `imported`, `line_sha256` and `legacy_notified` for a line of a run from before the chain), `claimed` (`claim`, a dispatch's token), `notified` (`targets`, `notice`, `claim`), `delivery_failed` (`claim`, `why`; `cause: no_target` when no target took it), `acknowledged`, `answered`, `declined`, `withdrawn` (`text`, `why`, `cause`), and `stage` (an acquisition's: `authorised`, `declined`, `collecting`, `received`, `validated`, `unavailable`, with `import`, `inventory_rev` and the files' `sha256` when evidence arrives). A request's state is derived: `pending` until a `notified`, `acknowledged` once acknowledged (or authorised, collecting or received), then the closing event's. The commit is where the request's state already lives (a lead's `close`, a question's `clarify_ask`, a grants chain's `item`; a stop proposal is opened here directly); `reconcileRequests` writes every request those imply and the chain does not hold, idempotently by key, and closes those whose answer they record (an operator's note on the lead after its close: answered; a reopen by anyone else first: withdrawn; the clarification's reply: answered; its question withdrawn: withdrawn; an item's close: answered or declined; the operator's stop: a proposal answered; a finish: withdrawn). An acquisition is held to the case policy as it is written: `more_evidence: no` declines it at once (`by: "case policy"`, `text`: exactly `no additional input under this case policy`), `yes` authorises it. `operator-requests.jsonl` and `requests/requests.md` are rendered from the chain after every write, and never over a line the chain does not hold: every write first imports each such line whole (a run from before the chain, a first write cut off after `requests.jsonl` appeared, a line an older harness appended), found again by its `line_sha256`; the first import is written beside the chain, flushed and renamed onto it. Delivery (`dispatchRequests`): each request committed, open, not yet notified, not claimed by a fresh claim (`DELIVERY_CLAIM_TTL_MS`, ten minutes) and past its backoff after a failure (a minute, doubling, at most an hour) is claimed on the chain under the requests' lock, then handed to the notifier with its ids only (`request`, `kind`, `run`, `lead`, `question`, `id`, `item`, `questions`, `urgency`, `show`), and `notified` (or `delivery_failed`) is appended after the hand-over, a failed `notify.sh` saying which way it failed in `why` (`could not be run (<errno>)`, `took more than 20 s and was stopped`, `was ended by <signal>`, `exited <status>`); an imported request is delivered unless its run's old watchdog had notified it (`traces/idle-nudge.requests` held the count of lines it had handed over); with no target configured nothing is claimed, sent or written, and it stays pending. The operator's acts (`requests-cli.ts ack|answer|decline|withdraw|authorise|collecting|unavailable`, which `swarm.sh requests` and the console run) go to the hub's admin socket while it runs (`op: "request_act"`) and are made there, or here with no hub; each carries `announce`, and `publishRequestActs` says it on the board from the event, once, by the key `request:<rid>:<seq>` (a system post), at the act and again on every round until it is said; `swarm.sh` records the outcome on the operator's record (`requests_outcome`). The hub runs reconcile and delivery after `leadClose`, `questionAsk` and `netRequest`, at start and on every round (`request_notified` on the trace); `scripts/requests-cli.ts fire` is the watchdog's fallback. `swarm.sh requests <run> list|show|ack|answer|decline|withdraw|authorise|collecting|unavailable` and the console's Requests tab act on it; custody seals the chain (`seal.requests`, the `operator requests` check); the package carries `requests.jsonl` and `requests.md`.

**The case policy** (`scripts/case-policy.ts`, `network/policy.json`, version 2): the network fields of ADR 0012, and `more_evidence` (`no | ask | yes`) and `material_use` (`{acquired_evidence, case_material, operator_supplied, external_capture}` each `evidence | reference | none`, with the preset's `material_note`). A version 1 record (material use as text) is read with the preset's uses and its text kept as the note. The kickoff writes it before the custody anchor (`case_policy_sha256`); custody holds it to the anchor (`case_policy` in the verdict, `seal.case_policy`); a release binds it (`case_policy`); a resume keeps it. `P.materialUseRefusal` refuses a record of any kind (in `appendLedgerEntry`, every non-external entry: a finding, an answer, a coverage record; and an attestation's or a dispute's refs) whose resolved lineage reaches material of a class the policy says `none` for: `externalLineage(S).probe` resolves each ref (the material's own `import:`/`job:` ref, the same bytes by `sha256:`, a job's output whose job read it, a catalogue member of such a job) and each entry it rests on (support, limitations, `derived_from`, a coverage record's result entries) to the classes it reaches. The lineage indexes every external attachment by the object it resolves to and by its digest, a job's output included. `check-answers` fails an answer whose lineage reaches such a class (`material_use`, fixed and never named).

**Evidence and material added** (`scripts/material.ts`). The file or directory (never a path inside the run; links and special files refused) is copied to a staging directory of the addition's own (`<sandbox>.staging/addition-*`), each copy held to its source's sha256 before it (and to `--sha256`). Then, under the run's `material` lock (one addition at a time, across processes): the acquisition is read again, an import id is reserved by making `store/imports/<id>/` (a directory made once; another addition that picked the same number takes the next), the copy is sealed with the store's `sealTree` as `store/imports/<id>/out/` with `manifest.json` (refused, and kept for the record, unless it names exactly the files copied, each at its copied hash), a read-only `material.json` is written (`{v: 2, import, mode, class, at, supplied_by, via, from, why, files: [{path, sha256, bytes}], manifest_sha256, permitted_use, request?, questions?, inventory_rev?, sensitive?, tool?, ledger_seq, lead_seq}`: the reason whole, and the ledger's last seq and the lead register's length at the commit), and the addition is committed by its journal line (`evidence_added` with `inventory_rev` and `catalogue`, or `material_added`; `manifest_sha256`, `material_json_sha256`, every file's sha256, `ledger_seq`, `lead_seq`), which custody's store check holds each import to. Everything below is derived from the record after the commit, each step found again by the import's id and made once (`applyAddition`), and the journal's `addition_applied` line says all of it is recorded; a process that dies between leaves it to `reconcileAdditions` (the hub at start and on every round, the next addition, `material.ts list`), and the finish gate names each committed addition not yet applied (`addition_incomplete`). A reason longer than the ledger's value or a lead's reopen allows is not cut: the entry says where it is kept whole. The ledger gets an `external` entry (`acquired_evidence`, `operator_supplied` or `case_material`) citing `import:<id>/<file>` (or `import:<id>` past 19 files), its provenance `{supplied_by, at, from, sha256, permitted_use, import, files, request?, inventory_rev?}` in the chained core. Evidence also: its acquisition `received` then `validated`; the closed leads under its questions (both sides resolved through the question register, so a custom section such as `bonus` is its `Q-n`) and the request's own lead reopened (`cause: evidence_added`, `import: <id>`: once per import, and only a close made before the commit); a question register `evidence` event per question (`decided: {import, request, ledger_seq, inventory_rev}`), which makes an answer with `seq <= ledger_seq` stale (`stale_why: "evidence"`, a `stale_answer` defect at the finish line) and lifts an acceptance made before it (`Q.acceptanceStands`); the negative bar's inventory revision includes every `evidence_added` line; and, when the catalogue is on, a detect pass over each file (`evidence_catalogue_queued`). The hub is the store journal's writer while it runs, so the act goes to its admin socket (`op: "material"`); with no hub, `material.ts` opens the journal itself. Every seat's VM mounts the run's directory read-only and live, so a sealed addition is readable there at once (`store/imports/<id>/out/`), and jobs read `import:<id>/<file>`; no frozen view is promised, and provenance never rests on the path read: the lineage resolves an `import:` ref, the same bytes by `sha256:`, and a job's output made from them to the addition's external entry. A question's attachment given as a host file is supplied first (`supplyAttachments`), and an attachment that is an object of the run is recorded as `operator_supplied` after the act (`recordAttachments`); `input:` and `member:` are the evidence itself and are not.

**A tool supplied** (`swarm.sh tool-supply <run> add`, `material.ts tool-add`, `MaterialRequest.tool`). A program no image holds is material of class `operator_supplied` sealed by the same path (`mat-<n>`, mode `material`; never `evidence`, never another class), with what only the operator knows: `tool: {source, built?, checked, for?}` in `material.json` and in the external entry's provenance (`provenance.tool`, in the chained core, so a rewritten statement is a broken chain). `source` (where it came from) is required; `source` and `built` are the operator's statement, at most 4000 characters each and refused beyond it, never cut. `checked` is the hashes the operator gave (`--sha256`, repeatable): each must be one of the supplied files' sha256, else the act is refused with every file's hash named and nothing is sealed (a hash of anything else goes in `source` or `built`). `for` is the requests and leads it is supplied for (`R-n` / `L-n`, each read from its register and refused if absent; a request's own lead is added beside it); nothing closes them. The case policy's rule for the class is kept: a policy that says `operator_supplied=none` refuses a tool before anything is sealed (`material add` under it is still kept on the record), since a record resting on the tool's output would be refused (`materialUseRefusal`); every preset (`standard`, `live_adversary`, `internal`, `ctf`) admits it, and `more_evidence: no` refuses evidence only. The external entry's value is `Tool supplied (operator_supplied): …` and its source `swarm.sh tool-supply add, by …`; the lineage flags what rests on it with its class as for any material. The board post (`TOOL SUPPLIED as import:<id>`, key `addition:<id>`, derived from the record so a reconciliation writes the same words) gives the seats the source and build as the operator's statement, the hashes checked, the requests and leads, that the harness vouches for the bytes only and a seat tests the tool on input whose answer it knows before relying on it, and how to run it: a sealed file has no execute bit (`sealTree` seals at 0444), so a job declares it (`inputs: ["import:<id>/<file>"]`, or `import:<id>` for a bundle), copies it and every library it loads into an executable temporary directory inside the job and runs it from the copy. The harness names no program and knows no format. The hub admits the act as it admits any material (`op: "material"`, with `tool`); a hub started by an older harness ignores `tool`, so `material.ts tool-add` holds the case policy's rule, the statements (`checkToolStatements`), the hidden-file refusal and the `--sha256` hashes against the files itself before it hands the act to a hub, and the shell's reply warns when the answer carries no `tool` (the source, build and `--for` were not recorded and the post did not say how to run it). A directory is sealed whole and read by every seat, so a tool directory with a hidden file or directory in it (`.env`, `.git`, `.netrc`) is refused, and the reply lists every sealed file; a path that holds the run (its parent, the runs directory) is refused for every addition (`holds the run`).


**External lineage** (`scripts/net-broker.ts` `externalLineage`): every capture and every `external` entry's material, every job that resolved one (by path or digest, or read the store with a broad scope after it arrived), and every entry resting on any of them, transitively, with the source classes of each (`classes`). `check-answers` names each answer that rests on it with its classes (and `external` in its machine line), the report marks it, and `release.json` binds `external.answers` (section, seq, hash, classes, via) and `acquisitions`.

**Sensitivity (B9).** `P.runSensitiveTokens` reads every ledger entry marked sensitive, of any kind and author, standing or superseded, into `P.b9SensitiveValues`: each entry's `value` whole, matched as a phrase on word boundaries (`exact`), and from the fields that hold what it records (its `value`, and `attribution.subject`; never its evidence, source, method, `indicates` or other notes, which name the tools and files a question names too) the words `P.distinctiveValue` takes for values (eight characters or more with a digit, a symbol other than a hyphen, dash or apostrophe, or a capital inside the word; or twelve letters or more with under a fifth vowels or five consonants in a row; never the run's ids, a number, a date, a time or a timestamp), found anywhere in the text or with its spaces taken out. `P.sensitiveRefusalOf` compares both sides folded by `P.sensitiveFold` (NFKC, invisible format and default-ignorable characters removed, case folded, the markup `tidyName` drops removed, whitespace collapsed); `claimName` checks the name as given and as tidied. The package's redaction scanner reads the broader `P.sensitiveTokens` (every field whole, every identifier-like run). `claimName` refuses a name or a `doing` that holds one (nothing is written), and the question register's words are held to the same function; there is no answer-value concept and no exemption for the goal's words.

### Reports, sensitive outputs, tool candidates and the library hint (docs/adr/0016)

**`job_run(secret_output)`.** A boolean on the job's spec (anything else is refused); it is on `job_accepted`'s spec. When the job's output is sealed, its `job_committed` line carries `sensitive: {why, from, note}`: `why` is `secret_output`, or `derived` when the job was made from a sensitive output, `from` the sensitive jobs it was made from. Derivation is read from the snapshot the job's scope manifest recorded — every accessible and expanded object's sha256, hashed at the job's start (`snapshotObjects`) — so a job is derived whenever it executed against the bytes of a sensitive output (its outputs or logs) by their digest, wherever the bytes sat: a work copy the agent carved out, a store blob, a catalogue link, a catalogue generation (`catalog/gen/<gen>/`) or alias a sensitive job made, or a directory scope that held one; a job with no declared scope (`all`, or nothing) is derived when its command, its arguments, its import source or its targets name a sensitive job's id as a word of its own. Derivation carries through chains of jobs. The job's projection (`store/jobs/<id>/job.json`) carries the same `sensitive`, `job_status` and the post that says the job is done say it, and a sensitivity that cannot be decided seals the output sensitive and says why. `scripts/output-hygiene.ts` reads it back from the journal (`sensitiveIndex`, whose `content` maps every sensitive output and log digest to its job; the empty-file digest is not a mark).

**Entries citing a sensitive output.** Every entry the ledger takes (of any kind but `external`) whose `refs` reach a sensitive output (`job:<id>…` of a sensitive job, its files or its logs; `sha256:<hex>` of one of its files; `member:<gen>#<n>` of a generation a sensitive job made) is recorded with `sensitive: true`, in its chained core, and the answer's `note` says which ref and why. From then on the run's sensitive values (B9, ADR 0014) include its value.

**`partial_output`.** A defect of the ledger gate (`ledgerGate`'s `partial`, `partialOutputCites`): a standing entry that cites `job:<id>…` of a job whose status is `cancelled` or `stopped` and carries no `qualifies {ref, why}` for that ref. `limitation`, `coverage`, `answer`, and an `absence` whose `completion` is not `complete`, are never one. `named_by` is always empty: the defect is fixed by the entry (a correction with `qualifies`) or by citing a job that ran to its end, never by a limitation.

**Packages.** Under `--redact`, `package-tools.ts redact` withholds every file whose sha256 is a sensitive job's — its outputs, `stdout.log`, `stderr.log` and an interrupted attempt's logs — wherever it sits in the package, not only under `store/jobs/<id>/out/`, so a byte-identical copy elsewhere goes too; each is replaced with `[withheld: sensitive content (<why>); matched <id>. Its bytes, digest and path are in the run owner's private sidecar, not here.]`. What it withholds or matches is named by a **keyed id** (`hidden-<24 hex>`, HMAC-SHA256 under a per-package key), never by an unsalted sha256, so a low-entropy value cannot be recovered from the record; the key, and each id's real digest, path and word, are written to a **private sidecar** beside the package (`<dir>.private.json`, mode 0600), outside the handover. `REDACTIONS.json` gains `sensitive_outputs` (`job`, `why`, `from`, `status`, `files`, `withheld` count), `withheld` (`id`, `job`, `why`, `bytes`, `path`), `changes` (with sensitive paths behind ids) and `output_words`; `REDACTIONS.txt` lists "Withheld whole" by id. The scan runs over every file, including the generated records and the filenames: the words are the sensitive entries' (the ledger's `sensitive`, and any entry whose refs reach a sensitive output) and the whole trimmed text of each sensitive output file of at most 256 bytes with no NUL, one line, of six characters or more with a digit or a sign in it, or of ten or more; it also looks for each sensitive output's digest in a record and for a filename that holds a sensitive word (`as: "filename"`); a hit is named by a keyed id or a sha256, never the word, and a hit on an output's text names it (`output: "job <id>, <path>"`). Without `--redact`, `package-tools.ts hygiene` writes `HYGIENE.json` when the run has a sensitive entry or output: `entries` (`seq`, `why`), `sensitive_outputs` (with `carried` counts), `carried` and `scan` (`files`, `words`, `hits`), with the same keyed ids and sidecar; nothing is taken out. `export --redact` treats an entry whose refs reach a sensitive output as sensitive.

**The library hint.** A tool's `manifest.json` may carry `use: {extensions?: [".ext"], magic?: [{offset, hex}], names?: ["name", "prefix*"]}`. At a command job's admission with a declared scope, the hub resolves the scope, lists up to 256 files of it (a directory's from `inputs.json` or the store's manifest, else as it stands), reads the first bytes each manifest's `magic` needs (at most 4096), and matches every tool in `tools/`: by extension, by magic, by name (`*` any run of characters, case-insensitive), and, for a manifest with no `use`, by its description naming the extension (three characters or more) as a word of its own. The answer to `jobSubmit` (and `job_run`) carries `library: {note, tools: [{tool, description, matched: [{input, by, what}], example?}], examined, of}`; a tool the command names (`tools/<name>/`, or its name as a word) is left out. `scripts/library-hint.ts`.

**Tool candidates.** `scripts/tool-candidates.ts <sandbox> [--out DIR] [--min-lines N] [--library DIR]... [--run ID] [--json]` (and `swarm.sh tools <id> --candidates`) reads every command job an agent (not `system`, not `derived`) ran and takes out: each heredoc body (`<<WORD`, `<<'WORD'`, `<<-WORD`; never `<<<`), with its language from its opener (the interpreter before `<<`, or the extension of the file it is written to; a data file is left out) or its first line; each inline script given to `python`, `perl`, `ruby` or `node` with `-c` or `-e`; the command with the heredoc bodies taken out; and each file under `work/` or `tool-output/` the job's scope manifest names and its command **ran as code** — an interpreter invoked it, or it was executed directly, not merely named or copied — read without following a link (`readNoFollow`) and only when its bytes still match the snapshot digest the job read, else omitted. Output hygiene runs first: a candidate from a sensitive job, or one whose text holds a sensitive value (a sensitive entry's word, a sensitive output's text, or a sensitive output's digest), is withheld (`sensitive: true`, empty `text` and `file`), its script never written. A text is counted once by the sha256 of its normalised form (blank lines at its ends and trailing spaces dropped); one of `--min-lines` lines or more (20) is a candidate. Candidates are ranked by `score` (lines times jobs), then lines. Each carries `jobs` (`job`, `seat`, `profile` from the spec or the journal's `job_started`, `status`, `at`), `reuse` (the distinct jobs after the first), `lines`, `bytes`, `kind`, `lang`, `source`, `note`, `sensitive` and `library` (`tool`, `where`, `why`: the script names the tool, or its `use` matches what the jobs declared by extension or name). The output directory (default `<sandbox>.tool-candidates/`) holds each non-withheld script whole (`NN-<lang>-<sha12>.<ext>`), `candidates.json` (everything but the text) and `README.txt`.

**The report.** `report-body.ts` reads the question register with the leads (`leadsSnapshot`, `questionViews`) and renders §1's table (`Question`, `Status`, `Asked by`, `Answer`, `Leads`, `Accepted`, `Tokens`) over every question, §2's chains (`id="qc-<Q-n>"`, grouped `original`, `asked`, `emergent`, `proposed`, `excluded`, `withdrawn`, then `id="unresolved"`), and Appendix F (`id="sF"`, each lead `id="reg-<L-n>"`). A register question in scope beyond the goal's joins the report's questions and, when material, the sections the report's gate holds. Events of a register never written (the goal's seed derived at the reading) are shown without a time. The cost (`scripts/question-cost.ts`): calls from `traces/model-gateway.jsonl` (lines with `seat`, `at` and tokens, refusals left out), else each seat's `budget.json` tokens spread over its trace rows; holding intervals from the lead register (from an `open` with a `holder` or a `claim`, to a `release`, a `close`, a `reopen` or another `claim`); a call split evenly over the leads its seat held at that moment and each lead's share over the questions it names (a register id, or `question:<section>` when the register holds none); calls outside every hold in `unheld` by seat.

**`release.json` `questions`.** `{lines, head, sealed, by_origin, analysts, post_seal: {lines, events: [{seq, ev, q, at}], note}, note}`: `lines` and `head` are the custody verdict's seal of `questions/questions.jsonl` (`sealed: false` and the chain as it is for a verdict from before the seal); `by_origin` counts the `open` events of the bound events by `origin.kind` (for a register never written, the goal's questions as derived); `analysts` is every `analyst`, `reviewer` or `observer` person in the bound events: `person`, `name`, `role`, `enrolled`, `identity` (`signed` when any of their acts carries a signature), `asked`, `acts`, `signed_acts`. Release verification fails when the chain here does not hold `head` at `lines`, and, in a run, when `by_origin` or `analysts` is not what those events say.

**Every chained register, in one list.** `scripts/chained-registers.ts` names each hash-chained register a run writes under its sandbox (the trace, the ledger, its attestations, disputes and sweeps, the lead and finish registers, the question register, the operator requests, the network's grants and fetches, the store journal, the model gateway's log): where custody seals it (`seal.<key>`), where a package carries it, how a release binds it (its own `chains`, or the verdict it binds), and its chain code; and every other `.jsonl` name the harness uses (`OTHER_JSONL`), each with why it is not one. Custody seals each by its length and head (`seal.sweeps` and `seal.finish` since 2026-09-29, the `store sweeps` and `finish register` checks); `sealDrift`, `sealPrefix` and `earlierSeals` hold each, so an earlier verdict still verifies as a prefix after a resume, which records the sweeps' and the finish register's heads too. A release binds the sweeps in its `chains` (`sweeps`) and holds the finish register, the store sweeps and the model gateway's log (its first sealed lines, by their sha256) to the verdict it binds; `asSealed` checks them before a draft or an adoption. A package carries `ledger-sweeps.jsonl`, `finish.jsonl`, `network/grants.jsonl`, `network/fetches.jsonl` and `trace/model-gateway.jsonl` as declared components, and `verify` walks each of them and the operator requests against the seal. `--redact` keeps a store sweep of a sensitive coverage record, one that found its strings in a sensitive job's output, and one that says a sensitive entry's words by its seq, target, state, prev and hash; a sensitive entry's `looked_for` strings are among its words; a finish event that says one is redacted the same way. `tests/chained-registers.test.ts` holds every register in the list to all of it, and fails on a `.jsonl` name in neither list.

**The operator requests and custody.** `sealDrift` holds `requests/requests.jsonl` to the verdict's `seal.requests`: grown with the sealed line still at its place, the lines after it are listed in `seal_after` (`operator requests: N event(s) after the seal`); otherwise a drift. `sealPrefix` and `earlierSeals` hold it as a prefix; release verification checks it with the other registers (`the operator requests`); a draft or an adoption (`asSealed`) checks the network's two chains and the requests against the verdict, the requests' later lines named in `missing`.

### Until solved (`--until-solved`, `budget.json` `until_solved`)

A run started `--until-solved` or `--stop operator` (or whose goal's metadata block says `until_solved: true` or `stop: operator`) has no wall clock (`wall_clock_minutes: 0`, and its VMs no maximum duration) and every cap advisory: `overCap`, `budgetPressure`, `agentPressure`, `modelPressure` and the model gateway read nothing as over, so spend is recorded and shown and nothing is stopped for it. `done` is refused until every question in scope has a disposition under the bar, as for any run: established; partial; a bounded negative or not determinable, each resting on a coverage record another seat reviewed; a premise shown not to hold; out of scope; accepted by the operator; or withdrawn (the answers check names each section's in `dispositions`, and the finish gate carries it on each question as `disposition`); with no material lead open, no lead's job uninterpreted, every answer with its critic's act and no defect, a defect a limitation only names included (the gate's `holding`). A best candidate, an answer resting on a limitation alone, a negative whose coverage no longer stands and a question behind a quick negative nobody attested have none. The policy adds no stricter answer requirement: a reviewed `not_determinable` ends the run examination-limited, but on a question the goal or the operator requires to be established (Questions, above), which takes only an answer that answers it, the operator's acceptance or its withdrawal, under this policy as under the others. A finish line that could not be run and an abandon (a vote or not; `markDone` refuses it too) are refusals, and the refusal names each question with no disposition, what blocks it, and the way to one (the routes, the coverage record, another seat's review, `not_determinable`). Otherwise only `swarm.sh stop` ends it. When nothing has moved for `stall_minutes` and a job runs under a lead, the idle watchdog first posts a nudge to that lead's holder (`REGROUP NUDGE`, with what the job is doing), and asks everyone a window later, job or not (a running job never holds it off for ever); otherwise it posts a regroup to everyone when nothing has moved for `stall_minutes` (15; no new standing entry, no lead closed, no job committed): the questions not answered, the leads open and blocked, what waits on the operator and the evidence no standing entry cites, and again with backoff (twice the wait each time, at most four hours) while nothing moves (`regroup` on the trace, `traces/regroup.json`). It keeps nudging an idle agent past its three nudges, with backoff, and prompts one whose turn ended in a provider error again with backoff up to half an hour; each new operator request runs the `--notify` command.

### Budget (`budget`, `budget.json`)

```json
{ "cap_usd": 1, "spent_usd": 0.061282, "tokens": 243160, "calls": 34,
  "wall_clock_minutes": 8, "started_at": "2026-09-16T09:12:00Z",
  "source": "pi.sessionManager.getEntries", "hard_kill": false, "cap_steer_sent": false,
  "metered": true,
  "agents": { "s1a2b00": { "spent_usd": 0.03, "tokens": 120000, "calls": 17,
                           "input": 0, "output": 0, "cache_read": 0, "cache_write": 0 } } }
```

On every `turn_end` and on `session_shutdown` the extension reads `ctx.sessionManager.getEntries()` and sums `Usage` the way Pi's footer and `get_session_stats` do: assistant messages (each counted as a `call`), tool results, compaction and branch summaries. `tokens = input + output + cacheRead + cacheWrite`, `spent_usd = Σ usage.cost.total`. The fold into `agents.<id>` never makes a seat's row smaller: its counters are the seat's whole run, and swarm totals are the sum of rows, all under the table lock. Pi reports a session's own totals, so the fold keys them on `ctx.sessionManager.getSessionId()`: `session_id` is the live session, `sessions` holds each session's last report by id and the row is their sum, and `earlier_sessions` is what the sessions other than the live one spent. A restart adds a session; `/new` then `/resume` back replaces the resumed session's entry. When Pi gives no id, a counter going down marks a new session and the row so far moves into `earlier_sessions`. `/fork` counts the copied prefix in both sessions, which errs high. `compactions`, `compaction_tokens`, `compaction_usd` and `handoffs` are carried forward the same way. A report of all zeros (a session read that failed) leaves the counters as they were. In a microVM run the hub folds a seat's report and takes only the counters and context fields (no `session_id`), and refuses a report smaller than the row it replaces (`usage went backwards`), so a Pi session that restarts inside a VM is not folded until its counters pass the old ones.

`budget.json` is replaced whole (a temp file beside it, then `rename`), so a reader never sees half a record; under Landlock alone, where a pane's rights on it are a rule on its inode, every process of the run writes it in place instead. A missing `budget.json` starts a new one. One that is there and does not parse is read once more (an editor caught mid-save); still unparseable, the fold is refused and the file left alone, never rebuilt from defaults, and the pane logs `budget_unreadable` and posts a `veto` to the board, once per process.

With self-compaction on (the default) the slice also carries `context_ceiling` (the effective ceiling the three lines are fractions of, from `extensions/context-ceiling.ts`), `context_level` (`idle`, `notice`, `warning` or `forced` against it), `context_locked` (true while every tool but `self_compact`, `budget` and `done` is refused), `compactions`, `compaction_tokens` and `compaction_usd` (every compaction Pi recorded in the session, hand-offs and its own fallbacks alike, and what their summary calls cost) and `handoffs` (the cycles completed through `self_compact`). The `budget` tool returns the same numbers to the agent under `context`, with the three thresholds and the tokens left before the compact line.

`metered` says whether that sum means anything. The kickoff sets it `false` when no model on the team bills — a server on this machine or this network, or a `models.json` provider with no `cost` block — because Pi then computes `cost.total` as an exact zero and a session cannot tell a free run from an unmeasured one. Such a team is started with `--cap-tokens N`, recorded as `cap_tokens`, and `over_budget` is `tokens >= cap_tokens` rather than `spent_usd >= cap_usd`; a metered team may carry `cap_tokens` too, as a second brake. `token_alerts` (the operator's `--token-alert` marks, ascending) are told once each as `tokens` crosses them, and brake nothing. The `budget` tool returns `metered` and `remaining_tokens` next to the dollar fields, and the steer on a token cap is `TOKEN_CAP_STEER`. Absent, `metered` means `true`, which is what every run before local models was.

Both caps are enforced the same way, and the clock is swarm-wide
(`stop_steer_at` / `stop_reason` in `budget.json`, claimed by whichever agent
notices first):

1. **Steer.** The agent over the line gets
   `pi.sendUserMessage(…, {deliverAs: "steer"})` telling it to post a
   checkpoint (`cap-pause`) or to call `done(reason=cannot_complete)`
   (`cap-stop`), and `system` announces it on the board once
   for the whole swarm. With `--hard-kill` that session also gets
   `ctx.shutdown()`.
2. **Grace.** Two minutes, measured from that one shared instant, so a restart
   or a slow agent does not restart the countdown.
3. **Harness stop, or the pause.** Still over? Under `cap-stop` the harness
   writes `done/SWARM_DONE` itself with `reason: cap` or `reason: wall_clock`
   (outcome `stopped`), re-checking under the lock so a raised cap cannot be
   overridden by a stale reading. Under `cap-pause` (the default) it writes
   `paused` `{at, reason, detail}` into `budget.json` instead (`run_paused` on
   the trace, a `stop` post, the notify command's `paused`): the extension's
   `context` hook holds every model call while it stands (`pause_hold`, the
   turn aborted without shutting the session), the model gateway refuses the
   call (`run_paused`), the hub prompts no seat but with a stop steer, and the
   watchdog nudges nobody. A kill switch that lives only in the prompt is not
   one.

The stop policy is `stop_policy` in `budget.json` (`cap-pause`, `cap-stop` or
`operator`; a budget without it reads as `cap-stop`, or `operator` when it says
`until_solved`). The steer's words follow it (`capSteerText`): under
`cap-pause` a seat is asked to post a checkpoint, under `cap-stop` to call
done. An extension (`swarm.sh extend`, or `cap`) that leaves room lifts the
pause: `paused` moves to `pauses` with `resumed_at` and `resumed_by`, and the
watchdog prompts each seat once (`resume_wake`; a seat not reached is tried
again on the next pass, and only a delivery that went through counts). The
operator is told of a pause once, whichever process wrote it: the watchdog and
the hub claim an unnotified pause with a mark under `traces/pause-notices/`
(`claimPauseNotice`). An extension reads the run's end (the sentinel,
`done/STOPPED`) under the table lock every stop writes it under. The watchdog
runs whatever `--idle-nudge-sec` says: at 0 it prompts nobody for being idle
and still holds all of this. The wall clock counts only
the time the run went: `wall_used_ms` holds what earlier stretches used and
`wall_base_at` when the current one began, so a pause and the time a stopped
run stood do not count. `resumes` lists each `swarm.sh resume` (`{at, by,
from}`).

Two pauses are not a cap's, and hold a run under every stop policy with the
same brakes. `provider_limit`: the watchdog (`scripts/provider-limit.ts`)
pauses the run when every live seat's last own row since the last lift is an
`agent_error` and every one of those seats is limited: its errors state a
wait of 30 minutes or more still ahead ("try again in ~N min", "in N hours",
"retry after N seconds", a Retry-After number, the first time with its zone
that is ahead; none past 30 days), or it was prompted again after its first
error (`idle_nudge`, `resume_wake`, `hub_prompt`; a prompt's row may land up
to 5 s after the refusal) and refused again. The watchdog retries a seat
whose last turn is an `agent_error` under every policy, with backoff: until
solved without end, under a cap policy three times per run of errors. A
seat's own rows the harness writes (`SEAT_HARNESS_ROWS`: a prompt's echo, a
lost hub link, an extension's error, a stop) are not turns, and a seat the
last lift's wake did not reach, with nothing of its own since, is left out.
The pause keeps `{at, reason: "provider_limit", detail, by: "harness",
models, until?, since?}`: `detail` the distinct error texts, whole, one a
line; `until` the longest end named when every limited seat is on one
provider (the model's part before the slash), else the earliest when each
was told one, else none; `since` the start of the spell when this pause
follows the harness's own try with no seat having worked since (the try is
then not charged to the wall clock: `wall_base_at` moves to the pause). The
rule is read again under the table lock (`pauseRun`'s `recheck`). The
harness tries again at `until` plus a minute, or 30 minutes after the pause
when no end is known (`liftProviderLimit`, `resumed_by: "harness"`; never on
a run with `done/STOPPED`), and the watchdog wakes each seat; a run whose
seats are all refused again is paused again. The operator is told once per
spell (`pauseNoticeKey`), with `reason`, `until`, `retry_at` and the advice,
and the board once, in one line. `operator`: `swarm.sh pause <run> [--why
TEXT]` writes `{at, reason: "operator", detail, by: "operator"}`; `swarm.sh
unpause <run>` (`unpauseRun`; the console's Unpause) lifts a pause whose
cause is gone: the provider's limit and the operator's hold always, a cap's
only when the caps leave room (refused otherwise). An extension does not
lift a pause that is not a cap's. The wake's words (`pauseLiftedText`) say
who lifted it and why; a pause `swarm.sh resume` folded into `pauses`
(`resumed_by: "<by> (resume)"`) wakes nobody.

A run's outcome (`runOutcome`) is read from its files: `done/STOPPED`
(`{outcome: "stopped", by, at, why}`, written by `swarm.sh stop` on a run with
no sentinel) is `stopped`; a sentinel says its own `outcome:`, and one the
harness wrote at a cap or the wall clock is `stopped`; a run whose seats all
died (`done/ALL_AGENTS_DEAD`, no sentinel) has none, paused or not; a
`paused` budget is `paused`; otherwise the run has none yet. `stopped` is never `completed`.

When nothing yields (no new finding, question disposition, acceptance or
coverage record since the later of the stretch's start and the last one)
for `SWARM_YIELD_MINUTES` (30) minutes, or across `SWARM_YIELD_JOBS`
committed jobs when that is set (unset or 0, the default, the count proposes
nothing: [ADR 0013](adr/0013-a-negative-is-bounded-and-a-cap-pauses.md), "The
stop proposal's window"), the watchdog writes an operator request of kind `decision` (`D-<n>`,
with the leads open and the questions unanswered) and `stop_proposed` on the
trace (`traces/stop-policy.yield.json` keeps the proposals). It stops nothing.

Caps are checked at `turn_end`, again after each tool result (throttled), and
on a timer — an agent that was steered and then sat in a long shell command
blocks the first two, so without the timer the deadline could pass with nobody
left to notice it. The `budget` tool returns `remaining_usd`, `remaining_minutes`,
`over_budget`, `over_time`, `this_agent`.

### Resume (`swarm.sh resume`, `done/history/`, the anchor's `resumes`)

A run that ended goes on in the same sandbox, on the same chains
(`scripts/resume.ts`, ADR 0013). What marked its end (`done/SWARM_DONE`,
`done/STOPPED`, `done/ALL_AGENTS_DEAD`, `done/agents/`, `done/abandon/`) is
moved whole to `done/history/<k>/`; the first segment's VM records to
`vm/earlier-<k>/` and its kept disks to `earlier-<k>/` in the snapshots
directory. Each seat's last hand-off note (`custom_message`
`self-compact-handoff`) or compaction summary in its Pi sessions, whichever is
later, is written whole to `inbox/<seat>/resume.md`. The custody anchor beside
the run gets a `resumes` entry `{at, by, from, segment, heads}` with each
chain's length and head (ledger, attestations, disputes, leads, questions,
the network's grants and fetches, the operator requests, trace). Nothing
recorded is rewritten: the ledger, the registers, the network records, the
trace and the store journal are appended to, and the case policy (`network/policy.json` and its section
of `SWARM.md`) stays as the first segment was given it, as the contract does.
Custody's next verdict is a new one (the earlier kept beside it);
`custody-verify` holds every earlier verdict the anchor names to the run as a
prefix (`sealPrefix`: the line each chain's seal names is still at its place
with its hash) and says whether a resume came after it. A release binds its
chains as they were: `releases --verify` verifies the ledger, attestations
and disputes it binds with their own verifiers over the lines it binds (every
hash recomputed from what the line holds, never read from its hash field),
and accepts them as a prefix of the run's only when a resume that stands was
recorded after the release: one with its segment and the chains' heads as it
found them, each the head the verified chain holds at that length, at or
past what the release binds. A bare time relaxes nothing, and a changed line
is never a prefix. Through the custody verdict it binds, it holds the lead
and question registers and the network's grants and fetches to the heads and
counts that verdict sealed: appended to since is a prefix; cut, deleted or
rewritten fails. The resume is anchored before anything of the run moves,
and one that cannot be anchored is refused with nothing changed. The report
bytes each release binds (`work/report.md` as it was sealed) are kept at
`release/bound/<sha256>`, read-only, before the continuation can write its
own report; an earlier release verifies against them ("kept at
release/bound/… when the run was resumed"). An earlier seal of the model
gateway's log is broken when the log is gone. Evidence on an image the stop
detached is attached again and held to the manifest (every file by name and
size) before anything moves; an image that does not hold it is refused. The
start options kept for the resume (`runs/resume/<id>.argv.json`: `{argv,
dropped_env, notify}`) never hold the notify command or its typed targets
(kept once, in `runs/notify/`, and given to the kickoff again from there) and
hold an `--env` value only where no pane can read it; elsewhere its name, and
the resume asks for the value again. Each question given to the resume is
checked first, as its admission would check it against the register as it
stands (`questions-cli.ts add --dry-run`, `checkAct`: who `--as` names, the
words, a question the register holds already); one it would refuse refuses
the resume before anything moves, naming the question and why, unless
`--skip-refused-questions` leaves it out (a `WARN` says so). The question is
admitted after the move, as before, and is checked again then. The dry run
refuses a broken chain as the admission does, and takes no lock, writes no
seed and reconciles nothing; it is offered on the register's acts only
(`direct`, `deliver` and `seed` refuse `--dry-run`).

### A microVM seat's socket (`<hub dir>/<agent>.sock`)

In a microVM run the protocol calls above travel from the VM to the hub over one Unix socket per seat, as JSON lines. Every connection a VM process opens starts with the seat's token, `{"t":"auth","token":"<SWARM_SEAT_TOKEN>"}` (`seatAuthLine()` in `extensions/protocol.ts`, used by the board client, the held trace connection and the nudge); the link's own `hello` carries the token instead. A good auth line gets no reply, so a client reads its answers as it would without one. Until a connection has shown its seat's token the hub serves nothing on it, not even state; a wrong or missing token gets `{"ok":false,"error":"this socket serves only its seat's VM: …"}`, the connection is closed, and the refusal is a `hub_call` line with `fn:"seat_auth"`. The token is compared in constant time. A run the hub was started without tokens for (an input from before them) asks for none.

No line on a seat's link, in either direction, is larger than one part: 32 KiB of payload (`TRANSFER_PART_BYTES`, `SWARM_TRANSFER_PART_BYTES`), 44,716 bytes on the wire (`WIRE_LINE_MAX`). msb's vsock path from guest to host stops moving on a single write of about 256 KiB, and a connection stalled that way stays open. A larger request is uploaded first: `{"t":"up", …}` parts, each acknowledged before the next, in order, then the call itself with `argsUpload: {id, size, sha256}` in place of `args`; the hub reassembles the args, checks their size and sha256, and runs the call as if they had come inline, with the same request-id dedupe, rate limits and refusals. A larger answer comes back as `{"ok":true,"download":{id,size,sha256}}`, and the client fetches it in `{"t":"down", …}` parts. Trace lines and prompts on the link travel the same way. Per seat the hub holds at most 96 MiB and 4 uploads at once; an upload or a download is dropped when idle for 5 minutes or when its connection closes, and each refusal is a `hub_call` line naming it. A line over the limit is never written: `WireLineTooLarge` on the client, a refusal with `fn:"reply"` on the hub. The client replaces a connection when a call times out or its write queue has not moved in 20 s; calls that change the board resend with their request id, which the hub answers once.

### Event log (`traces/events.jsonl`)

One JSON object per line, same schema for every writer (extension, `reap.sh`, web operator):

```json
{"ts":"2026-09-16T08:24:39.917Z","agent":"s7e5002","tool":"claim_file",
 "args":{"path":"work/hello.txt"},
 "result":{"ok":false,"conflict":true,"path":"work/hello.txt","owner":"s7e5000","expires_at":"2026-09-16T08:27:39.280Z"}}
```

A line written by the trace collector also carries `prev`: the sha256 of the
line before it. `verifyEventChain` walks that chain and the report's custody
section prints the result — intact, not chained (a run without a collector),
or broken at a line number. A tool's result carries what the model received,
whole, as `output` with `output_chars` beside `ok`, because `ok: true` is
not correctness. When that was a slice of something on disk (Pi's `read`,
`grep`, `find`, `ls` and `bash` past their own bounds) the row says so under
`view` (`truncated`, `by`, `total_lines`, `shown_lines`, `total_bytes`,
`shown_bytes`); when the whole output exists only because the harness kept it,
`full_output` names it: `{path, bytes, lines, sha256}` under `tool-output/`
(Pi's `bash` spill moved in from the host's temp directory, a forged tool's
stdout past 64 KB, `full_stderr` for its stderr, `full_text` for a page's
text past what `browser_check` delivers). Nothing a tool produced is dropped
anywhere; the model's own trailer names the same file.

`args` is `summarizeArgs`: every argument whole, whatever its size, numbers and booleans as they are. It once kept 20,000 characters of a string and, before that, 80 with objects dropped in silence — a `bash` line lost the half that said which file it read, and a refused `make_tool` recorded an error about params the record did not hold. An archived row from those days carries the true length under `_truncated`; the console says so on that row, and nothing written today has the key. The collector accepts a line of up to 64 MB and refuses the rest to the spill file (`work/.trace-spill.jsonl`), where it is still a record. Tools that appear:

### File history (`file_history`, `file_restore`)

Every legal `edit`/`write` copies the file into
`history/<sha256(path)>/<rev>.bin` and appends
`{rev, ts, agent, path, bytes, sha256}` to `index.json`. Revisions are
**content-addressed and deduped against the previous one**: a write that leaves
the bytes unchanged records nothing, so the pre-write and post-write snapshots
around an edit collapse whenever the file was already recorded. The first edit
of a file the harness has never seen still records both the old and the new
bytes — which is what you want, since the old bytes are the only copy. Agents quote the short hash when they sign off on an artifact
("canonical frozen at 2f7b1230, both sign-offs on that hash").

`file_history(path)` lists revisions. `file_diff(path, from, to)` takes
revision numbers, short or full hashes, or `disk`, and defaults to "the newest
recorded revision against what is on disk now" — which is how an agent finds
out whether someone changed a file under it. `file_restore(path, rev)` requires
a live claim held by the caller, records the current bytes first, restores, and
records the restore itself so history stays a truthful log of what the file
looked like and who put it that way. The web app's **Restore** does the same as
agent `operator`. Storage is local copies, not git.

### Registry (`runs/registry.json`)

Written by `swarm.sh`, read by `list`/`status`/`stop`/`reap` and the web app: `{id, label, workspace_id, workspace_ids[], sandbox, n, model, cap_usd, wall_clock_minutes, hard_kill, goal, agents[], started_at, state: prepared|running|stopped, tab_count, split_failures, extra_workspaces, probe_agent?}`. There is no `stopped_at`; the UI derives `done` from the sentinel.
