---
id: registry/devices
title: Removable-device identity and mounts
when: A storage device is in the story and you must separate attachment from transfer.
needs: []
tools: [regkv, lnk_parse, jumplist, shellbags]
requires_host: []
---

Use when you identify a device and its mount association. Not for first and last connection dates (`registry/devices-dates`: read it only if the question turns on when).

    SYSTEM\ControlSet00n\Enum\USBSTOR   class, vendor, product, revision, instance ID per device
    ...\Enum\USB    the same devices by VID and PID, with ContainerID where present
    ...\Enum\SCSI   devices attached through UASP, which USBSTOR does not list
    SYSTEM\MountedDevices   drive letter and volume GUID to device or disk
    SOFTWARE\Microsoft\Windows Portable Devices\Devices   friendly name per portable device
    NTUSER.DAT ...\Explorer\MountPoints2   volumes this profile's Explorer saw

Read hives by `registry/overview`; the clock by `registry/clock`.

- Identity: keep the whole instance identifier, hardware IDs and `ContainerID`, and the volume GUID and letter separately. Decide whether the serial part was supplied by the device or generated by Windows from the complete identifier and the bus, and say which; one character does not decide it. A supplied serial can be missing, duplicated across devices or altered; a generated one can differ between ports. Call two sightings one device only when serial, vendor and product, container identity and (if acquired) the volume's own identifiers agree; say what agreed and what was not available.
- Mounts: `MountedDevices` holds the latest assignment of a letter or volume GUID, so the next device to take a letter overwrites the earlier entry; it is not a mapping history. Its binary values arrive as hex (`registry/readers`): commonly a removable device's entry is the instance text in UTF-16LE and a fixed disk's a partition identifier, not text. `MountPoints2` keys are named by volume GUID (network shares by path): they show this profile's Explorer saw the volume, not that the person attached it.
- Not every portable device presents a file system, and not every USB storage device follows the same path: when an expected device is missing from `USBSTOR`, check `SCSI`, the portable-devices key and `setupapi.dev.log` before recording it absent.
- A link, jump-list entry or ShellBag naming the device's letter or volume serial (`lnk_parse`, `jumplist`, `shellbags`; `artifacts/shell`) shows a path on that volume was opened or browsed, not that content was copied. Moving data needs file-level evidence: the device's own file system if acquired, host records (`filesystem/journals`) naming the files inside the attachment window, or an application's record. Say which you looked for and did not find.

Sensitive output: `regkv` withholds by name and place only (`registry/readers`); serials and friendly names are identifiers.
Shows: that a device identity and a volume were recorded. Does not show: what was copied, by whom, or that the device was attached only when the dates say; a missing record is absent only from the hives, builds and range you searched. Record: instance ID, container ID, volume GUID, letter, key paths.
